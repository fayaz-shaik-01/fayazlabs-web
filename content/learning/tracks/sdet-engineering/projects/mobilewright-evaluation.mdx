# Project: MobileWright Evaluation

> **Module:** 12 — Projects
> **Prerequisites:** Project Roadmap, Appium Java Framework
> **Estimated Time:** 8-10 hours
> **Difficulty:** Intermediate
> **Purpose:** Learn how to evaluate new testing tools systematically — a critical SDET skill

---

## Why Evaluate Tools?

SDETs are frequently asked to evaluate new tools: "Should we switch from Appium to MobileWright?" or "Is Playwright better than Selenium for our use case?" Answering this requires a structured methodology, not gut feeling.

This project teaches you to:
1. Define evaluation criteria before testing any tool
2. Run identical scenarios with both tools for fair comparison
3. Score objectively using a rubric
4. Present findings with data, not opinions
5. Make a recommendation that considers trade-offs

The skill transfers to any tool evaluation — it's not just about MobileWright vs Appium.

---

## What Is MobileWright?

MobileWright is a newer mobile testing tool that aims to simplify mobile test automation compared to Appium. Before evaluating it, research the current state:

**Research checklist:**
- [ ] Visit the official MobileWright documentation
- [ ] Check GitHub stars, commit frequency, and issue resolution rate
- [ ] Read comparison articles by practitioners (not vendor marketing)
- [ ] Check if it supports your target platforms (Android, iOS)
- [ ] Verify language support (Java, TypeScript, etc.)
- [ ] Look for community size (Stack Overflow questions, Discord/Slack channels)

> **Note:** MobileWright is an emerging tool. If documentation or features have changed since this was written, adapt the evaluation criteria accordingly. The methodology is the important part, not the specific tool.

## Evaluation Criteria

### Criteria Definition Table

Each criterion is scored 1-5 with clear definitions to reduce subjectivity.

| # | Criterion | Weight | What It Measures |
| --- | --- | --- | --- |
| 1 | Setup Complexity | 15% | Time from zero to first passing test on a clean machine |
| 2 | Locator Strategies | 15% | Richness and reliability of element identification |
| 3 | Gesture Support | 10% | Swipe, scroll, pinch, long-press capabilities |
| 4 | Test Reliability | 20% | Consistency of results across 10 identical runs |
| 5 | Execution Speed | 10% | Time to complete the standard test suite |
| 6 | Debugging Experience | 10% | Quality of error messages, logs, and diagnostic tools |
| 7 | Maintenance Burden | 10% | Effort to keep tests working after app updates |
| 8 | Documentation & Community | 10% | Quality of docs, community support, and learning resources |

### Scoring Rubric

| Score | Meaning | Description |
| --- | --- | --- |
| 1 | Poor | Barely functional, significant workarounds required |
| 2 | Below Average | Works but with notable friction or gaps |
| 3 | Adequate | Meets basic needs, some rough edges |
| 4 | Good | Works well with minor limitations |
| 5 | Excellent | Best-in-class, smooth experience |

## Comparison Methodology

### Standard Test Scenarios

Run these exact scenarios with both Appium and MobileWright. Use the StayNest mobile app for both.

| Scenario | Actions | What It Tests |
| --- | --- | --- |
| S1: App Launch | Launch app, verify home screen loads | Setup, basic interaction |
| S2: Login | Enter email, enter password, tap login, verify home | Text input, button tap, navigation |
| S3: Search | Enter city, select dates, tap search, verify results | Complex input, date picker interaction |
| S4: Scroll Results | Search → scroll through 10+ results | Gesture: scroll/swipe |
| S5: Hotel Detail | Search → tap hotel card → verify detail page | Navigation, element identification |
| S6: Full Booking | Login → search → book → confirm | End-to-end flow, multiple screens |
| S7: Error Handling | Login with wrong password, verify error message | Error state verification |
| S8: Back Navigation | Navigate forward 3 screens, back 3 screens | Navigation stack handling |

### Measurement Protocol

For each scenario with each tool, record:

| Metric | How to Measure |
| --- | --- |
| Lines of code | Count non-blank, non-comment lines for the test + page/screen objects |
| Setup time | Time from `git clone` to first passing test (minutes) |
| Execution time | Average of 3 runs (seconds) |
| Pass rate | Pass count out of 10 identical runs |
| Error clarity | On intentional failure, rate error message usefulness (1-5) |
| Locator complexity | Number of platform-specific workarounds needed |

| Risk | Tool | Mitigation |
| --- | --- | --- |

## What This Project Demonstrates in Interviews

When asked "How do you evaluate a new tool?", reference this project:

1. **Define criteria with weights before testing** — prevents bias toward the "shiny new thing"
2. **Run identical scenarios** — ensures fair comparison, not cherry-picked demos
3. **Measure quantitatively** — pass rates, execution times, lines of code — not just feelings
4. **Consider team context** — the best tool objectively might not be the best tool for your team
5. **Document trade-offs** — every tool has strengths and weaknesses; present both honestly
