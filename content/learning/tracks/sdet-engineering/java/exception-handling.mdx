# Exception Handling in Java

> **Module:** 01-Programming Foundations / Java  
> **Prerequisites:** Syntax And Control Flow, Oop Fundamentals, Collections And Generics  
> **Mastery Target:** L3 (Independent)

---

## Quick Overview (2-minute read)

**What:** Exceptions are Java's mechanism for signaling and handling abnormal conditions that disrupt normal program flow.  
**Why:** In test automation, proper exception handling is the difference between a test that fails with a clear, actionable message and one that silently does the wrong thing or crashes with a cryptic stack trace.  
**Where:** Everywhere — element interactions, API calls, file I/O, database connections, test data setup, framework utilities.

<MentalModel>

Think of exceptions as **emergency signals on a production line**. When a machine detects a problem (a missing part, a jammed gear), it doesn't just stop silently — it triggers an alarm with a specific code so the operator knows *what* went wrong and *where*. Some alarms require immediate human intervention (checked exceptions), while others indicate fundamental design flaws that shouldn't happen in normal operation (unchecked exceptions). The worst thing you can do is disconnect the alarm and let defective products pass through — that's what happens when you swallow exceptions silently.

</MentalModel>


<KeyTakeaways>

1. **Checked exceptions** are compile-time contracts — they force callers to acknowledge things that can reasonably go wrong (file not found, network timeout).
2. **Unchecked exceptions** signal programming errors or unrecoverable conditions — catching them should be deliberate, not routine.
3. **try-with-resources** is non-negotiable for anything that implements `AutoCloseable` — WebDriver sessions, streams, database connections.
4. **Never swallow exceptions silently** — an empty catch block is a bug waiting to happen. Log, rethrow, or handle meaningfully.
5. **Custom exceptions with context** (test case ID, locator, environment) make debugging 10x faster in CI where you can't reproduce locally.

</KeyTakeaways>

## First-Principles Explanation

### The Throwable Hierarchy


```
java.lang.Throwable
├── java.lang.Error                          // JVM-level, don't catch these
│   ├── OutOfMemoryError
│   ├── StackOverflowError
│   └── ...
└── java.lang.Exception                      // Application-level
    ├── IOException                          // Checked
    ├── SQLException                         // Checked
    ├── InterruptedException                 // Checked
    └── java.lang.RuntimeException           // Unchecked
        ├── NullPointerException
        ├── IllegalArgumentException
        ├── IndexOutOfBoundsException
        ├── ClassCastException
        └── org.openqa.selenium.*            // Selenium exceptions extend RuntimeException
            ├── NoSuchElementException
            ├── StaleElementReferenceException
            ├── TimeoutException
            └── WebDriverException
```

**Key insight:** All Selenium exceptions are unchecked (extend `RuntimeException`). This is a deliberate design decision — you shouldn't be forced to wrap every `findElement()` call in try-catch. But it also means failures can propagate silently if you're not paying attention.

### Checked vs Unchecked Exceptions

| Aspect | Checked | Unchecked |
|--------|---------|-----------|
| **Superclass** | `Exception` (not `RuntimeException`) | `RuntimeException` or `Error` |
| **Compile-time enforcement** | Must be caught or declared in `throws` | No requirement |
| **When to use** | Recoverable conditions the caller should handle | Programming errors or unrecoverable states |
| **Automation examples** | `IOException` (reading test data files), `SQLException` (DB validation) | `NoSuchElementException`, `NullPointerException` |
| **Common debate** | Some argue they add noise without value | Some argue they hide important failure modes |

### try-catch-finally: Execution Flow


```java
public void demonstrateFlow() {
    System.out.println("Before try");
    try {
        System.out.println("Inside try — before risky operation");
        int result = 10 / 0;  // ArithmeticException
        System.out.println("Inside try — after risky operation");  // SKIPPED
    } catch (ArithmeticException e) {
        System.out.println("Inside catch — handling: " + e.getMessage());
    } finally {
        System.out.println("Inside finally — ALWAYS runs");
    }
    System.out.println("After try-catch-finally — execution continues");
}

// Output:
// Before try
// Inside try — before risky operation
// Inside catch — handling: / by zero
// Inside finally — ALWAYS runs
// After try-catch-finally — execution continues
```

**Multiple catch blocks — order matters (specific before general):**


```java
try {
    WebElement element = driver.findElement(By.id("submit"));
    element.click();
} catch (NoSuchElementException e) {
    // Most specific — element doesn't exist
    log.error("Element not found: {}", e.getMessage());
} catch (StaleElementReferenceException e) {
    // Specific — element existed but DOM changed
    log.warn("Stale element, DOM may have refreshed: {}", e.getMessage());
} catch (WebDriverException e) {
    // General Selenium — catches anything else (ElementClickInterceptedException, etc.)
    log.error("WebDriver error: {}", e.getMessage());
} catch (Exception e) {
    // Most general — last resort, catches non-Selenium errors too
    log.error("Unexpected error: {}", e.getMessage());
}
// Compile error if you put Exception before WebDriverException — unreachable catch block
```

### try-with-resources and AutoCloseable

Resources that implement `AutoCloseable` are automatically closed when the try block exits — even if an exception occurs.


```java
// BAD: Manual cleanup — fragile, error-prone
WebDriver driver = null;
try {
    driver = new ChromeDriver();
    driver.get("https://example.com");
    // ... test logic
} catch (Exception e) {
    log.error("Test failed", e);
} finally {
    if (driver != null) {
        driver.quit();  // What if quit() itself throws? Original exception is lost.
    }
}

// GOOD: try-with-resources (requires AutoCloseable wrapper for WebDriver)
// If you create a wrapper:
public class ManagedDriver implements AutoCloseable {
    private final WebDriver driver;

    public ManagedDriver(WebDriver driver) {
        this.driver = driver;
    }

    public WebDriver getDriver() { return driver; }

    @Override
    public void close() {
        if (driver != null) {
            driver.quit();
        }
    }
}

// Usage:
try (ManagedDriver managed = new ManagedDriver(new ChromeDriver())) {
    WebDriver driver = managed.getDriver();
    driver.get("https://example.com");
    // ... test logic
}  // driver.quit() called automatically, even if an exception is thrown
```

**Where try-with-resources matters most in automation:**
- File streams (reading test data CSV/JSON)
- Database connections (JDBC for DB validation)
- HTTP connections (RestAssured response streams)
- Custom resource wrappers (WebDriver sessions, temp file cleanup)

### throw vs throws


```java
// throws — DECLARES that a method might throw (part of the method signature)
public String readTestData(String filePath) throws IOException {
    return Files.readString(Path.of(filePath));
}

// throw — CREATES and LAUNCHES an exception object
public void validateTestData(Map<String, String> data) {
    if (data == null || data.isEmpty()) {
        throw new IllegalArgumentException("Test data cannot be null or empty");
    }
    if (!data.containsKey("username")) {
        throw new TestDataException("Missing required field: username",
            "TC-001", "test-data.json", null);
    }
}
```

### Custom Exceptions

**When to create custom exceptions:**
- Framework-specific failures that need additional context (test case ID, environment, locator)
- Distinguishing between different categories of failure (test data issue vs. environment issue vs. application bug)
- Wrapping low-level exceptions with business context

**Extend `RuntimeException` (unchecked) vs `Exception` (checked):**
- In test frameworks, unchecked is usually preferred — you don't want every test method to declare `throws FrameworkException`
- If the caller *must* handle it (e.g., a mandatory cleanup step), consider checked


```java
// Unchecked — framework-level exception with rich context
public class FrameworkException extends RuntimeException {

    private final String component;
    private final Map<String, String> context;

    public FrameworkException(String message, String component, Throwable cause) {
        super(message, cause);
        this.component = component;
        this.context = new HashMap<>();
    }

    public FrameworkException addContext(String key, String value) {
        this.context.put(key, value);
        return this;  // fluent API for chaining
    }

    @Override
    public String getMessage() {
        StringBuilder sb = new StringBuilder();
        sb.append(String.format("[%s] %s", component, super.getMessage()));
        if (!context.isEmpty()) {
            sb.append(" | Context: ").append(context);
        }
        return sb.toString();
    }
}
```

### Exception Chaining

Wrapping low-level exceptions with higher-level context preserves the original stack trace while adding meaning:


```java
public Map<String, String> loadTestData(String testCaseId) {
    try {
        String json = Files.readString(Path.of("test-data/" + testCaseId + ".json"));
        return objectMapper.readValue(json, new TypeReference<>() {});
    } catch (IOException e) {
        // Wrap with context — the original IOException is preserved as the cause
        throw new TestDataException(
            "Failed to load test data",
            testCaseId,
            "test-data/" + testCaseId + ".json",
            e  // original exception chained here
        );
    }
}
// Stack trace shows BOTH: TestDataException AND the original IOException with file details
```

### Common Exceptions in Test Automation

| Exception | When It Happens | Common Fix |
|-----------|----------------|------------|
| `NullPointerException` | Accessing a method/field on a null reference | Null checks, `Optional`, proper initialization |
| `NoSuchElementException` | `findElement()` can't locate the element | Verify locator, add wait, check page state |
| `TimeoutException` | Explicit wait condition not met within timeout | Increase timeout, check if condition is correct, verify page loads |
| `StaleElementReferenceException` | DOM changed after element was found | Re-find the element, use dynamic locators |
| `ElementClickInterceptedException` | Another element is covering the target | Scroll into view, wait for overlay to disappear |
| `IOException` | File not found, network error, stream closed | Verify paths, add retry for network, use try-with-resources |
| `JsonProcessingException` | JSON parsing/serialization fails | Validate JSON structure, check POJO mappings |
| `SQLException` | DB query fails, connection issue | Verify query, check connection pool, handle timeouts |

### Best Practices

1. **Catch specific exceptions** — never `catch (Exception e)` unless it's a top-level safety net.
2. **Never swallow exceptions silently** — `catch (Exception e) { }` is never acceptable.
3. **Log with context** — include the locator, test case ID, URL, or whatever helps diagnose the failure.
4. **Don't use exceptions for flow control** — checking if an element exists by catching `NoSuchElementException` is expensive and unclear. Use `findElements().isEmpty()` instead.
5. **Fail fast** — if test preconditions aren't met, throw immediately. Don't let a test proceed in a broken state.
6. **Prefer `Optional` for expected absence** — when "not found" is a valid outcome, return `Optional.empty()` instead of throwing.
7. **Clean up resources in `finally` or try-with-resources** — never rely on garbage collection for cleanup.
8. **Include the original exception as the cause** — `throw new CustomException("msg", originalException)`.

## Practical Implementation

### Example 1: Safe Element Interaction with Exception Handling


```java
import org.openqa.selenium.*;
import org.openqa.selenium.support.ui.*;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.time.Duration;
import java.util.Optional;

public class SafeElementActions {
    private static final Logger log = LoggerFactory.getLogger(SafeElementActions.class);
    private static final int MAX_STALE_RETRIES = 3;

    private final WebDriver driver;
    private final WebDriverWait wait;

    public SafeElementActions(WebDriver driver) {
        this.driver = driver;
        this.wait = new WebDriverWait(driver, Duration.ofSeconds(10));
    }

    /**
     * Gets text from an element safely, handling common failure modes.
     * Returns Optional.empty() if the element is not visible within the timeout.
     */
    public Optional<String> getTextSafely(By locator) {
        for (int attempt = 1; attempt <= MAX_STALE_RETRIES; attempt++) {
            try {
                WebElement element = wait.until(
                    ExpectedConditions.visibilityOfElementLocated(locator)
                );
                return Optional.of(element.getText());

            } catch (TimeoutException e) {
                log.warn("Element not visible within timeout: {} | URL: {}",
                    locator, driver.getCurrentUrl());
                return Optional.empty();

            } catch (StaleElementReferenceException e) {
                log.warn("Stale element on attempt {}/{}: {} | Retrying...",
                    attempt, MAX_STALE_RETRIES, locator);
                if (attempt == MAX_STALE_RETRIES) {
                    log.error("Element still stale after {} retries: {}", MAX_STALE_RETRIES, locator);
                    throw new FrameworkException("Element stale after max retries", "SafeElementActions", e)
                        .addContext("locator", locator.toString())
                        .addContext("url", driver.getCurrentUrl())
                        .addContext("retries", String.valueOf(MAX_STALE_RETRIES));
                }
            }
        }
        return Optional.empty();  // Unreachable, but compiler requires it
    }

    /**
     * Clicks an element with retry logic for intercepted clicks.
     * Throws FrameworkException with context if all retries fail.
     */
    public void clickSafely(By locator) {
        Exception lastException = null;
        for (int attempt = 1; attempt <= MAX_STALE_RETRIES; attempt++) {
            try {
                WebElement element = wait.until(
                    ExpectedConditions.elementToBeClickable(locator)
                );
                element.click();
                return;  // Success — exit immediately

            } catch (ElementClickInterceptedException e) {
                log.warn("Click intercepted on attempt {}/{}: {} | Scrolling into view...",
                    attempt, MAX_STALE_RETRIES, locator);
                lastException = e;
                scrollToElement(locator);

            } catch (StaleElementReferenceException e) {
                log.warn("Stale element on click attempt {}/{}: {}",
                    attempt, MAX_STALE_RETRIES, locator);
                lastException = e;
            }
        }
        throw new FrameworkException("Click failed after max retries", "SafeElementActions", lastException)
            .addContext("locator", locator.toString())
            .addContext("url", driver.getCurrentUrl());
    }

    private void scrollToElement(By locator) {
        try {
            WebElement element = driver.findElement(locator);
            ((JavascriptExecutor) driver).executeScript(
                "arguments[0].scrollIntoView({behavior: 'smooth', block: 'center'});", element
            );
        } catch (Exception e) {
            log.debug("Scroll attempt failed: {}", e.getMessage());
        }
    }
}
```

**What this does:** Provides reusable, safe element interactions that handle the three most common Selenium failure modes (timeout, stale element, intercepted click) with retry logic, structured logging, and rich exception context.

### Example 2: Custom Framework Exception with Context


```java
/**
 * Exception for test data loading/validation failures.
 * Carries test case ID and data source for quick CI diagnosis.
 */
public class TestDataException extends RuntimeException {

    private final String testCaseId;
    private final String dataSource;

    public TestDataException(String message, String testCaseId, String dataSource, Throwable cause) {
        super(formatMessage(message, testCaseId, dataSource), cause);
        this.testCaseId = testCaseId;
        this.dataSource = dataSource;
    }

    public TestDataException(String message, String testCaseId, String dataSource) {
        this(message, testCaseId, dataSource, null);
    }

    private static String formatMessage(String message, String testCaseId, String dataSource) {
        return String.format("[TestCase: %s | Source: %s] %s", testCaseId, dataSource, message);
    }

    public String getTestCaseId() { return testCaseId; }
    public String getDataSource() { return dataSource; }
}
```

**Usage in a test data loader:**


```java
public class TestDataLoader {
    private static final Logger log = LoggerFactory.getLogger(TestDataLoader.class);
    private final ObjectMapper objectMapper = new ObjectMapper();

    public <T> T loadTestData(String testCaseId, String fileName, Class<T> type) {
        Path dataPath = Path.of("src/test/resources/test-data", fileName);

        if (!Files.exists(dataPath)) {
            throw new TestDataException(
                "Test data file not found: " + dataPath.toAbsolutePath(),
                testCaseId, fileName
            );
        }

        try {
            String content = Files.readString(dataPath);
            T data = objectMapper.readValue(content, type);
            log.info("Loaded test data for {} from {}", testCaseId, fileName);
            return data;

        } catch (JsonProcessingException e) {
            throw new TestDataException(
                "Invalid JSON structure — check POJO mapping for " + type.getSimpleName(),
                testCaseId, fileName, e
            );
        } catch (IOException e) {
            throw new TestDataException(
                "Failed to read test data file",
                testCaseId, fileName, e
            );
        }
    }
}
```

### Example 3: Resource Cleanup with try-with-resources


```java
import java.sql.*;
import java.nio.file.*;
import java.io.*;
import org.testng.annotations.*;
import static org.testng.Assert.*;

public class OrderApiTest {

    /**
     * Verifies that creating an order via API correctly inserts into the database.
     * Demonstrates proper cleanup of DB connection and temp files.
     */
    @Test
    public void testCreateOrderWritesToDatabase() {
        String orderId = createOrderViaApi();  // API helper method

        // try-with-resources: connection AND statement both auto-closed
        String query = "SELECT status, total FROM orders WHERE order_id = ?";
        try (
            Connection conn = DriverManager.getConnection(DB_URL, DB_USER, DB_PASS);
            PreparedStatement stmt = conn.prepareStatement(query)
        ) {
            stmt.setString(1, orderId);
            try (ResultSet rs = stmt.executeQuery()) {
                assertTrue(rs.next(), "Order not found in database: " + orderId);
                assertEquals(rs.getString("status"), "PENDING");
                assertEquals(rs.getDouble("total"), 99.99, 0.01);
            }
        } catch (SQLException e) {
            throw new FrameworkException("DB validation failed for order", "OrderApiTest", e)
                .addContext("orderId", orderId)
                .addContext("query", query);
        }
    }

    /**
     * Demonstrates temp file cleanup — useful for screenshot comparison,
     * downloaded file verification, etc.
     */
    @Test
    public void testExportedReportContent() throws IOException {
        Path tempDir = Files.createTempDirectory("test-reports-");

        try {
            Path reportFile = downloadReport(tempDir);  // Downloads to tempDir

            // Read and verify content
            try (BufferedReader reader = Files.newBufferedReader(reportFile)) {
                String header = reader.readLine();
                assertEquals(header, "OrderID,Status,Total",
                    "Report header mismatch");

                long dataRows = reader.lines().count();
                assertTrue(dataRows > 0, "Report has no data rows");
            }
            // BufferedReader auto-closed here

        } finally {
            // Clean up temp directory and all contents
            Files.walk(tempDir)
                .sorted(java.util.Comparator.reverseOrder())
                .forEach(path -> {
                    try { Files.deleteIfExists(path); }
                    catch (IOException e) { log.warn("Cleanup failed: {}", path); }
                });
        }
    }
}
```

**What this does:** Shows three levels of resource management — JDBC connections with nested try-with-resources, file streams for verification, and temp directory cleanup in finally. Every resource is guaranteed to close regardless of test pass/fail.

## Failure and Debugging

### Scenario 1: The Swallowed Exception

**Deliberately Broken Example:**


```java
// BAD — this test always "passes" even when the element is missing
@Test
public void testProductPriceDisplayed() {
    driver.get(productPageUrl);
    try {
        WebElement price = driver.findElement(By.id("product-price"));
        assertEquals(price.getText(), "$29.99");
    } catch (Exception e) {
        // Swallowed! Test passes with no assertion executed.
    }
}
```

**Expected:** Test fails when the price element is missing or shows the wrong value.  
**Actual:** Test always passes. If the element doesn't exist, `NoSuchElementException` is caught and ignored. No assertion runs. CI shows green. The bug ships.

**Root Cause:** Empty catch block swallows the exception, bypassing the assertion entirely.

**Corrected Implementation:**


```java
@Test
public void testProductPriceDisplayed() {
    driver.get(productPageUrl);
    // No try-catch needed — let the exception propagate to the test framework
    WebElement price = new WebDriverWait(driver, Duration.ofSeconds(10))
        .until(ExpectedConditions.visibilityOfElementLocated(By.id("product-price")));
    assertEquals(price.getText(), "$29.99",
        "Product price mismatch on: " + driver.getCurrentUrl());
}
```

<BestPractice>

**Prevention:** Treat any empty catch block as a code review blocker. If you truly want to ignore an exception, add a comment explaining *why* — this forces you to think about whether it's actually safe.

</BestPractice>

### Scenario 2: Overly Broad Catch Masking Real Bugs

**Deliberately Broken Example:**


```java
// BAD — catches Exception when only NoSuchElementException is expected
public boolean isElementPresent(By locator) {
    try {
        driver.findElement(locator);
        return true;
    } catch (Exception e) {
        return false;  // Catches EVERYTHING: NullPointerException, ClassCastException, etc.
    }
}

// This hides a real bug:
// If driver is null → NullPointerException → caught → returns false
// Developer thinks "element not present" but the actual problem is null driver
```

**Expected:** `isElementPresent` returns false only when the element genuinely doesn't exist.  
**Actual:** Returns false for *any* error — null driver, invalid session, JavaScript error, etc.

**Corrected Implementation:**


```java
// GOOD — catch only the specific exception you expect
public boolean isElementPresent(By locator) {
    try {
        driver.findElement(locator);
        return true;
    } catch (NoSuchElementException e) {
        return false;  // Only this specific case means "not present"
    }
    // NullPointerException, WebDriverException, etc. propagate naturally
}

// BETTER — avoid exception-based flow control entirely
public boolean isElementPresent(By locator) {
    return !driver.findElements(locator).isEmpty();
}
```

### Scenario 3: Resource Leak from Exception in Finally

**Deliberately Broken Example:**


```java
// BAD — if close() throws, the original test exception is lost
Connection conn = null;
Statement stmt = null;
try {
    conn = DriverManager.getConnection(url, user, pass);
    stmt = conn.createStatement();
    ResultSet rs = stmt.executeQuery("SELECT * FROM invalid_table");  // SQLException!
    // ...
} catch (SQLException e) {
    log.error("Query failed", e);
    throw e;  // Rethrow to fail the test
} finally {
    stmt.close();   // What if stmt is null? NullPointerException!
    conn.close();   // This line never runs. Connection leaked.
    // The NullPointerException replaces the original SQLException in the stack trace
}
```

**Expected:** Test fails with `SQLException: invalid_table`.  
**Actual:** Test fails with `NullPointerException` in finally block. Original SQL error is lost. Developer chases the wrong bug.

**Corrected Implementation:**


```java
// GOOD — try-with-resources handles all of this automatically
try (
    Connection conn = DriverManager.getConnection(url, user, pass);
    Statement stmt = conn.createStatement();
    ResultSet rs = stmt.executeQuery("SELECT * FROM valid_table")
) {
    while (rs.next()) {
        // process results
    }
}
// All three resources closed in reverse order, even if exceptions occur
// If close() throws, it's added as a suppressed exception (accessible via getSuppressed())
```

<BestPractice>

**Prevention:** Always use try-with-resources for `AutoCloseable` resources. The compiler handles null checks, close ordering, and suppressed exceptions correctly.

</BestPractice>

## Engineering Judgment

### When to Let Exceptions Propagate vs. Catch and Handle

| Scenario | Strategy | Reasoning |
|----------|----------|-----------|
| Test assertion fails | **Propagate** | The test framework (TestNG/JUnit) needs to see the failure to report it |
| Element not found in a test step | **Propagate** | This is a real failure — the test should fail with a clear message |
| Element not found in an "is present" check | **Handle (return false/Optional)** | Absence is an expected outcome, not an error |
| Test data file missing | **Catch and rethrow with context** | Add test case ID and file path before propagating |
| WebDriver session crash | **Catch at framework level** | Ensure cleanup happens, then fail the test |
| Flaky network timeout in API setup | **Catch and retry** | Transient failures in test setup should be retried before failing |

### Exception Handling Strategy in a Test Framework

```
┌─────────────────────────────────────────────────┐
│  Test Level: @Test methods                       │
│  → Minimal try-catch. Let assertions propagate.  │
│  → Use framework utilities that handle retries.  │
├─────────────────────────────────────────────────┤
│  Page/Screen Object Level                        │
│  → Return Optional for "might not exist" cases.  │
│  → Throw custom exceptions with element context. │
│  → Retry on StaleElementReferenceException.      │
├─────────────────────────────────────────────────┤
│  Framework Utility Level                         │
│  → Handle resource lifecycle (drivers, conns).   │
│  → Catch and wrap low-level exceptions.          │
│  → Add rich context (locator, URL, timing).      │
├─────────────────────────────────────────────────┤
│  Base Test / Listener Level                      │
│  → Top-level safety net: screenshot on failure.  │
│  → Ensure driver cleanup on any exception.       │
│  → Log final failure context for CI debugging.   │
└─────────────────────────────────────────────────┘
```

**Principle:** Catch at the level where you have enough context to handle or enrich. Don't catch in tests what the framework should catch in listeners.

### Checked Exceptions in Method Signatures: The Debate

**Arguments for checked exceptions:**
- Forces callers to acknowledge failure modes
- Makes the API contract explicit
- Good for truly recoverable situations (retry with different input)

**Arguments against (especially in test frameworks):**
- Every method in the call chain must declare `throws` — noise accumulates
- Leads to `catch (Exception e) { throw new RuntimeException(e); }` wrapping everywhere
- Selenium chose unchecked for this reason — test code should be clean

**Practical guidance for automation code:**
- Use unchecked (`extends RuntimeException`) for framework exceptions — keeps test code clean
- Use checked only when the caller *must* make a decision (e.g., a method that connects to a DB where the caller chooses between retry, skip, or fail)

### Using Optional vs Exceptions for Expected Absence


```java
// Use Optional when "not found" is a VALID outcome
public Optional<String> getErrorMessage(By locator) {
    List<WebElement> elements = driver.findElements(locator);
    return elements.isEmpty()
        ? Optional.empty()
        : Optional.of(elements.get(0).getText());
}

// Use exceptions when "not found" means something is WRONG
public String getRequiredField(By locator) {
    WebElement element = new WebDriverWait(driver, Duration.ofSeconds(10))
        .until(ExpectedConditions.visibilityOfElementLocated(locator));
    return element.getText();
    // TimeoutException propagates — the field SHOULD be there
}

@Test
```

## Interview and Revision

### Fundamental Questions

**Q1: What is the difference between checked and unchecked exceptions?**  
**A:** Checked exceptions extend `Exception` (but not `RuntimeException`) and must be either caught or declared in the method's `throws` clause at compile time. Examples: `IOException`, `SQLException`. Unchecked exceptions extend `RuntimeException` and have no compile-time requirement. Examples: `NullPointerException`, `IllegalArgumentException`. The distinction is about whether the compiler forces you to acknowledge the failure mode.

**Q2: Why does the `finally` block execute even if a `return` statement is in the `try` block?**  
**A:** The JVM guarantees `finally` executes regardless of how the try block exits — normal completion, exception, or return. This is by design for resource cleanup. The only exceptions are `System.exit()` and JVM crash.

**Q3: What is exception chaining and why is it important?**  
**A:** Exception chaining wraps a low-level exception inside a higher-level one using the `cause` parameter: `throw new CustomException("context", originalException)`. This preserves the full stack trace of the original error while adding domain-specific context. Without chaining, you lose the root cause.

**Q4: Explain try-with-resources. What interface must a class implement?**  
**A:** try-with-resources automatically closes resources declared in the try parentheses when the block exits. The resource class must implement `AutoCloseable` (which has a single `close()` method). Multiple resources are closed in reverse declaration order. If `close()` throws while another exception is active, the close exception is added as a "suppressed" exception.

**Q5: Why are all Selenium exceptions unchecked?**  
**A:** Selenium exceptions extend `RuntimeException` because wrapping every `findElement()`, `click()`, and `sendKeys()` call in try-catch would make test code unreadable. The design assumes that element interaction failures should propagate naturally to the test framework's failure handler.

**Q6: What happens if both the `try` block and `finally` block throw exceptions?**  
**A:** The exception from `finally` replaces the one from `try` — the original exception is lost. This is a known pitfall. With try-with-resources, this is handled properly: the `close()` exception becomes a "suppressed" exception attached to the original, accessible via `Throwable.getSuppressed()`.

### Scenario-Based Questions

**S1: "Your test occasionally fails with `StaleElementReferenceException`. How do you diagnose and fix it?"**  
**A:** First, I'd identify *when* the staleness happens — is it during a page transition, after an AJAX update, or after a modal closes? Stale elements mean the DOM node was destroyed and recreated between when I found the element and when I used it. **Diagnosis:** Add logging to capture the page URL and element locator at failure time. Check if the page is doing dynamic re-rendering (React/Angular re-render cycles). **Fix:** (1) Re-find the element inside the action rather than caching the reference. (2) Use `WebDriverWait` with `ExpectedConditions` right before the interaction. (3) For repeated operations on the same locator, wrap in a retry loop (as in the `SafeElementActions` example). (4) If the staleness correlates with a specific page transition, add an explicit wait for the new page state before interacting.

**S2: "A colleague's test catches `Exception` everywhere and logs it, but tests always pass. What's wrong?"**  
**A:** They're swallowing exceptions. Every `catch (Exception e) { log.error(e); }` that doesn't rethrow means the test continues executing as if nothing happened. Assertions are never reached or exceptions from assertions are caught and logged. The fix is to (1) remove broad try-catch blocks in tests, (2) let exceptions propagate to the test framework, (3) only catch specific exceptions where recovery is possible, and (4) add a code review rule: every catch block must either rethrow, return a meaningful value, or have a comment explaining why swallowing is safe.

**S3: "You need to validate database state after an API call, but the DB connection sometimes times out. How do you handle this?"**  
**A:** I'd implement a layered approach: (1) Use try-with-resources for the connection to guarantee cleanup. (2) Configure connection pool timeouts appropriately. (3) Add a retry mechanism *specifically for* `SQLException` with connection timeout error codes — not a blanket retry for all exceptions. (4) If the retry exhausts, throw a custom `DatabaseValidationException` with the test case ID, query, and original exception as the cause. (5) Consider whether the timeout indicates a real environment problem that should fail the test vs. a transient issue worth retrying.




**Flashcard 1**  
**Q:** What's wrong with `catch (Exception e) { }` in a test?  
**A:** It silently swallows all exceptions, including assertion failures. The test will always pass regardless of the actual outcome. This is the most dangerous anti-pattern in test automation.

**Flashcard 2**  
**Q:** try-with-resources requires what interface?  
**A:** `AutoCloseable` (which defines a single `close()` method). `Closeable` extends `AutoCloseable` but is specific to I/O and throws only `IOException`.

**Flashcard 3**  
**Q:** `NoSuchElementException` vs `TimeoutException` — what's the difference in Selenium?  
**A:** `NoSuchElementException` is thrown by `findElement()` when the element doesn't exist in the current DOM. `TimeoutException` is thrown by `WebDriverWait` when the expected condition isn't met within the timeout period. The timeout may wrap a `NoSuchElementException` internally.

**Flashcard 4**  
**Q:** When should you use `Optional<T>` instead of throwing an exception?  
**A:** When the absence of a value is a *valid, expected outcome* — not an error. Example: checking if a promo banner exists on a page. Use exceptions when absence indicates something is *wrong*.

**Flashcard 5**  
**Q:** What is a suppressed exception?  
**A:** When try-with-resources calls `close()` and it throws while another exception is already in flight, the close exception is *suppressed* (attached to the primary exception via `addSuppressed()`). This prevents the original exception from being lost.
