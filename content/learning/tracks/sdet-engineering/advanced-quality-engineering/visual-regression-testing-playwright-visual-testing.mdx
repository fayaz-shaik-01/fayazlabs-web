# Playwright Visual Regression Testing

> **Module:** 09 — Advanced Quality Engineering / Visual Regression Testing  
> **Prerequisites:** Web Automation Fundamentals, Playwright Fundamentals  
> **Mastery Target:** L2 (Guided) → L3 (Independent) — can implement visual regression tests with Playwright, manage baselines, handle dynamic content, and integrate into CI

---

## Quick Overview (Layer 1)

**What:** Visual regression testing captures screenshots of your application and compares them pixel-by-pixel against approved baselines. Playwright's built-in `toHaveScreenshot()` assertion takes a screenshot, compares it to a stored baseline, and fails if the visual difference exceeds a threshold. It catches CSS regressions, layout breaks, missing elements, font changes, and unintended visual shifts that functional tests completely miss.

**Why:** Functional tests verify behavior: "clicking Book submits the form." But they don't verify appearance: "the Book button is still blue, 44px tall, and aligned to the right." A CSS change that moves the price below the fold, changes a font to unreadable, or hides a critical button passes every functional test. Visual regression testing is the only automated way to catch "it looks wrong" before users see it.

**Where:** Pages with stable, critical visual layouts. In StayNest: login page (brand consistency), search results (hotel cards, layout, pricing display), booking confirmation (receipt layout for printing), and the hotel management dashboard. Avoid pages with highly dynamic content (real-time feeds, randomized content) unless you mask the dynamic parts.

<KeyTakeaways>

1. **`toHaveScreenshot()`** is Playwright's built-in visual comparison — no third-party tools needed for basic visual testing.
2. First run creates the baseline. Subsequent runs compare against it. Differences generate a diff image highlighting changes.
3. **Dynamic content is the main challenge.** Timestamps, avatars, ads, and animations must be masked or frozen before screenshots.
4. Baselines are stored in git alongside tests. Updating baselines is a deliberate action reviewed in PRs.
5. Visual tests are slow and storage-heavy. Run them on key pages, not every page. Use element screenshots for component-level testing.

</KeyTakeaways>

## First-Principles Explanation (Layer 2)

### How Visual Comparison Works

```
First Run (no baseline):
  Screenshot taken → Saved as baseline → Test passes
  login-page-1.png (created)

Second Run:
  Screenshot taken → Compared to baseline → Diff calculated
  ┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
  │  Baseline        │    │  Actual          │    │  Diff            │
  │  (stored)        │ vs │  (current)       │ =  │  (differences)   │
  │  ┌─────────────┐ │    │  ┌─────────────┐ │    │  ┌─────────────┐ │
  │  │ Login       │ │    │  │ Login       │ │    │  │             │ │
  │  │ [email   ] │ │    │  │ [email   ] │ │    │  │             │ │
  │  │ [password] │ │    │  │ [password] │ │    │  │             │ │
  │  │ [Login ▪▪] │ │    │  │ [Sign In ▪] │ │    │  │ [XXXXXXXXX] │ │
  │  └─────────────┘ │    │  └─────────────┘ │    │  └─────────────┘ │
  └─────────────────┘    └─────────────────┘    └─────────────────┘
  Pixels differ: 847 > threshold (100) → TEST FAILS
```

### Playwright Visual Testing Configuration Options

| Option | What It Does | Default | When to Change |
|--------|-------------|---------|---------------|
| `maxDiffPixels` | Max pixels that can differ before failure | 0 | Small rendering differences across OS/browser |
| `maxDiffPixelRatio` | Max percentage of pixels that can differ | 0 | Alternative to maxDiffPixels for responsive layouts |
| `threshold` | Per-pixel color sensitivity (0-1) | 0.2 | Anti-aliasing differences, sub-pixel rendering |
| `animations` | How to handle CSS animations | `"disabled"` | Set to `"disabled"` to freeze animations |
| `mask` | Locators to mask (black rectangle) | none | Dynamic content: timestamps, avatars, ads |
| `fullPage` | Capture full scrollable page | false | Long pages, scrollable content |
| `clip` | Capture specific region only | none | Focus on a specific area |

## Practical Implementation (Layer 3)

### Basic Visual Regression Tests for StayNest


```java
import com.microsoft.playwright.*;
import org.junit.jupiter.api.*;

import java.nio.file.Paths;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;

/**
 * Visual regression test suite for StayNest key pages.
 * Baselines stored in: src/test/resources/screenshots/
 */
public class StayNestVisualTests {

    private static Playwright playwright;
    private static Browser browser;
    private BrowserContext context;
    private Page page;

    @BeforeAll
    static void launchBrowser() {
        playwright = Playwright.create();
        browser = playwright.chromium().launch(
            new BrowserType.LaunchOptions().setHeadless(true));
    }

    @BeforeEach
    void createContext() {
        // Consistent viewport for reproducible screenshots
        context = browser.newContext(new Browser.NewContextOptions()
            .setViewportSize(1280, 720)
            .setDeviceScaleFactor(1)         // Consistent DPI
            .setLocale("en-US")              // Consistent locale
            .setTimezoneId("America/New_York") // Consistent timezone
        );
        page = context.newPage();
    }

    // ── Login Page ──

    @Test
    void loginPage_matchesBaseline() {
        page.navigate("http://localhost:3000/login");
        page.waitForLoadState(LoadState.NETWORKIDLE);

        assertThat(page).hasScreenshot("login-page.png", new Page.HasScreenshotOptions()
            .setMaxDiffPixels(50)
            .setAnimations(Page.HasScreenshotOptions.Animations.DISABLED)
        );
    }

    // ── Search Results Page ──

    @Test
    void searchResults_matchesBaseline() {
        page.navigate("http://localhost:3000/hotels?city=NYC");
        page.waitForLoadState(LoadState.NETWORKIDLE);
        page.waitForSelector("[data-testid='hotel-card']");

        assertThat(page).hasScreenshot("search-results.png", new Page.HasScreenshotOptions()
            .setFullPage(true)
            .setMaxDiffPixels(100)
            .setAnimations(Page.HasScreenshotOptions.Animations.DISABLED)
            .setMask(java.util.List.of(
                page.locator("[data-testid='timestamp']"),    // Dynamic timestamp
                page.locator("[data-testid='user-avatar']")   // Randomized avatar
            ))
        );
    }

    // ── Booking Confirmation Page ──

    @Test
    void bookingConfirmation_matchesBaseline() {
        loginAsGuest();
        page.navigate("http://localhost:3000/bookings/1/confirmation");
        page.waitForLoadState(LoadState.NETWORKIDLE);

        assertThat(page).hasScreenshot("booking-confirmation.png", new Page.HasScreenshotOptions()
            .setMaxDiffPixels(50)
            .setAnimations(Page.HasScreenshotOptions.Animations.DISABLED)
            .setMask(java.util.List.of(
                page.locator("[data-testid='booking-date']"),  // Dynamic date
                page.locator("[data-testid='confirmation-id']") // Unique ID
            ))
        );
    }

    // ── Element-Level Screenshots ──

    @Test
    void hotelCard_matchesBaseline() {
        page.navigate("http://localhost:3000/hotels?city=NYC");
        page.waitForSelector("[data-testid='hotel-card']");

        Locator firstCard = page.locator("[data-testid='hotel-card']").first();
        assertThat(firstCard).hasScreenshot("hotel-card.png", new Locator.HasScreenshotOptions()
            .setMaxDiffPixels(30)
            .setAnimations(Locator.HasScreenshotOptions.Animations.DISABLED)
        );
    }

    @Test
    void navigationBar_matchesBaseline() {
        page.navigate("http://localhost:3000");
        page.waitForLoadState(LoadState.NETWORKIDLE);

        assertThat(page.locator("nav")).hasScreenshot("navigation-bar.png",
            new Locator.HasScreenshotOptions()
                .setMaxDiffPixels(20)
        );
    }

    @Test
    void footer_matchesBaseline() {
        page.navigate("http://localhost:3000");
        page.waitForLoadState(LoadState.NETWORKIDLE);

        // Scroll footer into view
        page.locator("footer").scrollIntoViewIfNeeded();
        assertThat(page.locator("footer")).hasScreenshot("footer.png",
            new Locator.HasScreenshotOptions()
                .setMaxDiffPixels(20)
        );
    }

    private void loginAsGuest() {
        page.navigate("http://localhost:3000/login");
        page.fill("[name=email]", "guest@staynest.com");
        page.fill("[name=password]", "TestPass123!");
        page.click("button[type=submit]");
        page.waitForURL("**/dashboard");
    }

    @AfterEach
    void closeContext() {
        if (context != null) context.close();
    }

    @AfterAll
    static void closeBrowser() {
        if (browser != null) browser.close();
        if (playwright != null) playwright.close();
    }
}
```

### Handling Dynamic Content Strategies


```java
/**
 * Strategies for handling dynamic content that causes false failures.
 */
public class DynamicContentStrategies {

    // Strategy 1: Mask dynamic elements
    static void maskDynamicElements(Page page) {
        assertThat(page).hasScreenshot("page.png", new Page.HasScreenshotOptions()
            .setMask(java.util.List.of(
                page.locator(".timestamp"),
                page.locator(".user-avatar"),
                page.locator(".ad-banner"),
                page.locator("[data-testid='live-count']")
            ))
        );
    }

    // Strategy 2: Freeze animations and transitions
    static void freezeAnimations(Page page) {
        page.evaluate("""
            () => {
                // Disable all CSS animations and transitions
                const style = document.createElement('style');
                style.textContent = `
                    *, *::before, *::after {
                        animation-duration: 0s !important;
                        animation-delay: 0s !important;
                        transition-duration: 0s !important;
                        transition-delay: 0s !important;
                    }
                `;
                document.head.appendChild(style);
            }
        """);
    }

    // Strategy 3: Replace dynamic text with static values
    static void stabilizeDynamicText(Page page) {
        page.evaluate("""
            () => {
                // Replace timestamps with fixed value
                document.querySelectorAll('[data-testid="timestamp"]')
                    .forEach(el => el.textContent = '2025-01-01 12:00:00');

                // Replace counters with fixed value
                document.querySelectorAll('[data-testid="result-count"]')
                    .forEach(el => el.textContent = '10 results');
            }
        """);
    }

    // Strategy 4: Hide dynamic elements entirely
    static void hideDynamicElements(Page page) {
        page.evaluate("""
            () => {
                const selectors = ['.chat-widget', '.cookie-banner', '.notification-popup'];
                selectors.forEach(sel => {
                    document.querySelectorAll(sel).forEach(el => {
                        el.style.display = 'none';
                    });
                });
            }
        """);
    }
}
```

### Baseline Management


```bash
# First run — creates baselines (test will pass, baselines saved)
npx playwright test --update-snapshots

# Subsequent runs — compare against baselines
npx playwright test

# Update baselines after intentional visual change
# 1. Make the UI change
# 2. Run tests (they will fail — visual diff detected)
# 3. Review the diff images in test-results/
# 4. If the change is intentional, update baselines:
npx playwright test --update-snapshots
# 5. Commit the updated baseline images in your PR
```

### Percy and Applitools — When Playwright Isn't Enough

| Aspect | Playwright toHaveScreenshot | Percy | Applitools Eyes |
|--------|---------------------------|-------|-----------------|
| **Cost** | Free (built-in) | Free tier + paid | Paid |
| **Comparison** | Pixel-by-pixel | Smart pixel comparison | AI-powered visual AI |
| **Cross-browser** | Run test per browser | Renders in multiple browsers from one snapshot | Renders in multiple browsers |
| **Dashboard** | None (file diffs) | Web dashboard with approval workflow | Web dashboard with AI grouping |
| **Dynamic content** | Manual masking | Layout comparison mode | AI ignores dynamic content |
| **CI Integration** | Built-in | SDK + cloud service | SDK + cloud service |
| **Best for** | Small teams, single browser, basic visual testing | Teams needing cross-browser and approval workflow | Enterprise with complex UIs |

**When to consider Percy/Applitools:**
- Cross-browser visual testing needed (Safari, Firefox rendering differences)
- Team needs a visual approval dashboard for designers/PMs to review
- AI-powered comparison that ignores minor rendering differences
- Managing baselines across 10+ pages and 3+ browsers becomes unmanageable locally

## Failure and Debugging (Layer 4)

### Failure 1: Visual Tests Fail on Different OS (CI vs Local)

**The Problem:** Tests pass on macOS locally but fail in CI (Linux). The diff shows subtle font rendering differences — macOS uses sub-pixel anti-aliasing that Linux doesn't.

**Root cause:** Font rendering is OS-dependent. The same font at the same size renders differently on macOS, Linux, and Windows at the sub-pixel level.

**The fix:** Use Docker to ensure consistent rendering environment:


```bash
# Run Playwright tests in Docker (consistent Linux rendering)
docker run --rm -v $(pwd):/app -w /app \
  mcr.microsoft.com/playwright:v1.44.0-jammy \
  npx playwright test

# Or increase the tolerance
assertThat(page).hasScreenshot("page.png", new Page.HasScreenshotOptions()
    .setMaxDiffPixelRatio(0.01)  // Allow 1% pixel difference
    .setThreshold(0.3)           // Less sensitive per-pixel comparison
);
```

Best practice: always generate baselines in the same environment (Docker) that CI uses.

### Failure 2: Tests Fail Because of Loading Spinners

**The Problem:** Screenshots capture a loading spinner instead of the actual content. The comparison fails because the spinner doesn't match the baseline.

**Root cause:** The screenshot was taken before the page finished loading. Network-idle doesn't guarantee all JavaScript has rendered content.

**The fix:** Wait for a specific content element before taking the screenshot:


```java
page.navigate("http://localhost:3000/hotels?city=NYC");

// Don't rely only on networkidle — wait for actual content
page.waitForSelector("[data-testid='hotel-card']",
    new Page.WaitForSelectorOptions().setTimeout(10000));

// Also wait for images to load (prevents blank image placeholders)
page.waitForFunction("() => Array.from(document.images).every(img => img.complete)");

// Now take the screenshot
assertThat(page).hasScreenshot("search-results.png");
```

### Failure 3: Baseline Update PR Has 50 Changed Screenshot Files

**The Problem:** A CSS framework upgrade changed the default font weight, and now every baseline is outdated. The PR shows 50 binary file changes that reviewers can't easily inspect.

**The fix:** Use Playwright's test report to visually review diffs. Add a review checklist:


```bash
# Generate HTML report with side-by-side visual diffs
npx playwright show-report

# In the PR description, document:
# - What changed (CSS framework upgrade)
# - Expected visual impact (font weight slightly bolder)
# - Pages affected (all pages — global style change)
# - Verification: ran manual spot-check on 5 key pages
```

## Engineering Judgment (Layer 5)

### What to Visually Test vs Not

| Test Visually | Don't Test Visually |
|---------------|---------------------|
| Login page (brand consistency) | Admin dashboards with real-time data |
| Search results layout (card alignment, pricing) | Pages with randomized content order |
| Booking confirmation (receipt for printing) | Chat interfaces (message content varies) |
| Navigation bar (present on every page) | Third-party embedded widgets |
| Error pages (404, 500) | Heavy animation sequences |
| Empty states (no results, no bookings) | User-generated content pages |

### Visual Testing Strategy by Team Size

| Team Size | Strategy | Why |
|-----------|----------|-----|
| 1-3 SDETs | Playwright `toHaveScreenshot()` only | Free, simple, sufficient for key pages |
| 4-8 SDETs | Playwright + Percy free tier | Cross-browser, approval dashboard |
| 8+ SDETs | Evaluate Applitools or Percy paid | AI comparison, enterprise workflow |

### Keeping Visual Tests Maintainable

1. **Fewer is better.** 10-15 well-chosen visual tests catch more regressions than 100 noisy ones.
2. **Element screenshots over full-page.** A change in the footer shouldn't break the header test.
3. **Consistent environment.** Docker or CI-only baselines — never commit baselines from a developer's laptop.
4. **Mask aggressively.** If it changes between runs and isn't what you're testing, mask it.
5. **Update baselines deliberately.** Never auto-accept. Review every diff. Commit with descriptive messages.

## Interview and Revision (Layer 6)




| # | Front | Back |
|---|-------|------|
| 1 | How does Playwright's `toHaveScreenshot()` work? | First run: saves screenshot as baseline. Subsequent runs: takes new screenshot, compares pixel-by-pixel against baseline, fails if differences exceed threshold (maxDiffPixels or maxDiffPixelRatio). Generates diff image showing exact changes |
| 2 | How do you handle dynamic content in visual tests? | Four strategies: mask elements (black rectangle over timestamps), freeze animations (CSS injection), replace dynamic text with static values (JS injection), hide elements entirely (display:none). Always mask what you can't control |
| 3 | Why do visual tests fail across different operating systems? | Font rendering is OS-dependent — macOS, Linux, and Windows render the same font differently at the sub-pixel level. Fix: generate baselines in Docker (consistent environment), or increase threshold/maxDiffPixelRatio tolerance |
| 4 | When should you use Percy or Applitools instead of Playwright? | When you need cross-browser visual testing (same baseline, multiple browsers), a visual approval dashboard for non-technical reviewers, or AI-powered comparison that handles minor rendering differences automatically |
| 5 | What's the difference between full-page and element screenshots? | Full-page captures everything (more comprehensive but more false positives — a footer change breaks all tests). Element screenshots focus on specific components (more stable, fewer false positives, faster comparison) |
