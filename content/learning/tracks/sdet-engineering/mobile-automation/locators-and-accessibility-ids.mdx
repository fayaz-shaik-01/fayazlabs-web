# Locators and Accessibility IDs

> **Module:** 06 — Mobile Automation > Locators and Accessibility IDs  
> **Prerequisites:** Native Mobile Fundamentals  
> **Mastery Target:** L3 (Independent) → L4 (Engineering Judgment)

---

## Quick Overview (Layer 1)

**What:** Mobile locator strategies determine how your test code identifies UI elements within the native View hierarchy. Unlike web automation (CSS selectors, IDs), mobile uses platform-specific attributes — accessibility ID (cross-platform preferred), `resource-id` (Android), `accessibilityIdentifier` (iOS), class name, and XPath (last resort). Choosing the right strategy is the single biggest factor in test reliability and maintainability.

**Why it matters:** Flaky locators are the #1 cause of mobile test failures. A solid locator strategy means tests survive UI redesigns, work across platforms, and run faster. Accessibility IDs give you the best of both worlds — stable locators for tests AND better app accessibility for users with disabilities. An SDET who understands platform-specific locator hierarchies writes tests that don't break every sprint.

**Where you encounter it:** Every mobile test you write. Appium Inspector sessions when building page objects. Cross-platform test suites where the same test logic must work on Android and iOS. Conversations with developers about adding accessibility identifiers to the app.

<MentalModel>

Think of mobile locators as **addresses for UI elements**. Accessibility ID is like a street address — universal, stable, and meaningful. Resource-id is like GPS coordinates — precise but platform-specific. XPath is like directions ("go past the third building, turn left") — fragile, slow, and breaks when the neighborhood changes.

</MentalModel>


```
Locator Reliability Spectrum (most → least reliable)
─────────────────────────────────────────────────────
Accessibility ID  →  resource-id / name  →  Class Name  →  UiAutomator / Predicate  →  XPath
   (preferred)        (platform-specific)    (too broad)     (powerful but complex)      (last resort)
```

<KeyTakeaways>

1. **Accessibility ID is the preferred locator** — it works on both Android (`content-desc`) and iOS (`accessibilityIdentifier`), and it improves the app's actual accessibility.
2. **Resource-id is Android's workhorse** — most Android elements have a `resource-id` attribute, which maps to `AppiumBy.id()` in test code.
3. **iOS uses predicate strings and class chains** — these are faster and more expressive than XPath for iOS element location.
4. **XPath is a last resort** — it's slow (Appium must traverse the full hierarchy), brittle (breaks on layout changes), and platform-specific.
5. **Cross-platform tests use locator maps** — same test logic, different locator values per platform, typically stored in configuration or platform-specific page objects.

</KeyTakeaways>

## First-Principles Explanation (Layer 2)

### Locator Strategies Ranked

Every locator strategy trades off between reliability, speed, readability, and cross-platform support:

| Strategy | Android Attribute | iOS Attribute | Speed | Reliability | Cross-Platform |
|---|---|---|---|---|---|
| Accessibility ID | `content-desc` | `accessibilityIdentifier` | Fast | High | ✅ Yes |
| ID / Resource ID | `resource-id` | `name` | Fast | High | ❌ Different values |
| Class Name | `android.widget.Button` | `XCUIElementTypeButton` | Fast | Low (too generic) | ❌ Different names |
| UiAutomator Selector | UiSelector API | — | Fast | High | ❌ Android only |
| Predicate String | — | NSPredicate | Fast | High | ❌ iOS only |
| Class Chain | — | XCUITest class chain | Fast | High | ❌ iOS only |
| XPath | XML hierarchy path | XML hierarchy path | Slow | Low | ⚠️ Different trees |

### Accessibility ID: The Preferred Strategy

Accessibility ID maps to `content-desc` on Android and `accessibilityIdentifier` on iOS. It's the only locator strategy that is truly cross-platform in Appium.

**Why it's preferred:**
- **Platform-independent:** Same `AppiumBy.accessibilityId("loginButton")` works on both platforms if developers set the same identifier.
- **Stable:** Accessibility IDs are intentionally set by developers, not auto-generated — they survive refactors and layout changes.
- **Meaningful:** IDs like `"searchField"`, `"bookNowButton"`, `"priceLabel"` describe the element's purpose, making tests self-documenting.
- **Accessibility benefit:** Adding `content-desc` (Android) and `accessibilityIdentifier` (iOS) improves the app for screen reader users — your test infrastructure literally makes the product more inclusive.

**The conversation with developers:** SDETs should advocate for accessibility IDs on every interactable and assertable element. This is a collaborative effort — file tickets, add it to the definition of done, create a naming convention (`screenName_elementPurpose`), and explain the dual benefit (testability + accessibility).

### Android-Specific Locators

**resource-id:** The most common Android locator. Appears as `com.staynest.app:id/emailInput` in the View hierarchy. You can use the full ID or just the suffix after the `/`.


```java
// Full resource-id
driver.findElement(AppiumBy.id("com.staynest.app:id/emailInput"));

// Short form — Appium resolves the package prefix automatically
driver.findElement(AppiumBy.id("emailInput"));
```

**UiAutomator2 Selectors:** Android's native automation API provides `UiSelector`, a powerful query mechanism that can search by text, description, class, scrollability, and more.


```java
// Find by text content
driver.findElement(AppiumBy.androidUIAutomator(
    "new UiSelector().text(\"Search destinations\")"
));

// Find by content description (accessibility ID equivalent)
driver.findElement(AppiumBy.androidUIAutomator(
    "new UiSelector().description(\"loginButton\")"
));

// Find scrollable container and scroll to text
driver.findElement(AppiumBy.androidUIAutomator(
    "new UiScrollable(new UiSelector().scrollable(true))" +
    ".scrollTextIntoView(\"Luxury Beachfront Villa\")"
));

// Combine criteria — clickable button with specific text
driver.findElement(AppiumBy.androidUIAutomator(
    "new UiSelector().className(\"android.widget.Button\").text(\"Book Now\")"
));
```

### iOS-Specific Locators

**Predicate Strings:** iOS equivalent of UiAutomator selectors. Uses NSPredicate syntax for fast, expressive queries.


```java
// Find by label
driver.findElement(AppiumBy.iOSNsPredicateString(
    "label == 'Search destinations'"
));

// Find by type and partial label
driver.findElement(AppiumBy.iOSNsPredicateString(
    "type == 'XCUIElementTypeButton' AND label CONTAINS 'Book'"
));

// Find by value (text field content)
driver.findElement(AppiumBy.iOSNsPredicateString(
    "type == 'XCUIElementTypeTextField' AND value BEGINSWITH 'Enter'"
));
```

**Class Chain Queries:** A faster, XPath-like syntax specific to XCUITest. Navigates the iOS element tree using class names and predicates.


```java
// Direct child of a specific type
driver.findElement(AppiumBy.iOSClassChain(
    "**/XCUIElementTypeButton[`label == 'Book Now'`]"
));

// Nth element of a type
driver.findElement(AppiumBy.iOSClassChain(
    "**/XCUIElementTypeCell[3]/XCUIElementTypeStaticText[1]"
));

// Combining class chain with predicate
driver.findElement(AppiumBy.iOSClassChain(
    "**/XCUIElementTypeTextField[`value BEGINSWITH 'Search'`]"
));
```

### Using Appium Inspector for Locator Discovery

Appium Inspector is your primary tool for finding and verifying locators. Here's the systematic workflow:

1. **Launch Inspector** and connect to your running Appium session (or start a new one with capabilities).
2. **Navigate to the target screen** in the app by interacting manually or through Inspector's controls.
3. **Click an element** in the screenshot — Inspector highlights it and shows all attributes in the right panel.
4. **Evaluate locator options:** Check which attributes are available — `content-desc` (accessibility ID), `resource-id`, `text`, `class`.
5. **Test the locator:** Use Inspector's search feature to verify your chosen locator finds exactly one element.
6. **Check uniqueness:** A locator that matches multiple elements will cause unpredictable test behavior. If it's not unique, combine attributes or use a more specific strategy.

## Practical Implementation (Layer 3)

### Cross-Platform Locator Strategy

The recommended pattern separates test logic from platform-specific locators. Tests reference logical element names; locator maps provide platform-specific values.


```java
// Locator map — centralized, easy to update
public class LoginScreenLocators {

    // Cross-platform (accessibility ID)
    public static final String EMAIL_FIELD = "emailInput";
    public static final String PASSWORD_FIELD = "passwordInput";
    public static final String LOGIN_BUTTON = "loginButton";
    public static final String FORGOT_PASSWORD = "forgotPasswordLink";

    // Platform-specific locators when accessibility IDs aren't available
    public static By getGoogleSignInButton(String platform) {
        if (platform.equals("Android")) {
            return AppiumBy.id("com.staynest.app:id/googleSignInBtn");
        } else {
            return AppiumBy.iOSNsPredicateString(
                "type == 'XCUIElementTypeButton' AND label == 'Sign in with Google'"
            );
        }
    }

    public static By getErrorMessage(String platform) {
        if (platform.equals("Android")) {
            return AppiumBy.androidUIAutomator(
                "new UiSelector().resourceId(\"com.staynest.app:id/errorText\")"
            );
        } else {
            return AppiumBy.iOSClassChain(
                "**/XCUIElementTypeStaticText[`label CONTAINS 'error'`]"
            );
        }
    }
}
```

### StayNest Login Screen — Locator Strategy


```java
public class LoginScreen {

    private final AppiumDriver driver;
    private final WebDriverWait wait;

    public LoginScreen(AppiumDriver driver) {
        this.driver = driver;
        this.wait = new WebDriverWait(driver, Duration.ofSeconds(10));
    }

    // Preferred: Accessibility IDs for all primary elements
    private WebElement emailField() {
        return wait.until(ExpectedConditions.visibilityOfElementLocated(
            AppiumBy.accessibilityId("emailInput")
        ));
    }

    private WebElement passwordField() {
        return driver.findElement(AppiumBy.accessibilityId("passwordInput"));
    }

    private WebElement loginButton() {
        return driver.findElement(AppiumBy.accessibilityId("loginButton"));
    }

    // Fallback: resource-id when accessibility ID isn't set
    private WebElement rememberMeCheckbox() {
        return driver.findElement(AppiumBy.id("rememberMeToggle"));
    }

    public void login(String email, String password) {
        emailField().clear();
        emailField().sendKeys(email);
        passwordField().clear();
        passwordField().sendKeys(password);
        loginButton().click();
    }

    public String getErrorMessage() {
        WebElement error = wait.until(ExpectedConditions.visibilityOfElementLocated(
            AppiumBy.accessibilityId("loginErrorMessage")
        ));
        return error.getText();
    }

    public boolean isDisplayed() {
        try {
            return emailField().isDisplayed();
        } catch (TimeoutException e) {
            return false;
        }
    }
}
```

### StayNest Search Screen — Locator Strategy


```java
public class SearchScreen {

    private final AppiumDriver driver;
    private final WebDriverWait wait;
    private final String platform;

    public SearchScreen(AppiumDriver driver, String platform) {
        this.driver = driver;
        this.wait = new WebDriverWait(driver, Duration.ofSeconds(10));
        this.platform = platform;
    }

    private WebElement searchField() {
        return wait.until(ExpectedConditions.visibilityOfElementLocated(
            AppiumBy.accessibilityId("searchDestinationField")
        ));
    }

    private WebElement searchButton() {
        return driver.findElement(AppiumBy.accessibilityId("searchButton"));
    }

    // Platform-specific: date picker is implemented differently on Android vs iOS
    private WebElement checkInDate() {
        if (platform.equals("Android")) {
            return driver.findElement(AppiumBy.id("checkInDatePicker"));
        } else {
            return driver.findElement(AppiumBy.iOSNsPredicateString(
                "type == 'XCUIElementTypeButton' AND label BEGINSWITH 'Check-in'"
            ));
        }
    }

    // Scroll to a listing by name — platform-specific scroll strategies
    public WebElement scrollToListing(String listingName) {
        if (platform.equals("Android")) {
            return driver.findElement(AppiumBy.androidUIAutomator(
                "new UiScrollable(new UiSelector().scrollable(true))" +
                ".scrollTextIntoView(\"" + listingName + "\")"
            ));
        } else {
            // iOS: use predicate after performing mobile:scroll
            Map<String, Object> scrollArgs = new HashMap<>();
            scrollArgs.put("direction", "down");
            scrollArgs.put("predicateString",
                "label == '" + listingName + "'");
            driver.executeScript("mobile: scroll", scrollArgs);
            return driver.findElement(AppiumBy.iOSNsPredicateString(
                "label == '" + listingName + "'"
            ));
        }
    }

    public void searchDestination(String destination) {
        searchField().clear();
        searchField().sendKeys(destination);
        searchButton().click();
    }

    public int getResultCount() {
        List<WebElement> results = driver.findElements(
            AppiumBy.accessibilityId("searchResultCard")
        );
        return results.size();
    }
}
```

## Failure and Debugging (Layer 4)

### Failure 1: Accessibility ID Not Found

**Symptom:** `NoSuchElementException` when using `AppiumBy.accessibilityId("loginButton")`.

**Diagnostic steps:**
1. Open Appium Inspector and navigate to the target screen.
2. Click the element you're trying to locate — check its attributes panel.
3. Look for `content-desc` (Android) or `accessibilityIdentifier` (iOS). If it's empty, the developer hasn't set it.
4. Check if the value is different from what you expected (typo, changed name).

<BestPractice>

**Fix:** If the accessibility ID is missing, file a ticket with the development team. In the meantime, use the next-best locator (`resource-id` on Android, predicate string on iOS). Never accept XPath as a permanent solution.

</BestPractice>


### Failure 2: Locator Matches Multiple Elements

**Symptom:** Test clicks the wrong element, or behavior is inconsistent between runs.

**Diagnostic:**


```java
// Check how many elements match your locator
List<WebElement> matches = driver.findElements(
    AppiumBy.accessibilityId("submitButton")
);
System.out.println("Found " + matches.size() + " elements");
// If > 1, your locator is ambiguous
```

<BestPractice>

**Fix:** Make the locator more specific — add parent context, use a compound UiAutomator selector, or ask developers to make accessibility IDs unique per screen.

</BestPractice>


### Failure 3: XPath Locator Breaks After Minor UI Change

**Symptom:** Test that worked yesterday fails today with `NoSuchElementException`. The element still exists but the XPath is invalid because a parent container changed.

**Root cause:** XPath locators like `/hierarchy/android.widget.FrameLayout/android.widget.LinearLayout[2]/android.widget.Button` encode the full tree path. Any structural change (adding a wrapper view, reordering children) breaks it.

<BestPractice>

**Fix:** Replace with accessibility ID or resource-id. If XPath is truly unavoidable, use relative XPath with stable attributes:

</BestPractice>



```java
// BRITTLE: absolute XPath
driver.findElement(By.xpath(
    "/hierarchy/android.widget.FrameLayout/android.view.ViewGroup/android.widget.Button[3]"
));

// BETTER: relative XPath with attribute anchor
driver.findElement(By.xpath(
    "//android.widget.Button[@resource-id='com.staynest.app:id/bookBtn']"
));

// BEST: accessibility ID (no XPath needed)
driver.findElement(AppiumBy.accessibilityId("bookNowButton"));
```

## Engineering Judgment (Layer 5)

### Building a Locator Convention with Your Dev Team

The most impactful thing an SDET can do for mobile test stability is **establish a naming convention for accessibility IDs** with the development team:

| Convention | Example | Benefit |
|---|---|---|
| `screenName_elementPurpose` | `login_emailField` | Unique per screen, self-documenting |
| `camelCase` | `loginEmailField` | Consistent with code style |
| Avoid positional names | `firstListItem` ❌ | Position can change; use purpose instead |
| Avoid visual names | `redButton` ❌ | Color changes don't reflect function |

**Add to Definition of Done:** "Every interactable element and assertion target has an accessibility ID following the `screenName_elementPurpose` convention."

### When to Accept Platform-Specific Locators

Cross-platform accessibility IDs are ideal, but pragmatism matters:

- **Custom widgets:** Platform-native date pickers, action sheets, and bottom sheets expose different structures. Platform-specific locators are fine here.
- **Legacy apps:** If the app has no accessibility IDs and adding them requires refactoring, use `resource-id` (Android) / predicate strings (iOS) while incrementally adding IDs.
- **System dialogs:** Permission dialogs, keyboard suggestions, and OS alerts use system-level elements that don't have your app's accessibility IDs.

## Interview and Revision (Layer 6)

### Fundamental Questions

**Q1: What locator strategy do you prefer for mobile automation and why?**

**A:** Accessibility ID is my first choice because it's the only locator that works identically on both Android and iOS. On Android it maps to `content-desc`, on iOS to `accessibilityIdentifier`. It's stable — developers set it intentionally, so it doesn't break when the UI layout changes. It's also fast because Appium uses native platform APIs to find elements by accessibility ID without traversing the full hierarchy. As a bonus, it makes the app more accessible for users with disabilities. I only fall back to `resource-id` (Android) or predicate strings (iOS) when accessibility IDs aren't available, and I use XPath only as a last resort because it's slow and fragile.

**Q2: How do you handle locators for a cross-platform mobile test suite?**

**A:** I use a locator map pattern where test logic references logical element names, and platform-specific locator values are resolved at runtime. When accessibility IDs are set consistently across platforms, the same locator works on both. For elements where that's not possible — custom widgets, platform-native components — I use a factory method or platform-specific page object that returns the correct locator based on the current platform. I also work with developers to establish a naming convention for accessibility IDs so both platforms use the same identifiers.

### Scenario-Based Questions

**S1: "A developer pushes a UI redesign that breaks 30% of your mobile tests. How do you prevent this?"**

**A:** First, I'd analyze which locator types broke. If they're mostly XPath or positional locators, that's the root cause — they're too tightly coupled to UI structure. I'd migrate them to accessibility IDs and resource-ids. To prevent recurrence, I'd establish a contract with the dev team: every interactable element gets an accessibility ID, and it's part of the definition of done. I'd add a locator health check that reports which tests use fragile locator types. Finally, I'd use Appium Inspector in CI to dump the element tree so locator changes can be detected early.
