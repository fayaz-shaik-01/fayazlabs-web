# Mobile Test Patterns

> **Module:** 06 — Mobile Automation > Mobile Test Patterns

## Quick Overview (Layer 1)

**What:** Mobile test patterns are the architectural blueprints for organizing mobile automation code. The Screen Object Model (mobile equivalent of the Page Object Model) encapsulates screen interactions behind clean APIs. A BaseScreen class provides common mobile actions — swipe, scroll, wait, dismiss keyboard — that every screen inherits. Platform abstraction lets the same test run against Android and iOS with different screen implementations. Together, these patterns transform raw Appium calls into a maintainable, readable, and scalable test suite.

**Why it matters:** Without patterns, mobile test code devolves into thousands of lines of `driver.findElement().click()` calls sprinkled with coordinate calculations and platform-specific branching. When the app changes (every sprint), you're updating locators in dozens of test files. The Screen Object Model centralizes locators and interactions so a UI change requires updating exactly one class. Platform abstraction prevents you from maintaining two completely separate test suites for Android and iOS. These patterns are the difference between a suite that scales and one that collapses under its own weight.

**Where you encounter it:** Every production mobile test framework. Code reviews where seniors enforce architectural consistency. Interview questions about how you structure mobile automation. Framework design discussions when starting a new mobile project.

<MentalModel>

Think of the Screen Object Model as a **menu at a restaurant**. The test is the diner ordering "I want the login" — it doesn't need to know the recipe (locators, waits, gestures). The Screen Object is the menu item that maps to a kitchen recipe (implementation details). The BaseScreen is the kitchen's standard equipment (oven, knives, pans) — common tools every recipe uses. Platform abstraction means the same menu works at both the New York and Tokyo locations, even though the kitchens use different equipment.

</MentalModel>


```
Test Architecture
─────────────────
Test Class           → What to test (business logic)
  └── Screen Object  → How to interact (locators, actions)
       └── BaseScreen → Common mobile utilities (swipe, scroll, wait)
            └── AppiumDriver → Raw device commands
```

<KeyTakeaways>

1. **Screen Object Model encapsulates screen interactions** — tests call `loginScreen.login(email, password)`, never `driver.findElement(...)`.
2. **BaseScreen provides mobile-specific utilities** — `swipe()`, `scrollToElement()`, `waitForElement()`, `hideKeyboard()`, `isScreenDisplayed()`.
3. **Platform abstraction uses interfaces** — define a `LoginScreen` interface, implement `AndroidLoginScreen` and `IOSLoginScreen`, and inject the right one at runtime.
4. **Mobile test data should be lean** — smaller data sets, offline-capable test data, and API-seeded state rather than UI-created state.
5. **Setup/teardown handles app state** — install, reset, login, and cleanup are more complex than web and must be explicitly managed.

</KeyTakeaways>

## First-Principles Explanation (Layer 2)

### Screen Object Model vs. Page Object Model

The Screen Object Model is the mobile adaptation of the Page Object Model. The principles are identical — encapsulation, single responsibility, fluent APIs — but the implementation accounts for mobile-specific realities:

| Aspect | Web Page Object | Mobile Screen Object |
|---|---|---|
| Element location | CSS/XPath selectors | Accessibility IDs, platform-specific locators |
| Navigation | URLs, links | Gestures, back button, deep links |
| Common actions | Click, type, select | Tap, swipe, scroll, long press, pinch |
| Waits | Page load, AJAX | Screen transition, animation completion |
| Keyboard | Always available (physical/virtual) | Soft keyboard appears/disappears, may cover elements |
| Alerts | Browser alerts | System permission dialogs, OS-level alerts |
| Platform | One browser, one implementation | Two platforms, potentially two implementations |

### BaseScreen Design Principles

A well-designed BaseScreen provides three categories of utilities:

1. **Element interaction wrappers** — methods that add implicit waits, retries, and error handling around raw Appium calls.
2. **Gesture utilities** — swipe, scroll, pull-to-refresh, long press — calculated from screen/element dimensions, never hard-coded coordinates.
3. **Screen state utilities** — is the screen displayed? Wait for screen to load. Dismiss keyboard. Handle unexpected alerts.

### Platform Abstraction Strategy

Three approaches to cross-platform mobile testing, from simplest to most robust:

**1. Shared tests, platform-specific locators (simplest):**
One test class uses locator maps that return platform-specific values. Works when screen structure is identical across platforms.

**2. Shared tests, platform-specific screen objects (recommended):**
Tests use a screen interface. Android and iOS each implement the interface with their own locators and interactions. A factory creates the right implementation.

**3. Separate test suites per platform (rare):**
Completely independent suites. Only justified when Android and iOS apps have fundamentally different UX flows.

## Practical Implementation (Layer 3)

### BaseScreen — Foundation for All Screens


```java
public abstract class BaseScreen {

    protected final AppiumDriver driver;
    protected final WebDriverWait wait;
    protected final GestureUtils gestures;
    protected final String platform;

    public BaseScreen(AppiumDriver driver) {
        this.driver = driver;
        this.wait = new WebDriverWait(driver, Duration.ofSeconds(15));
        this.gestures = new GestureUtils(driver);
        this.platform = driver.getCapabilities()
            .getCapability("platformName").toString();
    }

    // ─── Element Interaction Wrappers ───

    /**
     * Find element with explicit wait — use instead of raw findElement.
     */
    protected WebElement findElement(By locator) {
        return wait.until(
            ExpectedConditions.visibilityOfElementLocated(locator)
        );
    }

    /**
     * Find element with custom timeout.
     */
    protected WebElement findElement(By locator, int timeoutSeconds) {
        return new WebDriverWait(driver, Duration.ofSeconds(timeoutSeconds))
            .until(ExpectedConditions.visibilityOfElementLocated(locator));
    }

    /**
     * Check if an element is present without throwing an exception.
     */
    protected boolean isElementPresent(By locator) {
        try {
            new WebDriverWait(driver, Duration.ofSeconds(3))
                .until(ExpectedConditions.visibilityOfElementLocated(locator));
            return true;
        } catch (TimeoutException e) {
            return false;
        }
    }

    /**
     * Tap on an element — clears any existing text first if it's an input.
     */
    protected void tapElement(By locator) {
        findElement(locator).click();
    }

    /**
     * Type text into a field — clears existing text, types, hides keyboard.
     */
    protected void typeText(By locator, String text) {
        WebElement element = findElement(locator);
        element.clear();
        element.sendKeys(text);
    }

    /**
     * Get text from an element.
     */
    protected String getText(By locator) {
        return findElement(locator).getText();
    }

    // ─── Gesture Utilities ───

    protected void swipeLeft(WebElement element) {
        gestures.swipeLeft(element);
    }

    protected void swipeRight(WebElement element) {
        gestures.swipeRight(element);
    }

    protected void scrollDown() {
        gestures.scrollDown();
    }

    protected void pullToRefresh() {
        gestures.pullToRefresh();
    }

    protected WebElement scrollToElement(By locator, int maxScrolls) {
        for (int i = 0; i < maxScrolls; i++) {
            List<WebElement> elements = driver.findElements(locator);
            if (!elements.isEmpty() && elements.get(0).isDisplayed()) {
                return elements.get(0);
            }
            scrollDown();
        }
        throw new NoSuchElementException(
            "Element not found after " + maxScrolls + " scrolls");
    }

    // ─── Screen State Utilities ───

    /**
     * Each screen subclass defines its unique identifying element.
     */
    protected abstract By screenIdentifier();

    /**
     * Check if this screen is currently displayed.
     */
    public boolean isDisplayed() {
        return isElementPresent(screenIdentifier());
    }

    /**
     * Wait for this screen to be fully loaded.
     */
    public void waitForScreenLoaded() {
        findElement(screenIdentifier());
    }

    /**
     * Dismiss the soft keyboard if visible.
     */
    protected void hideKeyboard() {
        try {
            if (platform.equalsIgnoreCase("Android")) {
                ((AndroidDriver) driver).hideKeyboard();
            } else {
                // iOS: tap outside the text field
                Dimension size = driver.manage().window().getSize();
                gestures.tap(size.getWidth() / 2, 10);
            }
        } catch (Exception e) {
            // Keyboard wasn't visible — safe to ignore
        }
    }

    /**
     * Handle unexpected alert/dialog if present.
     */
    protected void dismissAlertIfPresent() {
        try {
            driver.switchTo().alert().dismiss();
        } catch (NoAlertPresentException e) {
            // No alert — nothing to do
        }
    }
}
```

### LoginScreen — Concrete Screen Object


```java
public class LoginScreen extends BaseScreen {

    // ─── Locators ───
    private final By emailField = AppiumBy.accessibilityId("emailInput");
    private final By passwordField = AppiumBy.accessibilityId("passwordInput");
    private final By loginButton = AppiumBy.accessibilityId("loginButton");
    private final By forgotPassword = AppiumBy.accessibilityId("forgotPasswordLink");
    private final By errorMessage = AppiumBy.accessibilityId("loginErrorMessage");
    private final By googleSignIn = AppiumBy.accessibilityId("googleSignInButton");

    public LoginScreen(AppiumDriver driver) {
        super(driver);
    }

    @Override
    protected By screenIdentifier() {
        return emailField;
    }

    // ─── Actions ───

    public HomeScreen login(String email, String password) {
        typeText(emailField, email);
        typeText(passwordField, password);
        hideKeyboard();
        tapElement(loginButton);
        return new HomeScreen(driver);
    }

    public LoginScreen loginExpectingError(String email, String password) {
        typeText(emailField, email);
        typeText(passwordField, password);
        hideKeyboard();
        tapElement(loginButton);
        return this;
    }

    public String getErrorText() {
        return getText(errorMessage);
    }

    public boolean isErrorDisplayed() {
        return isElementPresent(errorMessage);
    }

    public ForgotPasswordScreen tapForgotPassword() {
        tapElement(forgotPassword);
        return new ForgotPasswordScreen(driver);
    }
}
```

### SearchScreen — With Scroll and Gesture Support


```java
public class SearchScreen extends BaseScreen {

    private final By searchField = AppiumBy.accessibilityId("searchDestinationField");
    private final By searchButton = AppiumBy.accessibilityId("searchButton");
    private final By resultCards = AppiumBy.accessibilityId("searchResultCard");
    private final By filterButton = AppiumBy.accessibilityId("filterButton");
    private final By noResultsMessage = AppiumBy.accessibilityId("noResultsMessage");

    public SearchScreen(AppiumDriver driver) {
        super(driver);
    }

    @Override
    protected By screenIdentifier() {
        return searchField;
    }

    public SearchScreen searchDestination(String destination) {
        typeText(searchField, destination);
        hideKeyboard();
        tapElement(searchButton);
        // Wait for results or no-results to appear
        wait.until(ExpectedConditions.or(
            ExpectedConditions.visibilityOfElementLocated(resultCards),
            ExpectedConditions.visibilityOfElementLocated(noResultsMessage)
        ));
        return this;
    }

    public int getResultCount() {
        return driver.findElements(resultCards).size();
    }

    public ListingDetailScreen selectListing(int index) {
        List<WebElement> results = driver.findElements(resultCards);
        if (index >= results.size()) {
            // Need to scroll to find more results
            scrollDown();
            results = driver.findElements(resultCards);
        }
        results.get(index).click();
        return new ListingDetailScreen(driver);
    }

    public ListingDetailScreen scrollToAndSelectListing(String listingName) {
        By listingLocator = AppiumBy.accessibilityId("listing_" + listingName);
        WebElement listing = scrollToElement(listingLocator, 5);
        listing.click();
        return new ListingDetailScreen(driver);
    }

    public SearchScreen refreshResults() {
        pullToRefresh();
        wait.until(ExpectedConditions.visibilityOfElementLocated(resultCards));
        return this;
    }

    public boolean hasNoResults() {
        return isElementPresent(noResultsMessage);
    }
}
```

### BookingScreen — Complex Form Interactions


```java
public class BookingScreen extends BaseScreen {

    private final By guestCountField = AppiumBy.accessibilityId("guestCountInput");
    private final By checkInDate = AppiumBy.accessibilityId("checkInDatePicker");
    private final By checkOutDate = AppiumBy.accessibilityId("checkOutDatePicker");
    private final By specialRequests = AppiumBy.accessibilityId("specialRequestsField");
    private final By totalPrice = AppiumBy.accessibilityId("totalPriceLabel");
    private final By confirmButton = AppiumBy.accessibilityId("bookingConfirmButton");
    private final By cancelButton = AppiumBy.accessibilityId("cancelBookingButton");

    public BookingScreen(AppiumDriver driver) {
        super(driver);
    }

    @Override
    protected By screenIdentifier() {
        return guestCountField;
    }

    public BookingScreen setGuestCount(String count) {
        typeText(guestCountField, count);
        return this;
    }

    public BookingScreen selectCheckInDate(String date) {
        tapElement(checkInDate);
        // Date picker interaction — platform-specific
        selectDateFromPicker(date);
        return this;
    }

    public BookingScreen addSpecialRequests(String requests) {
        // Special requests field may be below the fold
        WebElement requestsField = scrollToElement(specialRequests, 3);
        requestsField.clear();
        requestsField.sendKeys(requests);
        hideKeyboard();
        return this;
    }

    public String getTotalPrice() {
        return getText(totalPrice);
    }

    public ConfirmationScreen confirmBooking() {
        // Confirm button is often at the bottom — scroll to it
        WebElement confirm = scrollToElement(confirmButton, 3);
        confirm.click();
        return new ConfirmationScreen(driver);
    }

    public SearchScreen cancelBooking() {
        tapElement(cancelButton);
        return new SearchScreen(driver);
    }

    private void selectDateFromPicker(String date) {
        // Platform-specific date picker implementation
        // (simplified — real implementation depends on the app's picker widget)
        By dateLocator = AppiumBy.accessibilityId("date_" + date);
        tapElement(dateLocator);
        tapElement(AppiumBy.accessibilityId("datePickerConfirm"));
    }
}
```

```java
// Test using the screen objects — reads like a user story
public class BookingFlowTest {

    public void setUp() throws Exception {

    @Test
    public void shouldCompleteBookingFlow() {

        loginScreen.waitForScreenLoaded();

        ConfirmationScreen confirmation = booking.confirmBooking();
        Assert.assertTrue(confirmation.isDisplayed());
        Assert.assertTrue(confirmation.getConfirmationId().length() > 0);
    }

    @AfterMethod(alwaysRun = true)
    public void tearDown() {
        if (driver != null) driver.quit();
    }
```

### Setup/Teardown Patterns


```java
public class MobileTestBase {

    protected AppiumDriver driver;
    protected static final boolean IS_CI = System.getenv("CI") != null;

    @BeforeSuite
    public void suiteSetup() {
        // One-time setup: verify Appium server is running
        // Upload app to cloud if using BrowserStack
        if (IS_CI) {
            // App upload, environment validation
        }
    }

    @BeforeMethod
    public void setUp(Method method) throws Exception {
        CapabilityFactory.Environment env = IS_CI
            ? CapabilityFactory.Environment.CI
            : CapabilityFactory.Environment.LOCAL_EMULATOR;

        UiAutomator2Options options = CapabilityFactory.getAndroidCapabilities(env);
        driver = new AndroidDriver(
            new URL(getAppiumUrl()), options
        );

        // Ensure app is in a known state
        ensureAppReady();
    }

    @AfterMethod(alwaysRun = true)
    public void tearDown(ITestResult result) {
        if (driver != null) {
            // Capture artifacts on failure
            if (!result.isSuccess()) {
                captureScreenshot(result.getMethod().getMethodName());
                capturePageSource(result.getMethod().getMethodName());
            }
            driver.quit();
        }
    }

    /**
     * Ensure the app is on the expected starting screen.
     * Handles cases where the app was left in an unexpected state.
     */
    private void ensureAppReady() {
        try {
            WebDriverWait shortWait = new WebDriverWait(driver, Duration.ofSeconds(5));
            shortWait.until(ExpectedConditions.or(
                ExpectedConditions.visibilityOfElementLocated(
                    AppiumBy.accessibilityId("homeScreenTitle")),
                ExpectedConditions.visibilityOfElementLocated(
                    AppiumBy.accessibilityId("emailInput"))
            ));
        } catch (TimeoutException e) {
            // App might be in a bad state — reset it
            driver.terminateApp("com.staynest.app");
            driver.activateApp("com.staynest.app");
        }
    }

    private String getAppiumUrl() {
        return IS_CI
            ? System.getenv("APPIUM_URL")
            : "http://localhost:4723";
    }

    private void captureScreenshot(String testName) {
        // ... screenshot capture logic ...
    }

    private void capturePageSource(String testName) {
        // ... page source capture logic ...
    }
}
```

## Failure and Debugging (Layer 4)

### Failure 1: Screen Object Returns Wrong Screen

**Symptom:** `loginScreen.login()` returns a `HomeScreen`, but the app actually shows an error message on the login screen.

**Root cause:** The `login()` method always returns `new HomeScreen(driver)` regardless of whether login succeeded.

<BestPractice>

**Fix:** Verify the screen transition before returning:

</BestPractice>



```java
// BROKEN: always returns HomeScreen
public HomeScreen login(String email, String password) {
    typeText(emailField, email);
    typeText(passwordField, password);
    tapElement(loginButton);
    return new HomeScreen(driver);  // what if login failed?
}

// FIXED: verify the transition
public HomeScreen login(String email, String password) {
    typeText(emailField, email);
    typeText(passwordField, password);
    hideKeyboard();
    tapElement(loginButton);

    HomeScreen home = new HomeScreen(driver);
    home.waitForScreenLoaded();  // throws if home screen doesn't appear
    return home;
}
```

### Failure 2: Tests Fail When Run in Sequence but Pass Individually

**Symptom:** Test B fails when run after Test A, but passes when run alone.

**Root cause:** Test A leaves the app in an unexpected state (e.g., on the booking screen instead of home). Test B assumes it starts from the login/home screen.

<BestPractice>

**Fix:** Each test's setup must ensure the app is in a known starting state. Use the `ensureAppReady()` pattern from the `MobileTestBase` above, or use `noReset: false` to clear app data between tests (slower but more reliable).

</BestPractice>

## Engineering Judgment (Layer 5)

### Choosing the Right Abstraction Level

| Scenario | Recommended Pattern | Why |
|---|---|---|
| Single platform, small app | Simple Screen Objects with direct locators | Over-engineering adds complexity without benefit |
| Cross-platform, same UX | Shared Screen Objects with locator maps | Maximum code reuse, minimal duplication |
| Cross-platform, different UX | Screen interfaces with platform-specific implementations | Tests share logic, screens handle platform differences |
| Large team, many screens | Screen Object + Component Objects (for reusable widgets) | Navigation bars, search bars, cards used across screens |

### Test Data Strategy for Mobile

Mobile tests need leaner data strategies than web:

- **Pre-seed via API:** Create test users, listings, and bookings via backend API in `@BeforeSuite`, not through the mobile UI. UI-based data creation is 10x slower.
- **Use deterministic test data:** Fixed user accounts (`test-sdet-001@staynest.com`) with known passwords. Random data makes failures harder to reproduce.
- **Account for offline scenarios:** If the app has offline mode, some tests should work with cached data — seed the data, put the device in airplane mode, then test.
- **Keep data small:** Mobile screens show fewer items than web. A test that needs to find a specific listing shouldn't require scrolling through 100 results — pre-filter or use a unique search term.

## Interview and Revision (Layer 6)

### Fundamental Questions

**Q1: How do you structure a mobile test automation framework?**

**A:** I use a layered architecture with four layers. At the bottom, a BaseScreen class provides common mobile utilities — explicit wait wrappers, gesture helpers (swipe, scroll, pull-to-refresh), keyboard management, and screen state checks. Screen Objects extend BaseScreen, encapsulating locators and interactions for each app screen — tests call `loginScreen.login(email, password)`, never raw `driver.findElement()`. A CapabilityFactory manages device configurations per environment (local, CI, cloud). Test classes focus purely on business logic and assertions. For cross-platform, I use an interface per screen with Android and iOS implementations, and a factory that creates the right one at runtime.

**Q2: What's the difference between the Page Object Model and the Screen Object Model?**

**A:** The principles are identical — encapsulation, single responsibility, fluent return types. The differences are in what the base class provides. A web BasePage typically handles page load waits and basic click/type operations. A mobile BaseScreen must also handle gestures (swipe, scroll, pinch), keyboard show/dismiss, system dialog handling, screen transitions (which are slower and animated), and platform-specific locator resolution. The naming convention changes from "Page" to "Screen" to reflect that mobile apps have screens, not pages — there's no URL, no refresh, no back-button-in-browser.

### Scenario-Based Questions

**S1: "You're building a mobile framework for an app that runs on both Android and iOS. How do you avoid maintaining two separate codebases?"**

**A:** I'd use a three-layer approach. First, an interface per screen — `LoginScreen` defines methods like `login()`, `getError()`, `isDisplayed()`. Second, platform-specific implementations — `AndroidLoginScreen` and `IOSLoginScreen` — each with their own locators and gesture implementations. Third, a ScreenFactory that uses the driver's platform capability to instantiate the right implementation. Tests only reference the interface: `LoginScreen login = ScreenFactory.loginScreen(driver)`. This way, test logic is 100% shared. Only the screen implementations diverge. If accessibility IDs are consistent across platforms (which I'd advocate for), many screen objects can be a single shared implementation.

Every screen object inherits these. |
| 2 | Why should screen object methods return the next screen object? | Fluent API pattern: `loginScreen.login(email, pass)` returns `HomeScreen`. API-seeded data is 10x faster than UI-created data. |
