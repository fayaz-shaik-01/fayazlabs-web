# App Lifecycle and Permissions

> **Module:** 06 — Mobile Automation > App Lifecycle and Permissions  
> **Prerequisites:** Gestures And Touch Actions, Native Mobile Fundamentals  
> **Mastery Target:** L3 (Independent) → L4 (Engineering Judgment)

---

## Quick Overview (Layer 1)

**What:** Mobile apps have a lifecycle — they launch (cold start), run in the foreground, get backgrounded, may be suspended by the OS, and can be killed entirely. Unlike web pages that live inside a browser tab, mobile apps must handle state transitions gracefully. Additionally, mobile platforms enforce a permission model — apps must request access to the camera, location, notifications, and storage through system dialogs that sit outside the app's UI. Testing these lifecycle transitions and permission flows is unique to mobile automation.

**Why it matters:** Real users don't use apps in a linear path. They switch between apps, get phone calls mid-booking, lock the screen, and open the app from a push notification. An SDET must verify the app preserves state through these transitions. Permission handling is equally critical — if the test can't get past the camera permission dialog, it can't test photo upload. Deep links let you skip navigation and launch directly to a specific screen, cutting test execution time dramatically.

**Where you encounter it:** Login state persistence after backgrounding. Booking flow interrupted by a phone call. Location-based search requiring GPS permission. Push notification testing. Deep link-based test setup. Any CI pipeline where app state between tests must be managed.

<MentalModel>

Think of the app lifecycle as a **traffic light for your app process**. Green = foreground (user interacting), yellow = background (still alive but not visible), red = killed (process terminated). Your tests must verify the app behaves correctly at each light change. Permissions are the **security checkpoints** — gates the OS places between your app and sensitive resources. Your test automation must either pre-approve these gates or handle the dialogs when they appear.

</MentalModel>


```
App Lifecycle States
────────────────────
Not Running → Cold Start → Foreground (Active)
                                ↕ (background/resume)
                           Background (Alive)
                                ↓ (OS kills for memory)
                           Suspended / Killed
```

<KeyTakeaways>

1. **Cold start vs. warm start** — cold start launches the app from scratch (slower, shows splash screen). Warm start resumes from background (faster, restores state). Both must be tested.
2. **Deep links bypass navigation** — launch the app to a specific screen (`staynest://listing/123`), saving minutes of test setup time.
3. **Permissions are platform-specific** — Android uses `autoGrantPermissions` or ADB commands. iOS uses auto-accept alerts or `simctl` privacy commands.
4. **`runAppInBackground()` simulates backgrounding** — Appium can push the app to background for a specified duration and bring it back.
5. **Push notification testing is possible** — you can trigger notifications via test APIs and verify tap behavior navigates to the correct screen.

</KeyTakeaways>

## First-Principles Explanation (Layer 2)

### App Lifecycle States

**Android lifecycle:**

| State | What Happens | Automation Relevance |
|---|---|---|
| Created | Activity created, UI inflating | Session creation; wait for elements |
| Resumed (Foreground) | User interacts with app | Normal test execution |
| Paused | Partially visible (dialog over it) | Permission dialogs cover the app |
| Stopped (Background) | Not visible, still in memory | `runAppInBackground()` simulates this |
| Destroyed | Process killed by OS or user | `terminateApp()` + `activateApp()` = cold restart |

**iOS lifecycle:**

| State | What Happens | Automation Relevance |
|---|---|---|
| Not Running | App process doesn't exist | Initial launch or after `terminateApp()` |
| Inactive | Transitioning (brief moment) | System dialogs (permissions) put app here |
| Active (Foreground) | User interacts | Normal test execution |
| Background | Running but not visible | `runAppInBackground()` |
| Suspended | In memory but not executing | OS may kill it; next launch may be cold |

### Deep Links

Deep links are URIs that open a specific screen in the app, bypassing all navigation. Instead of tapping through Home → Search → Results → Listing #123, a deep link like `staynest://listing/123` opens the listing directly.

**Types:**
- **Custom URI scheme:** `staynest://booking/456` — app registers the scheme.
- **Android App Links:** `https://staynest.com/listing/123` — verified by the OS via `assetlinks.json`.
- **iOS Universal Links:** `https://staynest.com/listing/123` — verified via `apple-app-site-association`.

**Why SDETs love deep links:** They turn 30-second navigation sequences into 1-second direct launches. Use them for test setup (get to the right screen fast) and for testing the deep link routing itself.

### Permissions Model

Modern mobile platforms enforce **runtime permissions** — the app must ask the user for access to sensitive resources when it first needs them.

**Android permissions:**
- Dangerous permissions (camera, location, contacts, storage) trigger a system dialog at runtime.
- Normal permissions (internet, Bluetooth) are granted at install time, no dialog.
- Once granted, a permission stays granted until the user revokes it in Settings.

**iOS permissions:**
- All sensitive permissions (camera, location, notifications, photos) trigger a system alert.
- The alert appears only once per app install — if denied, the user must go to Settings to enable it.
- Location has three options: "While Using the App", "Always", "Don't Allow".

## Practical Implementation (Layer 3)

### Testing App Lifecycle with Appium


```java
public class AppLifecycleTest {

    private AndroidDriver driver;

    @Test
    public void shouldPreserveBookingFormAfterBackgrounding() {
        // Navigate to booking screen and fill in data
        WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
        driver.findElement(AppiumBy.accessibilityId("searchField"))
              .sendKeys("Beach house");
        driver.findElement(AppiumBy.accessibilityId("searchButton")).click();
        wait.until(ExpectedConditions.visibilityOfElementLocated(
            AppiumBy.accessibilityId("firstListingCard")
        )).click();
        driver.findElement(AppiumBy.accessibilityId("bookNowButton")).click();

        // Fill booking form
        driver.findElement(AppiumBy.accessibilityId("guestCountInput"))
              .sendKeys("4");
        driver.findElement(AppiumBy.accessibilityId("specialRequests"))
              .sendKeys("Late check-in");

        // Background the app for 5 seconds (simulates user switching apps)
        driver.runAppInBackground(Duration.ofSeconds(5));

        // App should return to foreground with form data intact
        WebElement guestCount = driver.findElement(
            AppiumBy.accessibilityId("guestCountInput"));
        Assert.assertEquals(guestCount.getText(), "4");

        WebElement requests = driver.findElement(
            AppiumBy.accessibilityId("specialRequests"));
        Assert.assertEquals(requests.getText(), "Late check-in");
    }

    @Test
    public void shouldHandleColdStartAfterTermination() {
        // Log in first
        driver.findElement(AppiumBy.accessibilityId("emailInput"))
              .sendKeys("test@staynest.com");
        driver.findElement(AppiumBy.accessibilityId("passwordInput"))
              .sendKeys("password123");
        driver.findElement(AppiumBy.accessibilityId("loginButton")).click();

        WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
        wait.until(ExpectedConditions.visibilityOfElementLocated(
            AppiumBy.accessibilityId("homeScreenTitle")
        ));

        // Terminate the app (simulates OS killing it or user force-closing)
        driver.terminateApp("com.staynest.app");

        // Relaunch the app — this is a cold start
        driver.activateApp("com.staynest.app");

        // Verify the app restores session (user should still be logged in)
        WebElement homeTitle = wait.until(
            ExpectedConditions.visibilityOfElementLocated(
                AppiumBy.accessibilityId("homeScreenTitle")
            )
        );
        Assert.assertTrue(homeTitle.isDisplayed(),
            "User should remain logged in after cold start");
    }
}
```

### Deep Link Testing


```java
public class DeepLinkTest {

    private AndroidDriver driver;

    /**
     * Open a deep link on Android using ADB shell command.
     */
    private void openDeepLink(String url) {
        driver.executeScript("mobile: deepLink", Map.of(
            "url", url,
            "package", "com.staynest.app"
        ));
    }

    @Test
    public void shouldNavigateToListingViaDeepLink() {
        // Skip all navigation — go directly to listing #123
        openDeepLink("staynest://listing/123");

        WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
        WebElement title = wait.until(
            ExpectedConditions.visibilityOfElementLocated(
                AppiumBy.accessibilityId("listingTitle")
            )
        );
        Assert.assertEquals(title.getText(), "Luxury Beachfront Villa");
    }

    @Test
    public void shouldNavigateToBookingConfirmation() {
        // Deep link to booking confirmation screen
        openDeepLink("staynest://booking/456/confirmation");

        WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
        WebElement confirmationId = wait.until(
            ExpectedConditions.visibilityOfElementLocated(
                AppiumBy.accessibilityId("bookingConfirmationId")
            )
        );
        Assert.assertTrue(confirmationId.getText().contains("456"));
    }

    /**
     * iOS deep link — uses Safari URL bar approach.
     */
    private void openDeepLinkIOS(IOSDriver iosDriver, String url) {
        iosDriver.executeScript("mobile: deepLink", Map.of(
            "url", url,
            "bundleId", "com.staynest.app"
        ));
    }
}
```

### Permission Handling


```java
public class PermissionTest {

    /**
     * Android: auto-grant all permissions via capability.
     * Set this in setUp() — simplest approach.
     */
    private UiAutomator2Options autoGrantPermissions() {
        return new UiAutomator2Options()
            .setAutoGrantPermissions(true);
        // This grants all requested permissions at install time.
        // No permission dialogs will appear.
    }

    /**
     * Android: grant specific permission via ADB when autoGrant is too broad.
     */
    private void grantAndroidPermission(AndroidDriver driver, String permission) {
        driver.executeScript("mobile: shell", Map.of(
            "command", "pm",
            "args", List.of("grant", "com.staynest.app", permission)
        ));
    }

    /**
     * Android: revoke a permission to test denial flow.
     */
    private void revokeAndroidPermission(AndroidDriver driver, String permission) {
        driver.executeScript("mobile: shell", Map.of(
            "command", "pm",
            "args", List.of("revoke", "com.staynest.app", permission)
        ));
    }

    @Test
    public void shouldHandleCameraPermissionGrant() {
        AndroidDriver driver = getAndroidDriver(
            new UiAutomator2Options().setAutoGrantPermissions(false)
        );
        WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));

        // Navigate to profile photo upload
        driver.findElement(AppiumBy.accessibilityId("profileTab")).click();
        driver.findElement(AppiumBy.accessibilityId("changePhotoButton")).click();
        driver.findElement(AppiumBy.accessibilityId("takePhotoOption")).click();

        // System permission dialog appears — tap "Allow"
        WebElement allowButton = wait.until(
            ExpectedConditions.visibilityOfElementLocated(
                AppiumBy.id("com.android.permissioncontroller:id/permission_allow_foreground_only_button")
            )
        );
        allowButton.click();

        // Verify camera preview opens
        wait.until(ExpectedConditions.visibilityOfElementLocated(
            AppiumBy.accessibilityId("cameraPreview")
        ));
    }

    @Test
    public void shouldShowLocationPermissionRationale() {
        AndroidDriver driver = getAndroidDriver(
            new UiAutomator2Options().setAutoGrantPermissions(false)
        );

        // Revoke location permission to ensure dialog appears
        revokeAndroidPermission(driver,
            "android.permission.ACCESS_FINE_LOCATION");

        // Tap "Search Nearby" which requires location
        driver.findElement(AppiumBy.accessibilityId("searchNearbyButton")).click();

        // Verify the app shows a rationale before the system dialog
        WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
        WebElement rationale = wait.until(
            ExpectedConditions.visibilityOfElementLocated(
                AppiumBy.accessibilityId("locationRationaleText")
            )
        );
        Assert.assertTrue(rationale.getText().contains(
            "location to find nearby"));
    }

    /**
     * iOS: set permissions before app launch using simctl.
     * Run this before creating the Appium session.
     */
    // Terminal: xcrun simctl privacy <device-udid> grant location com.staynest.app
    // Terminal: xcrun simctl privacy <device-udid> grant camera com.staynest.app

    /**
     * iOS: handle permission alert during test using auto-accept capability.
     */
    private XCUITestOptions autoAcceptAlerts() {
        return new XCUITestOptions()
            .setAutoAcceptAlerts(true);
        // Automatically taps "Allow" on all iOS system alerts.
        // Use with caution — may dismiss alerts you want to verify.
    }
}
```

```java
public class NotificationTest {

    private AndroidDriver driver;

    @Test
    public void shouldDisplayBookingConfirmationNotification() {

            ExpectedConditions.visibilityOfElementLocated(
                AppiumBy.accessibilityId("bookingConfirmationId")
            )
        );
        Assert.assertTrue(confirmationScreen.getText().contains("456"));
    }
```

## Failure and Debugging (Layer 4)

### Failure 1: App State Lost After Background/Foreground Cycle

**Symptom:** Test fills a form, backgrounds the app, and resumes — but the form is empty.

**Diagnostic:** This is usually an app bug, not a test bug. Verify manually first. If the app genuinely loses state, that's a valid test failure to report.

**If it's a test issue:** Check that `runAppInBackground()` duration isn't too long — the OS may kill the app. On Android, check logcat for `ActivityManager: Killing <process>` messages during the background period.

### Failure 2: Permission Dialog Not Found

**Symptom:** `NoSuchElementException` when trying to tap the "Allow" button on a permission dialog.

**Common causes:**

| Cause | Fix |
|---|---|
| `autoGrantPermissions(true)` is set | Permission was already granted — no dialog appears. Set to `false` when testing permission flows. |
| Permission was previously granted | Use `revokeAndroidPermission()` before the test. On iOS, reset the simulator or use `simctl privacy reset`. |
| Wrong locator for system dialog | System dialog resource-ids vary by Android version. Check with Inspector. |
| iOS alert dismissed by `autoAcceptAlerts` | Disable `autoAcceptAlerts` when testing permission denial flows. |

### Failure 3: Deep Link Opens Browser Instead of App

**Symptom:** Deep link opens in the device's browser rather than the StayNest app.

**Root cause (Android):** The app's intent filter isn't properly configured for App Links, or the domain verification is failing. For custom scheme links (`staynest://`), the app might not be set as the default handler.

**Root cause (iOS):** Universal Links require the `apple-app-site-association` file to be hosted on the domain. If verification fails, iOS opens Safari instead.

**Fix for testing:** Use `mobile: deepLink` Appium command which opens the link through the app directly, bypassing browser routing. For custom scheme testing, use ADB: `adb shell am start -W -a android.intent.action.VIEW -d "staynest://listing/123" com.staynest.app`.

## Engineering Judgment (Layer 5)

### Permission Testing Strategy

Not every test should interact with permission dialogs. Here's when to use each approach:

| Strategy | When to Use | Trade-off |
|---|---|---|
| `autoGrantPermissions(true)` | Most functional tests — you're testing features, not permissions | Hides permission-related bugs |
| Grant via ADB/simctl before test | Tests that need specific permissions but not the dialog flow | Requires setup step; more control |
| Test the dialog interaction | Dedicated permission test suite | Slower; dialog locators vary by OS version |
| Test denial + rationale | Verify graceful degradation when permission is denied | Important UX path often missed |

**Recommendation:** Auto-grant permissions for 90% of your tests. Have a separate permission test suite (5-10 tests) that explicitly tests grant, deny, and rationale flows.

### Deep Links as Test Accelerators

Deep links are the most underused optimization in mobile testing. A typical navigation to a booking screen might take 15-20 seconds (launch → login → search → select listing → book). A deep link takes 1-2 seconds.

**Strategy:** Use deep links for test setup (get to the screen you want to test). Use traditional navigation only when you're testing the navigation flow itself. This can cut your overall suite runtime by 50-70%.

## Interview and Revision (Layer 6)

### Fundamental Questions

**Q1: How do you test app lifecycle transitions in mobile automation?**

**A:** Appium provides methods for lifecycle testing. `runAppInBackground(duration)` pushes the app to background and resumes it after the specified time — I use this to verify state preservation (form data, scroll position, login state). `terminateApp(bundleId)` kills the process entirely, and `activateApp(bundleId)` relaunches it — this simulates a cold start and tests whether the app properly restores session state from persistent storage. I test both warm start (background/resume) and cold start (kill/relaunch) because they exercise different state-saving mechanisms in the app.

**Q2: How do you handle permission dialogs in your test suite?**

**A:** I use a layered approach. For most functional tests, I set `autoGrantPermissions(true)` so permission dialogs never appear — the tests focus on features, not dialogs. For a dedicated permission test suite, I disable auto-grant and explicitly interact with the system dialogs. On Android, I use ADB commands to grant or revoke specific permissions before tests. On iOS, I use `simctl privacy` commands. I also test the denial path — verifying the app shows a rationale message and degrades gracefully without the permission. The key insight is that permission dialog locators vary by OS version, so I abstract them into platform-specific helpers.

### Scenario-Based Questions

**S1: "Your mobile tests take 45 minutes. The PM wants them under 15 minutes without cutting tests. What do you do?"**

**A:** The biggest time sink in mobile tests is navigation. I'd audit the suite and identify tests that spend most of their time navigating to a target screen. Then I'd implement deep link shortcuts — instead of tapping through 4-5 screens to reach a booking form, I'd deep link to `staynest://booking/new?listingId=123`. This alone can cut 60-70% of navigation time. I'd also ensure `noReset(true)` is set so the app isn't reinstalled between tests, and verify that test data is pre-seeded so tests don't waste time creating test state through the UI.
