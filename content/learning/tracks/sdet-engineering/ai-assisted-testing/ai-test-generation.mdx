# AI Test Generation

> **Module:** 10 — AI-Assisted Testing  
> **Prerequisites:** Ai Assisted Development, Test Design Techniques, Assertions And Test Oracles  
> **Mastery Target:** L3 (independent) — can use AI to generate tests from requirements or code and critically evaluate the output

---

## Quick Overview (2-minute read)

**What:** AI test generation is the practice of using LLMs to create test cases, test code, and test data from requirements documents, source code, or API specifications. It covers the spectrum from high-level scenario ideation to fully executable test methods.

**Why:** Writing tests is one of the most repetitive tasks in software engineering. AI can generate a first draft of 20 test methods in 30 seconds. But the draft is only valuable if you know how to evaluate it — AI-generated tests frequently have shallow assertions, miss edge cases, and contain hallucinated API calls. The skill isn't generating tests; it's generating *useful* tests and recognizing when the output falls short.

**Where:** Requirements-to-test-case mapping, unit test generation from source code, API test generation from OpenAPI specs, UI test scaffolding from page descriptions, and test data creation for complex domain models.

<MentalModel>

Think of AI test generation like a **first draft from a prolific but careless writer**. The writer produces 20 pages in an hour — impressive speed. But 5 pages are repetitive, 3 have factual errors, 2 contradict each other, and the remaining 10 need editing. You'd never publish the first draft. But you'd also never throw it away — it's faster to edit 20 pages than to write 10 from scratch. AI test generation works the same way: fast first drafts that require careful editing.

</MentalModel>


<KeyTakeaways>

1. AI can generate tests from two starting points: **requirements** (what the system should do) and **source code** (what it actually does). Both approaches have different strengths and gaps.
2. AI-generated tests tend toward happy-path coverage with shallow assertions. Edge cases, error handling, and security scenarios are consistently underrepresented.
3. The value chain: AI generates → you evaluate → you fix gaps → you run → you maintain. Skipping evaluation is how bad tests enter your suite.
4. AI is best at generating test *variations* once you provide one solid example that follows your project conventions.
5. Test data generation is AI's strongest use case — creating realistic, diverse, and boundary-value test data for complex domains.

</KeyTakeaways>

## First-Principles Explanation

### The Two Input Modes

#### Requirements → Tests (Black-Box)

You provide business rules, user stories, or acceptance criteria. AI generates test scenarios and optionally executable test code.

**Strengths:** Produces scenarios a human might overlook. Good at combinatorial thinking ("what about invalid email AND weak password at the same time?").

**Weaknesses:** AI doesn't know your API contracts, response shapes, or error codes unless you tell it. It generates plausible but potentially wrong assertions.

#### Source Code → Tests (White-Box)

You provide the actual implementation code. AI generates unit tests or integration tests that exercise the code paths.

**Strengths:** Can identify branches, conditions, and edge cases by reading the code. Tests are more likely to match actual method signatures.

**Weaknesses:** Tests may simply mirror the implementation rather than testing behavior. If the code has a bug, AI-generated tests may encode that bug as "expected" behavior.

### Quality Characteristics of AI-Generated Tests

| Characteristic | AI Typical Quality | What "Good" Looks Like |
|---|---|---|
| **Compiles** | ~85% of the time | 100% — always compiles |
| **Runs** | ~70% of the time | 100% — always runs without infrastructure issues |
| **Meaningful assertions** | ~50% | Every assertion verifies a business requirement |
| **Edge cases** | ~30% coverage | Boundary values, nulls, empty strings, max lengths |
| **Realistic test data** | ~40% | Data that represents real usage, not "test123" |
| **Project conventions** | ~10% without context | Follows naming, structure, and patterns consistently |
| **Cleanup** | ~20% | Every test cleans up resources it creates |

### Why AI Tests Are Shallow

LLMs optimize for *plausibility*, not *correctness*. A test that asserts `status == 200` looks correct to the model because millions of training examples do exactly that. But a test that asserts the response body contains a specific field with a specific format is rarer in training data, so AI produces it less often.

This means AI consistently produces tests that:
- Assert status codes but not response bodies
- Assert presence but not correctness ("field exists" vs "field equals expected value")
- Cover happy paths but skip error paths
- Use generic test data ("John Doe", "test@test.com") instead of boundary values

## Practical Implementation

### Generating Tests from Requirements: StayNest Signup

**The requirement:**
> Users can register for StayNest by providing email, password, first name, and last name. Email must be valid format and unique. Password must be at least 8 characters with one uppercase letter and one number. First and last name are required, 1-50 characters each.

**The prompt:**


```markdown
Generate API integration tests for StayNest user registration.

Endpoint: POST /api/v1/auth/register
Tech Stack: Java 17, JUnit 5, RestAssured, AssertJ
Request body: { "email": string, "password": string, "firstName": string, "lastName": string }

Success response (201):
{ "userId": "uuid-string", "email": "user@example.com", "firstName": "Jane", "lastName": "Doe" }

Validation rules:
- email: valid format, unique across system
- password: min 8 chars, at least 1 uppercase, at least 1 number
- firstName: required, 1-50 chars
- lastName: required, 1-50 chars

Error response (400): { "errors": [{ "field": "email", "message": "Invalid email format" }] }
Duplicate email (409): { "error": "Email already registered" }

Project conventions:
- @DisplayName on every test
- AssertJ assertions (assertThat)
- Builder pattern for request bodies: RegisterRequest.builder().email("...").build()
- Test data uses UUID suffix for uniqueness: "user-" + UUID.randomUUID() + "@test.com"
- Cleanup: DELETE /api/v1/admin/users/{userId} in @AfterEach

Write tests covering: happy path, all validation failures, duplicate email, boundary values.
```

**What AI typically generates (with typical quality issues):**


```java
@ExtendWith(RestAssuredExtension.class)
class RegistrationApiTest {

    private String createdUserId;

    @AfterEach
    void cleanup() {
        if (createdUserId != null) {
            given()
                .pathParam("userId", createdUserId)
                .when()
                .delete("/api/v1/admin/users/{userId}")
                .then()
                .statusCode(204);
        }
    }

    @Test
    @DisplayName("Should register user with valid data")
    void shouldRegisterUser() {
        String uniqueEmail = "user-" + UUID.randomUUID() + "@test.com";

        RegisterRequest request = RegisterRequest.builder()
            .email(uniqueEmail)
            .password("Password1")
            .firstName("Jane")
            .lastName("Doe")
            .build();

        Response response = given()
            .contentType(ContentType.JSON)
            .body(request)
            .when()
            .post("/api/v1/auth/register");

        assertThat(response.statusCode()).isEqualTo(201);

        // ISSUE 1: Extracts userId but doesn't assert its format
        createdUserId = response.jsonPath().getString("userId");

        // ISSUE 2: Doesn't verify email, firstName, lastName in response
        assertThat(createdUserId).isNotNull();
    }

    @Test
    @DisplayName("Should return 400 for invalid email")
    void shouldRejectInvalidEmail() {
        RegisterRequest request = RegisterRequest.builder()
            .email("not-an-email")        // Only one invalid format tested
            .password("Password1")
            .firstName("Jane")
            .lastName("Doe")
            .build();

        Response response = given()
            .contentType(ContentType.JSON)
            .body(request)
            .when()
            .post("/api/v1/auth/register");

        assertThat(response.statusCode()).isEqualTo(400);
        // ISSUE 3: Doesn't verify the error body — which field? what message?
    }

    @Test
    @DisplayName("Should return 400 for weak password")
    void shouldRejectWeakPassword() {
        RegisterRequest request = RegisterRequest.builder()
            .email("user-" + UUID.randomUUID() + "@test.com")
            .password("weak")             // Only tests "too short"
            .firstName("Jane")
            .lastName("Doe")
            .build();

        // ISSUE 4: Doesn't test "no uppercase" or "no number" separately
        assertThat(given()
            .contentType(ContentType.JSON)
            .body(request)
            .when()
            .post("/api/v1/auth/register")
            .statusCode()).isEqualTo(400);
    }

    // ISSUE 5: No test for missing firstName/lastName
    // ISSUE 6: No test for boundary values (1-char name, 50-char name, 51-char name)
    // ISSUE 7: No test for empty string vs null
    // ISSUE 8: No duplicate email test despite being in the prompt
}
```

### Critical Evaluation of the Generated Tests

| Issue | Category | Impact |
|---|---|---|
| Doesn't verify response body fields | Shallow assertion | Real bugs in response mapping go undetected |
| Doesn't verify error body structure | Shallow assertion | Error response format could break without detection |
| Only one invalid email format | Missing edge cases | "missing@domain", "@nodomain.com", empty string not tested |
| Only "too short" password tested | Missing edge cases | "nouppercase1", "NONUMBER!" patterns not covered |
| No missing field tests | Missing scenarios | Required field validation entirely untested |
| No boundary value tests | Missing edge cases | 1-char, 50-char, 51-char names not tested |
| No duplicate email test | Missing scenario | Core business rule untested despite being in requirements |
| No null vs empty distinction | Missing edge case | Server may handle null and "" differently |

### What the Tests Should Look Like After Human Review


```java
@Test
@DisplayName("Should register user and return complete profile")
void shouldRegisterUser() {
    String uniqueEmail = "user-" + UUID.randomUUID() + "@test.com";

    RegisterRequest request = RegisterRequest.builder()
        .email(uniqueEmail)
        .password("SecurePass1")
        .firstName("Jane")
        .lastName("Doe")
        .build();

    Response response = given()
        .contentType(ContentType.JSON)
        .body(request)
        .when()
        .post("/api/v1/auth/register");

    assertThat(response.statusCode()).isEqualTo(201);
    assertThat(response.jsonPath().getString("userId")).matches(UUID_PATTERN);
    assertThat(response.jsonPath().getString("email")).isEqualTo(uniqueEmail);
    assertThat(response.jsonPath().getString("firstName")).isEqualTo("Jane");
    assertThat(response.jsonPath().getString("lastName")).isEqualTo("Doe");

    createdUserId = response.jsonPath().getString("userId");
}

@ParameterizedTest(name = "Should reject invalid email: {0}")
@ValueSource(strings = {"not-an-email", "missing@", "@nodomain.com", "spaces in@email.com", ""})
@DisplayName("Should reject invalid email formats")
void shouldRejectInvalidEmail(String invalidEmail) {
    RegisterRequest request = defaultValidRequest().email(invalidEmail).build();

    Response response = given()
        .contentType(ContentType.JSON)
        .body(request)
        .when()
        .post("/api/v1/auth/register");

    assertThat(response.statusCode()).isEqualTo(400);
    assertThat(response.jsonPath().getString("errors[0].field")).isEqualTo("email");
}
```

### Generating Test Data with AI

AI is particularly effective at generating test data. This is its strongest testing use case.


```markdown
## Test Data Prompt

"Generate 15 test email addresses for testing email validation. Include:
- 3 valid emails (different domains, formats)
- 3 missing @ symbol variations
- 3 missing domain variations  
- 2 with special characters that are valid per RFC 5321
- 2 with special characters that are invalid
- 2 boundary cases (very long, very short)

Format as a Java String array."
```

AI will produce diverse, realistic test data much faster than you'd write it manually, and it's easy to verify correctness by visual inspection.

## Failure and Debugging

### The "Tests Pass but Test Nothing" Problem


```java
// AI-generated test that always passes but never catches bugs
@Test
@DisplayName("Should handle booking creation")
void shouldCreateBooking() {
    Response response = given()
        .contentType(ContentType.JSON)
        .body(bookingRequest)
        .when()
        .post("/api/v1/bookings");

    // PROBLEM: This assertion passes even if the endpoint returns an error
    assertThat(response).isNotNull();  // Response object is never null in RestAssured
}
```

**Expected:** Test catches booking creation bugs.  
**Actual:** Test passes regardless of server response. A 500 error, a 400 validation failure, even a connection timeout would still produce a non-null Response object.

**Root cause:** AI generated the most generic assertion possible. `isNotNull()` on a RestAssured Response is a tautology — it can never be null.

**Corrected Implementation:**


```java
@Test
@DisplayName("Should create booking with confirmed status")
void shouldCreateBooking() {
    Response response = given()
        .contentType(ContentType.JSON)
        .body(bookingRequest)
        .when()
        .post("/api/v1/bookings");

    assertThat(response.statusCode()).isEqualTo(201);
    assertThat(response.jsonPath().getString("status")).isEqualTo("CONFIRMED");
    assertThat(response.jsonPath().getString("bookingId")).matches(UUID_PATTERN);
    assertThat(response.jsonPath().getString("propertyId")).isEqualTo(bookingRequest.getPropertyId());
    assertThat(response.jsonPath().getString("checkIn")).isEqualTo(bookingRequest.getCheckIn());
    assertThat(response.jsonPath().getString("checkOut")).isEqualTo(bookingRequest.getCheckOut());
}
```

### Prevention

Before accepting any AI-generated test, ask: "If the system under test were broken, would this test fail?" If the answer is "not necessarily," the assertions are too shallow.

## Engineering Judgment

### When to Use AI Test Generation

| Scenario | AI Value | Approach |
|---|---|---|
| CRUD endpoint tests | **High** — patterns are predictable | Generate all, review assertions |
| Parameterized test variations | **High** — AI excels at data variations | Provide one example, ask for 10 more |
| Test data creation | **Very high** — AI generates diverse realistic data | Generate and spot-check |
| Complex workflow tests | **Low** — AI lacks domain context | Write manually, use AI for boilerplate only |
| Security test scenarios | **Low** — AI may miss subtle vectors | Use AI for ideas, write tests yourself |

### The 80/20 Rule of AI Test Generation

AI typically generates 80% of the scaffolding (imports, class structure, method signatures, basic happy path) correctly. The remaining 20% — meaningful assertions, edge cases, project-specific patterns — is where you spend your review time. Accept this ratio. Don't expect 100% usable output.

### Common Overengineering Mistakes

- Generating 50 tests with AI when 10 well-chosen tests would provide the same coverage.
- Using AI to generate tests for trivially simple code where the test is more complex than the code itself.
- Trusting AI-generated test data for security tests (AI may generate "safe" payloads that don't actually test vulnerabilities).
- Iterating on prompts for 20 minutes to get AI to produce perfect tests, when writing them directly would take 10 minutes.

## Interview and Revision

### Questions and Answers

**Q1: How would you use AI to generate tests for a new API endpoint?**

**A:** I'd start by writing a detailed prompt with the endpoint contract (method, path, request/response shapes, status codes), business rules, and our project conventions (framework, assertion style, naming). I'd generate the first batch, then evaluate each test against an 8-point checklist: compiles, runs, meaningful assertions, edge cases, realistic data, project conventions, cleanup, trustworthy failure signal. I'd fix the gaps — typically shallow assertions and missing edge cases — then run the suite and verify each test fails when it should.

**Q2: What are the typical gaps in AI-generated tests?**

**A:** Three consistent gaps: shallow assertions (status code only, no body verification), missing edge cases (no boundary values, no null handling, no empty strings), and missing error path tests (AI covers happy paths but skips 409s, 403s, and validation errors). Additionally, AI rarely generates cleanup logic and almost never follows project-specific conventions unless explicitly told.

**Q3: Would you trust AI to generate your entire test suite?**

**A:** No. I'd trust AI to generate the first draft — boilerplate, happy paths, and test data. But I'd never trust it as the final authority on what to test or how to assert. AI doesn't understand business risk, so it can't prioritize which scenarios matter most. It doesn't understand your system's failure modes, so it can't write tests that target known weaknesses. I'd use AI for speed, then apply human judgment for completeness and correctness.




**Flashcard 1**
**Q:** What are the two input modes for AI test generation?
**A:** Requirements → Tests (black-box: business rules in, test scenarios out) and Source Code → Tests (white-box: implementation in, unit tests out). Requirements mode needs explicit contracts. Code mode risks encoding existing bugs as expected behavior.

**Flashcard 2**
**Q:** What is the most common quality issue in AI-generated tests?
**A:** Shallow assertions — asserting status codes but not response bodies, asserting presence but not correctness. A test that only checks `status == 200` passes even when the response body is completely wrong.

**Flashcard 3**
**Q:** What is AI's strongest use case in test generation?
**A:** Test data generation — creating diverse, realistic, boundary-value test data for complex domains. It's easy to verify by visual inspection and AI produces better variety than most humans would manually.
