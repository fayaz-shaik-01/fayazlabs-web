# Evaluating Generated Tests

> **Module:** 10 — AI-Assisted Testing  
> **Prerequisites:** Ai Test Generation, Assertions And Test Oracles, Test Design Techniques  
> **Mastery Target:** L3 (independent) — can systematically evaluate AI-generated tests and identify all categories of quality issues

---

## Quick Overview (2-minute read)

**What:** Evaluating generated tests is the discipline of systematically reviewing AI-produced test code against a defined quality checklist before accepting it into your test suite. It covers both automated checks (compilation, linting, execution) and human judgment (assertion quality, coverage completeness, maintainability).

**Why:** AI-generated tests that enter your suite without evaluation are technical debt from day one. They create false confidence — the test count goes up, the coverage metric improves, but the actual defect detection capability doesn't change. Worse, bad AI tests that always pass train the team to ignore test results. Evaluation is the quality gate between "AI wrote some tests" and "we have reliable tests."

**Where:** Every code review that includes AI-generated tests, every PR that uses Copilot suggestions, every batch of tests generated from requirements, and every refactoring where AI rewrites test logic.

<MentalModel>

Think of evaluating AI tests like **food inspection at a restaurant supply warehouse**. The food arrives in bulk — it looks fine from the outside. But the inspector checks expiration dates (does it compile?), opens sample packages to inspect quality (are assertions meaningful?), tests temperature (does it run?), and verifies the supplier's claims match the actual contents (does it test what it claims to test?). The inspection takes a fraction of the time it took to produce the food, but without it, the restaurant serves spoiled meals.

</MentalModel>


<KeyTakeaways>

1. Every AI-generated test must pass 8 evaluation criteria before it enters the test suite.
2. The most dangerous AI test is one that always passes — it provides false confidence without catching any bugs.
3. Automated checks (compilation, lint, execution) catch ~40% of issues. Human review catches the remaining 60%.
4. The evaluation habit must be fast — 30-60 seconds per test method — or teams will skip it.
5. Common AI failure patterns are predictable: hallucinated APIs, wrong method signatures, shallow assertions, missing imports. Knowing the patterns makes review faster.

</KeyTakeaways>

## First-Principles Explanation

### The 8-Criteria Evaluation Checklist

Every AI-generated test must pass all 8 criteria:

#### Criterion 1: Compiles and Runs Without Errors

The absolute minimum. AI frequently generates code that references non-existent classes, uses wrong method signatures, or imports packages that don't exist in your project.

**What to check:**
- All imports resolve to actual classes in your classpath
- Method signatures match the real API (parameter types, return types, exceptions)
- No syntax errors, unclosed brackets, or mismatched generics

**Quick test:** Run `mvn compile` or your equivalent. If it fails, the test fails criterion 1.

#### Criterion 2: Meaningful Assertions

The test must assert something that would fail if the system had a real bug. `assertNotNull(response)` is almost never meaningful for API tests because the response object exists even for errors.

**What to check:**
- Assertions verify specific field values, not just existence
- Status codes AND response body content are asserted
- Assertions match the business requirements, not just implementation details

**Red flags:** `isNotNull()`, `isNotEmpty()`, `assertTrue(true)`, assertions on framework objects rather than business values.

#### Criterion 3: Edge Cases Covered

AI defaults to happy paths. A test suite without edge cases misses the bugs that matter most.

**What to check:**
- Boundary values tested (0, 1, max, max+1)
- Null and empty string handling
- Invalid format inputs
- Combinations of valid and invalid fields

#### Criterion 4: Realistic Test Data

`"test"`, `"test@test.com"`, `"John Doe"` are not realistic test data. They don't exercise unicode handling, length boundaries, or real-world formats.

**What to check:**
- Email addresses use UUID or timestamp suffixes for uniqueness
- Names include reasonable variety (not always "John Doe")
- Numeric values include boundaries, not just arbitrary middle values
- Dates consider timezone and calendar boundary issues

#### Criterion 5: Stable Selectors/Locators (UI Tests)

AI-generated UI tests frequently use fragile locators — XPath based on DOM structure, CSS selectors based on styling classes, or indexes that break when the page layout changes.

**What to check:**
- Uses `data-testid`, `aria-label`, or semantic HTML selectors
- No XPath with positional indexes (`//div[3]/span[2]`)
- No CSS selectors tied to styling (`div.btn-primary.ml-3`)
- Locators match your page object conventions

#### Criterion 6: Follows Project Conventions

AI doesn't know your project conventions unless you tell it. Even when you do, it often drifts to "generic best practices" that contradict your team's patterns.

**What to check:**
- Naming conventions match existing tests
- Test structure follows your team's pattern (AAA, Given-When-Then)
- Uses project utility methods instead of raw framework calls
- Logging, tagging, and categorization match your standards

#### Criterion 7: Cleanup Handled

AI rarely generates cleanup code. Tests that create data without cleanup cause shared state issues and test pollution.

**What to check:**
- `@AfterEach` or equivalent cleans up created resources
- Database records, files, and sessions are cleaned
- Cleanup is in a `finally` block or teardown method (not after assertions that might fail)

#### Criterion 8: Trustworthy Failure Signal

The most important criterion: when this test fails, does the failure message tell you exactly what's wrong?

**What to check:**
- Failure messages are descriptive (not just "expected true but was false")
- Each test tests one thing — a failure points to one specific cause
- The test actually fails when the system is broken (run it against a broken implementation)

### Common AI Failure Patterns

| Pattern | Example | Why It Happens | Detection |
|---|---|---|---|
| **Hallucinated API** | `driver.waitForStable()` | AI blends methods from different frameworks | Compilation fails |
| **Wrong method signature** | `findElement(By.css("div"))` | AI uses Playwright syntax in Selenium context | Compilation or runtime error |
| **Missing imports** | Uses `Assertions.assertThat()` without import | AI assumes imports are implicit | Compilation fails |
| **Always-pass assertion** | `assertThat(response).isNotNull()` | AI picks the safest assertion | Human review required |
| **Wrong HTTP method** | `GET` for a create operation | AI confuses CRUD patterns | Human review of API contract |
| **Hardcoded test data** | `"user123@test.com"` in every test | AI doesn't think about parallel execution | Human review for uniqueness |
| **Outdated API version** | Uses v1 endpoint when v2 is current | Training data cutoff | Check against current API docs |
| **Copy-paste test names** | Three tests all named `shouldWork` | AI ran out of creative names | Human review of `@DisplayName` |

## Practical Implementation

### Evaluation Exercise: Review These AI-Generated Tests

The following test class was generated by AI for StayNest's property search endpoint. Each test has at least one issue. Identify and fix them all.


```java
// AI-GENERATED — REVIEW REQUIRED
@ExtendWith(SpringExtension.class)
class PropertySearchApiTest {

    // TEST 1: Search by city
    @Test
    @DisplayName("Search properties by city")
    void testSearchByCity() {
        Response response = given()
            .queryParam("city", "Tokyo")
            .when()
            .get("/api/v1/properties/search");

        assertThat(response.statusCode()).isEqualTo(200);
        assertThat(response.jsonPath().getList("results")).isNotNull();
        // ISSUE A: ________________________________________________
    }

    // TEST 2: Search with date range
    @Test
    @DisplayName("Search properties with date range")
    void testSearchWithDates() {
        Response response = given()
            .queryParam("city", "Tokyo")
            .queryParam("checkIn", "2025-08-01")
            .queryParam("checkOut", "2025-08-05")
            .when()
            .get("/api/v1/properties/search");

        assertEquals(200, response.statusCode());
        // ISSUE B: ________________________________________________
    }

    // TEST 3: Search with invalid dates
    @Test
    @DisplayName("Should return error for checkout before checkin")
    void testInvalidDateRange() {
        Response response = given()
            .queryParam("city", "Tokyo")
            .queryParam("checkIn", "2025-08-05")
            .queryParam("checkOut", "2025-08-01")
            .when()
            .get("/api/v1/properties/search");

        assertThat(response.statusCode()).isEqualTo(400);
        // ISSUE C: ________________________________________________
    }

    // TEST 4: Search with guests count
    @Test
    @DisplayName("Search for property")
    void searchProperty() {
        Response response = given()
            .queryParam("city", "Tokyo")
            .queryParam("guests", 5)
            .when()
            .get("/api/v1/properties/search");

        assertThat(response).isNotNull();
        // ISSUE D: ________________________________________________
    }

    // TEST 5: Search with no results
    @Test
    @DisplayName("Should return empty results for unknown city")
    void testNoResults() {
        Response response = given()
            .queryParam("city", "Xyzzyville")
            .when()
            .get("/api/v1/properties/search");

        assertThat(response.statusCode()).isEqualTo(200);
        assertThat(response.jsonPath().getList("results").size()).isEqualTo(0);
        // This one is actually okay — but what's missing overall?
        // ISSUE E: ________________________________________________
    }
}
```

### Answer Key

| Issue | Criterion Violated | Problem | Fix |
|---|---|---|---|
| **A** | #2 Meaningful assertions | `isNotNull()` on a list is meaningless — check size > 0, verify result structure | Assert `results.size() > 0`, verify each result has `propertyId`, `name`, `city` fields |
| **B** | #6 Project conventions | Uses JUnit `assertEquals` instead of AssertJ `assertThat` — mixing assertion styles | Use `assertThat(response.statusCode()).isEqualTo(200)` consistently |
| **C** | #2 Meaningful assertions | Asserts 400 status but doesn't verify error message explains *why* it's 400 | Assert `response.jsonPath().getString("error")` contains "checkout" or "date range" |
| **D** | #2 Meaningful assertions + #6 Conventions | `isNotNull()` on Response is a tautology; `@DisplayName` is generic; method name doesn't follow pattern | Assert status, response body structure, property capacity >= 5; fix DisplayName and method name |
| **E** | #3 Edge cases (suite-level) | Individual test is fine, but the suite is missing: no city parameter, empty city, special characters in city, guests=0, guests=-1 | Add parameterized edge case tests |

### Automated Evaluation Pipeline


```bash
#!/bin/bash
# automated-test-evaluation.sh
# Run this on AI-generated test files before committing

echo "=== AI Test Evaluation Pipeline ==="

# Criterion 1: Compiles
echo "[1/4] Compilation check..."
mvn compile -pl test-module -q
if [ $? -ne 0 ]; then
    echo "FAIL: AI-generated tests do not compile"
    exit 1
fi

# Criterion 6: Conventions (lint)
echo "[2/4] Lint check..."
mvn checkstyle:check -pl test-module -q
if [ $? -ne 0 ]; then
    echo "WARN: Convention violations detected — review checkstyle report"
fi

# Criterion 1+8: Runs and produces failures when expected
echo "[3/4] Execution check..."
mvn test -pl test-module -Dtest="*AiGenerated*" -q
if [ $? -ne 0 ]; then
    echo "FAIL: AI-generated tests fail during execution"
    exit 1
fi

# Criterion 2: Assertion quality (heuristic)
echo "[4/4] Shallow assertion scan..."
grep -rn "isNotNull()" src/test/ --include="*.java" | grep -i "response\|result"
grep -rn "assertTrue(true)" src/test/ --include="*.java"
grep -rn "assertNotNull(given" src/test/ --include="*.java"
echo "Review any matches above for shallow assertions"

echo "=== Pipeline complete — manual review required for criteria 2-5, 7-8 ==="
```

## Failure and Debugging

### The "100% Pass Rate" False Confidence

**Scenario:** Your team adopts AI test generation. In one sprint, you generate 200 new tests. All 200 pass. Test coverage jumps from 65% to 82%. Everyone celebrates.

Two weeks later, a critical bug ships to production. The bug is in a code path covered by 3 of the AI-generated tests. All 3 passed, even with the bug present.

**Root cause:** The 3 tests had tautological assertions:


```java
// All three tests had this pattern
assertThat(response.statusCode()).isIn(200, 201, 400, 404, 500);
// This assertion passes for ANY status code the server returns
```

**Why this happens:** AI, when uncertain about the expected status code, sometimes generates overly permissive assertions. The test "passes" regardless of server behavior.

**Detection:** The "mutation test" approach — deliberately break the system under test and verify the test fails. If you change the endpoint to return 500 for everything and the test still passes, the test is worthless.

<BestPractice>

**Prevention:** For every AI-generated test, mentally ask: "What would the server need to return for this test to fail?" If the answer is "almost nothing," the assertion is too weak.

</BestPractice>


### Diagnostic Steps for Evaluating Unfamiliar AI Output

1. **Read the test name and DisplayName.** Does it clearly state what's being tested?
2. **Read the assertions FIRST, before the setup.** What exactly is being verified?
3. **Check: does the assertion match the DisplayName?** A test named "should validate email format" that only checks status 200 is lying.
4. **Check: are there assertions at all?** AI sometimes generates tests with no assertions — just API calls.
5. **Run it.** Compilation and execution catch 40% of issues.
6. **Break the system.** Return wrong data from the endpoint. Does the test fail? This catches 50% of what's left.
7. **Compare to requirements.** Does the test verify the actual business rule, or just technical details?

## Engineering Judgment

### Evaluation Depth vs Speed

Not every AI-generated test needs the same evaluation depth. Allocate review time based on risk:

| Test Type | Evaluation Depth | Time Per Test | Rationale |
|---|---|---|---|
| Happy path CRUD tests | Light — check assertions | 15 seconds | Patterns are predictable, AI does these well |
| Validation/error tests | Medium — check specific error codes and messages | 30 seconds | AI often gets status codes right but misses error body details |
| Business logic tests | Deep — verify against requirements | 60 seconds | AI doesn't understand domain rules |
| Security tests | Full re-examination | 2-3 minutes | AI may generate tests that look like security tests but miss real vulnerabilities |
| Data cleanup tests | Medium — verify teardown completeness | 30 seconds | AI frequently forgets cleanup |

### When to Regenerate vs When to Fix

- **Regenerate** when the AI fundamentally misunderstood the requirement (testing the wrong endpoint, wrong HTTP method, wrong business rule).
- **Fix** when the structure is correct but assertions are shallow or edge cases are missing — this is faster than regenerating and re-reviewing.
- **Write manually** when AI has failed twice on the same test — spending more time on prompts is not productive.

### Common Overengineering Mistakes

- Building a complex automated evaluation framework when a simple checklist and `mvn compile` would suffice.
- Spending 10 minutes evaluating a test that would take 3 minutes to write from scratch.
- Creating evaluation metrics (AI test quality score) that nobody looks at after the first week.

## Interview and Revision

### Questions and Answers

**Q1: How do you evaluate AI-generated test code before merging it?**

**A:** I use an 8-point checklist: compilation, meaningful assertions, edge case coverage, realistic test data, stable selectors, project conventions, cleanup handling, and trustworthy failure signal. The first check is automated — compile and run. The remaining checks require human review. The most critical criterion is #8: would a real bug cause this test to fail with a message that tells me what's wrong? If not, the test provides false confidence and is worse than no test at all.

**Q2: What's the most common problem you see in AI-generated tests?**

**A:** Shallow assertions — tests that check `status 200` but never verify the response body. They pass even when the server returns completely wrong data. I've seen AI generate `assertThat(response).isNotNull()` as the only assertion — that's a tautology in RestAssured because the Response object is never null. The fix is to always assert specific business values: field names, field values, data formats, and error messages.

**Q3: How do you know if an AI-generated test is actually catching bugs?**

**A:** I use the mutation approach: I mentally (or actually) break the system under test and check whether the test would fail. If I change the endpoint to return `"status": "CANCELLED"` instead of `"status": "CONFIRMED"` and the test still passes, it's not catching anything. Every meaningful test should have at least one assertion that would fail if the system behavior changed in a way that violates the business requirement.




**Flashcard 1**
**Q:** Name the 8 evaluation criteria for AI-generated tests.
**A:** 1) Compiles/runs, 2) Meaningful assertions, 3) Edge cases covered, 4) Realistic test data, 5) Stable selectors, 6) Project conventions, 7) Cleanup handled, 8) Trustworthy failure signal.

**Flashcard 2**
**Q:** What is a tautological assertion?
**A:** An assertion that can never fail regardless of system behavior. Example: `assertThat(response).isNotNull()` in RestAssured — the Response object is always non-null. These provide zero defect detection value.

**Flashcard 3**
**Q:** How do you verify an AI-generated test actually catches bugs?
**A:** The mutation approach: deliberately break the system under test (return wrong data, wrong status code, wrong field values) and verify the test fails with a clear message. If the test still passes with broken input, its assertions are too weak.
