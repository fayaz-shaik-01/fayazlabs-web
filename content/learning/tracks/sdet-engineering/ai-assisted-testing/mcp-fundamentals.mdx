# MCP Fundamentals

> **Module:** 10 — AI-Assisted Testing

> **Mastery Target:** L2 (guided) — can explain MCP architecture, understand tool calling, and identify testing-relevant MCP integrations

## Quick Overview (2-minute read)

**What:** The Model Context Protocol (MCP) is an open standard for connecting AI models to external tools and data sources. It defines a client-server architecture where the AI model (client) can request to use tools (functions on MCP servers) and read resources (structured data). MCP is how AI agents interact with the outside world — reading files, querying databases, calling APIs, and controlling browsers.

**Why:** Without MCP (or equivalent protocols), AI is limited to generating text. It can write code but can't run it. It can suggest a query but can't execute it. MCP bridges this gap, turning assistants into agents. For test automation, MCP enables AI to interact with your actual test infrastructure — running tests via CI, reading failure logs from GitHub, creating issues in Jira, and even driving browsers through Playwright.

**Where:** AI development environments (Cursor, Windsurf, Claude Desktop), CI/CD pipeline integrations, test infrastructure tooling, and any workflow where AI needs to interact with external systems.

<MentalModel>

Think of MCP like **USB for AI**. Before USB, every device needed its own proprietary cable and driver. Printers, scanners, keyboards — each required custom integration. USB standardized the connection: any device that speaks USB works with any computer that has a USB port. MCP does the same for AI tools: any AI model that speaks MCP can use any tool that exposes an MCP server. Instead of building custom integrations between Claude and GitHub, Claude and Jira, Claude and Playwright — each tool implements one MCP server, and any MCP-compatible AI model can use it.

</MentalModel>


<KeyTakeaways>

1. MCP is a protocol (like HTTP), not a product. Any AI model can be an MCP client; any tool can be an MCP server.
2. The two core primitives: **tools** (functions the AI can call) and **resources** (data the AI can read).
3. Tool calling follows a request-approve-execute-return cycle. The AI requests a tool call; the system (or human) approves it; the tool executes; results return to the AI.
4. MCP matters for testing because it's how AI agents can run tests, read CI logs, create bug reports, and interact with test infrastructure.
5. Security is the MCP user's responsibility, not the protocol's. MCP defines *how* tools are called, not *whether* they should be.

</KeyTakeaways>

## First-Principles Explanation

### MCP Architecture

```
┌─────────────────────────────────────────────────────┐
│                    HOST APPLICATION                  │
│  (Cursor, Windsurf, Claude Desktop, custom app)     │
│                                                      │
│  ┌──────────────┐                                    │
│  │   AI MODEL   │  "I need to read the test results" │
│  │   (Client)   │                                    │
│  └──────┬───────┘                                    │
│         │ MCP Protocol                               │
│  ┌──────┴───────┐  ┌──────────────┐  ┌────────────┐│
│  │  MCP Server  │  │  MCP Server  │  │ MCP Server ││
│  │   GitHub     │  │   Jira       │  │ Playwright ││
│  │  - read PRs  │  │ - create     │  │ - navigate ││
│  │  - read logs │  │   issues     │  │ - click    ││
│  │  - list runs │  │ - read board │  │ - assert   ││
│  └──────────────┘  └──────────────┘  └────────────┘│
└─────────────────────────────────────────────────────┘
```

**Host Application:** The environment running the AI model. It manages connections to MCP servers and mediates tool calls.

**MCP Client:** The AI model's interface to the MCP protocol. It discovers available tools, requests their use, and processes results.

**MCP Server:** A lightweight program that exposes tools and resources for a specific domain. Each server is independent — you can add or remove servers without affecting others.

### Core Primitives

#### Tools: Functions the AI Can Call

A tool is a function with a defined name, description, input schema, and output format. The AI reads the tool's description and schema to decide when and how to call it.


```json
{
  "name": "run_tests",
  "description": "Execute a test suite by name and return pass/fail results",
  "inputSchema": {
    "type": "object",
    "properties": {
      "suite_name": {
        "type": "string",
        "description": "Name of the test suite (e.g., 'smoke', 'regression', 'booking-api')"
      },
      "parallel": {
        "type": "boolean",
        "description": "Run tests in parallel (default: false)"
      }
    },
    "required": ["suite_name"]
  }
}
```

When the AI wants to run tests, it generates a tool call:


```json
{
  "tool": "run_tests",
  "arguments": {
    "suite_name": "booking-api",
    "parallel": true
  }
}
```

The MCP server executes the function and returns results to the AI.

#### Resources: Data the AI Can Read

Resources are structured data that MCP servers expose for reading. Unlike tools (which perform actions), resources provide information.


```json
{
  "uri": "github://staynest/test-automation/runs/latest",
  "name": "Latest CI Run Results",
  "description": "Test results from the most recent CI pipeline run",
  "mimeType": "application/json"
}
```

The AI can read this resource to get test results without executing any action:


```json
{
  "results": {
    "total": 342,
    "passed": 338,
    "failed": 3,
    "skipped": 1,
    "failures": [
      {
        "test": "BookingCreationTest.shouldCreateBooking",
        "error": "Expected 201 but got 500",
        "duration_ms": 1234
      }
    ]
  }
}
```

### The Tool Calling Lifecycle

```
1. DISCOVERY:  AI model receives list of available tools and their schemas
2. SELECTION:  AI decides which tool to call based on user's request
3. REQUEST:    AI generates a tool call with specific arguments
4. APPROVAL:   Host application (or human) approves/denies the call
5. EXECUTION:  MCP server executes the function
6. RETURN:     Results are sent back to the AI model
7. REASONING:  AI incorporates results into its response or next action
```

Step 4 (Approval) is the security gate. The host application decides whether each tool call is safe to execute. This can be automatic (pre-approved read-only tools) or manual (human clicks "Approve" for write operations).

### MCP Servers Relevant to Testing

| MCP Server | Tools | Resources | Testing Use Case |
|---|---|---|---|
| **GitHub** | Create issues, comment on PRs, trigger workflows | Read PRs, read workflow runs, read file contents | Agent reads CI results, creates issues for failures |
| **Jira** | Create/update issues, transition status | Read board, read sprint, read issue details | Agent creates bug tickets from test failures |
| **Playwright** | Navigate, click, fill, screenshot, assert | Read DOM state, read console logs | Agent drives browser for E2E test exploration |
| **BrowserStack** | Start session, run test, capture network | Read test results, read session logs | Agent manages cross-browser test execution |
| **Filesystem** | Read/write files, list directories | File contents, directory listings | Agent reads test code, writes generated tests |
| **Database** | Execute queries (read-only recommended) | Query results, schema information | Agent reads test data, verifies database state |
| **Slack/Teams** | Post messages, create channels | Read channel messages | Agent posts test report summaries |

## Practical Implementation

### Setting Up an MCP Server for Testing

A minimal MCP server that exposes test-running capabilities:


```python
# test_runner_mcp_server.py
# A minimal MCP server that exposes test execution tools

from mcp.server import Server
from mcp.types import Tool, TextContent
import subprocess
import json

server = Server("test-runner")

@server.list_tools()
async def list_tools():
    return [
        Tool(
            name="run_test_suite",
            description="Run a named test suite and return results",
            inputSchema={
                "type": "object",
                "properties": {
                    "suite": {
                        "type": "string",
                        "description": "Suite name: 'smoke', 'regression', 'booking-api'"
                    }
                },
                "required": ["suite"]
            }
        ),
        Tool(
            name="get_test_report",
            description="Get the HTML test report from the last run",
            inputSchema={
                "type": "object",
                "properties": {},
            }
        )
    ]

@server.call_tool()
async def call_tool(name: str, arguments: dict):
    if name == "run_test_suite":
        suite = arguments["suite"]
        # Execute tests via Maven (sandboxed — no production access)
        result = subprocess.run(
            ["mvn", "test", f"-Dgroups={suite}", "-pl", "test-module"],
            capture_output=True, text=True, timeout=300
        )
        return [TextContent(
            type="text",
            text=json.dumps({
                "exit_code": result.returncode,
                "stdout_tail": result.stdout[-2000:],  # Last 2000 chars
                "stderr_tail": result.stderr[-1000:]
            })
        )]
    
    elif name == "get_test_report":
        try:
            with open("target/surefire-reports/index.html", "r") as f:
                return [TextContent(type="text", text=f.read()[:5000])]
        except FileNotFoundError:
            return [TextContent(type="text", text="No test report found. Run tests first.")]
```

### How AI Uses MCP in Practice

A realistic conversation with an AI that has MCP access to GitHub and a test runner:

```
Human: "The booking API tests failed in the last CI run. What happened?"

AI reasoning: I need to read the CI results. I'll use the GitHub MCP server.

AI tool call: github.get_workflow_run(repo="staynest/api", run_id="latest")

[MCP server returns: 3 failures in BookingApiTest]

AI tool call: github.get_workflow_run_logs(repo="staynest/api", run_id="12345")

[MCP server returns: detailed logs showing TimeoutException in shouldCreateBooking]

AI response: "Three tests failed in BookingApiTest. All three show TimeoutException 
when waiting for the booking confirmation response. The logs show the booking service 
took 45 seconds to respond (timeout is 30s). This looks like a performance regression 
in the booking service, not a test issue. I recommend checking the booking service 
deployment — was there a recent change?"
```

## Failure and Debugging

### The Tool Schema Mismatch Problem


```json
// AI generates this tool call:
{
  "tool": "run_tests",
  "arguments": {
    "test_class": "BookingApiTest"     // AI used "test_class"
  }
}

// But the tool schema expects:
{
  "suite": "booking-api"               // Tool expects "suite", not "test_class"
}
```

**What happens:** The MCP server receives an argument it doesn't recognize. Depending on implementation, it either ignores the argument (runs with defaults, producing unexpected results) or returns an error.

**Why it happens:** AI reads the tool description but may misremember the exact parameter names, especially when multiple tools have similar but not identical schemas.

<BestPractice>

**Prevention:** Write clear, unambiguous tool descriptions. Include example values in the schema description field. The more specific the schema, the less room for AI misinterpretation.

</BestPractice>


### When MCP Calls Fail Silently

**Scenario:** AI calls a database query tool to verify test data. The tool returns an empty result set. AI interprets this as "no matching records" and reports that the test data is missing. But the actual problem is that the database connection string points to an empty test database, not the populated staging database.

**Why this is dangerous:** The tool executed successfully (no error), returned valid data (empty set), but the result was misleading because the tool's configuration was wrong. AI has no way to detect environment misconfigurations.

**Prevention:**
- Validate MCP server configurations before first use.
- Include health-check tools that verify connectivity and data presence.
- Don't trust AI's interpretation of empty results — verify the tool's connection manually.

## Engineering Judgment

### When to Build Custom MCP Servers

| Build Custom | Use Existing | Don't Use MCP |
|---|---|---|
| Your test infrastructure has unique APIs | Standard tools (GitHub, Jira, Slack) | Simple scripts that don't need AI reasoning |
| You need AI to interact with internal test dashboards | Well-maintained community servers exist | One-off tasks where AI adds no value |
| Multiple AI tools need the same integration | Official MCP server from the vendor | Security-sensitive operations that shouldn't go through AI |

### MCP Adoption Checklist for Test Teams

```
[ ] Identified which existing MCP servers match your tools (GitHub, Jira, etc.)
[ ] Evaluated which custom MCP servers you'd need to build
[ ] Defined permission scopes for each MCP server (read-only vs read-write)
[ ] Set up approval workflow for write operations
[ ] Tested MCP servers in non-production environment first
[ ] Documented what each MCP server can and cannot do
[ ] Established audit logging for all MCP tool calls
[ ] Trained team on MCP concepts and security implications
```

### Common Overengineering Mistakes

- Building MCP servers for tools that have simpler integration options (a webhook is simpler than an MCP server for notifications).
- Exposing write access to production systems through MCP before establishing proper guardrails.
- Building a custom MCP server when an existing community server already does what you need.
- Giving AI access to 20 MCP tools when it only needs 3 for the current workflow — more tools increase the chance of wrong tool selection.

## Interview and Revision

### Questions and Answers

**Q1: What is MCP and why does it matter for testing?**

**A:** MCP — Model Context Protocol — is an open standard that connects AI models to external tools. It defines a client-server architecture: the AI model is the client, and tools (GitHub, Jira, test runners, browsers) are servers. Each server exposes tools (functions to call) and resources (data to read). For testing, MCP enables AI agents to interact with test infrastructure directly — running test suites, reading CI logs, creating bug tickets, and even driving browsers for exploratory testing. The key is the approval step: every tool call goes through a security gate before execution.

**Q2: How does MCP tool calling work?**

**A:** Seven-step lifecycle: Discovery (AI learns available tools and their schemas), Selection (AI picks the right tool for the task), Request (AI generates a tool call with arguments), Approval (host application or human approves/denies), Execution (MCP server runs the function), Return (results come back to AI), Reasoning (AI incorporates results into its response). The approval step is where security is enforced — read-only operations can be auto-approved while write operations require human confirmation.

**Q3: What are the security considerations for MCP in testing?**

**A:** Three main concerns. First, scope: each MCP server should have minimal permissions — a test runner MCP server shouldn't have access to production databases. Second, approval gates: destructive operations (delete, write, deploy) should require explicit human approval via the host application. Third, secrets management: API tokens and credentials should be in environment variables, never in MCP server code or tool call arguments. AI should never see raw credentials in tool responses.
