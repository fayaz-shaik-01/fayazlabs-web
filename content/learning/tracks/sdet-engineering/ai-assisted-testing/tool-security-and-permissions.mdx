# Tool Security and Permissions

> **Module:** 10 — AI-Assisted Testing  
> **Prerequisites:** Mcp Fundamentals, Agent Workflows And Subagents  
> **Mastery Target:** L3 (independent) — can design a permission model for AI testing agents, implement proper secrets management, and establish audit trails

---

## Quick Overview (2-minute read)

**What:** Tool security and permissions covers the rules, boundaries, and safeguards that control what AI agents can and cannot do when interacting with external systems. This includes permission scoping (what tools an agent can access), secrets management (how credentials are handled), sandboxing (what environments the agent can reach), and audit trails (what the agent did and when).

**Why:** An AI agent with unrestricted access is a security incident waiting to happen. Agents can accidentally delete databases, leak credentials in logs, expose PII in prompts, or execute destructive operations on production systems. The risk multiplies because agents act faster than humans can intervene — by the time you notice the problem, the damage is done. Security isn't an afterthought for AI tooling; it's a prerequisite.

**Where:** Every AI agent deployment, every MCP server configuration, every CI pipeline that involves AI, and every development environment where AI tools have terminal or file system access.

<MentalModel>

Think of AI agent permissions like **key cards in a hotel**. A guest's key opens their room and common areas, but not other rooms, staff areas, or the safe. A housekeeper's key opens all rooms on their floor, but not the manager's office. The manager's key opens everything. You don't give the guest a master key "for convenience" — you give the minimum access needed for their role. AI agents should get guest-level access by default: the minimum tools and permissions needed for their specific task, nothing more.

</MentalModel>


<KeyTakeaways>

1. **Principle of least privilege:** Every AI agent should have the minimum permissions needed for its task. No more, no less.
2. **Secrets are never exposed to the AI model.** Credentials go in environment variables. The AI sees tool responses, not the authentication mechanism.
3. **Destructive actions require human approval.** Read operations can be auto-approved; write/delete operations need explicit human confirmation.
4. **Audit everything.** Every tool call, every argument, every result — logged with timestamps. If something goes wrong, you need the trail.
5. **Production is off-limits.** AI agents test against staging, dev, or sandboxed environments. Never production without a human approving every action.

</KeyTakeaways>

## First-Principles Explanation

### The Threat Model for AI Agents in Testing

| Threat | How It Happens | Impact |
|---|---|---|
| **Credential leakage** | AI includes API keys in generated code or log output | Keys exposed in PRs, logs, chat transcripts |
| **Data exfiltration** | AI reads production database and includes PII in its response | Privacy violation, regulatory exposure |
| **Destructive actions** | AI runs `DELETE` or `DROP` while "investigating" a test data issue | Data loss, service disruption |
| **Prompt injection** | Malicious test data contains instructions that redirect the AI | AI performs unintended actions |
| **Unauthorized access** | AI uses broad permissions to access systems beyond its task scope | Violation of access policies |
| **Resource exhaustion** | AI spawns infinite loops or runs expensive operations repeatedly | CI costs, infrastructure overload |

### The Permission Model

#### Scope Hierarchy

```
MOST RESTRICTIVE (default)
│
├── READ-ONLY: Can read files, logs, test results
│   └── Auto-approve: Safe, no side effects
│
├── WRITE-SANDBOXED: Can create/modify files in specific directories
│   └── Auto-approve with scope check: Only within allowed paths
│
├── EXECUTE-SANDBOXED: Can run commands in sandboxed environments
│   └── Require approval: Each command reviewed before execution
│
├── WRITE-STAGING: Can modify staging environment data
│   └── Require approval: Each write operation reviewed
│
├── WRITE-PRODUCTION: Can modify production systems
│   └── NEVER AUTO-APPROVE: Explicit human approval for every action
│
LEAST RESTRICTIVE (never default)
```

### Secrets Management

**The rule: AI should never see raw credentials.**

```
WRONG:
  AI prompt → "Use this API key: sk-abc123xyz to authenticate"
  AI sees the key, may include it in generated code, logs, or responses

RIGHT:
  Environment variable: STAYNEST_API_KEY=sk-abc123xyz
  MCP server reads env var internally
  AI calls tool → tool authenticates using env var → AI sees only the response
  AI never sees "sk-abc123xyz"
```

#### Implementation Pattern


```python
# MCP server handles authentication internally
# AI never sees the credentials

import os

class GitHubMCPServer:
    def __init__(self):
        # Credentials from environment — never exposed to AI
        self.token = os.environ["GITHUB_TOKEN"]
        if not self.token:
            raise ValueError("GITHUB_TOKEN environment variable not set")
    
    async def read_pr(self, repo: str, pr_number: int):
        # Token used internally for authentication
        response = requests.get(
            f"https://api.github.com/repos/{repo}/pulls/{pr_number}",
            headers={"Authorization": f"token {self.token}"}
        )
        
        # Return only the data — no auth details
        return {
            "title": response.json()["title"],
            "status": response.json()["state"],
            "diff_url": response.json()["diff_url"]
            # Token is NOT included in the response
        }
```

#### Secrets Checklist

```
[ ] API keys are in environment variables, not in code or config files
[ ] MCP server configurations reference env vars (${GITHUB_TOKEN}), not raw values
[ ] AI-generated code is scanned for accidentally hardcoded credentials
[ ] Tool responses are filtered to exclude auth headers and tokens
[ ] Log output from tool calls is sanitized before returning to AI
[ ] .env files are in .gitignore and never committed
[ ] Credential rotation procedure exists and is documented
```

### Sandboxing

Sandboxing restricts what AI agents can reach — which environments, which file systems, which networks.

#### Environment Sandboxing

| Environment | AI Agent Access | Rationale |
|---|---|---|
| **Local dev** | Full read, scoped write | Developer's environment, acceptable risk |
| **CI sandbox** | Full read/execute within container | Ephemeral, destroyed after run |
| **Staging** | Read-only by default, write with approval | Shared environment, mistakes affect team |
| **Production** | No access | Absolutely no AI agent access without extraordinary process |
| **Test database** | Read-only queries | Write access creates shared state issues |

## Practical Implementation

### Permission Checklist for AI Testing Agent Setup

Before deploying any AI agent in your testing workflow, complete this checklist:

```
IDENTITY AND SCOPE
[ ] Agent has a unique identifier for audit logging
[ ] Agent's purpose is documented (what it does, what it doesn't do)
[ ] Agent's maximum session duration is configured (prevents runaway agents)

TOOL ACCESS
[ ] Each MCP tool is individually allowed or denied
[ ] Read-only tools are auto-approved
[ ] Write tools require human approval
[ ] Destructive tools (delete, drop, deploy) are denied by default
[ ] Tool list is reviewed quarterly for unnecessary permissions

FILE SYSTEM
[ ] Allowed read paths are explicitly listed
[ ] Allowed write paths are restricted to test/output directories
[ ] Sensitive files (.env, keys, prod configs) are explicitly denied
[ ] File size limits prevent writing oversized files

NETWORK
[ ] Agent can only reach staging/test endpoints, not production
[ ] External API calls are logged and rate-limited
[ ] Agent cannot make arbitrary HTTP requests outside defined tool calls

SECRETS
[ ] All credentials are in environment variables
[ ] No API keys appear in tool call arguments
[ ] Tool responses are sanitized to remove auth headers
[ ] Generated code is scanned for hardcoded credentials

AUDIT
[ ] Every tool call is logged with timestamp, arguments, and result
[ ] Audit logs are stored outside the agent's write scope
[ ] Anomalous patterns trigger alerts (unusual volume, denied operations)
[ ] Audit logs are retained for at least 90 days

HUMAN CONTROLS
[ ] Human can pause/stop the agent at any time
[ ] Human approves all PRs created by the agent
[ ] Human reviews agent's actions before each deployment cycle
[ ] Rollback procedure is documented for reversing agent changes
```

### Implementing Approval Gates


```python
# Approval gate implementation for an MCP host application

class ApprovalGate:
    # Tools that never need approval
    AUTO_APPROVE = {"read_file", "list_directory", "get_test_report", 
                    "read_pr", "read_issue"}
    
    # Tools that always need human approval
    REQUIRE_APPROVAL = {"write_file", "create_pr", "create_issue",
                        "comment_on_pr", "run_command"}
    
    # Tools that are never allowed
    DENIED = {"delete_file", "merge_pr", "deploy", "execute_ddl",
              "reset_database", "delete_branch"}
    
    def check(self, tool_name: str, arguments: dict) -> str:
        if tool_name in self.DENIED:
            return "DENIED"
        
        if tool_name in self.AUTO_APPROVE:
            return "APPROVED"
        
        if tool_name in self.REQUIRE_APPROVAL:
            # Display to human for approval
            print(f"\n⚠️  Agent requests: {tool_name}")
            print(f"   Arguments: {json.dumps(arguments, indent=2)}")
            response = input("   Approve? (y/n): ").strip().lower()
            return "APPROVED" if response == "y" else "DENIED"
        
        # Unknown tool — deny by default
        return "DENIED"
```

## Failure and Debugging

### The Credential Leak Scenario

**Scenario:** An AI agent is debugging a test that fails with a 401 authentication error. The agent's MCP tool returns the full HTTP request/response including the `Authorization` header. The agent includes the header value in its analysis:

```
"The test fails because the token 'eyJhbGciOiJIUzI1...' is expired. 
Generate a new token using the auth endpoint."
```

The agent then generates code containing the token, which gets committed to a PR.

**Impact:** JWT token exposed in version control. Even if the PR is closed, the token is in git history.

**Root cause:** The MCP server returned raw authentication headers in its response. The AI model has no concept of "secret" — it treats all text equally.

<BestPractice>

**Fix:** MCP servers must sanitize responses:

</BestPractice>



```python
def sanitize_response(response_data: dict) -> dict:
    """Remove sensitive fields before returning to AI"""
    sensitive_keys = {"authorization", "token", "api_key", "secret", 
                      "password", "cookie", "set-cookie"}
    
    if "headers" in response_data:
        response_data["headers"] = {
            k: "[REDACTED]" if k.lower() in sensitive_keys else v
            for k, v in response_data["headers"].items()
        }
    
    return response_data
```

### Prevention Framework

1. **Sanitize at the source:** MCP servers strip sensitive data before returning responses.
2. **Scan at the gate:** Pre-commit hooks scan AI-generated code for credential patterns.
3. **Monitor in production:** Alerts trigger when credential-like patterns appear in PRs or logs.
4. **Rotate on exposure:** If a credential is exposed, rotate it immediately — don't wait to assess impact.

## Engineering Judgment

### Security vs Productivity Tradeoff

| Approach | Security | Productivity | Best For |
|---|---|---|---|
| Approve every tool call | Maximum | Very low — constant interruptions | First week of agent deployment |
| Auto-approve reads, approve writes | High | Good — most operations are reads | Established trust, ongoing use |
| Auto-approve all in sandbox | Medium | Maximum | Ephemeral CI environments |
| Auto-approve everything | Very low | Maximum | Never — this is negligent |

The recommended progression:
1. **Week 1-2:** Approve everything. Build understanding of what the agent does.
2. **Week 3-4:** Auto-approve read operations. Approve writes.
3. **Month 2+:** Auto-approve reads and writes to sandboxed paths. Approve PRs and infrastructure changes.
4. **Never:** Auto-approve production access or destructive operations.

### Common Overengineering Mistakes

- Building an enterprise-grade permission system for a team of 3 using AI tools casually. Start with a simple allow/deny list.
- Requiring human approval for every read operation — this makes the agent unusable and the team will bypass it.
- Logging tool call arguments that contain large file contents (bloats audit logs). Log hashes instead.
- Creating separate credentials for each agent when one scoped service account would suffice.
- Spending weeks on security setup before actually using AI agents — start simple, iterate based on real usage patterns.

## Interview and Revision

### Questions and Answers

**Q1: How do you handle secrets when AI agents interact with your test infrastructure?**

**A:** AI should never see raw credentials. All secrets go in environment variables. MCP servers read env vars internally for authentication and return only the data — never auth headers or tokens. I sanitize tool responses to strip any sensitive fields before they reach the AI model. Generated code is scanned by pre-commit hooks for credential patterns. If a credential is accidentally exposed, we rotate it immediately.

**Q2: What permission model would you use for an AI testing agent?**

**A:** Principle of least privilege applied per tool. Read-only operations (read files, get test reports, list PRs) are auto-approved — they're safe and don't need human friction. Write operations (create files, run commands) require human approval in the first weeks, then auto-approve to sandboxed paths once trust is established. Destructive operations (delete, drop, deploy, merge) are always denied or always require explicit human approval. Every operation is logged with timestamp, arguments, and result for audit.

**Q3: What are the biggest security risks with AI agents in testing?**

**A:** Four main risks. Credential leakage — the agent includes API keys in generated code or analysis output. Data exfiltration — the agent reads PII from a database and includes it in responses visible to unauthorized users. Destructive actions — the agent runs DELETE or DROP while "investigating." Prompt injection — malicious test data contains instructions that redirect the agent to perform unintended actions. Mitigations: sanitize responses, restrict database to read-only, require approval for writes, validate all agent inputs.




**Flashcard 1**
**Q:** What is the principle of least privilege for AI agents?
**A:** Every agent gets the minimum permissions needed for its specific task. Read-only by default. Write access only to designated paths. Destructive operations always denied or human-approved. No production access. Permissions are reviewed regularly and reduced when no longer needed.

**Flashcard 2**
**Q:** How should secrets be handled in MCP server configurations?
**A:** Secrets go in environment variables. MCP configs reference variables (`${GITHUB_TOKEN}`), not raw values. The MCP server reads env vars internally for authentication. Tool responses are sanitized to strip auth headers. The AI model never sees the raw credential — it sees only the data that results from authenticated requests.

**Flashcard 3**
**Q:** What must an audit trail for AI agents capture?
**A:** Every tool call with: timestamp, agent ID, tool name, arguments (sanitized), approval status (auto/human/denied), result summary, and duration. Audit logs are stored outside the agent's write scope so the agent can't modify its own trail. Anomalous patterns (high volume, denied operations) trigger alerts.
