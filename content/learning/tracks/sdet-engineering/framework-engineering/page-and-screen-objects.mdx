# Page and Screen Objects

> **Module:** 03 — Framework Engineering > Page and Screen Objects  
> **Prerequisites:** Framework Architecture, Dependency Injection And Composition, Oop Fundamentals  
> **Mastery Target:** L3 (Independent) → L4 (Engineering Judgment)

---

## Quick Overview (Layer 1)

**What:** The Page Object Model (POM) is a design pattern that separates page structure (locators, elements) from test logic (assertions, test flow). Each page or screen in the application gets its own class that encapsulates all element locators and interaction methods. Tests call readable methods like `loginPage.loginAs("user", "pass")` instead of raw `driver.findElement(By.id("email")).sendKeys("user")`.

**Why it matters:** Without POM, locators are scattered across every test file. When the login button's ID changes from `"login-btn"` to `"submit-login"`, you update 40 test files. With POM, you update `LoginPage.java` — one file, one change. POM is the single most impactful pattern in UI test automation because it transforms a locator change from an O(n) problem (proportional to test count) to an O(1) fix.

**Where you encounter it:** Every UI automation framework you'll build or maintain. Selenium, Appium, Playwright, Cypress — the tools differ, but the pattern is universal.

<MentalModel>

Think of a page object as a **TV remote control**. The remote has buttons labeled "Volume Up," "Channel 3," "Mute" — high-level actions. You press "Volume Up" without knowing the infrared signal encoding or the TV's internal amplifier circuit. The remote *encapsulates* the implementation and exposes a clean interface. A page object does the same: `loginPage.loginAs("user", "pass")` hides the locators, the waits, the click sequence. The test presses the button; the page object handles the wiring.

</MentalModel>


<KeyTakeaways>

1. **Locators live in page objects, never in tests** — a test should never contain `By.id(...)` or `By.xpath(...)`. Locators are implementation details that belong behind the page object boundary.
2. **Methods return page objects** — `loginPage.loginAs(...)` returns a `DashboardPage` because successful login navigates to the dashboard. This enables fluent chaining and models real navigation.
3. **No assertions in page objects** — page objects provide state (`getErrorMessage()`, `isLoginButtonEnabled()`). Tests make assertions. Mixing assertions into pages couples them to specific test expectations.
4. **Reusable components for shared UI elements** — headers, footers, modals, and date pickers appear on multiple pages. Extract them as components, not duplicated code in every page object.
5. **One level of inheritance maximum** — `BasePage` provides shared utilities (`click`, `type`, `waitFor`). Concrete pages extend it. Never go deeper.

</KeyTakeaways>

## First-Principles Explanation (Layer 2)

### Core Principles of POM

**Principle 1: Encapsulate locators.**

Locators are the most fragile part of UI automation — they break when developers change IDs, class names, or DOM structure. Encapsulating them in one place means each locator has exactly one owner.


```java
// BAD — locator in the test (duplicated across 20 tests)
driver.findElement(By.id("email-input")).sendKeys("user@test.com");

// GOOD — locator in the page object (one source of truth)
loginPage.enterEmail("user@test.com");
```

**Principle 2: Methods return page objects.**

When an action navigates to a different page, the method should return the page object for that destination. This models the application's navigation flow in code.


```java
// Login navigates to Dashboard — return type communicates this
public DashboardPage loginAs(String email, String password) {
    enterEmail(email);
    enterPassword(password);
    clickLoginButton();
    return new DashboardPage(driver);
}

// Invalid login stays on LoginPage — return type communicates this
public LoginPage loginWithInvalidCredentials(String email, String password) {
    enterEmail(email);
    enterPassword(password);
    clickLoginButton();
    return this;  // stays on the same page
}
```

**Principle 3: No assertions in page objects.**

Page objects are reusable across tests with different expectations. If `LoginPage.loginAs()` asserts "Dashboard loaded," it can't be used in a test that expects login to fail.


```java
// BAD — assertion baked into page object
public void loginAs(String email, String password) {
    // ...
    assertThat(driver.getTitle()).contains("Dashboard");  // not every test expects this
}

// GOOD — page provides state, test asserts
public String getPageTitle() {
    return driver.getTitle();
}
// Test: assertThat(dashboardPage.getPageTitle()).contains("Dashboard");
```

### BasePage: Shared Utilities

Every page object needs basic operations: clicking elements, typing text, waiting for visibility. A `BasePage` provides these so concrete pages don't reimplement them.


```java
public abstract class BasePage {

    protected final WebDriver driver;
    protected final WebDriverWait wait;

    protected BasePage(WebDriver driver) {
        this.driver = driver;
        this.wait = new WebDriverWait(driver, Duration.ofSeconds(10));
    }

    protected void click(By locator) {
        wait.until(ExpectedConditions.elementToBeClickable(locator)).click();
    }

    protected void type(By locator, String text) {
        WebElement element = wait.until(
            ExpectedConditions.visibilityOfElementLocated(locator));
        element.clear();
        element.sendKeys(text);
    }

    protected String getText(By locator) {
        return wait.until(
            ExpectedConditions.visibilityOfElementLocated(locator)).getText();
    }

    protected boolean isDisplayed(By locator) {
        try {
            return driver.findElement(locator).isDisplayed();
        } catch (NoSuchElementException e) {
            return false;
        }
    }

    protected void waitForPageLoad() {
        wait.until(d -> ((JavascriptExecutor) d)
            .executeScript("return document.readyState").equals("complete"));
    }
}
```

**Design decisions:**
- **`protected` methods** — accessible to subclasses, not to tests. Tests call business-level methods (`loginAs`), not utility methods (`click`).
- **Waits built into every action** — `click()` waits for clickability before clicking. No test should ever need `Thread.sleep()`.
- **`WebDriver` received via constructor** — DI, not creation. The driver comes from the framework; the page object uses it.

### Components: Reusable Page Fragments

A header navigation bar appears on every page. A date picker appears on booking and search pages. These are *components* — reusable UI fragments that don't represent a full page.


```java
public class HeaderComponent {

    private final WebDriver driver;
    private final WebDriverWait wait;

    // Locators for header elements
    private final By userMenu = By.id("user-menu");
    private final By logoutLink = By.id("logout-link");
    private final By searchBar = By.id("header-search");
    private final By notificationBell = By.id("notifications");

    public HeaderComponent(WebDriver driver) {
        this.driver = driver;
        this.wait = new WebDriverWait(driver, Duration.ofSeconds(5));
    }

    public void logout() {
        wait.until(ExpectedConditions.elementToBeClickable(userMenu)).click();
        wait.until(ExpectedConditions.elementToBeClickable(logoutLink)).click();
    }

    public SearchPage searchFor(String query) {
        WebElement search = wait.until(
            ExpectedConditions.visibilityOfElementLocated(searchBar));
        search.clear();
        search.sendKeys(query + Keys.ENTER);
        return new SearchPage(driver);
    }

    public int getNotificationCount() {
        String text = driver.findElement(notificationBell).getText();
        return text.isEmpty() ? 0 : Integer.parseInt(text);
    }
}
```

Pages that have a header *compose* it rather than inheriting it:


```java
public class DashboardPage extends BasePage {

    private final HeaderComponent header;

    public DashboardPage(WebDriver driver) {
        super(driver);
        this.header = new HeaderComponent(driver);
    }

    public HeaderComponent header() {
        return header;
    }

    // Dashboard-specific methods...
}

// Usage: dashboardPage.header().logout();
```

### Fluent API: Method Chaining

A fluent API makes tests read like natural language by returning `this` (or the next page) from every method:


```java
public class BookingPage extends BasePage {

    public BookingPage selectProperty(String name) {
        type(By.id("property-search"), name);
        click(By.xpath("//li[text()='" + name + "']"));
        return this;
    }

    public BookingPage setCheckIn(String date) {
        type(By.id("checkin"), date);
        return this;
    }

    public BookingPage setCheckOut(String date) {
        type(By.id("checkout"), date);
        return this;
    }

    public BookingPage setGuests(int count) {
        type(By.id("guests"), String.valueOf(count));
        return this;
    }

    public ConfirmationPage submitBooking() {
        click(By.id("submit-booking"));
        return new ConfirmationPage(driver);
    }
}
```

**Usage in test:**


```java
ConfirmationPage confirmation = new BookingPage(getDriver())
    .selectProperty("Tokyo Suite")
    .setCheckIn("2025-09-01")
    .setCheckOut("2025-09-05")
    .setGuests(2)
    .submitBooking();

assertThat(confirmation.getStatus()).isEqualTo("Confirmed");
```

### Screen Objects for Mobile

Mobile automation (Appium) uses the same pattern with different challenges:

- **Gestures:** Swipe, scroll, long-press are not just clicks. Screen objects expose `swipeToElement()`, `scrollDown()`, `longPressOn()`.
- **Platform differences:** iOS and Android have different UI components. A `LoginScreen` might have platform-specific locators via `MobileBy.accessibilityId()` or different navigation patterns.
- **Context switching:** Hybrid apps switch between native and webview contexts. The screen object manages `driver.context("WEBVIEW")` transitions internally.


```java
public class LoginScreen {

    private final AppiumDriver driver;
    private final WebDriverWait wait;

    // Platform-agnostic locators using accessibility IDs
    private final By emailField = MobileBy.accessibilityId("email-input");
    private final By passwordField = MobileBy.accessibilityId("password-input");
    private final By loginButton = MobileBy.accessibilityId("login-button");
    private final By errorMessage = MobileBy.accessibilityId("error-text");

    public LoginScreen(AppiumDriver driver) {
        this.driver = driver;
        this.wait = new WebDriverWait(driver, Duration.ofSeconds(15));
    }

    public HomeScreen loginAs(String email, String password) {
        wait.until(ExpectedConditions.visibilityOfElementLocated(emailField))
            .sendKeys(email);
        driver.findElement(passwordField).sendKeys(password);
        driver.findElement(loginButton).click();
        return new HomeScreen(driver);
    }

    public String getErrorMessage() {
        return wait.until(
            ExpectedConditions.visibilityOfElementLocated(errorMessage)).getText();
    }
}
```

## Practical Implementation (Layer 3)

### Example: Full POM Hierarchy for StayNest

A complete page object hierarchy demonstrating BasePage, concrete pages, components, and fluent navigation.


```java
// === BasePage — shared utilities for all pages ===

public abstract class BasePage {

    protected final WebDriver driver;
    protected final WebDriverWait wait;
    protected final HeaderComponent header;

    protected BasePage(WebDriver driver) {
        this.driver = driver;
        this.wait = new WebDriverWait(driver, Duration.ofSeconds(10));
        this.header = new HeaderComponent(driver);
    }

    protected void click(By locator) {
        wait.until(ExpectedConditions.elementToBeClickable(locator)).click();
    }

    protected void type(By locator, String text) {
        WebElement el = wait.until(
            ExpectedConditions.visibilityOfElementLocated(locator));
        el.clear();
        el.sendKeys(text);
    }

    protected String getText(By locator) {
        return wait.until(
            ExpectedConditions.visibilityOfElementLocated(locator)).getText();
    }

    protected void selectDropdown(By locator, String visibleText) {
        new Select(wait.until(
            ExpectedConditions.visibilityOfElementLocated(locator)))
            .selectByVisibleText(visibleText);
    }

    public HeaderComponent header() {
        return header;
    }

    public String getPageTitle() {
        return driver.getTitle();
    }
}
```


```java
// === LoginPage — login form interactions ===

public class LoginPage extends BasePage {

    private final By emailField = By.id("login-email");
    private final By passwordField = By.id("login-password");
    private final By loginButton = By.id("login-submit");
    private final By errorMessage = By.cssSelector(".login-error-message");
    private final By forgotPasswordLink = By.linkText("Forgot password?");

    public LoginPage(WebDriver driver) {
        super(driver);
    }

    public DashboardPage loginAs(String email, String password) {
        type(emailField, email);
        type(passwordField, password);
        click(loginButton);
        return new DashboardPage(driver);
    }

    public LoginPage loginExpectingError(String email, String password) {
        type(emailField, email);
        type(passwordField, password);
        click(loginButton);
        return this;  // stays on login page
    }

    public String getErrorMessage() {
        return getText(errorMessage);
    }

    public boolean isLoginButtonEnabled() {
        return driver.findElement(loginButton).isEnabled();
    }

    public ForgotPasswordPage clickForgotPassword() {
        click(forgotPasswordLink);
        return new ForgotPasswordPage(driver);
    }
}
```


```java
// === SearchPage — property search and filtering ===

public class SearchPage extends BasePage {

    private final By searchInput = By.id("search-destination");
    private final By checkInDate = By.id("search-checkin");
    private final By checkOutDate = By.id("search-checkout");
    private final By guestsDropdown = By.id("search-guests");
    private final By searchButton = By.id("search-submit");
    private final By resultsList = By.cssSelector(".property-card");
    private final By noResultsMessage = By.cssSelector(".no-results");

    public SearchPage(WebDriver driver) {
        super(driver);
    }

    public SearchPage searchFor(String destination) {
        type(searchInput, destination);
        click(searchButton);
        waitForResults();
        return this;
    }

    public SearchPage setDates(String checkIn, String checkOut) {
        type(checkInDate, checkIn);
        type(checkOutDate, checkOut);
        return this;
    }

    public SearchPage setGuests(int count) {
        selectDropdown(guestsDropdown, String.valueOf(count));
        return this;
    }

    public int getResultCount() {
        return driver.findElements(resultsList).size();
    }

    public PropertyPage selectResult(int index) {
        List<WebElement> results = driver.findElements(resultsList);
        results.get(index).click();
        return new PropertyPage(driver);
    }

    public boolean hasNoResults() {
        return isDisplayed(noResultsMessage);
    }

    private void waitForResults() {
        wait.until(d -> !d.findElements(resultsList).isEmpty()
                     || !d.findElements(noResultsMessage).isEmpty());
    }
}
```

## Failure and Debugging (Layer 4)

### Failure 1: God Page Object

**The Problem:**


```java
public class StayNestPage extends BasePage {
    // 200 locators for EVERY page in the application
    private final By loginEmail = By.id("login-email");
    private final By searchInput = By.id("search-input");
    private final By bookingConfirm = By.id("booking-confirm");
    private final By adminUserList = By.id("admin-users");
    // ... 196 more locators

    public void login(String email, String password) { /* ... */ }
    public void search(String query) { /* ... */ }
    public void createBooking() { /* ... */ }
    public void deleteUser() { /* ... */ }
    // ... 50 more methods
}
```

**What happens:** Every UI change touches this file. Multiple developers edit it simultaneously, causing merge conflicts. The class is 800 lines — finding anything requires scrolling. Half the locators are stale because no one knows which are still used.

**The fix:** One class per page. `LoginPage`, `SearchPage`, `BookingPage`, `AdminPage`. Each is 50-100 lines. Each has one owner. Each can change independently.

### Failure 2: Assertions Inside Page Objects

**The Problem:**


```java
public class LoginPage extends BasePage {

    public DashboardPage loginAs(String email, String password) {
        type(emailField, email);
        type(passwordField, password);
        click(loginButton);

        // Assertion baked into the page object
        assertThat(driver.getTitle()).contains("Dashboard");

        return new DashboardPage(driver);
    }
}
```

**What happens:** This works for happy-path tests. But a negative test that expects login to *fail* can't use `loginAs()` because the assertion throws. The team creates `loginAsExpectingFailure()` — now there are two methods doing the same thing with different assertions. This multiplies with every test scenario.

**The fix:** Page objects provide state, tests assert:


```java
// Page: provides data
public String getPageTitle() { return driver.getTitle(); }

// Test: makes the assertion
DashboardPage dashboard = loginPage.loginAs("user", "pass");
assertThat(dashboard.getPageTitle()).contains("Dashboard");
```

### Failure 3: Static Locators Causing Stale Elements

**The Problem:**


```java
public class SearchPage extends BasePage {

    // Elements resolved ONCE at construction time
    private final WebElement searchInput = driver.findElement(By.id("search"));
    private final WebElement searchButton = driver.findElement(By.id("search-btn"));

    public SearchPage(WebDriver driver) {
        super(driver);
    }

    public void searchFor(String query) {
        searchInput.sendKeys(query);  // StaleElementReferenceException!
        searchButton.click();
    }
}
```

**What happens:** Elements are resolved at page construction time. If the DOM refreshes (AJAX, page navigation, React re-render), the cached `WebElement` references become stale. Any interaction throws `StaleElementReferenceException`.

**The fix — store locators (`By`), not elements (`WebElement`):**


```java
public class SearchPage extends BasePage {

    // Store locators — resolve fresh each time
    private final By searchInput = By.id("search");
    private final By searchButton = By.id("search-btn");

    public void searchFor(String query) {
        type(searchInput, query);   // resolves element fresh via BasePage.type()
        click(searchButton);        // resolves element fresh via BasePage.click()
    }
}
```

## Engineering Judgment (Layer 5)

### When POM Is Overkill

| Situation | Use POM? | Alternative |
|-----------|----------|-------------|
| 5-10 quick smoke tests, solo developer | Maybe not | Direct driver calls are fine; extract POM when tests grow past 15-20 |
| 50+ tests, team of 3+ | Yes | POM pays for itself on the first locator change |
| One-off automation script (not a test suite) | No | Script doesn't need maintainability architecture |
| API-only tests | No (wrong pattern) | Use service layer pattern instead (see Api Client Design) |

### Locator Strategy Priority

| Strategy | Reliability | Readability | Use When |
|----------|-------------|-------------|----------|
| `By.id()` | Highest (unique) | High | Element has a stable ID |
| `By.cssSelector()` | High | Medium | No ID; use class + attribute combination |
| `By.name()` | High | High | Form elements with name attributes |
| `By.linkText()` | Medium | Highest | Stable link text that won't be translated |
| `By.xpath()` | Varies | Low | Complex DOM traversal; last resort |
| Custom data attributes (`data-testid`) | Highest | Highest | Team adds `data-testid` for testing — best practice |

**Recommendation:** Advocate for `data-testid` attributes with your development team. They're stable (developers know they're for testing and won't change them casually), readable (`By.cssSelector("[data-testid='login-button']")`), and decoupled from styling (unlike class names that change with CSS refactors).

### How Many Page Objects?

**Rule of thumb:** One page object per distinct page or major view. A single-page app with tabs might have `DashboardPage`, `ProfileTab`, `SettingsTab` — each tab is a distinct view even if the URL doesn't change.

**When to split:** If a page object exceeds 150 lines or has locators for functionally separate areas, split it. A `DashboardPage` with admin widgets and user widgets might split into `AdminDashboardView` and `UserDashboardView`.

**When to compose:** If the same UI element (header, sidebar, modal dialog) appears on multiple pages, extract it as a component. Pages that have it compose it; pages that don't, skip it.

## Interview and Revision (Layer 6)

### Fundamental Questions

**Q1: What is the Page Object Model and why do you use it?**

**A:** POM is a design pattern that encapsulates page-level UI interactions — locators and action methods — into dedicated classes. Each page gets its own class: `LoginPage` knows its locators and how to perform login. Tests call `loginPage.loginAs("user", "pass")` instead of raw `driver.findElement()` calls. The primary benefit is maintainability: when a locator changes, I update one page object file, not 40 test files. Secondary benefits are readability (tests read like specifications) and reusability (multiple tests share the same page object).

**Q2: Why should page objects not contain assertions?**

**A:** Because assertions encode expectations, and different tests have different expectations. If `loginAs()` asserts "Dashboard loaded," it can't be used in a test that expects login to fail. Page objects should provide state — `getErrorMessage()`, `getPageTitle()`, `isElementVisible()` — and let tests make assertions based on their specific scenario. This keeps page objects reusable across positive, negative, and edge-case tests.

**Q3: What is the difference between a page object and a page component?**

**A:** A page object represents a full page — `LoginPage`, `DashboardPage`. It has its own URL, its own purpose, its own test scenarios. A component represents a reusable UI fragment that appears on multiple pages — `HeaderComponent`, `DatePickerComponent`, `ModalDialog`. Components are composed into page objects: `DashboardPage` has-a `HeaderComponent`. This avoids duplicating header logic across every page object.

**Q4: How do you handle pages in a single-page application where the URL doesn't change?**

**A:** I create page objects based on distinct views or states, not URLs. If a SPA shows a login form, then a dashboard, then a settings panel — all at the same URL — I create `LoginPage`, `DashboardPage`, `SettingsPage`. Each page object waits for its characteristic element to be visible before allowing interactions. The "page" in Page Object Model is a logical concept (a distinct UI state), not a physical URL.




| # | Front (Question) | Back (Answer) |
|---|---|---|
| 1 | Why store `By` locators instead of `WebElement` references in page objects? | `WebElement` references go stale when the DOM refreshes (AJAX, navigation, React re-render). Storing `By` locators and resolving elements fresh on each interaction avoids `StaleElementReferenceException`. |
| 2 | What should a page object method return? | Another page object representing the destination page (e.g., `loginAs()` returns `DashboardPage`), or `this` if the action stays on the same page (e.g., `setCheckIn()` returns `this` for chaining). |
| 3 | What is a "God page object" and why is it harmful? | A single page object class that contains locators and methods for the entire application. It becomes unmaintainable (800+ lines), causes merge conflicts, and makes locator ownership unclear. Split into one class per page. |
| 4 | How do you handle shared UI elements (header, footer) across pages? | Extract them as components (`HeaderComponent`). Pages that have the header compose it: `this.header = new HeaderComponent(driver)`. Tests access via `page.header().logout()`. |
| 5 | What locator strategy should you advocate for with developers? | Custom `data-testid` attributes: `<button data-testid="login-button">`. They're stable (won't change with CSS refactors), readable, and clearly signal "this is for automated testing." |
