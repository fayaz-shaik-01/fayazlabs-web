# Synchronization and Waits

> **Module:** 05 — Web Automation > Synchronization & Waits  
> **Prerequisites:** Browser And Dom Fundamentals, Locator Strategy  
> **Mastery Target:** L3 (Independent) → L4 (Teaching)

---

## Quick Overview (Layer 1)

**What:** Synchronization is the art of making your test wait for the browser to be ready before acting. The browser and your test code run in separate processes at different speeds — the test sends commands instantly while the browser needs time to fetch resources, execute JavaScript, render DOM changes, and complete animations. Waits are the mechanism to bridge this timing gap.

**Why:** You've already hit this at work. Intermittent `NoSuchElementException`, tests that pass locally but fail in CI, `Thread.sleep(3000)` scattered through the codebase "because it works." These are all symptoms of poor synchronization. With 3 years of Selenium experience, you know about `WebDriverWait` but may not fully understand *why* Playwright rarely needs explicit waits, or how to build custom wait conditions for complex scenarios. This topic eliminates the #1 cause of flaky tests.

**Where:** Every test action — clicking, typing, asserting, navigating — has a synchronization concern. Waits appear in page objects, test methods, fixtures, and framework utilities.

<MentalModel>

Think of your test and the browser as two people working on an assembly line. Your test is the **foreman** issuing instructions ("type in the email," "click submit"). The browser is the **worker** who needs time to prepare the workstation before each task. `Thread.sleep()` is the foreman blindly waiting 5 seconds between every instruction — wasteful when the worker is fast, insufficient when the worker is slow. Explicit waits are the foreman watching the worker and moving on the moment the workstation is ready. Playwright's auto-waiting is a smart foreman who automatically checks readiness before every instruction.

</MentalModel>


<KeyTakeaways>

1. **`Thread.sleep()` is never the answer** — it's either too long (slows the suite) or too short (causes flaky failures)
2. **Selenium requires explicit waits everywhere** — `WebDriverWait` + `ExpectedConditions` is the standard pattern
3. **Playwright auto-waits for actionability** — it checks visibility, stability, enabled state, and more before every action
4. **Implicit waits in Selenium are a trap** — they combine poorly with explicit waits and hide real timing issues
5. **Custom wait conditions handle what built-in waits can't** — waiting for API responses, animation completion, or element count changes

</KeyTakeaways>

## First-Principles Explanation (Layer 2)

### The Timing Problem

Your test code executes in milliseconds. Browser operations take variable time:

```
Test Code (instant)              Browser (variable time)
───────────────────              ──────────────────────
page.goto('/login')   ────→     DNS + HTTP + HTML parse + JS execute + render
                                 50ms–5000ms depending on network/CPU
fill('Email', '...')  ────→     Find input, focus it, dispatch key events
                                 5ms–500ms depending on DOM readiness
click('Login')        ────→     Find button, scroll into view, click, 
                                 handle event, send API request
                                 10ms–2000ms depending on JS handlers
expect(heading)       ────→     Wait for API response, state update, 
                                 React re-render, DOM paint
                                 200ms–10000ms depending on server/network
```

The gap between "test sends command" and "browser is ready" is where all synchronization problems live.

### Why Thread.sleep() Is Wrong


```java
// The "I don't understand waits" pattern
driver.get("http://localhost:5173/login");
Thread.sleep(3000);  // Wait 3 seconds and hope the page is ready
driver.findElement(By.id("email")).sendKeys("user@staynest.com");

Thread.sleep(1000);  // Wait again before typing password
driver.findElement(By.id("password")).sendKeys("password123");

driver.findElement(By.id("login-button")).click();
Thread.sleep(5000);  // Wait for login to complete
assertEquals("Dashboard", driver.getTitle());
```

**Problems with Thread.sleep():**

| Problem | Impact |
|---|---|
| **Too slow** | 3s sleep × 200 tests = 10 minutes of pure waiting doing nothing |
| **Too fast** | On a slow CI server, 3 seconds isn't enough → flaky failure |
| **Non-deterministic** | Works today, fails tomorrow when server is under load |
| **Hides real issues** | If the page *should* load in 1 second but takes 5, the sleep masks a real performance bug |
| **Not intention-revealing** | `sleep(3000)` doesn't explain *what* you're waiting for |

**Total test time with sleeps:** Assume a test uses 3 sleeps averaging 3s each. A suite of 200 tests spends **30 minutes** in `Thread.sleep()` — time where the CPU is idle, the browser is ready, and no useful work is happening.

### Selenium Waits — The Full Taxonomy

#### 1. Implicit Wait (Avoid)


```java
// Set once — applies globally to every findElement call
driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));

// Now every findElement will poll for up to 10 seconds before throwing
driver.findElement(By.id("email"));  // Waits up to 10s for element to appear in DOM
```

**Why to avoid implicit waits:**
- They poll for DOM *presence* only, not visibility or clickability
- They combine unpredictably with explicit waits (timeouts can double or conflict)
- They slow down `findElements()` — when you *expect* zero elements, it waits the full timeout
- They mask the actual timing issue — you don't know *which* find needed waiting

#### 2. Explicit Wait (Use This)


```java
// Explicit wait — targeted, specific, intention-revealing
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));

// Wait for element to be VISIBLE (in DOM + displayed)
WebElement email = wait.until(
    ExpectedConditions.visibilityOfElementLocated(By.cssSelector("[data-testid='email-input']"))
);

// Wait for element to be CLICKABLE (visible + enabled + not obscured)
WebElement loginBtn = wait.until(
    ExpectedConditions.elementToBeClickable(By.cssSelector("[data-testid='login-button']"))
);

// Wait for element to DISAPPEAR (loading spinner gone)
wait.until(
    ExpectedConditions.invisibilityOfElementLocated(By.cssSelector("[data-testid='loading-spinner']"))
);

// Wait for text to be present
wait.until(
    ExpectedConditions.textToBePresentInElementLocated(
        By.cssSelector("[data-testid='welcome-msg']"), "Welcome"
    )
);

// Wait for URL to change (after navigation)
wait.until(ExpectedConditions.urlContains("/dashboard"));

// Wait for title
wait.until(ExpectedConditions.titleIs("StayNest Dashboard"));
```

**Common ExpectedConditions:**

| Condition | Waits For | Use Case |
|---|---|---|
| `presenceOfElementLocated` | Element in DOM (may be hidden) | Element exists but might not be visible yet |
| `visibilityOfElementLocated` | Element in DOM AND displayed | Most common — element ready to read |
| `elementToBeClickable` | Visible + enabled + not obscured | Before clicking buttons/links |
| `invisibilityOfElementLocated` | Element removed or hidden | Spinner/overlay disappearing |
| `textToBePresentInElement` | Element contains specific text | Dynamic text loaded from API |
| `numberOfElementsToBe` | Exact count of matching elements | Search results fully loaded |
| `stalenessOf` | Element no longer attached to DOM | After re-render, old element gone |
| `alertIsPresent` | JavaScript alert dialog | Before switching to alert |
| `frameToBeAvailableAndSwitchToIt` | iframe loaded and switched | Before interacting with iframe content |

#### 3. Fluent Wait (Explicit Wait with Custom Polling)


```java
// Fluent wait — explicit wait with custom polling interval and ignored exceptions
Wait<WebDriver> fluentWait = new FluentWait<>(driver)
    .withTimeout(Duration.ofSeconds(30))           // Max wait time
    .pollingEvery(Duration.ofMillis(500))           // Check every 500ms (default is 500ms)
    .ignoring(NoSuchElementException.class)         // Don't fail on this during polling
    .ignoring(StaleElementReferenceException.class) // Also ignore stale element
    .withMessage("Timed out waiting for hotel search results to load");

WebElement results = fluentWait.until(driver -> {
    WebElement el = driver.findElement(By.cssSelector("[data-testid='search-results']"));
    return el.isDisplayed() ? el : null;  // Return null to keep waiting
});
```

**When to use Fluent Wait over Explicit Wait:**
- When you need a custom polling interval (e.g., poll every 2s for a slow operation)
- When you need to ignore specific exceptions during polling
- When you want a custom error message for better diagnostics
- When the wait condition is complex and can't be expressed with `ExpectedConditions`

### Playwright Auto-Waiting — Why It's Better

Playwright performs **actionability checks** before every action, automatically:

```
page.click('#submit')
       │
       ▼
┌─────────────────────────────┐
│  Actionability Checks       │
│  (automatic, no code needed)│
│                             │
│  ✓ Attached to DOM?         │
│  ✓ Visible?                 │
│  ✓ Stable? (not animating)  │
│  ✓ Enabled?                 │
│  ✓ Receives events?         │
│    (not obscured by overlay)│
└─────────────┬───────────────┘
              │ All checks pass
              ▼
        [Click performed]
```


```typescript
import { test, expect } from '@playwright/test';

test('login flow — no explicit waits needed', async ({ page }) => {
    await page.goto('http://localhost:5173/login');

    // Auto-waits for input to be visible, stable, and enabled before filling
    await page.getByLabel('Email').fill('admin@staynest.com');
    await page.getByLabel('Password').fill('Admin123!');

    // Auto-waits for button to be clickable (visible, enabled, not obscured)
    await page.getByRole('button', { name: 'Login' }).click();

    // Assertion auto-retries — keeps checking until timeout (default 5s)
    await expect(page.getByRole('heading', { name: /welcome/i }))
        .toBeVisible();

    // No Thread.sleep, no WebDriverWait, no ExpectedConditions
    // Playwright handles all timing automatically
});
```

**Playwright's auto-waiting works because:**
1. **Locators are lazy** — they don't resolve until the action is performed
2. **Actions auto-retry** — if the element isn't ready, Playwright retries until the timeout
3. **Assertions auto-retry** — `expect(locator).toBeVisible()` keeps checking, unlike Selenium's immediate assertion
4. **Navigation auto-waits** — `page.goto()` waits for `load` event by default

### When Playwright Needs Explicit Waits

Even with auto-waiting, some scenarios need manual synchronization:


```typescript
// 1. Wait for a specific network response
await page.goto('http://localhost:5173/search');
const responsePromise = page.waitForResponse(
    response => response.url().includes('/api/v1/hotels') && response.status() === 200
);
await page.getByRole('button', { name: 'Search' }).click();
const response = await responsePromise;  // Wait for API to respond

// 2. Wait for navigation after an action
await Promise.all([
    page.waitForURL('**/dashboard'),
    page.getByRole('button', { name: 'Login' }).click(),
]);

// 3. Wait for element count to stabilize (lazy loading)
await expect(page.getByTestId('hotel-card')).toHaveCount(10);

// 4. Wait for an element to be hidden (loading state to finish)
await expect(page.getByTestId('loading-spinner')).toBeHidden();

// 5. Wait for a specific condition using page.waitForFunction
await page.waitForFunction(() => {
    const results = document.querySelectorAll('[data-testid="hotel-card"]');
    return results.length >= 5;
});
```

### Custom Wait Conditions

When built-in waits aren't enough, build custom ones:

**Selenium — Custom ExpectedCondition:**


```java
// Custom wait: wait for element count to stabilize (no more elements being added)
public static ExpectedCondition<Boolean> elementCountStabilized(By locator, Duration stableFor) {
    return new ExpectedCondition<Boolean>() {
        private int lastCount = -1;
        private Instant lastChange = Instant.now();

        @Override
        public Boolean apply(WebDriver driver) {
            int currentCount = driver.findElements(locator).size();
            if (currentCount != lastCount) {
                lastCount = currentCount;
                lastChange = Instant.now();
                return false;
            }
            return Duration.between(lastChange, Instant.now()).compareTo(stableFor) >= 0;
        }

        @Override
        public String toString() {
            return String.format("element count to stabilize at %d for %s", lastCount, stableFor);
        }
    };
}

// Usage: wait for hotel cards to stop loading (infinite scroll)
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(15));
wait.until(elementCountStabilized(
    By.cssSelector("[data-testid='hotel-card']"),
    Duration.ofSeconds(2)  // Count must be stable for 2 seconds
));
```


```java
// Custom wait: wait for an API call to complete (via JavaScript)
public static ExpectedCondition<Boolean> ajaxComplete() {
    return driver -> {
        JavascriptExecutor js = (JavascriptExecutor) driver;
        // Check if jQuery is present and has active AJAX requests
        return (Boolean) js.executeScript(
            "return (typeof jQuery === 'undefined') || (jQuery.active === 0);"
        );
    };
}

// Custom wait: wait for React to finish rendering
public static ExpectedCondition<Boolean> reactRenderComplete() {
    return driver -> {
        JavascriptExecutor js = (JavascriptExecutor) driver;
        return (Boolean) js.executeScript(
            "return document.querySelector('[data-reactroot]') !== null && " +
            "document.readyState === 'complete';"
        );
    };
}
```

**Playwright — Custom assertions with polling:**


```typescript
// Custom wait: poll until a condition is true (with auto-retry)
import { expect } from '@playwright/test';

// Wait for localStorage to have a JWT token (after login)
await expect(async () => {
    const token = await page.evaluate(() => localStorage.getItem('authToken'));
    expect(token).not.toBeNull();
}).toPass({ timeout: 10_000 });

// Wait for a CSS animation to complete
await expect(async () => {
    const animating = await page.evaluate((sel) => {
        const el = document.querySelector(sel);
        return el ? getComputedStyle(el).animationPlayState === 'running' : true;
    }, '[data-testid="modal"]');
    expect(animating).toBe(false);
}).toPass({ timeout: 5_000 });

// Wait for specific attribute value
await expect(page.getByTestId('submit-btn')).toHaveAttribute('aria-disabled', 'false');
```

### Race Conditions in Browser Tests

#### Race Condition 1: Element Appears Then Disappears

```
Timeline:
─────────────────────────────────────────────────
[Click Search]  →  [Loading...]  →  [Results]  →  [Sort applied]  →  [Results re-render]
                         ↑                              ↑
                  Test finds "Loading"           Test acts on old element
                  but asserts on results         which has been replaced
```


```java
// BAD: Race between loading state and results
driver.findElement(By.cssSelector("[data-testid='search-button']")).click();
// Results might flash briefly, then loading appears, then final results
WebElement firstResult = driver.findElement(By.cssSelector("[data-testid='hotel-card']"));

// GOOD: Wait for loading to finish, THEN find results
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
wait.until(ExpectedConditions.invisibilityOfElementLocated(
    By.cssSelector("[data-testid='loading-spinner']")
));
// Now results are stable
List<WebElement> results = driver.findElements(By.cssSelector("[data-testid='hotel-card']"));
```

#### Race Condition 2: Stale Element Reference


```java
// BAD: Element reference becomes stale after DOM re-render
WebElement card = driver.findElement(By.cssSelector("[data-testid='hotel-card']:first-child"));
driver.findElement(By.cssSelector("[data-testid='sort-price']")).click();  // Re-renders list
String name = card.getText();  // StaleElementReferenceException — card was re-rendered

// GOOD: Re-locate after actions that cause re-renders
driver.findElement(By.cssSelector("[data-testid='sort-price']")).click();
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
WebElement card = wait.until(ExpectedConditions.visibilityOfElementLocated(
    By.cssSelector("[data-testid='hotel-card']:first-child")
));
String name = card.getText();
```

## Practical Implementation (Layer 3)

### Practical Exercise: Convert Thread.sleep() Tests to Proper Waits

**Before — Thread.sleep() Everywhere (Selenium):**


```java
public class SleepyLoginTest {
    @Test
    void testLoginAndViewDashboard() {
        driver.get("http://localhost:5173/login");
        Thread.sleep(3000);  // Wait for page

        driver.findElement(By.id("email")).sendKeys("admin@staynest.com");
        driver.findElement(By.id("password")).sendKeys("Admin123!");
        driver.findElement(By.id("login-button")).click();

        Thread.sleep(5000);  // Wait for login API and redirect

        String welcomeText = driver.findElement(By.className("welcome-header")).getText();
        assertEquals("Welcome, Admin", welcomeText);

        driver.findElement(By.linkText("Hotels")).click();
        Thread.sleep(3000);  // Wait for hotels to load

        int hotelCount = driver.findElements(By.className("hotel-card")).size();
        assertTrue(hotelCount > 0, "Expected at least one hotel");

        Thread.sleep(2000);  // Just in case
    }
    // Total wasted time: 13 seconds of Thread.sleep() per test run
}
```

**After — Explicit Waits (Selenium):**


```java
public class ProperLoginTest {
    private WebDriverWait wait;

    @BeforeEach
    void setup() {
        wait = new WebDriverWait(driver, Duration.ofSeconds(10));
    }

    @Test
    void testLoginAndViewDashboard() {
        driver.get("http://localhost:5173/login");

        // Wait for login form to be visible (SPA rendering complete)
        wait.until(ExpectedConditions.visibilityOfElementLocated(
            By.cssSelector("[data-testid='login-form']")
        ));

        driver.findElement(By.cssSelector("[data-testid='email-input']"))
              .sendKeys("admin@staynest.com");
        driver.findElement(By.cssSelector("[data-testid='password-input']"))
              .sendKeys("Admin123!");
        driver.findElement(By.cssSelector("[data-testid='login-button']")).click();

        // Wait for URL to change to dashboard (login API complete + redirect)
        wait.until(ExpectedConditions.urlContains("/dashboard"));

        // Wait for welcome text to appear
        WebElement welcome = wait.until(
            ExpectedConditions.visibilityOfElementLocated(
                By.cssSelector("[data-testid='welcome-header']")
            )
        );
        assertEquals("Welcome, Admin", welcome.getText());

        // Navigate to hotels
        driver.findElement(By.cssSelector("[data-testid='nav-hotels']")).click();

        // Wait for hotel cards to appear
        wait.until(ExpectedConditions.numberOfElementsToBeMoreThan(
            By.cssSelector("[data-testid='hotel-card']"), 0
        ));

        int hotelCount = driver.findElements(
            By.cssSelector("[data-testid='hotel-card']")
        ).size();
        assertTrue(hotelCount > 0, "Expected at least one hotel");
    }
    // Total time: only waits as long as actually needed — typically 2-4 seconds
}
```

**After — Playwright (best):**


```typescript
import { test, expect } from '@playwright/test';

test('login and view dashboard', async ({ page }) => {
    await page.goto('http://localhost:5173/login');

    // Auto-waits for inputs to be ready
```

### Practical Exercise: Wait for Complex Conditions


```typescript
// Scenario: StayNest search with filters — multiple async operations

import { test, expect } from '@playwright/test';

test('search with filters waits correctly', async ({ page }) => {
    await page.goto('http://localhost:5173/search');

    // Type in search — triggers debounced API call
    await page.getByLabel('Location').fill('New York');

    // Wait for autocomplete dropdown to appear
    await expect(page.getByTestId('autocomplete-dropdown')).toBeVisible();
    await page.getByTestId('autocomplete-dropdown')
        .getByText('New York, NY').click();

    // Set dates
    await page.getByLabel('Check-in').fill('2025-08-01');
    await page.getByLabel('Check-out').fill('2025-08-05');

    // Click search — wait for both the request and response
    const searchResponse = page.waitForResponse(
        resp => resp.url().includes('/api/v1/hotels/search') && resp.ok()
    );
    await page.getByRole('button', { name: 'Search' }).click();
    await searchResponse;

    // Wait for loading to finish and results to render
    await expect(page.getByTestId('loading-spinner')).toBeHidden();
    await expect(page.getByTestId('hotel-card').first()).toBeVisible();

    // Apply a filter — triggers re-fetch
    const filterResponse = page.waitForResponse(
        resp => resp.url().includes('/api/v1/hotels/search') && resp.ok()
    );
    await page.getByLabel('Max Price').fill('200');
    await page.getByRole('button', { name: 'Apply Filters' }).click();
    await filterResponse;

    // Assert filtered results
    await expect(page.getByTestId('hotel-card')).not.toHaveCount(0);

    // Verify all displayed prices are under $200
    const prices = await page.getByTestId('hotel-price').allTextContents();
    for (const price of prices) {
        const numericPrice = parseInt(price.replace(/[^0-9]/g, ''));
        expect(numericPrice).toBeLessThanOrEqual(200);
    }
});
```

## Failure and Debugging (Layer 4)

### Failure: Implicit + Explicit Wait Conflict

**The Broken Test:**


```java
// NEVER mix implicit and explicit waits
driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));

WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(5));
// Q: How long does this actually wait?
// A: Unpredictable — could be 5s, 10s, or 15s depending on the interaction
wait.until(ExpectedConditions.visibilityOfElementLocated(By.id("results")));
```

**Root Cause:** When both implicit and explicit waits are active, each `findElement` call inside the explicit wait's polling loop waits up to the implicit timeout. If the explicit wait polls 10 times with a 10-second implicit wait, the worst case is 100 seconds — not the 5 seconds you configured.

**The Fix:**


```java
// Set implicit wait to 0, use explicit waits exclusively
driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(0));

// All waiting is explicit — predictable and debuggable
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
WebElement results = wait.until(
    ExpectedConditions.visibilityOfElementLocated(By.id("results"))
);
```

### Failure: Playwright Auto-Wait Timeout on Overlapping Element

**The Broken Test:**


```typescript
// Playwright's click() fails — element is obscured by a cookie banner
await page.getByRole('button', { name: 'Book Now' }).click();
// Error: locator.click: Element is not visible or is obscured by another element
// Element is covered by <div class="cookie-banner">...</div>
```

**Root Cause:** Playwright's actionability checks detected that the cookie banner is covering the "Book Now" button. Unlike Selenium, Playwright won't click through overlapping elements.

**The Fix:**


```typescript
// Dismiss the cookie banner first
await page.getByRole('button', { name: 'Accept Cookies' }).click();

// Or, if it's a test concern and not a real user flow:
await page.evaluate(() => {
    document.querySelector('.cookie-banner')?.remove();
});

// Now the button is no longer obscured
await page.getByRole('button', { name: 'Book Now' }).click();
```

### Failure: Waiting for Wrong Condition

**The Broken Test:**


```java
// Waits for presence but needs visibility
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
WebElement element = wait.until(
    ExpectedConditions.presenceOfElementLocated(By.id("results"))
);
element.click();  // ElementNotInteractableException — element is in DOM but hidden!
```

**Root Cause:** `presenceOfElementLocated` only checks that the element is in the DOM. The element might have `display: none` or `visibility: hidden`. You need `elementToBeClickable` before clicking.

**Decision guide:**

```
What do you want to do?         →  Which wait condition?
─────────────────────────────      ────────────────────────
Read text from element          →  visibilityOfElementLocated
Click a button/link             →  elementToBeClickable
Check element exists in DOM     →  presenceOfElementLocated
Assert element is gone          →  invisibilityOfElementLocated
Wait for page navigation        →  urlContains / urlToBe
Wait for text content           →  textToBePresentInElement
```

## Engineering Judgment (Layer 5)

### Choosing the Right Wait Strategy

| Scenario | Selenium Approach | Playwright Approach |
|---|---|---|
| Element appearing after page load | `visibilityOfElementLocated` | Auto-wait (no code) |
| Button becoming clickable | `elementToBeClickable` | Auto-wait (no code) |
| Spinner disappearing | `invisibilityOfElementLocated` | `expect(spinner).toBeHidden()` |
| Text loading from API | `textToBePresentInElement` | `expect(el).toHaveText('...')` |
| URL change after navigation | `urlContains("/dashboard")` | `expect(page).toHaveURL(...)` |
| API response completing | Custom + JavaScriptExecutor | `page.waitForResponse(...)` |
| Animation completing | Custom + JS check | `expect().toPass()` with polling |
| Multiple elements loading | `numberOfElementsToBe` | `expect(locator).toHaveCount(n)` |

### Wait Timeout Strategy

| Test Type | Recommended Timeout | Rationale |
|---|---|---|
| Unit/Component | 2–5 seconds | Fast operations, local rendering |
| Integration (UI) | 10–15 seconds | API calls, database queries |
| E2E (full flow) | 15–30 seconds | Multiple services, external APIs |
| Performance-sensitive | 3–5 seconds | You're testing that it's fast |
| File upload/download | 30–60 seconds | Large file operations |

**Global timeout vs per-wait timeout:**


```typescript
// Playwright — set global timeout in config
// playwright.config.ts
export default defineConfig({
    timeout: 30_000,          // Per-test timeout: 30 seconds
    expect: {
        timeout: 5_000,       // Per-assertion timeout: 5 seconds
    },
    use: {
        actionTimeout: 10_000, // Per-action timeout: 10 seconds
        navigationTimeout: 15_000,
    },
});
```

```java
    private static final Duration LONG_TIMEOUT = Duration.ofSeconds(30);

        return new WebDriverWait(driver, DEFAULT_TIMEOUT);

        return new WebDriverWait(driver, LONG_TIMEOUT);

        return new WebDriverWait(driver, timeout);
    }
```

### When to Add Explicit Waits Even in Playwright

Playwright's auto-waiting covers 90% of cases. Add explicit waits for:

1. **Waiting for a network request** before asserting on data the response populates
2. **Waiting for download/upload** operations that Playwright can't auto-detect
3. **Asserting on element count** — auto-wait doesn't apply to `count()` (use `toHaveCount()`)
4. **Waiting for third-party content** (ads, embedded widgets) that load independently
5. **Complex multi-step conditions** where you need all parts to be true simultaneously

## Interview and Revision (Layer 6)

### Fundamental Questions

**Q1: Why is Thread.sleep() problematic in test automation?**

**A:** Thread.sleep() is a fixed delay that doesn't adapt to actual conditions. It's either too long (wasting time — multiply by hundreds of tests and you lose minutes per run) or too short (causing flaky failures when the environment is slow). It's also non-deterministic — the same test passes locally but fails in CI because the fixed delay doesn't account for server load. And it hides performance regressions — if a page should load in 1 second but takes 8, a 10-second sleep masks the problem. The alternative is explicit waits that poll for a condition and return immediately when it's met.

**Q2: What are the three types of waits in Selenium and when should you use each?**

**A:** (1) Implicit wait — a global timeout applied to every `findElement` call; I avoid it because it interacts unpredictably with explicit waits, only checks DOM presence (not visibility), and makes `findElements()` slow when expecting zero results. (2) Explicit wait — `WebDriverWait` with `ExpectedConditions` targeted at a specific element and condition; this is my standard approach. (3) Fluent wait — extends explicit wait with custom polling interval, ignored exceptions, and custom messages; I use it for complex or slow-polling scenarios.

**Q3: How does Playwright's auto-waiting work, and when do you still need explicit waits?**

**A:** Playwright performs actionability checks before every action: it waits for the element to be attached to DOM, visible, stable (not animating), enabled, and receiving events (not obscured). This eliminates most explicit waits. I still need explicit waits for: (1) network responses (`waitForResponse`) when I need to assert on API data, (2) element count assertions (`toHaveCount`), (3) URL changes after navigation, and (4) complex custom conditions that Playwright can't auto-detect.

### Scenario-Based Questions

**S1: "Your Selenium test suite takes 45 minutes to run. You notice Thread.sleep() calls throughout. How do you fix it?"**

**A:** First, I'd audit the codebase with `grep -rn "Thread.sleep"` to find all instances. Then I'd categorize them: (1) sleeps after navigation → replace with `urlContains` or `visibilityOfElementLocated`, (2) sleeps before clicking → replace with `elementToBeClickable`, (3) sleeps after clicking → replace with waiting for the expected result (new element appears, spinner disappears, URL changes). I'd create a utility class with common wait patterns so the team has easy alternatives. Finally, I'd add a static analysis rule to flag new `Thread.sleep()` calls in code review.

**S2: "Your Playwright test fails in CI with a timeout but passes locally. What do you investigate?"**

**A:** First, I'd check the CI environment: is it running headless (different timing), on a slower machine, with network latency to test servers? I'd look at the Playwright trace file (if configured) to see exactly where it timed out and what the page looked like. Common causes: (1) slower rendering on CI → increase the specific assertion timeout, not the global one, (2) a third-party resource blocked in CI (font, analytics, ad) → mock or block it, (3) different viewport size in CI triggering a responsive layout change, (4) the test server not fully started before tests begin → add a health check wait to CI setup.
