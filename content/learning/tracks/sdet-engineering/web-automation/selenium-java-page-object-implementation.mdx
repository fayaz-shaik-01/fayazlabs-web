# Page Object Implementation — Selenium Java

> **Module:** 05 — Web Automation > Selenium Java > Page Object Implementation  
> **Prerequisites:** Setup And First Tests, Page And Screen Objects, Oop Fundamentals  
> **Mastery Target:** L3 (Independent) → L4 (Engineering Judgment)

## Quick Overview (Layer 1)

**What:** The Page Object Model (POM) in Selenium Java separates page structure (locators, interaction methods) from test logic (assertions, flows). Each page in the application becomes a Java class that encapsulates all locators and exposes readable action methods. Tests call `loginPage.loginAs("user", "pass")` instead of raw `driver.findElement(...).sendKeys(...)`.

**Why:** You've used POM before — most Selenium projects have some version of it. But there's a gap between "I have page object classes" and "my POM is well-designed." Common problems: PageFactory annotations that break with dynamic elements, page objects that contain assertions, inheritance hierarchies that go four levels deep, and component objects that are never extracted (so every page duplicates the navbar locators). This file addresses all of these with a production-grade POM hierarchy for StayNest.

**Where:** Every Selenium test class delegates element interaction to page objects. The patterns here — BasePage utilities, method chaining through return types, component extraction — are the same patterns you'll use in Appium screen objects and any other UI automation tool.

<MentalModel>

Think of a POM hierarchy as an **organizational chart for your UI**. `BasePage` is the CEO — it provides shared capabilities (wait, click, type) that every page needs. Each concrete page (LoginPage, SearchPage, BookingPage) is a department — it owns its specific locators and actions. Component objects (NavigationBar, DatePicker) are shared services — they serve multiple departments without being duplicated.

</MentalModel>


<KeyTakeaways>

1. **BasePage provides shared utilities** — `waitForVisible()`, `click()`, `type()`, `getText()` wrap raw Selenium calls with waits. Concrete pages never call `driver.findElement` directly.
2. **Methods return page objects to model navigation** — `loginPage.loginAs(...)` returns `DashboardPage` because successful login navigates there. This makes tests read like user stories.
3. **No assertions in page objects** — page objects expose state (`getErrorMessage()`, `isButtonEnabled()`). Tests make the assertions. This decouples page structure from test expectations.
4. **PageFactory has real downsides** — `@FindBy` initializes elements eagerly, doesn't play well with dynamic DOM or explicit waits, and encourages storing WebElement references that go stale.
5. **Extract component objects for shared UI elements** — navbar, footer, date picker, modals appear on multiple pages. One component class, many pages that use it.

</KeyTakeaways>

## First-Principles Explanation (Layer 2)

### BasePage: The Foundation

BasePage wraps raw Selenium calls with explicit waits and provides a clean API for all concrete pages. This eliminates `WebDriverWait` boilerplate from every page class.


```java
import org.openqa.selenium.*;
import org.openqa.selenium.support.ui.ExpectedConditions;
import org.openqa.selenium.support.ui.WebDriverWait;

import java.time.Duration;

public abstract class BasePage {

    protected final WebDriver driver;
    protected final WebDriverWait wait;

    private static final Duration DEFAULT_TIMEOUT = Duration.ofSeconds(10);

    protected BasePage(WebDriver driver) {
        this.driver = driver;
        this.wait = new WebDriverWait(driver, DEFAULT_TIMEOUT);
    }

    // --- Core interaction methods ---

    protected WebElement waitForVisible(By locator) {
        return wait.until(ExpectedConditions.visibilityOfElementLocated(locator));
    }

    protected WebElement waitForClickable(By locator) {
        return wait.until(ExpectedConditions.elementToBeClickable(locator));
    }

    protected void click(By locator) {
        waitForClickable(locator).click();
    }

    protected void type(By locator, String text) {
        WebElement element = waitForVisible(locator);
        element.clear();
        element.sendKeys(text);
    }

    protected String getText(By locator) {
        return waitForVisible(locator).getText();
    }

    protected String getAttribute(By locator, String attribute) {
        return waitForVisible(locator).getAttribute(attribute);
    }

    protected boolean isDisplayed(By locator) {
        try {
            return driver.findElement(locator).isDisplayed();
        } catch (NoSuchElementException e) {
            return false;
        }
    }

    protected void waitForUrlContains(String urlFragment) {
        wait.until(ExpectedConditions.urlContains(urlFragment));
    }

    protected void waitForInvisibility(By locator) {
        wait.until(ExpectedConditions.invisibilityOfElementLocated(locator));
    }

    // --- Page readiness ---

    public String getCurrentUrl() {
        return driver.getCurrentUrl();
    }

    public String getPageTitle() {
        return driver.getTitle();
    }
}
```

**Design decisions:**
- `BasePage` is `abstract` — it's never instantiated directly, only extended
- `driver` and `wait` are `protected` — accessible to subclasses but not to test classes
- Interaction methods are `protected` — tests call page-specific methods, not generic `click(By)`
- Every interaction uses explicit waits — no raw `findElement` that could race with the DOM

### PageFactory and @FindBy — Why Many Teams Avoid It

Selenium's `PageFactory` uses `@FindBy` annotations to declare locators and initializes them via `PageFactory.initElements()`:


```java
import org.openqa.selenium.support.FindBy;
import org.openqa.selenium.support.PageFactory;

public class LoginPageWithFactory {

    @FindBy(id = "email")
    private WebElement emailInput;

    @FindBy(id = "password")
    private WebElement passwordInput;

    @FindBy(css = "[data-testid='login-button']")
    private WebElement loginButton;

    public LoginPageWithFactory(WebDriver driver) {
        PageFactory.initElements(driver, this);
    }

    public void loginAs(String email, String password) {
        emailInput.sendKeys(email);      // No explicit wait — risky!
        passwordInput.sendKeys(password);
        loginButton.click();
    }
}
```

**Problems with PageFactory:**
1. **No built-in waits** — `@FindBy` elements are proxies that call `findElement` on first use. If the element isn't in the DOM yet, you get `NoSuchElementException`. You still need explicit waits, defeating the purpose.
2. **Stale elements** — stored WebElement references go stale when React re-renders. Without PageFactory, you re-find on every interaction.
3. **Limited locator support** — `@FindBy` supports standard locators but not custom conditions like "wait until clickable."
4. **Hard to debug** — when a `@FindBy` element fails, the stack trace points to the proxy, not the actual locator evaluation.

**Recommendation:** Use `By` locators stored as constants with BasePage helper methods. It's more explicit, more debuggable, and works naturally with waits.

### Page Methods Return Page Objects

When an action navigates to a different page, the method's return type communicates this:


```java
public class LoginPage extends BasePage {

    // Successful login → navigates to DashboardPage
    public DashboardPage loginAs(String email, String password) {
        type(EMAIL_INPUT, email);
        type(PASSWORD_INPUT, password);
        click(LOGIN_BUTTON);
        waitForUrlContains("/dashboard");
        return new DashboardPage(driver);
    }

    // Failed login → stays on LoginPage
    public LoginPage loginWithInvalidCredentials(String email, String password) {
        type(EMAIL_INPUT, email);
        type(PASSWORD_INPUT, password);
        click(LOGIN_BUTTON);
        waitForVisible(ERROR_MESSAGE);
        return this;  // stay on the same page
    }
}
```

This makes tests self-documenting:


```java
// The return types tell the reader exactly what navigation happens
DashboardPage dashboard = loginPage.loginAs("user@staynest.com", "pass");
SearchResultsPage results = dashboard.searchForProperty("Austin");
BookingPage booking = results.selectProperty(0);
```

### Component Objects for Reusable UI Parts

The StayNest navigation bar appears on every page after login. Instead of duplicating its locators in DashboardPage, SearchPage, and BookingPage, extract it as a component:


```java
public class NavigationBar {

    private final WebDriver driver;
    private final WebDriverWait wait;

    private static final By SEARCH_INPUT = By.cssSelector("[data-testid='nav-search']");
    private static final By PROFILE_MENU = By.cssSelector("[data-testid='profile-menu']");
    private static final By LOGOUT_BUTTON = By.cssSelector("[data-testid='logout-btn']");
    private static final By NOTIFICATIONS = By.cssSelector("[data-testid='notifications']");

    public NavigationBar(WebDriver driver) {
        this.driver = driver;
        this.wait = new WebDriverWait(driver, Duration.ofSeconds(10));
    }

    public SearchResultsPage searchFor(String query) {
        WebElement searchInput = wait.until(
            ExpectedConditions.visibilityOfElementLocated(SEARCH_INPUT)
        );
        searchInput.clear();
        searchInput.sendKeys(query);
        searchInput.sendKeys(Keys.ENTER);
        return new SearchResultsPage(driver);
    }

    public LoginPage logout() {
        wait.until(ExpectedConditions.elementToBeClickable(PROFILE_MENU)).click();
        wait.until(ExpectedConditions.elementToBeClickable(LOGOUT_BUTTON)).click();
        return new LoginPage(driver);
    }

    public int getNotificationCount() {
        String countText = wait.until(
            ExpectedConditions.visibilityOfElementLocated(NOTIFICATIONS)
        ).getText();
        return Integer.parseInt(countText);
    }
}
```

Pages that have the navbar compose it as a field:


```java
public class DashboardPage extends BasePage {

    private final NavigationBar navbar;

    public DashboardPage(WebDriver driver) {
        super(driver);
        this.navbar = new NavigationBar(driver);
    }

    public NavigationBar navbar() {
        return navbar;
    }

    // ... dashboard-specific methods ...
}
```

## Practical Implementation (Layer 3)

### Complete POM Hierarchy for StayNest


```java
// ── LoginPage.java ──

public class LoginPage extends BasePage {

    private static final By EMAIL_INPUT = By.id("email");
    private static final By PASSWORD_INPUT = By.id("password");
    private static final By LOGIN_BUTTON = By.cssSelector("[data-testid='login-button']");
    private static final By ERROR_MESSAGE = By.cssSelector("[data-testid='error-message']");
    private static final By SIGNUP_LINK = By.cssSelector("[data-testid='signup-link']");

    public LoginPage(WebDriver driver) {
        super(driver);
    }

    public static LoginPage open(WebDriver driver, String baseUrl) {
        driver.get(baseUrl + "/login");
        LoginPage page = new LoginPage(driver);
        page.waitForVisible(LOGIN_BUTTON);
        return page;
    }

    public DashboardPage loginAs(String email, String password) {
        type(EMAIL_INPUT, email);
        type(PASSWORD_INPUT, password);
        click(LOGIN_BUTTON);
        waitForUrlContains("/dashboard");
        return new DashboardPage(driver);
    }

    public LoginPage loginExpectingError(String email, String password) {
        type(EMAIL_INPUT, email);
        type(PASSWORD_INPUT, password);
        click(LOGIN_BUTTON);
        waitForVisible(ERROR_MESSAGE);
        return this;
    }

    public String getErrorMessage() {
        return getText(ERROR_MESSAGE);
    }

    public boolean isLoginButtonEnabled() {
        return waitForVisible(LOGIN_BUTTON).isEnabled();
    }
}
```


```java
// ── SearchPage.java ──

public class SearchPage extends BasePage {

    private final NavigationBar navbar;

    private static final By LOCATION_INPUT = By.cssSelector("[data-testid='location-input']");
    private static final By CHECK_IN_DATE = By.cssSelector("[data-testid='checkin-date']");
    private static final By CHECK_OUT_DATE = By.cssSelector("[data-testid='checkout-date']");
    private static final By GUESTS_INPUT = By.cssSelector("[data-testid='guests-input']");
    private static final By SEARCH_BUTTON = By.cssSelector("[data-testid='search-button']");
    private static final By PROPERTY_CARDS = By.cssSelector("[data-testid='property-card']");
    private static final By NO_RESULTS = By.cssSelector("[data-testid='no-results']");

    public SearchPage(WebDriver driver) {
        super(driver);
        this.navbar = new NavigationBar(driver);
    }

    public NavigationBar navbar() {
        return navbar;
    }

    public SearchPage enterLocation(String location) {
        type(LOCATION_INPUT, location);
        return this;
    }

    public SearchPage enterCheckInDate(String date) {
        type(CHECK_IN_DATE, date);
        return this;
    }

    public SearchPage enterCheckOutDate(String date) {
        type(CHECK_OUT_DATE, date);
        return this;
    }

    public SearchPage enterGuests(int guests) {
        type(GUESTS_INPUT, String.valueOf(guests));
        return this;
    }

    public SearchPage clickSearch() {
        click(SEARCH_BUTTON);
        // Wait for either results or no-results message
        wait.until(driver -> isDisplayed(PROPERTY_CARDS) || isDisplayed(NO_RESULTS));
        return this;
    }

    public int getPropertyCount() {
        return driver.findElements(PROPERTY_CARDS).size();
    }

    public BookingPage selectProperty(int index) {
        List<WebElement> cards = driver.findElements(PROPERTY_CARDS);
        cards.get(index).click();
        waitForUrlContains("/property/");
        return new BookingPage(driver);
    }
}
```

### Test Class Using the POM Hierarchy


```java
public class StayNestBookingFlowTest extends BaseTest {

    private static final String BASE_URL = "http://localhost:5173";

    @Test(description = "Complete booking flow: login → search → book")
    public void testEndToEndBookingFlow() {
        LoginPage loginPage = LoginPage.open(driver, BASE_URL);

        DashboardPage dashboard = loginPage.loginAs("user@staynest.com", "SecurePass123!");

        SearchPage searchPage = dashboard.navbar().searchFor("Austin, TX");
        searchPage.enterCheckInDate("2025-08-01");
        searchPage.enterCheckOutDate("2025-08-05");
        searchPage.enterGuests(2);
        searchPage.clickSearch();

        Assert.assertTrue(searchPage.getPropertyCount() > 0,
            "Expected at least one property in Austin");

        BookingPage bookingPage = searchPage.selectProperty(0);
        String propertyTitle = bookingPage.getPropertyTitle();
        Assert.assertFalse(propertyTitle.isEmpty(), "Property title should not be empty");

        bookingPage.confirmBooking();
        Assert.assertTrue(bookingPage.getConfirmationMessage().contains("confirmed"),
            "Expected booking confirmation message");
    }

    @Test(description = "Invalid login shows error, does not navigate away")
    public void testInvalidLoginStaysOnPage() {
        LoginPage loginPage = LoginPage.open(driver, BASE_URL);

        loginPage.loginExpectingError("bad@email.com", "wrongpass");

        Assert.assertEquals(loginPage.getErrorMessage(), "Invalid email or password");
        Assert.assertTrue(loginPage.getCurrentUrl().contains("/login"),
            "Should remain on login page after failed login");
    }
}
```

## Failure and Debugging (Layer 4)

### Failure: Page Object Returns Wrong Page After Action

**Symptom:** `loginAs()` returns `DashboardPage`, but the login fails silently (API returns 401 without a visible error) and the user stays on the login page. The next method call on `DashboardPage` throws `NoSuchElementException`.

**Root Cause:** The page transition method doesn't verify that navigation actually happened before returning the new page object.


```java
// BROKEN: no verification of navigation
public DashboardPage loginAs(String email, String password) {
    type(EMAIL_INPUT, email);
    type(PASSWORD_INPUT, password);
    click(LOGIN_BUTTON);
    return new DashboardPage(driver); // Returns DashboardPage even if login failed!
}

// FIXED: wait for URL change before returning
public DashboardPage loginAs(String email, String password) {
    type(EMAIL_INPUT, email);
    type(PASSWORD_INPUT, password);
    click(LOGIN_BUTTON);
    waitForUrlContains("/dashboard"); // Throws TimeoutException if login fails
    return new DashboardPage(driver);
}
```

### Failure: Component Object Constructed Too Early

**Symptom:** `NavigationBar` methods throw `NoSuchElementException` because the navbar hasn't rendered yet.

**Root Cause:** The navbar component is constructed in the page constructor, but its elements don't exist until after the page fully renders.

<BestPractice>

**Fix:** Component methods should use waits internally, not assume elements exist at construction time. The component constructor should only store the driver, not find any elements.

</BestPractice>

## Engineering Judgment (Layer 5)

### BasePage Helpers: How Much to Wrap

| Approach | Pros | Cons |
|---|---|---|
| Thin wrappers (just add waits) | Simple, easy to understand | Every page still has boilerplate |
| Rich wrappers (dropdown, datepicker, table) | Less code in pages, consistent behavior | Abstraction can hide tool behavior |
| No BasePage (each page uses WebDriverWait directly) | Full control, no abstraction overhead | Massive duplication, inconsistent wait usage |

**Recommendation:** Start with thin wrappers (wait + interact). Add rich wrappers only when you see the same interaction pattern in three or more pages. Over-abstraction in BasePage creates a "framework within a framework" that nobody can debug.

### One Base Class vs Interface Composition

For small-to-medium projects (fewer than 30 page objects), single inheritance from `BasePage` works well. For larger projects, consider interface-based composition where capabilities (HasNavBar, HasDatePicker) are mixed in as default interface methods. The trade-off: interfaces are more flexible but harder for junior team members to understand.

## Interview and Revision (Layer 6)

### Fundamental Questions

**Q1: Explain the Page Object Model and its benefits.**

**A:** POM separates locators and interactions from test logic by creating a class per application page. Each class owns its locators (stored as `By` constants) and exposes methods for actions (`loginAs`, `searchFor`) and state queries (`getErrorMessage`). Benefits: locator changes affect one file, tests read like user stories, and reusable components reduce duplication. Key rules: no assertions in page objects, methods return page objects to model navigation, and one level of inheritance maximum (BasePage → concrete page).

**Q2: Why do some teams avoid Selenium's PageFactory?**

**A:** PageFactory uses `@FindBy` annotations and `initElements()` to create lazy proxies. Problems: no built-in waits (the proxy calls `findElement` which fails if the element isn't rendered yet), stale references after DOM re-renders (stored proxies point to removed nodes), limited locator strategy support (can't compose complex conditions), and difficult debugging (stack traces point to proxy internals, not the locator). The alternative — `By` locators as constants with BasePage wait methods — is more explicit, more debuggable, and works naturally with explicit waits.

**Q3: How do component objects differ from page objects?**

**A:** Page objects represent full pages (LoginPage, DashboardPage) — each corresponds to a URL or screen. Component objects represent reusable UI parts that appear on multiple pages — navigation bar, date picker, footer, modal dialog. Pages compose components as fields (`private final NavigationBar navbar`). A component never exists alone; it's always used within a page context. This avoids duplicating shared locators across pages.




| # | Front (Question) | Back (Answer) |
|---|---|---|
| 1 | What should page object methods return? | Other page objects. If `loginAs()` navigates to the dashboard, it returns `DashboardPage`. If `loginExpectingError()` stays on the same page, it returns `this` (LoginPage). Return types model navigation flow. |
| 2 | Should page objects contain assertions? | No. Page objects expose state (`getErrorMessage()`, `isButtonEnabled()`). Tests make assertions. This decouples page structure from test expectations and makes page objects reusable across different test scenarios. |
| 3 | What goes in BasePage? | WebDriver and WebDriverWait fields, common interaction methods (click, type, getText) that wrap raw Selenium calls with explicit waits, and utility methods (isDisplayed, waitForUrl). One level of inheritance only. |
| 4 | Why store locators as `By` constants instead of `@FindBy`? | `By` constants work with `WebDriverWait` and `ExpectedConditions`. They're re-evaluated on each use (no stale references). They're easier to debug. `@FindBy` proxies lack built-in waits and go stale after DOM changes. |
| 5 | What is a component object? | A class representing a reusable UI part (navbar, date picker, modal) that appears on multiple pages. Pages compose components as fields. Eliminates locator duplication across page objects. |
