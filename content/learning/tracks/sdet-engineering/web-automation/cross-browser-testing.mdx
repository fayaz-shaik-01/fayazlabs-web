# Cross-Browser Testing

> **Module:** 05 — Web Automation > Cross-Browser Testing  
> **Prerequisites:** Browser And Dom Fundamentals, Locator Strategy  
> **Mastery Target:** L2 (Guided) → L3 (Independent)

---

## Quick Overview (Layer 1)

**What:** Cross-browser testing verifies that your web application works correctly across different browsers (Chrome, Firefox, Safari, Edge), operating systems (Windows, macOS, Linux), and viewport sizes (desktop, tablet, mobile). Each browser uses a different rendering engine that can interpret HTML, CSS, and JavaScript slightly differently.

**Why:** Your tests might pass perfectly on Chrome (where you develop) and break completely on Safari (where 25% of mobile users browse). Different rendering engines handle CSS layouts, date inputs, scroll behavior, and JavaScript APIs differently. As an SDET, you need a strategy to cover the right browsers without running every test on every combination — that would be prohibitively slow and expensive. The skill is knowing *what* to test *where*.

**Where:** Pre-release validation, regression testing across browser matrix, responsive design verification, mobile web testing, and compliance testing for enterprise apps that must support specific browser versions.

<MentalModel>

Think of browsers as **language translators** interpreting the same document (HTML/CSS/JS). Chrome, Firefox, and Safari are three translators who mostly agree on the translation but differ on some idioms. Cross-browser testing is **proofreading** each translation to catch the differences. You don't proofread every word in every translation — you focus on the passages most likely to be interpreted differently (complex CSS layouts, newer JavaScript APIs, date/time handling).

</MentalModel>


<KeyTakeaways>

1. **Rendering engines, not browser names** — Chromium (Chrome, Edge, Opera), Gecko (Firefox), WebKit (Safari) are the three engines that matter
2. **Playwright includes all three engines** — `chromium`, `firefox`, `webkit` are built-in; no additional setup needed
3. **Selenium requires separate drivers** — ChromeDriver, GeckoDriver, etc., each managed independently
4. **Test matrix prioritization is essential** — run core tests on all browsers, full suite on the primary browser only
5. **Cloud platforms (BrowserStack, Sauce Labs)** extend your matrix to real devices and old browser versions

</KeyTakeaways>

## First-Principles Explanation (Layer 2)

### Why Browsers Behave Differently

Every browser interprets the same web standards, but implementations vary:

| Area | Chrome (Blink) | Firefox (Gecko) | Safari (WebKit) |
|---|---|---|---|
| CSS Grid/Flexbox | Most complete | Slightly different gap handling | Older WebKit versions lack features |
| `<input type="date">` | Native date picker | Native date picker | No native picker (older versions) |
| Scroll behavior | `scrollBehavior: smooth` works | Works but different smoothness | Requires prefix or polyfill |
| Clipboard API | Full support | Requires permission | Limited `navigator.clipboard` |
| Shadow DOM | Full v1 support | Full v1 support | Some CSS piercing differences |
| Fetch API | Full support | Full support | Stricter CORS handling |
| Service Workers | Full support | Full support | Limited in private browsing |
| WebSocket | Standard | Standard | Stricter handshake validation |

**What this means for testing:** You'll encounter failures that only happen in one browser — a CSS layout that collapses in Safari, a date picker that doesn't exist in older WebKit, or a fetch call that fails due to stricter CORS in Firefox.

### The Browser Test Matrix

Not every test needs to run on every browser. Prioritize:

```
                        Browsers
                Chrome    Firefox    Safari    Edge
Tests           ──────    ───────    ──────    ────
Smoke (P0)        ✅        ✅        ✅        ✅    ← Critical paths on ALL
Regression (P1)   ✅        ✅        ✅               ← Core functionality on 3
Full Suite (P2)   ✅                                    ← Everything on primary only
Visual            ✅                  ✅               ← Chrome + Safari (most different)
Performance       ✅                                    ← Primary browser only
```

**Deciding which browsers to test:**

1. **Check analytics** — what do your actual users use? If 5% use Firefox, don't spend 25% of your test budget on it
2. **Check rendering engine diversity** — Chrome and Edge both use Blink, so testing both adds little value; test Chrome + Firefox + Safari for engine diversity
3. **Check business requirements** — enterprise apps may need IE11 (painful but real); government apps may need specific browser versions
4. **Consider mobile** — Safari/WebKit dominates iOS (all iOS browsers use WebKit under the hood)

### Playwright Multi-Browser Configuration

Playwright ships with Chromium, Firefox, and WebKit — no external driver management:


```typescript
// playwright.config.ts — multi-browser configuration
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
    testDir: './tests',
    fullyParallel: true,
    retries: process.env.CI ? 2 : 0,

    projects: [
        // Desktop browsers
        {
            name: 'chromium',
            use: { ...devices['Desktop Chrome'] },
        },
        {
            name: 'firefox',
            use: { ...devices['Desktop Firefox'] },
        },
        {
            name: 'webkit',
            use: { ...devices['Desktop Safari'] },
        },

        // Mobile viewports (emulated, not real devices)
        {
            name: 'mobile-chrome',
            use: { ...devices['Pixel 5'] },
        },
        {
            name: 'mobile-safari',
            use: { ...devices['iPhone 13'] },
        },

        // Tablet
        {
            name: 'tablet',
            use: { ...devices['iPad (gen 7)'] },
        },
    ],
});
```


```bash
# Run all browsers
npx playwright test

# Run specific browser
```

### Selenium Multi-Browser Configuration

Selenium requires separate WebDriver binaries and browser installations:


```java
// Selenium: browser-agnostic test with factory pattern
public class BrowserFactory {

    public static WebDriver createDriver(String browser) {
        return switch (browser.toLowerCase()) {
            case "chrome" -> {
                ChromeOptions options = new ChromeOptions();
                options.addArguments("--headless=new");
                yield new ChromeDriver(options);
            }
            case "firefox" -> {
                FirefoxOptions options = new FirefoxOptions();
                options.addArguments("-headless");
                yield new FirefoxDriver(options);
            }
            case "edge" -> {
                EdgeOptions options = new EdgeOptions();
                options.addArguments("--headless=new");
                yield new EdgeDriver(options);
            }
            case "safari" -> {
                // Safari requires macOS, SafariDriver is built-in
                SafariOptions options = new SafariOptions();
                yield new SafariDriver(options);
            }
            default -> throw new IllegalArgumentException("Unknown browser: " + browser);
        };
    }
}
```


```java
// Parameterized test that runs on multiple browsers
@ParameterizedTest
@ValueSource(strings = {"chrome", "firefox", "edge"})
void testLoginAcrossBrowsers(String browser) {
    WebDriver driver = BrowserFactory.createDriver(browser);
    try {
        driver.get("http://localhost:5173/login");

        WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
        wait.until(ExpectedConditions.visibilityOfElementLocated(
            By.cssSelector("[data-testid='email-input']")
        )).sendKeys("admin@staynest.com");

        driver.findElement(By.cssSelector("[data-testid='password-input']"))
              .sendKeys("Admin123!");
        driver.findElement(By.cssSelector("[data-testid='login-button']")).click();

        wait.until(ExpectedConditions.urlContains("/dashboard"));
        String title = driver.getTitle();
        assertEquals("StayNest Dashboard", title);
    } finally {
        driver.quit();
    }
}
```

```typescript
        // Verify grid layout — 2 columns instead of 3
        const gridColumns = await page.evaluate(() => {
```

### Practical Exercise: Tiered Cross-Browser Strategy for StayNest

## Failure and Debugging (Layer 4)

### Failure: Test Passes in Chrome, Fails in WebKit

**The Broken Test:**


```typescript
// Works in Chromium, fails in WebKit
test('date input accepts formatted date', async ({ page }) => {
    await page.goto('http://localhost:5173/search');
    await page.getByLabel('Check-in').fill('2025-08-01');
    // WebKit: Error — fill() doesn't work on date inputs the same way
});
```

**Root Cause:** WebKit handles `<input type="date">` differently from Chromium. The `fill()` method sends keystrokes, and WebKit's date input expects a different format or interaction.

**The Fix:**


```typescript
test('date input works across browsers', async ({ page, browserName }) => {
    await page.goto('http://localhost:5173/search');

    if (browserName === 'webkit') {
        // WebKit: use JavaScript to set the value directly
        await page.getByLabel('Check-in').evaluate(
            (el: HTMLInputElement, value: string) => {
                el.value = value;
                el.dispatchEvent(new Event('input', { bubbles: true }));
                el.dispatchEvent(new Event('change', { bubbles: true }));
            },
            '2025-08-01'
        );
    } else {
        await page.getByLabel('Check-in').fill('2025-08-01');
    }
});
```

**Better long-term fix:** Use a date picker component library that provides consistent behavior across browsers, and interact with it via its accessible interface rather than the native date input.

### Failure: CSS Layout Breaks on Firefox


```typescript
// Grid layout has 3 columns in Chrome, 1 column in Firefox
test('hotel grid shows 3 columns', async ({ page }) => {
    await page.goto('http://localhost:5173/search');
    // ... trigger search ...

    const columns = await page.evaluate(() => {
        const grid = document.querySelector('[data-testid="hotel-grid"]');
        return getComputedStyle(grid!).gridTemplateColumns;
    });

    // Chrome: "300px 300px 300px"
    // Firefox: "300px" (only 1 column)
    // Root cause: Firefox handles gap with auto-fit differently
});
```

**Diagnosis:** Use `browserName` fixture to log which browser failed. Then open DevTools in that specific browser to inspect the CSS. Often the fix is in the application's CSS, not the test.

### Failure: Different Scroll Behavior


```java
// Selenium: scrollIntoView behaves differently across browsers
JavascriptExecutor js = (JavascriptExecutor) driver;
js.executeScript("arguments[0].scrollIntoView({behavior: 'smooth', block: 'center'});", element);
// Safari: 'smooth' might not work; 'block: center' might be ignored

// Safer cross-browser scroll
```

## Engineering Judgment (Layer 5)

### Playwright vs Selenium Grid — Which to Use

| Factor | Playwright Built-in | Selenium Grid + Docker |
|---|---|---|
| Setup complexity | `npx playwright install` — done | Docker Compose + driver management |
| Browser coverage | Chromium, Firefox, WebKit | Chrome, Firefox, Edge, Safari (macOS only) |
| Real browser vs engine | Uses browser engines (not real Chrome) | Real browser binaries |
| Parallelism | Built-in with workers | Grid manages node distribution |
| Mobile testing | Emulation only (viewport, touch, UA) | Real devices via cloud (Appium) |
| CI integration | Simple — just install browsers | Need Docker or infrastructure |
| **Best for** | **Most teams, fastest setup** | **Teams needing real browsers, existing Selenium investment** |

### When to Use Cloud Platforms

**Use BrowserStack/Sauce Labs when:**
- You need real devices (not emulation) — especially iOS Safari
- You need old browser versions (IE11, Safari 14, Chrome 90)
- You don't want to manage browser infrastructure
- You need visual testing across OS-specific rendering (font rendering differs)
- Your CI environment can't run browsers (container without display)

**Don't use cloud platforms when:**
- You only need Chromium, Firefox, and WebKit — Playwright covers these for free
- Your tests are still flaky — fix stability before scaling to more browsers
- Cost is a concern — cloud minutes are expensive at scale

### Test Matrix Strategy Summary

```
Development (local):     Primary browser only (Chromium)
PR/CI pipeline:          Primary browser + smoke on secondary
Nightly regression:      Full matrix (all browsers, all viewports)
Pre-release:             Full matrix + cloud platform for edge cases
```

## Interview and Revision (Layer 6)

### Fundamental Questions

**Q1: Why is cross-browser testing necessary?**

**A:** Different browsers use different rendering engines — Blink (Chrome/Edge), Gecko (Firefox), WebKit (Safari) — which interpret HTML, CSS, and JavaScript with subtle differences. A CSS layout that works in Chrome might collapse in Safari; a date input might behave differently in Firefox; CORS handling varies between engines. Cross-browser testing catches these differences before users do. The key is prioritization: not every test on every browser, but critical paths on diverse engines.

**Q2: How does Playwright handle cross-browser testing compared to Selenium?**

**A:** Playwright ships with Chromium, Firefox, and WebKit engines — `npx playwright install` downloads all three, and you configure projects in `playwright.config.ts` to run tests on each. No driver management needed. Selenium requires separate WebDriver binaries (ChromeDriver, GeckoDriver), separate browser installations, and uses real browser binaries rather than engines. For distributed execution, Selenium uses Grid (hub/node architecture), while Playwright uses built-in parallelism with workers. Playwright's approach is simpler to set up but uses browser engines, not real browser builds.

**Q3: How do you decide which browsers to include in your test matrix?**

**A:** I start with analytics data — which browsers do our users actually use? Then I ensure rendering engine diversity: at minimum Chrome (Blink), Firefox (Gecko), and Safari (WebKit). I tier the strategy: full suite on the primary browser (usually Chrome), smoke tests on secondary browsers, and mobile viewport smoke tests. For CI pipelines, I run the primary browser on every PR and the full matrix nightly. I'd add BrowserStack or Sauce Labs only when we need real devices, old browser versions, or OS-specific testing that Playwright emulation can't cover.

### Scenario-Based Questions

**S1: "Your team runs all 500 tests on Chrome, Firefox, and Safari. It takes 2 hours. How do you speed it up?"**

**A:** Running all 500 tests on all three browsers is likely overkill. I'd tier the strategy: tag ~50 critical-path tests as "smoke" and run those on all three browsers (~12 minutes). Run the full 500 on Chrome only (~40 minutes). This cuts total time from 2 hours to under an hour. For the smoke tests, I'd focus on areas where browser differences are most likely: form handling, responsive layouts, date pickers, and CSS-heavy pages. I'd also run the full cross-browser suite nightly rather than on every PR.
