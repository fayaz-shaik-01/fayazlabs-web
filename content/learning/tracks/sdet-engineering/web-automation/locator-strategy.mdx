# Locator Strategy

> **Module:** 05 — Web Automation > Locator Strategy  
> **Prerequisites:** Browser And Dom Fundamentals  
> **Mastery Target:** L3 (Independent) → L4 (Teaching)

---

## Quick Overview (Layer 1)

**What:** A locator is a query that finds an element in the DOM. Locator strategy is the discipline of choosing the *right* query — one that is stable across code changes, readable to other engineers, and fast enough for thousands of test runs. The two dominant approaches are Selenium's `By.*` locators and Playwright's semantic locators (`getByRole`, `getByTestId`).

**Why:** Fragile locators are the #1 cause of broken tests that aren't actually testing broken software. You've seen this at work — a developer renames a CSS class and 40 tests fail, none of which found a real bug. Robust locator strategy is the difference between a test suite that gives you confidence and one that wastes your time. With 3 years of Selenium experience, you already know `By.id` and `By.cssSelector`. This topic fills two gaps: (1) modern Playwright locators that eliminate entire categories of fragility, and (2) a principled hierarchy for choosing locators when multiple options exist.

**Where:** Every single web test starts with finding an element. Locators appear in page objects, test methods, utility functions, and assertion helpers. Getting them right is a force multiplier.

<MentalModel>

Think of locators as **addressing systems**. You can describe a house as "the third house on the left past the blue mailbox" (fragile — what if the blue mailbox is painted?), "123 Main Street" (stable — doesn't change when neighbors renovate), or "the house where the Johnson family lives" (semantic — describes *what* it is, not *where*). Test-IDs are street addresses; semantic locators describe purpose; CSS/XPath describe position in the DOM tree.

</MentalModel>


<KeyTakeaways>

1. **Locator hierarchy:** `data-testid` > semantic (role, label, text) > CSS selector > XPath > positional/index
2. **Playwright's `getByRole`/`getByLabel`/`getByText` mirror how users find elements** — making tests resilient to refactoring
3. **CSS selectors outperform XPath in most browsers** and are more readable; use XPath only when you need text matching or ancestor traversal
4. **Never use absolute XPath** (`/html/body/div[3]/form/input[2]`) — any DOM change breaks it
5. **Always test locator uniqueness** in DevTools Console before coding — `$$('selector').length === 1`

</KeyTakeaways>

## First-Principles Explanation (Layer 2)

### Locator Types — From Basic to Modern

#### Traditional Locators (Selenium-Era)

These locators identify elements by their HTML attributes or DOM structure:

| Locator Type | Selenium Syntax | Best For | Fragility |
|---|---|---|---|
| ID | `By.id("email")` | Unique elements with stable IDs | Low (if IDs are stable) |
| Name | `By.name("username")` | Form inputs | Low |
| CSS Selector | `By.cssSelector(".btn-primary")` | Flexible, multi-attribute matching | Medium |
| XPath | `By.xpath("//button[text()='Login']")` | Text content, ancestor traversal | Medium–High |
| Class Name | `By.className("form-control")` | Styling classes | High (changes with CSS) |
| Tag Name | `By.tagName("input")` | Rarely useful alone | Very High |
| Link Text | `By.linkText("Sign Up")` | Anchor elements | Medium |

#### Modern Locators (Playwright-Era)

Playwright introduced locators that describe elements the way a user perceives them — by role, label, and text:

| Locator | Playwright Syntax | What It Does |
|---|---|---|
| Test ID | `page.getByTestId('login-button')` | Finds `[data-testid="login-button"]` |
| Role | `page.getByRole('button', { name: 'Login' })` | Finds by ARIA role + accessible name |
| Label | `page.getByLabel('Email')` | Finds input associated with a `<label>` |
| Text | `page.getByText('Welcome back')` | Finds element containing visible text |
| Placeholder | `page.getByPlaceholder('Search hotels')` | Finds by placeholder attribute |
| Alt Text | `page.getByAltText('Hotel photo')` | Finds images by alt text |
| Title | `page.getByTitle('Close dialog')` | Finds by title attribute |

### The Locator Hierarchy — Why Order Matters

```
Most Preferred
    │
    ▼
┌──────────────────────────────────────────────────────────┐
│  1. data-testid / data-test / data-cy                    │
│     Explicit contract between dev and test                │
│     Survives refactoring, restyling, content changes      │
├──────────────────────────────────────────────────────────┤
│  2. Semantic / Accessible (role, label, alt text)         │
│     Mirrors how users and assistive tech find elements    │
│     Also validates accessibility — two birds, one stone   │
├──────────────────────────────────────────────────────────┤
│  3. CSS Selector (by stable attributes)                   │
│     [name="email"], [type="submit"], #login-form          │
│     Fast, readable, well-supported                        │
├──────────────────────────────────────────────────────────┤
│  4. XPath (relative, with predicates)                     │
│     //input[@data-testid="email"]                         │
│     Use when you need ancestor/sibling traversal or text  │
├──────────────────────────────────────────────────────────┤
│  5. Text content                                          │
│     Fragile if content is localized (i18n), dynamic,      │
│     or changes often — but readable for static content    │
├──────────────────────────────────────────────────────────┤
│  6. Positional / Index-based  ← AVOID                     │
│     //div[3]/ul/li[2] — breaks when any sibling changes   │
└──────────────────────────────────────────────────────────┘
    │
    ▼
Least Preferred
```

**Why `data-testid` is #1:** It creates an explicit contract. A developer changing CSS classes or restructuring divs knows not to remove `data-testid` attributes. It's the only locator where the attribute *exists solely for testing*, so nobody changes it accidentally.

**Why semantic locators are #2:** `getByRole('button', { name: 'Login' })` survives a change from `<button>Login</button>` to `<input type="submit" value="Login">` because both have the ARIA role "button" with accessible name "Login." The test validates accessibility as a side effect.

### CSS Selectors — Deep Dive

CSS selectors are the workhorse of Selenium locators and are also available in Playwright. Understanding them well covers 80% of locating needs.


```javascript
// === Basic Selectors ===
'#email'                    // By ID
'.form-control'             // By class
'input'                     // By tag name
'[data-testid="login"]'     // By attribute (exact match)

// === Combinators ===
'form input'                // Descendant — any input inside form
'form > input'              // Direct child — input that is a direct child of form
'input + button'            // Adjacent sibling — button immediately after input
'input ~ button'            // General sibling — button that is a sibling of input

// === Attribute Selectors ===
'[type="email"]'            // Exact match
'[class*="btn"]'            // Contains substring
'[class^="btn-"]'           // Starts with
'[class$="-primary"]'       // Ends with
'input[type="email"][required]'  // Multiple attributes (AND)

// === Pseudo-classes ===
'li:first-child'            // First child
'li:last-child'             // Last child
'li:nth-child(2)'           // Second child (1-indexed)
'input:not([disabled])'     // Negation
'input:checked'             // Checked checkbox/radio

// === StayNest Examples ===
'[data-testid="hotel-card"]:first-child .hotel-name'   // First hotel card's name
'form[data-testid="login-form"] input[type="email"]'   // Email input within login form
'.search-results > [data-testid="hotel-card"]'          // Direct hotel cards in results
```

### XPath — When and How

XPath is more powerful than CSS selectors but slower in most browsers and less readable. Use it for capabilities CSS lacks:


```javascript
// === CSS can't do these — XPath can ===

// 1. Find by text content
'//button[text()="Login"]'                        // Exact text match
'//button[contains(text(), "Log")]'               // Partial text match
'//button[normalize-space()="Login"]'             // Ignore whitespace

// 2. Traverse upward (parent/ancestor)
'//input[@id="email"]/parent::div'                // Parent div of email input
'//input[@id="email"]/ancestor::form'             // Containing form
'//span[text()="$150"]/ancestor::div[@data-testid="hotel-card"]'  // Card containing price

// 3. Traverse to siblings
'//label[text()="Email"]/following-sibling::input' // Input after "Email" label

// 4. Combine conditions with and/or
'//input[@type="text" and @placeholder="Search"]' // AND condition
'//button[@type="submit" or @type="button"]'      // OR condition

// 5. Index-based (use sparingly)
'(//div[@data-testid="hotel-card"])[1]'           // First hotel card
```

**CSS vs XPath — Decision Matrix:**

| Criteria | CSS Selector | XPath |
|---|---|---|
| Performance | Faster (native browser API) | Slower (evaluated by browser engine) |
| Readability | More concise | More verbose |
| Text matching | Cannot match text content | Can match text (`text()`, `contains()`) |
| Upward traversal | Cannot traverse to parent | Can traverse to parent/ancestor |
| Sibling traversal | Limited (adjacent, general) | Full sibling axis (following, preceding) |
| Browser support | Consistent across browsers | Minor differences between browsers |
| **Recommendation** | **Default choice** | **Use when CSS can't do it** |

### Playwright Locators — Why They're Better

Playwright's built-in locators solve problems that Selenium locators can't:


```typescript
// === Playwright locators auto-wait and auto-retry ===

// getByRole — finds by ARIA role + accessible name
// This survives DOM restructuring because it matches semantics, not structure
await page.getByRole('button', { name: 'Login' }).click();
await page.getByRole('heading', { name: 'Welcome to StayNest' }).isVisible();
await page.getByRole('link', { name: 'Sign Up' }).click();
await page.getByRole('textbox', { name: 'Email' }).fill('user@test.com');

// getByLabel — finds form controls by their label text
// Works with <label for="email">, aria-label, aria-labelledby
await page.getByLabel('Email').fill('user@staynest.com');
await page.getByLabel('Password').fill('secret123');
await page.getByLabel('Remember me').check();

// getByTestId — finds by data-testid attribute
// Most stable — test-specific attribute that developers agree not to change
await page.getByTestId('login-form').isVisible();
await page.getByTestId('hotel-card').first().click();
await page.getByTestId('search-results').getByTestId('hotel-card').count();

// getByText — finds by visible text content
await page.getByText('No hotels found').isVisible();
await page.getByText(/\$\d+ per night/).first().isVisible(); // regex support

// getByPlaceholder — finds by placeholder attribute
await page.getByPlaceholder('Search hotels...').fill('New York');

// Chaining — narrow scope before locating
const loginForm = page.getByTestId('login-form');
await loginForm.getByLabel('Email').fill('user@test.com');
await loginForm.getByRole('button', { name: 'Login' }).click();
```

**Why Playwright locators are preferred over raw CSS/XPath:**

1. **Auto-waiting:** They automatically wait for the element to appear, become visible, and be stable before acting
2. **Strict mode:** They throw an error if the locator matches multiple elements (prevents acting on the wrong element)
3. **Accessibility validation:** `getByRole` and `getByLabel` only work if the app has proper ARIA — your test validates accessibility for free
4. **Resilience:** They survive DOM restructuring because they match by semantics, not by position

### Selenium Equivalents — Side-by-Side


```java
// === Selenium — traditional locator approach ===

// By ID
driver.findElement(By.id("email"));

// By CSS selector
driver.findElement(By.cssSelector("[data-testid='login-button']"));
driver.findElement(By.cssSelector("form.login-form input[type='email']"));

// By XPath
driver.findElement(By.xpath("//button[text()='Login']"));
driver.findElement(By.xpath("//input[@data-testid='email-input']"));

// By Name
driver.findElement(By.name("username"));

// By Link Text
driver.findElement(By.linkText("Sign Up"));
driver.findElement(By.partialLinkText("Sign"));

// Combining with explicit waits (always do this)
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
WebElement emailInput = wait.until(
    ExpectedConditions.visibilityOfElementLocated(By.cssSelector("[data-testid='email-input']"))
);
emailInput.sendKeys("user@staynest.com");
```


```java
// === Approximating Playwright-style locators in Selenium ===

// There's no built-in getByRole, but you can build helpers:
public class SemanticLocators {

    // Approximate getByRole("button", { name: "Login" })
    public static By buttonByName(String name) {
        return By.xpath(String.format(
            "//button[normalize-space()='%s'] | //input[@type='submit' and @value='%s']",
            name, name
        ));
    }

    // Approximate getByLabel("Email")
    public static By byLabel(String labelText) {
        return By.xpath(String.format(
            "//label[normalize-space()='%s']/following-sibling::input | " +
            "//input[@id=//label[normalize-space()='%s']/@for]",
            labelText, labelText
        ));
    }

    // Approximate getByTestId("login-button")
    public static By byTestId(String testId) {
        return By.cssSelector(String.format("[data-testid='%s']", testId));
    }
}

// Usage
driver.findElement(SemanticLocators.byTestId("login-button")).click();
driver.findElement(SemanticLocators.byLabel("Email")).sendKeys("test@example.com");
```

## Practical Implementation (Layer 3)

### Practical Exercise: Convert Fragile Locators to Robust Ones

Below is a StayNest login test with terrible locators. Your job: rewrite each locator using the hierarchy.

**The Fragile Version (Selenium):**


```java
// DON'T DO THIS — every locator here is fragile
public class FragileLoginTest {
    @Test
    void testLogin() {
        driver.get("http://localhost:5173/login");

        // Fragile: absolute XPath — breaks if any wrapper div is added/removed
        driver.findElement(By.xpath("/html/body/div/div/div/form/div[1]/input"))
              .sendKeys("admin@staynest.com");

        // Fragile: CSS class that's for styling — changes when CSS is updated
        driver.findElement(By.className("password-field"))
              .sendKeys("Admin123!");

        // Fragile: nth-child — breaks if a new button is added before this one
        driver.findElement(By.cssSelector("form button:nth-child(3)"))
              .click();

        // Fragile: generated/dynamic class name — changes on every build
        driver.findElement(By.cssSelector(".MuiButton-root-jss123"))
              .isDisplayed();

        // Fragile: deeply nested CSS path — tracks DOM structure too closely
        driver.findElement(By.cssSelector("div.app > div.main > div.content > h1"))
              .getText();
    }
}
```

**The Robust Version (Selenium):**


```java
// DO THIS — stable, readable, maintainable
public class RobustLoginTest {
    private WebDriverWait wait;

    @BeforeEach
    void setup() {
        wait = new WebDriverWait(driver, Duration.ofSeconds(10));
    }

    @Test
    void testLogin() {
        driver.get("http://localhost:5173/login");

        // Robust: data-testid — explicit test contract
        wait.until(ExpectedConditions.visibilityOfElementLocated(
            By.cssSelector("[data-testid='email-input']")
        )).sendKeys("admin@staynest.com");

        // Robust: data-testid for password
        driver.findElement(By.cssSelector("[data-testid='password-input']"))
              .sendKeys("Admin123!");

        // Robust: data-testid for submit button
        driver.findElement(By.cssSelector("[data-testid='login-button']"))
              .click();

        // Robust: wait for dashboard element by test ID
        WebElement dashboard = wait.until(
            ExpectedConditions.visibilityOfElementLocated(
                By.cssSelector("[data-testid='dashboard-header']")
            )
        );

        // Robust: assert on text content
        assertEquals("Welcome, Admin", dashboard.getText());
    }
}
```

**The Playwright Version (even better):**


```typescript
// Playwright — semantic locators, auto-waiting, built-in assertions
import { test, expect } from '@playwright/test';

test('login to StayNest', async ({ page }) => {
    await page.goto('http://localhost:5173/login');

    // Semantic: by label — mirrors how users find form fields
    await page.getByLabel('Email').fill('admin@staynest.com');
    await page.getByLabel('Password').fill('Admin123!');

    // Semantic: by role — mirrors how users identify buttons
    await page.getByRole('button', { name: 'Login' }).click();

    // Auto-waiting assertion — Playwright retries until condition is met
    await expect(page.getByRole('heading', { name: 'Welcome, Admin' }))
        .toBeVisible();
});
```

### Practical Exercise: StayNest Hotel Search Page Locators


```typescript
// Building a locator strategy for the StayNest search/results page
import { test, expect, Page } from '@playwright/test';

// --- Page Object with well-chosen locators ---
class SearchPage {
    constructor(private page: Page) {}

    // Search controls — by role/label (semantic)
    get locationInput()  { return this.page.getByLabel('Location'); }
    get checkInDate()    { return this.page.getByLabel('Check-in'); }
    get checkOutDate()   { return this.page.getByLabel('Check-out'); }
    get guestCount()     { return this.page.getByLabel('Guests'); }
    get searchButton()   { return this.page.getByRole('button', { name: 'Search' }); }

    // Results — by test ID (contract with developers)
    get hotelCards()     { return this.page.getByTestId('hotel-card'); }
    get resultCount()    { return this.page.getByTestId('result-count'); }
    get noResults()      { return this.page.getByText('No hotels found'); }
    get loadingSpinner() { return this.page.getByTestId('loading-spinner'); }

    // Individual hotel card fields — chained locators
    hotelName(card: number) {
        return this.hotelCards.nth(card).getByTestId('hotel-name');
    }
    hotelPrice(card: number) {
        return this.hotelCards.nth(card).getByTestId('hotel-price');
    }
    hotelRating(card: number) {
        return this.hotelCards.nth(card).getByTestId('hotel-rating');
    }
    bookButton(card: number) {
        return this.hotelCards.nth(card).getByRole('button', { name: 'Book Now' });
    }

    // Actions
    async searchHotels(location: string, checkIn: string, checkOut: string, guests: number) {
        await this.locationInput.fill(location);
        await this.checkInDate.fill(checkIn);
        await this.checkOutDate.fill(checkOut);
        await this.guestCount.fill(String(guests));
        await this.searchButton.click();
    }
}

test('search for hotels in New York', async ({ page }) => {
    const searchPage = new SearchPage(page);
    await page.goto('http://localhost:5173/search');

    await searchPage.searchHotels('New York', '2025-08-01', '2025-08-05', 2);

    // Assert results loaded
    await expect(searchPage.hotelCards).toHaveCount(5);  // expect 5 results
    await expect(searchPage.hotelName(0)).toContainText('Grand Hotel');
    await expect(searchPage.hotelPrice(0)).toContainText('$');
});
```

## Failure and Debugging (Layer 4)

### Failure: Locator Matches Multiple Elements

**The Broken Test:**


```typescript
// Playwright strict mode catches this — Selenium silently uses the first match
await page.locator('.btn').click();
// Error: strict mode violation: locator('.btn') resolved to 5 elements
```

**Root Cause:** The CSS class `.btn` is a styling class applied to every button on the page. Clicking "a button" is ambiguous — which one?

**The Fix:**


```typescript
// Option 1: Use a more specific locator
await page.getByRole('button', { name: 'Login' }).click();

// Option 2: Scope to a container first
await page.getByTestId('login-form').locator('.btn').click();

// Option 3: Use nth() when index matters (e.g., first result card)
await page.locator('.btn').first().click();  // explicit about "first"
```

**Selenium equivalent problem:**


```java
// Selenium silently returns the first match — no error, but might be wrong element
WebElement btn = driver.findElement(By.className("btn"));
btn.click();  // Clicks the first .btn on the page — is that what you wanted?

// Better: verify uniqueness first, or use findElements
List<WebElement> btns = driver.findElements(By.className("btn"));
System.out.println("Found " + btns.size() + " buttons");  // Debug: how many?

// Best: use data-testid
driver.findElement(By.cssSelector("[data-testid='login-button']")).click();
```

### Failure: Stale Element Due to DOM Re-render

**The Broken Test:**


```java
// In a React SPA — the element is replaced when state changes
WebElement hotelCard = driver.findElement(By.cssSelector("[data-testid='hotel-card']:first-child"));
driver.findElement(By.cssSelector("[data-testid='sort-by-price']")).click(); // triggers re-render
String name = hotelCard.getText();  // StaleElementReferenceException!
```

**Root Cause:** Clicking "Sort by Price" causes React to re-render the hotel cards. The old DOM nodes are removed and new ones are created. The `hotelCard` variable holds a reference to the old, now-removed node.

**The Fix (Selenium):**


```java
// Re-locate after any action that might re-render
driver.findElement(By.cssSelector("[data-testid='sort-by-price']")).click();

// Re-find the element after the DOM change
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
WebElement hotelCard = wait.until(
    ExpectedConditions.visibilityOfElementLocated(
        By.cssSelector("[data-testid='hotel-card']:first-child")
    )
);
String name = hotelCard.getText();
```

**The Fix (Playwright):** Playwright locators are lazy — they re-query the DOM every time you act on them, so stale element errors don't exist:


```typescript
// Playwright re-queries automatically — no stale element problem
const firstCard = page.getByTestId('hotel-card').first();
await page.getByTestId('sort-by-price').click();

// This re-queries the DOM, finds the *current* first card
const name = await firstCard.textContent();  // Works — no stale reference
```

### Failure: Dynamic IDs Breaking Locators

**The Broken Test:**


```java
// IDs generated by a framework — different on every page load
driver.findElement(By.id("react-select-3-input"));   // Works today
// Tomorrow: "react-select-7-input" because another component loaded first
```

**Root Cause:** Many UI frameworks generate dynamic IDs that include counters, random hashes, or build hashes. These are not meant for external use.

**Diagnostic:** In DevTools, reload the page twice. If the ID changes, it's dynamic — don't use it.

**The Fix:**


```java
// Use the aria-label or data-testid instead
driver.findElement(By.cssSelector("[aria-label='Select location']"));
// Or ask developers to add data-testid to the component
driver.findElement(By.cssSelector("[data-testid='location-select']"));
```

<AntiPattern>

| Anti-Pattern | Example | Why It Breaks | Better Alternative |
|---|---|---|---|
| Absolute XPath | `/html/body/div[3]/form/input` | Any DOM change breaks path | `[data-testid='email']` |
| Dynamic ID | `By.id("ember123")` | ID changes on reload | `By.cssSelector("[data-testid='...']")` |
| Styling class | `By.className("btn-blue-lg")` | Changes with CSS redesign | `getByRole('button', { name: '...' })` |
| Index-based | `By.xpath("//li[3]")` | Breaks when list order changes | `By.xpath("//li[text()='Hotels']")` |
| Generated class | `By.cssSelector(".jss-3847")` | Changes on every build | `[data-testid='...']` |
| Over-scoped CSS | `div > div > div > span.text` | Tracks structure too closely | `.hotel-card .hotel-name` or test ID |
| Text in i18n apps | `getByText('Login')` | Breaks in other languages | `getByTestId('login-button')` |

</AntiPattern>

## Engineering Judgment (Layer 5)

### When to Use data-testid vs Semantic Locators

**Use `data-testid` when:**
- The element has no accessible role or label (custom components, non-semantic HTML)
- Your app is internationalized (i18n) — text-based locators break across languages
- You need a guaranteed-stable locator for a critical test (smoke/regression)
- The development team has agreed to maintain `data-testid` attributes as a contract

**Use semantic locators (`getByRole`, `getByLabel`) when:**
- You want tests to double as accessibility checks
- The element has a clear ARIA role (button, link, textbox, heading)
- The text content is stable and not localized
- You're building tests in parallel with development and want to catch accessibility regressions

**Use CSS selectors when:**
- You're in Selenium and can't use Playwright's semantic locators
- The element has stable attributes (`name`, `type`, unique class) but no test ID
- You need to combine multiple attribute conditions

**Use XPath when (and only when):**
- You need to find an element by its text content (and Playwright's `getByText` isn't available)
- You need to traverse upward to a parent/ancestor
- You need to find an element relative to a sibling (label → input pattern)
- CSS selectors can't express the query

### Collaborating with Developers on Locators

The most impactful thing an SDET can do for locator stability is get `data-testid` attributes into the source code:

1. **Propose a convention:** `data-testid="component-action"` (e.g., `login-button`, `hotel-card`, `search-input`)
2. **Add a linting rule:** Require `data-testid` on all interactive elements (buttons, inputs, links)
3. **Document which test IDs exist** — maintain a shared list so developers know not to remove them
4. **Never rely on implementation-detail attributes** — generated classes, internal framework IDs, React keys

### Cost of Locator Maintenance

| Locator Strategy | Maintenance When Devs... | Flaky Test Risk |
|---|---|---|

## Interview and Revision (Layer 6)

### Fundamental Questions

**Q1: What is the recommended locator hierarchy, and why?**

**A:** The hierarchy is: test IDs > semantic (role, label) > CSS selectors > XPath > text > positional. Test IDs are most preferred because they're an explicit contract for testing — they don't change when styling, structure, or content changes. Semantic locators (like Playwright's `getByRole`) are next because they match how users perceive elements and also validate accessibility. CSS selectors are the workhorse for attribute-based matching. XPath is reserved for capabilities CSS lacks (text matching, parent traversal). Positional/index locators are last because they break whenever any sibling changes.

**Q2: What's the difference between CSS selectors and XPath? When would you use each?**

**A:** CSS selectors are faster (native browser API), more concise, and consistent across browsers. They're my default choice. XPath is more powerful — it can match text content (`text()`), traverse upward to parents (`parent::`, `ancestor::`), and navigate siblings in both directions. I use XPath when I need to find an element by its visible text (in Selenium, since Playwright has `getByText`), when I need to go from a child to its parent or ancestor, or when I need to combine conditions that CSS can't express.

**Q3: How do Playwright locators differ from Selenium locators?**

**A:** Three key differences: (1) Playwright locators are lazy — they don't query the DOM until you act on them, so there's no `StaleElementReferenceException`. (2) Playwright has built-in semantic locators (`getByRole`, `getByLabel`, `getByText`) that match user-facing attributes instead of DOM structure. (3) Playwright enforces strict mode — if a locator matches multiple elements, it throws an error instead of silently using the first one, catching ambiguity bugs early.

### Scenario-Based Questions

**S1: "A developer says removing data-testid attributes because they 'pollute the HTML.' How do you respond?"**

**A:** I'd make the case that `data-testid` attributes are a quality contract between development and testing, like API versioning. They cost zero runtime performance (they're ignored by the browser), can be stripped in production builds via a Babel/webpack plugin if there's a size concern, and they save hours of test maintenance. Without them, tests depend on CSS classes (which change with redesigns), DOM structure (which changes with refactoring), or text content (which changes with copy updates). I'd offer to add the stripping build step myself and show the maintenance cost of the alternative.

**S2: "Your test finds two matching elements when you expected one. How do you debug this?"**

**A:** First, I open DevTools and run `$$('my-selector')` in the Console to see all matches. I check if there's a hidden duplicate (e.g., a mobile-specific copy rendered but invisible). If there's a legitimate duplicate, I narrow the scope — use `getByTestId('login-form').getByRole('button')` instead of just `getByRole('button')`. If the second match is from a different section, I adjust the locator to include the parent context. In Playwright, strict mode catches this automatically; in Selenium, I use `findElements` (plural) and assert `size() == 1` to verify uniqueness.
