# Framework Design Interview Questions

## How to Use This File

Framework design questions are the most differentiating part of SDET interviews. Every candidate can write a test — few can design a maintainable framework. Each question includes: the question, a structured answer, trade-offs to discuss, and what interviewers look for.

## Questions 1-6: Architecture and Patterns

### Q1: Explain the Page Object Model. What are its benefits and limitations?

**Structured Answer:**

POM is a design pattern that creates a class for each page (or significant component) of the application. The class encapsulates locators and user interactions, exposing meaningful methods that tests call.

```java
<!-- unverified -->
// Page Object — encapsulates page structure
public class LoginPage extends BasePage {
    private final By usernameField = By.id("username");
    private final By passwordField = By.id("password");
    private final By loginButton = By.id("login-btn");
    private final By errorMessage = By.cssSelector(".error-text");
    
    public LoginPage enterUsername(String username) {
        driver.findElement(usernameField).sendKeys(username);
        return this;
    }
    
    public LoginPage enterPassword(String password) {
        driver.findElement(passwordField).sendKeys(password);
        return this;
    }
    
    public DashboardPage clickLogin() {
        driver.findElement(loginButton).click();
        return new DashboardPage(driver);
    }
    
    public String getErrorMessage() {
        return driver.findElement(errorMessage).getText();
    }
}

// Test — reads like a user story
@Test
public void shouldShowErrorForInvalidCredentials() {
    String error = new LoginPage(driver)
        .enterUsername("invalid@test.com")
        .enterPassword("wrong")
        .clickLoginExpectingError()
        .getErrorMessage();
    
    assertThat(error).isEqualTo("Invalid credentials");
}
```

**Benefits:**
- **Single responsibility:** Locator changes require updating one class, not hundreds of tests
- **Readability:** Tests read like user flows, not Selenium API calls
- **Reusability:** Multiple tests share the same page methods
- **Maintainability:** New team members understand tests without knowing Selenium internals

**Limitations:**
- **Page explosions:** Large applications generate many page classes
- **God objects:** Pages with many elements become massive classes
- **Rigid navigation:** Methods that return the next page class create coupling (what if a flow varies?)
- **Over-engineering:** Simple utility scripts don't need full POM

**Trade-offs to Discuss:**
- **Page Object vs. Screenplay Pattern:** Screenplay models user tasks rather than pages, better for complex multi-page flows but harder to learn
- **Component objects:** Extract reusable components (header, footer, search bar) that appear on multiple pages
- **Fluent API:** Method chaining (`page.enterUsername(x).enterPassword(y).clickLogin()`) improves readability but can complicate error methods

**What Interviewers Look For:** Understanding of *why* POM exists (separation of concerns), not just *how* to implement it. Mention trade-offs, not just benefits.

### Q2: How do you manage WebDriver instances in a parallel execution framework?

**Structured Answer:**

The core problem: WebDriver is not thread-safe. If multiple tests share a single driver instance, they'll interfere with each other (clicking on wrong elements, navigating to wrong pages).

**Solution: ThreadLocal + Factory Pattern**

```java
<!-- unverified -->
public class DriverFactory {
    private static final ThreadLocal<WebDriver> driverThreadLocal = new ThreadLocal<>();
    
    public static WebDriver getDriver() {
        return driverThreadLocal.get();
    }
    
    public static void initDriver(String browser) {
        WebDriver driver;
        switch (browser.toLowerCase()) {
            case "chrome":
                driver = new ChromeDriver(getChromeOptions());
                break;
            case "firefox":
                driver = new FirefoxDriver(getFirefoxOptions());
                break;
            default:
                throw new IllegalArgumentException("Unsupported browser: " + browser);
        }
        driverThreadLocal.set(driver);
    }
    
    public static void quitDriver() {
        WebDriver driver = driverThreadLocal.get();
        if (driver != null) {
            driver.quit();
            driverThreadLocal.remove(); // Prevent memory leak in thread pools
        }
    }
    
    private static ChromeOptions getChromeOptions() {
        ChromeOptions options = new ChromeOptions();
        options.addArguments("--headless", "--no-sandbox", "--disable-dev-shm-usage");
        return options;
    }
}
```

**Lifecycle integration with TestNG:**

```java
<!-- unverified -->
public class BaseTest {
    @BeforeMethod
    @Parameters("browser")
    public void setUp(@Optional("chrome") String browser) {
        DriverFactory.initDriver(browser);
    }
    
    @AfterMethod(alwaysRun = true)
    public void tearDown() {
        DriverFactory.quitDriver();
    }
    
    protected WebDriver getDriver() {
        return DriverFactory.getDriver();
    }
}
```

**Trade-offs to Discuss:**
- **ThreadLocal vs. passing driver as parameter:** ThreadLocal is implicit (no passing required) but harder to debug. Explicit passing is verbose but transparent.
- **Driver per test vs. driver per class:** Per test is safer (full isolation) but slower (browser startup). Per class is faster but tests within a class share state.
- **`remove()` is critical:** Without it, thread pool reuse causes memory leaks and stale driver references.

**What Interviewers Look For:** Understanding of thread safety, not just "use ThreadLocal." They want to hear about the remove() call, thread pool risks, and the Factory pattern for browser abstraction.

### Q3: How do you handle configuration management in a test framework?

**Structured Answer:**

Configuration management ensures the framework works across environments (local, QA, staging, prod) without code changes.

**Configuration hierarchy (priority order):**

```
System Properties (-Denv=qa)          ← Highest priority (CI override)
    ↓
Environment Variables (ENV=qa)        ← Deployment-level config
    ↓
Profile-specific file (qa.properties) ← Environment defaults
    ↓
Default file (default.properties)     ← Fallback values
```

**Implementation:**

```java
<!-- unverified -->
public class Config {
    private static final Properties props = new Properties();
    
    static {
        String env = System.getProperty("env", 
                     System.getenv().getOrDefault("ENV", "local"));
        
        // Load default first, then environment-specific (overrides defaults)
        loadProperties("config/default.properties");
        loadProperties("config/" + env + ".properties");
    }
    
    public static String get(String key) {
        // System property > env var > config file
        return System.getProperty(key,
               System.getenv().getOrDefault(key.toUpperCase().replace(".", "_"),
               props.getProperty(key)));
    }
    
    public static String getBaseUrl() { return get("base.url"); }
    public static int getTimeout() { return Integer.parseInt(get("timeout")); }
    public static String getBrowser() { return get("browser"); }
    
    private static void loadProperties(String path) {
        try (InputStream is = Config.class.getClassLoader().getResourceAsStream(path)) {
            if (is != null) props.load(is);
        } catch (IOException e) {
            // Log warning — file is optional
        }
    }
}
```

**What belongs in config vs. code:**

| Config file | Code |
| --- | --- |
| Base URLs, timeouts, browser type | Test logic, assertions |
| API keys (via env vars, not files) | Page object locators |
| Parallel thread count | Framework behavior |
| Feature flags for test execution | Test data patterns |

**Trade-offs to Discuss:**
- **Properties vs. YAML vs. JSON:** Properties are simple and Java-native. YAML is more readable for nested config. JSON is machine-friendly but hard to comment.
- **Secrets management:** Never commit API keys. Use environment variables or a vault (HashiCorp Vault, AWS Secrets Manager).
- **Owner library:** `owner.aeonbits.org` provides type-safe config with interface-based access.

**What Interviewers Look For:** A layered approach where CI can override defaults. They don't want to hear "we hardcode the URL."

### Q4: How do you implement reporting in a test framework? What information should reports include?

**Structured Answer:**

**Reporting layers:**

1. **Console output** — real-time feedback during execution (test name, pass/fail, duration)
2. **Structured report** (Allure, ExtentReports) — HTML dashboard with details, screenshots, steps
3. **CI integration** — report as build artifact, trend charts over time
4. **Notifications** — Slack/Teams message on failure with build link

**What a good report includes:**

| Information | Why |
| --- | --- |
| Pass/fail status per test | Obvious — what passed, what didn't |
| Failure screenshots | Visual evidence of the state when it failed |
| Step-by-step execution log | Trace what happened before the failure |
| Stack trace | For debugging the root cause |
| Duration per test | Identify slow tests for optimization |
| Environment info | Which browser, URL, build number |
| Historical trends | Is this a new failure or recurring flaky? |
| Categories/labels | Group by feature area, priority, test type |

**Allure integration example:**

```java
<!-- unverified -->
// Custom TestNG listener for screenshots on failure
public class ScreenshotListener implements ITestListener {
    
    @Override
    public void onTestFailure(ITestResult result) {
        WebDriver driver = DriverFactory.getDriver();
        if (driver instanceof TakesScreenshot) {
            byte[] screenshot = ((TakesScreenshot) driver).getScreenshotAs(OutputType.BYTES);
            Allure.addAttachment("Failure Screenshot", 
                "image/png", new ByteArrayInputStream(screenshot), ".png");
        }
    }
    
    @Override
    public void onTestStart(ITestResult result) {
        Allure.step("Starting test: " + result.getMethod().getMethodName());
    }
}
```

**Trade-offs to Discuss:**
- **Allure vs. ExtentReports:** Allure has better CI integration and trend analysis; ExtentReports is simpler to set up
- **Screenshot on failure only vs. every step:** Every step provides complete debugging context but increases report size significantly
- **Video recording:** Tools like Playwright and Selenoid support video — invaluable for debugging complex flows but storage-heavy

**What Interviewers Look For:** That reporting is a first-class concern, not an afterthought. Screenshots on failure is the minimum expectation.

### Q5: How do you implement data-driven testing? Compare different approaches.

**Structured Answer:**

Data-driven testing separates test logic from test data, allowing the same test to run with multiple input/output combinations.

**Approach 1: TestNG DataProvider**

```java
<!-- unverified -->
@DataProvider(name = "loginData")
public Object[][] loginData() {
    return new Object[][] {
        {"valid@email.com", "Pass123!", true, "Valid credentials"},
        {"invalid@email.com", "wrong", false, "Invalid credentials"},
        {"", "Pass123!", false, "Empty email"},
        {"valid@email.com", "", false, "Empty password"},
    };
}

@Test(dataProvider = "loginData")
public void testLogin(String email, String password, boolean expectSuccess, String scenario) {
    LoginPage loginPage = new LoginPage(driver);
    loginPage.enterUsername(email).enterPassword(password).clickLogin();
    
    if (expectSuccess) {
        assertThat(new DashboardPage(driver).isDisplayed()).isTrue();
    } else {
        assertThat(loginPage.getErrorMessage()).isNotEmpty();
    }
}
```

**Approach 2: External data source (CSV/Excel/JSON)**

```java
<!-- unverified -->
@DataProvider(name = "bookingData")
public Iterator<Object[]> bookingData() throws IOException {
    List<Map<String, String>> data = CsvReader.read("testdata/bookings.csv");
    return data.stream()
        .map(row -> new Object[]{row})
        .iterator();
}
```

**Approach 3: Builder pattern with factories**

```java
<!-- unverified -->
@Test
public void shouldCreateBookingWithMinimumFields() {
    Booking booking = BookingBuilder.minimal().build();
    // test with minimal data
}

@Test
public void shouldCreateBookingWithAllFields() {
    Booking booking = BookingBuilder.complete().build();
    // test with complete data
}
```

**Comparison:**

| Approach | Pros | Cons | Best For |
| --- | --- | --- | --- |
| DataProvider (inline) | Simple, visible in code | Data + code coupled | Small data sets (&lt;10 rows) |
| External files | Non-technical team can maintain | Extra parsing, harder to debug | Large data sets, shared with QA |
| Builder pattern | Type-safe, IDE-friendly | More code to write | Complex objects, API testing |

**What Interviewers Look For:** Awareness of multiple approaches and knowing when each is appropriate. Bonus: mentioning that data-driven tests should each be independently meaningful, not just random combinations.

### Q6: How do you design an API client layer in your test framework?

**Structured Answer:**

The API client layer abstracts HTTP interactions so tests read as business operations, not HTTP calls.

**Layered design:**

```
Test:         apiClient.createBooking(request)
    ↓
API Client:   BookingApi.createBooking(BookingRequest) → BookingResponse
    ↓
Base Spec:    RestAssured.given().baseUri(url).contentType(JSON).auth()...
    ↓
HTTP:         POST /api/v1/bookings {body}
```

```java
<!-- unverified -->
// Base specification — shared config for all API calls
public class ApiBase {
    protected static RequestSpecification baseSpec() {
        return RestAssured.given()
            .baseUri(Config.getBaseUrl())
            .contentType(ContentType.JSON)
            .filter(new AllureRestAssured())  // Auto-log requests to Allure
            .log().ifValidationFails();
    }
}

// Domain-specific API client
public class BookingApi extends ApiBase {
    
    public static BookingResponse createBooking(BookingRequest request, String token) {
        return baseSpec()
            .header("Authorization", "Bearer " + token)
            .body(request)
            .post("/api/v1/bookings")
            .then()
            .statusCode(201)
            .extract()
            .as(BookingResponse.class);
    }
    
    public static BookingResponse getBooking(int id, String token) {
        return baseSpec()
            .header("Authorization", "Bearer " + token)
            .pathParam("id", id)
            .get("/api/v1/bookings/{id}")
            .then()
            .statusCode(200)
            .extract()
            .as(BookingResponse.class);
    }
}

// Test reads cleanly
@Test
public void shouldCreateAndRetrieveBooking() {
    String token = AuthApi.getToken("admin", "password");
    BookingRequest request = BookingBuilder.aBooking().build();
    
    BookingResponse created = BookingApi.createBooking(request, token);
    BookingResponse retrieved = BookingApi.getBooking(created.getId(), token);
    
    assertThat(retrieved.getGuestName()).isEqualTo(request.getGuestName());
}
```

**Trade-offs to Discuss:**
- **Static methods vs. instance methods:** Static is simpler. Instance allows dependency injection and mocking.
- **Assertion in API client vs. in test:** Validating status code in the client (fail fast) vs. in the test (more control). Consider: client validates expected codes, test validates business logic.
- **POJO vs. Map for request/response:** POJOs are type-safe and IDE-friendly. Maps are flexible for negative testing (send invalid fields).

**What Interviewers Look For:** Separation of concerns — tests shouldn't contain HTTP details. Mention auth management, logging, and error handling.

## Questions 7-10: Advanced Topics

### Q7: How do you handle test retries? What are the risks?

**Structured Answer:**

Retries re-execute a failed test automatically, typically once or twice, to handle transient failures.

**When retries are appropriate:**
- UI tests with genuine timing issues (network latency, animation delays)
- Tests interacting with external services (third-party API flakiness)
- Known infrastructure instability (CI environment resource contention)

**When retries are dangerous:**
- Masking real bugs — a test that needs 3 retries to pass has a real problem
- Hiding data issues — test data conflicts that succeed on retry due to cleanup timing
- API tests — these should be deterministic; retries hide bugs

**Implementation with TestNG:**

```java
<!-- unverified -->
public class RetryAnalyzer implements IRetryAnalyzer {
    private int retryCount = 0;
    private static final int MAX_RETRY = 1; // Maximum 1 retry
    
    @Override
    public boolean retry(ITestResult result) {
        if (retryCount < MAX_RETRY) {
            retryCount++;
            Logger.warn("Retrying test: {} (attempt {})", 
                result.getName(), retryCount + 1);
            return true;
        }
        return false;
    }
}

// Apply globally via listener, not per-test annotation
@Listeners(RetryListener.class)
public class BaseTest { }
```

**Critical rule: Log and track all retries.** If a test retries frequently, it should be flagged for investigation, not silently passing.

**Trade-offs to Discuss:**
- **Retry at test level vs. action level:** Test-level retry (run entire test again) is simpler. Action-level retry (retry just the click or API call) is more efficient but more complex.
- **Max retries:** 1 retry for UI, 0 for API is a reasonable policy.
- **Retry in CI vs. local:** Some teams only enable retries in CI where environment flakiness is higher.

**What Interviewers Look For:** Nuanced understanding — retries are a tool, not a solution. They want to hear about tracking, limits, and root-cause fixing.

### Q8: How do you design your framework for maintainability when the team grows?

**Structured Answer:**

A framework that works for 2 SDETs breaks at 10. Maintainability requires conventions, enforcement, and documentation.

**1. Enforced conventions:**
- Naming standards: `testShould<Behavior>When<Condition>()` for test methods
- Package structure: `tests/`, `pages/`, `api/`, `utils/`, `config/` — no ambiguity
- Locator strategy hierarchy: ID > data-testid > CSS > XPath (documented)

**2. Code quality gates:**
- Checkstyle/PMD rules in build pipeline — reject PRs with violations
- PR review checklist: page objects used, no hardcoded data, assertions present, cleanup in @AfterMethod
- SonarQube for complexity metrics

**3. Reusable building blocks:**

```java
<!-- unverified -->
// Shared wait helper — nobody writes their own wait logic
public class WaitHelper {
    public static void waitForElement(WebDriver driver, By locator, int timeoutSeconds) {
        new WebDriverWait(driver, Duration.ofSeconds(timeoutSeconds))
            .until(ExpectedConditions.visibilityOfElementLocated(locator));
    }
    
    public static void waitForTextToBe(WebDriver driver, By locator, String text) {
        new WebDriverWait(driver, Duration.ofSeconds(10))
            .until(ExpectedConditions.textToBe(locator, text));
    }
}
```

**4. Documentation:**
- README with quick-start guide (clone, configure, run first test in 5 minutes)
- CONTRIBUTING.md with coding standards and PR process
- Page object template file that new SDETs copy

**5. Onboarding:**
- New SDET writes their first test on Day 1 using the template
- Code review of first 3 PRs is detailed and educational
- Pair programming session on framework internals in Week 1

**What Interviewers Look For:** Thinking beyond "write good code" — they want organizational strategies: standards, automation of standards, and knowledge transfer.

### Q9: When would you use inheritance vs. composition in framework design?

**Structured Answer:**

**Inheritance (is-a):** Create a base class that child classes extend. Useful for shared setup/teardown.

```java
<!-- unverified -->
// BaseTest provides driver lifecycle for ALL tests
public class BaseTest {
    protected WebDriver driver;
    
    @BeforeMethod
    public void setUp() { driver = DriverFactory.create(); }
    
    @AfterMethod
    public void tearDown() { DriverFactory.quit(); }
}

public class LoginTest extends BaseTest {
    @Test
    public void testLogin() { /* uses this.driver */ }
}
```

**Composition (has-a):** Inject dependencies as fields. More flexible, avoids deep hierarchies.

```java
<!-- unverified -->
// Instead of: LoginPage extends BasePage extends BaseComponent extends...
// Use composition:
public class LoginPage {
    private final WebDriver driver;
    private final WaitHelper waiter;
    private final HeaderComponent header;
    
    public LoginPage(WebDriver driver) {
        this.driver = driver;
        this.waiter = new WaitHelper(driver);
        this.header = new HeaderComponent(driver);
    }
}
```

**Guidelines:**

| Use Inheritance When | Use Composition When |
| --- | --- |
| Shared lifecycle (BaseTest) | Shared behavior across unrelated classes |
| True "is-a" relationship | "Has-a" relationship |
| 1-2 levels deep maximum | Avoiding deep class hierarchies |
| Framework infrastructure | Business-level page objects |

**The rule:** Prefer composition. Use inheritance only for framework infrastructure (BaseTest, BasePage) and keep it shallow (1-2 levels).

**Trade-offs to Discuss:**
- **Deep inheritance breaks flexibility:** `LoginTest extends WebBaseTest extends BaseTest extends AbstractTest` — changing BaseTest affects everything
- **Composition enables mixing:** A page can compose WaitHelper, LogHelper, and ScreenshotHelper without inheriting from all three
- **Java interfaces with default methods:** A middle ground — get behavior from interfaces without class hierarchy coupling

**What Interviewers Look For:** "Favor composition over inheritance" with real justification, not just repeating the phrase.

### Q10: How do you handle authentication/tokens in your test framework?

**Structured Answer:**

Authentication should be centralized, cached, and transparent to tests.

```java
<!-- unverified -->
public class TokenManager {
    private static final ConcurrentHashMap<String, TokenInfo> tokenCache = new ConcurrentHashMap<>();
    
    public static String getToken(String role) {
        TokenInfo cached = tokenCache.get(role);
        if (cached != null && !cached.isExpired()) {
            return cached.getToken();
        }
        
        // Generate new token
        String token = AuthApi.login(
            Config.get("auth." + role + ".username"),
            Config.get("auth." + role + ".password")
        );
        
        tokenCache.put(role, new TokenInfo(token, Instant.now().plusSeconds(3500)));
        return token;
    }
    
    public static void clearCache() {
        tokenCache.clear();
    }
    
    private static class TokenInfo {
        private final String token;
        private final Instant expiresAt;
        
        TokenInfo(String token, Instant expiresAt) {
            this.token = token;
            this.expiresAt = expiresAt;
        }
        
        boolean isExpired() { return Instant.now().isAfter(expiresAt); }
        String getToken() { return token; }
    }
}

// Test usage — clean and simple
@Test
public void adminShouldSeeAllBookings() {
    String token = TokenManager.getToken("admin");
    List<Booking> bookings = BookingApi.getAll(token);
    assertThat(bookings).isNotEmpty();
}
```

**Key design decisions:**
- **Cache tokens by role** — avoid generating a new token for every test (slow, hammers the auth server)
- **Auto-refresh on expiry** — check expiration before returning cached token
- **ConcurrentHashMap** — thread-safe for parallel test execution
- **Credentials in config, not code** — environment variables in CI, config files locally

**What Interviewers Look For:** Token caching, thread safety, and credential management. They don't want to see username/password hardcoded in tests.

## Whiteboard Exercises

### Whiteboard 1: "Design a Selenium test automation framework from scratch for an e-commerce website."

**Structured Approach (15 minutes):**

**Step 1: Gather Requirements (2 min)**
- "What's the scale? How many pages, how many SDETs?"
- "What environments? Local, QA, staging, production?"
- "What's the CI/CD setup? Jenkins, GitHub Actions?"
- "Any existing infrastructure? Docker, cloud grids?"

**Step 2: Architecture Diagram (3 min)**

```
┌─────────────────────────────────────────────────┐
│                  Test Layer                       │
│  LoginTest, SearchTest, CheckoutTest, CartTest   │
├─────────────────────────────────────────────────┤
│               Page Object Layer                   │
│  LoginPage, SearchPage, ProductPage, CartPage    │
│  HeaderComponent, FooterComponent                │
├─────────────────────────────────────────────────┤
│              Framework Core Layer                 │
│  DriverFactory, WaitHelper, Config, TestDataAPI  │
│  TokenManager, ScreenshotHelper, AllureReporter  │
├─────────────────────────────────────────────────┤
│             Infrastructure Layer                  │
│  TestNG runner, Maven build, Docker, Jenkins     │
└─────────────────────────────────────────────────┘
```

**Step 3: Key Design Decisions (5 min)**
- **Driver management:** ThreadLocal + Factory for parallel safety
- **Configuration:** Properties files with environment profiles + system property overrides
- **Test data:** API-generated per test, UUID-based for uniqueness
- **Reporting:** Allure with screenshots on failure, Slack notifications
- **Parallel execution:** TestNG with `parallel="methods"`, thread-count=3-5

**Step 4: Code Walkthrough (3 min)**
Show the DriverFactory, one Page Object, and one test method.

**Step 5: CI Integration (2 min)**
- Jenkins pipeline: build → start app (Docker) → smoke tests → regression tests → report → notify
- Headless Chrome in CI, headed locally for debugging
- Allure report as build artifact

### Whiteboard 2: "Design an API test automation framework for a microservice architecture with 10 services."

**Structured Approach (15 minutes):**

**Step 1: Gather Requirements (2 min)**
- "How do services communicate? REST, gRPC, messaging?"
- "Is there an API gateway or direct service-to-service calls?"
- "Authentication model? OAuth2, API keys, service tokens?"
- "Do I own all 10 services or is this cross-team?"

**Step 2: Architecture Diagram (3 min)**

```
┌─────────────────────────────────────────────────┐
│                  Test Layer                       │
│  ServiceA_Tests, ServiceB_Tests, E2E_Flow_Tests │
├─────────────────────────────────────────────────┤
│               API Client Layer                    │
│  ServiceAClient, ServiceBClient (per service)    │
│  Request/Response POJOs per service              │
├─────────────────────────────────────────────────┤
│             Shared Infrastructure                 │
│  BaseApiSpec, TokenManager, SchemaValidator      │
│  TestDataBuilder, WireMock stubs, Config         │
├─────────────────────────────────────────────────┤
│             Test Orchestration                    │
│  TestNG suites (per-service, cross-service, E2E) │
│  Docker Compose (services + DB), Maven profiles  │
└─────────────────────────────────────────────────┘
```

**Step 3: Key Design Decisions (5 min)**
- **Per-service test suites:** Each service has its own test class + API client. Can run independently.
- **Service virtualization:** WireMock stubs for testing one service without its dependencies
- **Contract testing:** Pact contracts at service boundaries
- **E2E flows:** Minimal — test critical cross-service flows (user creates order → payment processes → inventory updates)
- **Schema validation:** JSON Schema files versioned alongside API specs

**Step 4: Test Categories (3 min)**

| Category | Scope | When to Run |
| --- | --- | --- |
| Component tests | Single service + WireMock stubs | Every commit |
| Contract tests | Consumer-provider pairs | Every commit |
| Integration tests | 2-3 real services | PR merge |
| E2E tests | Full system | Pre-release |

**Step 5: CI Pipeline (2 min)**
- Docker Compose to spin up required services
- Parallel execution by service (each service's tests in a separate JVM)
- Fail-fast: if Service A tests fail, still run Service B tests (independent)
- Consolidated Allure report across all services

## Questions 11-12: Scenario-Based

### Q11: Your test suite takes 45 minutes. How do you get it under 15?

**Structured Answer:**

**Step 1: Profile** — find where time is spent
- Add timing to test categories (smoke, regression, E2E)
- Identify the 10 slowest individual tests
- Measure: browser startup time, test data setup, actual test execution, teardown

**Step 2: Quick wins (usually get you 50% reduction)**
- **Parallelize:** If running sequentially, add `parallel="methods"` in TestNG with 3-5 threads. Single biggest improvement.
- **Replace UI data setup with API calls:** Creating test data through the UI (login, navigate, fill forms) takes 30-60 seconds. API calls take 200ms.
- **Share authentication:** Don't log in separately for every test. Use API-based token generation.

**Step 3: Structural improvements**
- **Push tests down the pyramid:** If an API test can verify the same thing, remove the UI test
- **Remove redundant tests:** Two tests checking the same behavior differently
- **Optimize waits:** Replace `Thread.sleep(5000)` with explicit waits
- **Headless mode:** 20-30% faster in CI

**Step 4: Infrastructure**
- **Selenium Grid or Docker:** Distribute tests across multiple nodes
- **Selective execution:** Only run tests related to changed code (test impact analysis)
- **Faster CI machines:** Sometimes the cheapest fix is better hardware

**What Interviewers Look For:** A data-driven approach (profile first, then optimize) rather than guessing.

### Q12: A developer says "Page Objects are over-engineering — I can write tests faster without them." How do you respond?

**Structured Answer:**

"You're right that for a single test, writing directly against Selenium is faster. The question is: what happens at 50 tests? 200 tests?"

**The argument for POM:**
- **Maintainability:** When a UI element changes, you update one page class instead of 20 tests
- **Readability:** `loginPage.enterUsername("test")` is clearer than `driver.findElement(By.id("usr")).sendKeys("test")`
- **Reusability:** The login flow is written once and used by every test that needs authentication
- **Onboarding:** New team members read tests as user stories, not Selenium API calls

**When the developer might be right:**
- **Throwaway tests** for a proof of concept — POM is overkill
- **Very small test suites** (&lt; 10 tests) where the overhead isn't justified
- **Exploratory automation** where you're investigating a bug, not building a suite

**How to demonstrate value:**
- Show a real example: "Last month, the login page redesign required changing 3 locators. With POM, it was a 5-minute update. Without POM, it would have been 25 test files."

**What Interviewers Look For:** Diplomatic communication + technical reasoning. Not "POM is always right" dogma, but context-aware trade-off thinking.
