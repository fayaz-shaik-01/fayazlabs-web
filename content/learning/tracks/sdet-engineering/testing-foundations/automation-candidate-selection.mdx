# Automation Candidate Selection

> **Module:** 02 — Testing Foundations  
> **Prerequisites:** Testing Principles, Risk Based Testing, Test Levels And Pyramid  
> **Mastery Target:** L3 (independent) — can evaluate any test scenario for automation suitability using a structured decision framework

---

## Quick Overview (2-minute read)

**What:** Automation candidate selection is the discipline of deciding which tests to automate and which to leave as manual or exploratory. Not every test is worth automating. The decision is an ROI calculation: will the time saved by automation exceed the time spent building and maintaining the automated test?

**Why:** The most common automation failure is not tool selection or framework design — it's automating the wrong things. Teams that automate everything end up with massive, slow, fragile suites that cost more to maintain than they save. Teams that automate nothing miss the consistency and regression safety that automation provides. The skill is knowing which tests fall on which side of the ROI line.

**Where:** Sprint planning (what to automate this sprint), test strategy reviews, automation backlog grooming, new feature analysis, and every conversation where someone says "we should automate this."

<MentalModel>

Think of automation like **hiring an employee**. Before you hire, you calculate: How much will this person save me? How much will they cost (salary, training, management)? How long before they pay for themselves? A test scenario is a job candidate. Some will pay for themselves in the first month (high-frequency regression tests for critical features). Some will never pay for themselves (one-time verification of a feature that's being replaced next quarter). Your job is to make the hiring decision wisely.

</MentalModel>


<KeyTakeaways>

1. Automation ROI = (manual effort saved x frequency) - (build cost + maintenance cost). If it's negative, don't automate.
2. The best automation candidates are repetitive, deterministic, stable, high-risk, and high-frequency.
3. The worst candidates are subjective, volatile, one-time, low-risk, and dependent on uncontrollable externals.
4. Automating at the wrong level is as wasteful as not automating at all — a UI test for an API contract is a bad investment.
5. The decision to NOT automate something is a valid engineering decision, not a failure.

</KeyTakeaways>

## First-Principles Explanation

### The ROI Question

Every automation decision is an investment. The formula:

```
Automation ROI = (Manual Run Time × Runs Per Year) - (Build Time + Maintenance Per Year)
```

**Example — StayNest login test:**

| Factor | Value |
|---|---|
| Manual run time | 5 minutes per execution |
| Frequency | Every regression cycle, 2x per sprint, 26 sprints/year = 52 runs |
| Manual cost | 5 min × 52 runs = 260 minutes/year (~4.3 hours) |
| Build time | 30 minutes to automate |
| Annual maintenance | 2 hours (login page is stable, rarely changes) |
| Automation cost | 30 min + 2 hours = 2.5 hours/year |
| **Net savings** | **4.3 - 2.5 = 1.8 hours/year** |

**Verdict:** Positive ROI. Automate it.

**Counter-example — StayNest marketing banner test:**

| Factor | Value |
|---|---|
| Manual run time | 3 minutes per execution |
| Frequency | Once per campaign, ~6 times/year |
| Manual cost | 3 min × 6 = 18 minutes/year |
| Build time | 45 minutes (dynamic content, visual check) |
| Annual maintenance | 4 hours (banner changes every campaign, selectors break) |
| Automation cost | 45 min + 4 hours = 4.75 hours/year |
| **Net savings** | **0.3 - 4.75 = -4.45 hours/year** |

**Verdict:** Negative ROI. Don't automate it. Manual spot check is sufficient.

### The 5 Criteria for Automation Candidates

#### Criterion 1: Repetitive

Will this test run more than once? Regression tests that run every sprint are prime candidates. A one-time verification of a data migration is not.

#### Criterion 2: Deterministic

Can you define exact inputs and expected outputs? If the test requires human judgment ("does this look right?", "is this confusing?"), it cannot be automated meaningfully. A test that checks `status == "CONFIRMED"` is deterministic. A test that checks "the confirmation page feels trustworthy" is not.

#### Criterion 3: Stable

Is the feature likely to remain unchanged for at least 3-6 months? Automating a feature that changes every sprint produces tests that break every sprint — the maintenance cost exceeds the value. Wait until the feature stabilizes.

#### Criterion 4: High-Risk

Does the feature handle critical business logic — payments, authentication, data integrity, booking creation? High-risk features justify higher automation investment because the cost of a missed bug is severe.

#### Criterion 5: Automatable at the Right Level

Can this test be automated at the lowest effective level? A date validation rule that can be tested via API should not be automated as an E2E browser test. The "right level" criterion prevents over-investment in expensive test types.

---

### The Decision Matrix

Score each test scenario on the 5 criteria (1-3 scale) and sum the scores:

| Score | Meaning |
|---|---|
| 1 | Low — doesn't strongly satisfy this criterion |
| 2 | Medium — partially satisfies |
| 3 | High — strongly satisfies |

| Total Score | Decision |
|---|---|
| 13-15 | **Automate immediately** — high-value, low-risk investment |
| 10-12 | **Automate when capacity allows** — good candidate, not urgent |
| 7-9 | **Consider carefully** — may have negative ROI or require specific conditions |
| 5-6 | **Do not automate** — manual or exploratory is more cost-effective |

## Practical Implementation

### Evaluating 10 StayNest Test Scenarios

| # | Scenario | Repetitive (1-3) | Deterministic (1-3) | Stable (1-3) | High-Risk (1-3) | Right Level (1-3) | Total | Decision |
|---|---|---|---|---|---|---|---|---|
| 1 | Login with valid credentials | 3 | 3 | 3 | 3 | 3 (API) | **15** | Automate immediately |
| 2 | Create booking via API with valid data | 3 | 3 | 3 | 3 | 3 (API) | **15** | Automate immediately |
| 3 | Payment processing — successful charge | 3 | 3 | 3 | 3 | 3 (API) | **15** | Automate immediately |
| 4 | Booking status transitions (full lifecycle) | 3 | 3 | 3 | 3 | 3 (API) | **15** | Automate immediately |
| 5 | Search properties by city and date range | 3 | 3 | 2 | 2 | 3 (API) | **13** | Automate immediately |
| 6 | E2E booking flow — guest searches, books, confirms | 3 | 3 | 2 | 3 | 2 (E2E) | **13** | Automate immediately |
| 7 | Hotel manager creates and activates a property | 3 | 3 | 2 | 2 | 3 (API) | **13** | Automate immediately |
| 8 | Verify promotional banner displays correct campaign | 1 | 2 | 1 | 1 | 1 (E2E) | **6** | Do not automate |
| 9 | Verify email notification content after booking | 2 | 2 | 2 | 2 | 2 (integration) | **10** | Automate when capacity allows |
| 10 | Exploratory: booking flow usability for new users | 1 | 1 | 2 | 2 | 1 (manual) | **7** | Do not automate — exploratory |

### Analysis

**Scenarios 1-4 (score 15):** These are the foundation of the regression suite. They cover critical business flows, are highly repetitive, and can all be tested at the API level — cheap to build and maintain.

**Scenarios 5-7 (score 13):** Strong candidates. Scenario 6 is E2E, which is more expensive, but the booking flow is critical enough to justify the cost. Limit to 1-2 E2E variations.

**Scenario 8 (score 6):** Promotional banners change with every campaign. Automating this means rewriting the test every time. Manual verification takes 2 minutes and happens 6 times a year. Negative ROI.

**Scenario 9 (score 10):** Email testing is valuable but tricky — requires email interception (Mailhog, Mailosaur), content parsing, and timing. Worth automating for booking confirmation emails, but lower priority than core flow tests.

**Scenario 10 (score 7):** Usability assessment requires human judgment. This is an exploratory testing charter, not an automation candidate.

<AntiPattern>

#### Mistake 1: Automating Everything

</AntiPattern>


**Symptom:** 500 automated tests, 4-hour CI pipeline, 30% flaky, 20 hours/week spent on maintenance.

**Root cause:** The team equated "more automated tests" with "more quality." No ROI analysis was performed. Tests that should be manual or exploratory were automated because "automation is our job."

<BestPractice>

**Fix:** Audit the suite. For each test, ask: "If this test didn't exist, what risk would be unmitigated?" If the answer is "very little," delete it.

</BestPractice>


#### Mistake 2: Automating Too Early

**Symptom:** The feature is still being redesigned. Every sprint, 15 tests break because the UI changed, the API contract changed, or the business rules changed. SDETs spend all their time fixing tests instead of writing new ones.

**Root cause:** Automation started before the feature stabilized. The feature was in active development, and the tests were built against a moving target.

<BestPractice>

**Fix:** Wait. Use exploratory testing while the feature is volatile. Start automation when the feature passes the "stability threshold" — no major changes for 2 sprints.

</BestPractice>


#### Mistake 3: Automating at the Wrong Level

**Symptom:** The E2E suite has 200 tests. 150 of them verify API behavior (validation rules, error codes, status transitions) through the browser. Each takes 30 seconds. The same verification via API would take 200ms.

**Root cause:** The team defaulted to E2E because "that's what the user does." They didn't apply the push-down rule — verify at the lowest level that can cover the behavior.

<BestPractice>

**Fix:** For each E2E test, ask: "Does this test require a browser?" If it's verifying a validation rule, an error code, or a state transition, push it to the API level. Reserve E2E for tests that genuinely need UI interaction (visual rendering, multi-page journeys, accessibility).

</BestPractice>


#### Mistake 4: Ignoring Maintenance Cost

**Symptom:** A test took 2 hours to write and has been broken 4 times in 6 months, each fix taking 30 minutes. Total investment: 4 hours. The test covers a low-risk tooltip feature.

**Root cause:** Build cost was estimated, but ongoing maintenance was ignored. The true cost is build + (maintenance × lifetime).

<BestPractice>

**Fix:** Track maintenance cost per test or per test area. When maintenance exceeds value, delete the test.

</BestPractice>


#### Mistake 5: Automating Subjective Checks

**Symptom:** An E2E test takes a screenshot and compares it pixel-by-pixel to a baseline. Every font rendering difference, anti-aliasing change, or screen resolution variation causes a failure. The team spends hours reviewing false positives.

**Root cause:** Visual appearance is subjective and environment-dependent. Pixel-perfect comparison is too brittle for most use cases.

<BestPractice>

**Fix:** Use structural assertions (element exists, correct text, correct order) for functional tests. Use dedicated visual regression tools (Percy, Applitools) with intelligent comparison and approval workflows for visual testing — don't mix them into the functional suite.

</BestPractice>

## Failure and Debugging

### When the Wrong Tests Get Automated

**Scenario:** A team automated 100 tests in Q1. In Q2, they spent 60% of their time maintaining those tests. In Q3, they disabled 40 tests because nobody had time to fix them. By Q4, the suite had 60 active tests and no new automation written in 6 months.

**What went wrong:** No ROI analysis. The team automated the easiest tests first (UI smoke tests for low-risk features) instead of the highest-value tests (critical API flows). The easy tests were also the most brittle (UI-dependent).

**Lesson:** Automate by value, not by ease. The first 20 tests automated should cover the 20 highest-risk scenarios, even if they're harder to write.

## Engineering Judgment

### The Automation Backlog

Treat automation candidates as a prioritized backlog, just like a product backlog:

1. **P0 — Critical path regression:** Login, booking creation, payment, cancellation. Automate first.
2. **P1 — High-risk business rules:** Validation rules, state transitions, authorization checks. Automate second.
3. **P2 — Medium-risk features:** Search, filtering, notifications. Automate when P0/P1 are covered.
4. **P3 — Low-risk, stable features:** Profile updates, preferences, settings. Automate if time permits.
5. **Never automate:** One-time tests, volatile features, subjective checks, features being deprecated.

### The 80/20 Rule in Practice

In most applications, 20% of the test scenarios cover 80% of the risk. Your job is to identify that 20% and automate it thoroughly. The remaining 80% of scenarios can be covered by exploratory testing, manual spot checks, or lightweight smoke tests.

For StayNest, the 20% is:
- Authentication (login, signup, token refresh, authorization)
- Booking lifecycle (init → guests → payment → confirm → cancel)
- Payment processing (charge, refund, failure handling)
- Search (core query, filters, availability)

Automating these four areas with depth (positive, negative, boundary, state transition tests) provides more risk coverage than 200 shallow tests spread across every feature.

## Interview and Revision

### Questions and Answers

**Q1: How do you decide what to automate?**

**A:** I use a 5-criteria scoring matrix: repetitive, deterministic, stable, high-risk, and automatable at the right level. Each criterion gets a 1-3 score. Scenarios scoring 13+ are automated immediately. 10-12 are queued for when capacity allows. Below 10, I evaluate whether manual or exploratory testing is more cost-effective. I also apply an ROI calculation: if (manual time × frequency) exceeds (build time + annual maintenance), automation is justified.

**Q2: A stakeholder says "automate all 200 test cases." How do you respond?**

**A:** I'd present the ROI analysis: automating all 200 would cost approximately X hours to build and Y hours/year to maintain. Instead, I'd propose automating the top 50 by risk score, which covers 80% of our critical paths. The remaining 150 would be covered by a combination of exploratory testing charters (for complex, subjective scenarios) and lightweight API checks (for simple validations). This approach gives us better coverage with lower total cost.

**Q3: When should you NOT automate a test?**

**A:** Five situations: (1) The feature is still changing rapidly — wait for stability. (2) The test requires human judgment (usability, visual aesthetics). (3) It's a one-time verification that won't repeat. (4) The ROI is negative — maintenance cost exceeds time saved. (5) The feature is being deprecated — don't invest in automation for code that's being removed.
