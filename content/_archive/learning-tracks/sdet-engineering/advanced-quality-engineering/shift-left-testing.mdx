# Shift-Left Testing

> **Module:** 09 — Advanced Quality Engineering  
> **Prerequisites:** Testing Fundamentals, Pipeline As Code  
> **Mastery Target:** L3 (Independent) — can implement shift-left practices including static analysis, PR-level testing, and test impact analysis

---

## Quick Overview (Layer 1)

**What:** Shift-left testing means moving testing activities earlier in the software development lifecycle (SDLC). Instead of testing after development is "done," you embed quality checks at every stage: during coding (static analysis, linting), at commit (pre-commit hooks), at pull request (automated test runs), and at merge (integration tests). The name comes from shifting leftward on the timeline: requirements → design → coding → **testing** → deployment becomes requirements → **testing** → design → **testing** → coding → **testing** → deployment.

**Why:** Bugs found later cost exponentially more to fix. A bug caught by a linter during coding takes 5 minutes to fix. The same bug found in QA takes hours (reproduce, file, triage, fix, retest). Found in production, it takes days plus reputational damage. Shift-left doesn't add more testing — it moves existing testing to where it's cheaper, faster, and more effective.

**Where:** Every stage of the SDLC. As an SDET, your shift-left contributions include: configuring static analysis tools, writing unit test helpers that developers use, setting up PR-level test pipelines, and implementing test impact analysis so only affected tests run per change.

<KeyTakeaways>

1. Shift-left is a philosophy, not a tool. It means "find bugs as early as possible, as cheaply as possible."
2. Static analysis (linting, SonarQube) catches bugs without executing code — the fastest and cheapest feedback loop.
3. SDETs promote unit testing culture by providing test utilities, builders, and mock helpers that make unit testing easy for developers.
4. PR-level testing runs relevant tests on every pull request, preventing broken code from reaching the main branch.
5. Test impact analysis identifies which tests are affected by a code change, so you run 50 tests instead of 5,000.

</KeyTakeaways>

## First-Principles Explanation (Layer 2)

### The Cost-of-Defect Curve

```
Cost to Fix
    ▲
    │                                          ████  Production
    │                                    ████        ($10,000+)
    │                              ████
    │                        ████                    QA/Staging
    │                  ████                          ($1,000)
    │            ████
    │      ████                                      PR/CI
    │████                                            ($100)
    │█                                               Coding
    └──────────────────────────────────────────→     ($10)
     Coding    PR     Integration   QA    Production
```

### Static Analysis — Catching Bugs Without Running Code

| Tool | What It Catches | Integration Point |
|------|----------------|-------------------|
| **Checkstyle** | Code style violations, naming conventions | Pre-commit hook, CI |
| **SpotBugs** | Null pointer risks, resource leaks, concurrency bugs | CI build step |
| **SonarQube** | Code smells, duplications, security vulnerabilities, coverage gaps | PR decoration, quality gates |
| **PMD** | Dead code, empty catch blocks, unnecessary object creation | CI build step |

### SDET's Role in Promoting Unit Tests

SDETs don't write all unit tests — developers do. But SDETs make unit testing *easier* by providing:

- **Test data builders** — `BookingBuilder.aBooking().withGuests(5).build()` instead of constructing 15-field objects
- **Mock factories** — Pre-configured mocks for common dependencies (database, external services)
- **Assertion helpers** — `assertBookingMatches(expected, actual)` instead of 10 individual field assertions
- **Test templates** — Starter test classes for common patterns (controller tests, service tests, repository tests)

### Pre-Commit Hook — Fast Feedback Before Push


```java
// .git/hooks/pre-commit (shell script concept, shown for understanding)
// #!/bin/bash
// echo "Running Checkstyle..."
// ./gradlew checkstyleMain --quiet
// if [ $? -ne 0 ]; then
//     echo "Checkstyle failed. Fix violations before committing."
//     exit 1
// fi
//
// echo "Running unit tests..."
// ./gradlew test --quiet --fail-fast
// if [ $? -ne 0 ]; then
//     echo "Unit tests failed. Fix tests before committing."
//     exit 1
// fi

// Java equivalent: a TestNG listener that enforces quality before suite runs
public class QualityGateListener implements ISuiteListener {

    @Override
    public void onStart(ISuite suite) {
        // Check that static analysis passed before running integration tests
        boolean staticAnalysisPassed = Boolean.parseBoolean(
            System.getProperty("static.analysis.passed", "true"));
        if (!staticAnalysisPassed) {
            throw new SkipException("Static analysis failed — skipping integration tests");
        }
    }
}
```

### PR-Level Test Pipeline — Run Relevant Tests Per Change


```java
// Conceptual: a test selector that picks tests based on changed files
public class TestImpactAnalyzer {

    private final Set<String> changedFiles;

    public TestImpactAnalyzer(Set<String> changedFiles) {
        this.changedFiles = changedFiles;
    }

    /**
     * Maps source file changes to relevant test classes.
     * Simple heuristic: if BookingService.java changed, run BookingServiceTest
     * and BookingIntegrationTest.
     */
    public Set<String> getAffectedTests() {
        Set<String> affectedTests = new HashSet<>();

        for (String file : changedFiles) {
            if (file.contains("BookingService")) {
                affectedTests.add("BookingServiceTest");
                affectedTests.add("BookingIntegrationTest");
                affectedTests.add("BookingApiTest");
            } else if (file.contains("HotelController")) {
                affectedTests.add("HotelApiTest");
                affectedTests.add("HotelSearchTest");
            } else if (file.contains("auth/")) {
                // Auth changes affect everything — run full suite
                affectedTests.add("*");
                break;
            }
        }

        // If no mapping found, run smoke tests as minimum
        if (affectedTests.isEmpty()) {
            affectedTests.add("SmokeTest");
        }

        return affectedTests;
    }
}
```

### Unit Test Helper — Making Testing Easy for Developers


```java
/**
 * SDET-provided assertion helper that developers use in their unit tests.
 * Reduces 10 assertEquals calls to 1 readable assertion.
 */
public class BookingAssertions {

    public static void assertBookingMatches(Booking expected, Booking actual) {
        assertAll("Booking fields",
            () -> assertEquals(actual.getStatus(), expected.getStatus(), "status"),
            () -> assertEquals(actual.getRoomId(), expected.getRoomId(), "roomId"),
            () -> assertEquals(actual.getCheckInDate(), expected.getCheckInDate(), "checkIn"),
            () -> assertEquals(actual.getCheckOutDate(), expected.getCheckOutDate(), "checkOut"),
            () -> assertEquals(actual.getNumberOfGuests(), expected.getNumberOfGuests(), "guests")
        );
    }

    /** Soft assertion version — reports all mismatches, not just the first */
    public static void assertBookingMatchesSoft(SoftAssertions soft,
            Booking expected, Booking actual) {
        soft.assertThat(actual.getStatus()).as("status").isEqualTo(expected.getStatus());
        soft.assertThat(actual.getRoomId()).as("roomId").isEqualTo(expected.getRoomId());
        soft.assertThat(actual.getCheckInDate()).as("checkIn").isEqualTo(expected.getCheckInDate());
    }
}
```

## Failure and Debugging (Layer 4)

### Failure 1: SonarQube Quality Gate Blocks PRs for Legacy Code

**The Problem:** A developer fixes a one-line bug in a file with 0% coverage. SonarQube fails the PR because "new code coverage &lt; 80%" — the developer's one line is the "new code" and it's not covered.

**Root cause:** SonarQube's "new code" definition includes all changed lines, even in legacy files.

**The fix:** Configure SonarQube to focus on new code *in new files* vs *modified lines in existing files* differently. Or: the developer adds a unit test for their fix (which they should anyway — if it's worth fixing, it's worth testing).

### Failure 2: Test Impact Analysis Misses Affected Tests

**The Problem:** A change to `PaymentService.java` doesn't trigger `BookingIntegrationTest`, which indirectly depends on payment logic. The PR passes, but integration tests fail on merge.

**The fix:** Test impact analysis requires a dependency graph, not just filename matching. Start with conservative mappings (more tests, not fewer) and refine over time. Always run the full suite on merge to main as a safety net.

## Engineering Judgment (Layer 5)

### What to Shift Left vs Keep Right

| Shift Left (Early) | Keep Right (Later) |
|--------------------|--------------------|
| Static analysis, linting | Performance/load testing |
| Unit tests | E2E tests with real infrastructure |
| API contract tests | Exploratory testing |
| Security scanning (SAST) | Chaos/resilience testing |
| Accessibility linting | User acceptance testing |

### SDET's Shift-Left Contribution Priorities

| Priority | Action | Impact |
|----------|--------|--------|
| 1 | Set up SonarQube with quality gates | Catches bugs before code review |
| 2 | Create test data builders and helpers | Developers write 3x more unit tests |
| 3 | Configure PR-level test pipeline | Broken code never reaches main |
| 4 | Implement test impact analysis | PR feedback in 2 min instead of 20 |
| 5 | Review test plans during design phase | Catches requirement gaps before coding |
