# Mock Interviews

> **Module:** 13 — Interview Preparation
> **Prerequisites:** Modules 01-12 (or concurrent progress through at least modules 01-08)
> **Purpose:** Practice interview performance so knowledge translates into offers

---

## Why Mock Interviews Matter

Knowing the material is necessary but not sufficient. Interviews are a performance — you need to think out loud, manage time, handle ambiguity, and communicate clearly under pressure. Mock interviews are the bridge between "I know this" and "I can demonstrate this in 45 minutes with a stranger watching."

**The gap this closes:** Many strong SDETs fail interviews not because they lack knowledge but because they:
- Freeze when the problem isn't exactly like something they've practiced
- Write code silently for 10 minutes without explaining their approach
- Give theoretical answers when the interviewer wants practical examples
- Run out of time because they didn't scope the problem before coding

---

## Mock Interview Format

A typical SDET interview loop has three segments. Practice all three, not just coding.

| Segment | Duration | What's Evaluated |
| --- | --- | --- |
| Coding | 15 minutes | Problem-solving, code quality, testing mindset |
| Framework Design | 15 minutes | Architecture, design patterns, trade-off reasoning |
| Behavioral | 15 minutes | Communication, teamwork, problem-solving stories |

**Total mock session:** 45 minutes + 10 minutes self-review = 55 minutes

## Coding Mock: Structure and Strategy

### The 5-Step Process

Every coding problem should follow this sequence. Practice it until it's automatic.

**Step 1: Understand (2 minutes)**
- Restate the problem in your own words
- Ask clarifying questions: "Can the input be null? Can the array be empty? What's the expected output for this edge case?"
- Confirm constraints: "So N can be up to 10^5, meaning O(N^2) might be too slow?"

**Step 2: Plan (3 minutes)**
- Describe your approach out loud before writing code
- State the time and space complexity of your plan
- "I'll use a HashMap to track frequencies, iterate once through the array, and return the first element with count > 1. That's O(N) time and O(N) space."

**Step 3: Code (7 minutes)**
- Write clean code with meaningful variable names
- Talk while you code: "Now I'm iterating through the array, for each element I check if it's in the map..."
- Don't optimize prematurely — get a working solution first

**Step 4: Test (2 minutes)**
- Walk through your code with a concrete example
- Test edge cases: empty input, single element, all duplicates
- "Let me trace through with [1, 2, 3, 2]: first iteration adds 1 to map, second adds 2, third adds 3, fourth finds 2 already in map — returns 2. Correct."

**Step 5: Optimize (1 minute)**
- If time permits, discuss potential optimizations
- "If memory is a concern, I could sort first and use O(1) space, but that's O(N log N) time."

### Common Coding Mistakes

| Mistake | What Happens | Prevention |
| --- | --- | --- |
| Coding immediately | You solve the wrong problem or use a suboptimal approach | Always spend 2-3 minutes planning out loud |
| Silent coding | Interviewer can't evaluate your thought process | Narrate every decision: "I'm choosing a HashMap because..." |
| Ignoring edge cases | Solution fails on empty input or boundary values | Always test with: empty, single element, all same, already sorted |
| Perfect code syndrome | You run out of time polishing instead of completing | Get a working solution first, then optimize if time allows |
| Not testing | You declare "done" without verifying | Always trace through at least one example manually |

### Practice Problems for SDETs

These are realistic coding problems that appear in SDET interviews — they blend DSA with testing scenarios:

| Problem | Key Concept | Time Target |
| --- | --- | --- |
| Validate that a list of test results is sorted by priority | Array traversal, comparison | 10 min |
| Find duplicate test IDs in a test suite | HashMap, Set | 10 min |
| Merge two sorted lists of test execution timestamps | Two-pointer merge | 12 min |
| Check if a test dependency graph has cycles | Graph DFS, cycle detection | 15 min |
| Parse a log file and count failures per test class | String parsing, HashMap | 12 min |
| Implement a retry mechanism with exponential backoff | Recursion or loop, math | 10 min |

## Framework Design Mock: Structure and Strategy

### The 5-Step Process

Framework design questions are open-ended. Structure prevents rambling.

**Step 1: Gather Requirements (2 minutes)**
- "What's the application? Web, mobile, API?"
- "What's the team size? How many tests do we expect?"
- "What's the tech stack? Java, Python, TypeScript?"
- "Any existing infrastructure? Jenkins, Docker, cloud?"

**Step 2: Propose Architecture (4 minutes)**
- Draw the layer diagram (test → page/API → driver → config → utility)
- Name specific patterns: "I'll use Page Object for UI, Builder for test data, Factory for drivers"
- "The framework has 5 layers. Tests at the top call page objects which use a driver managed by a factory..."

**Step 3: Deep-Dive on Key Layers (5 minutes)**
- Pick 2-3 layers and explain implementation details
- Show code snippets or pseudo-code if whiteboard is available
- "For parallel execution, I'd use ThreadLocal`<WebDriver>` so each test thread has its own driver instance..."

**Step 4: Discuss Patterns and Trade-offs (3 minutes)**
- "I chose composition over inheritance because deep base class hierarchies make the framework brittle"
- "REST Assured over plain HttpClient because the fluent DSL makes tests more readable"
- "TestNG over JUnit because of built-in parallel execution and data providers"

**Step 5: CI Integration (1 minute)**
- "Tests run in Jenkins with Docker. API tests first, then UI tests in headless mode."
- "Allure reports show trends over time. Slack notifications on failure."

### Common Framework Design Questions

| Question | Key Points to Cover |
| --- | --- |
| "Design an API testing framework" | Base specs, POJO models, auth management, schema validation, reporting |
| "Design a Selenium framework" | POM, driver factory, ThreadLocal, config, screenshots, parallel execution |
| "How would you handle test data?" | Builders, unique data per test, API-based setup, cleanup strategies |
| "How do you handle flaky tests?" | Retries (limited), explicit waits, test isolation, CI dashboards for trends |
| "Design a framework for 50 developers" | Standards, linting, code review, shared libraries, documentation, onboarding |

## Behavioral Mock: STAR Format

### The STAR Structure

Every behavioral answer should follow this pattern:

- **S**ituation: Set the context (1-2 sentences)
- **T**ask: What was your specific responsibility?
- **A**ction: What did you do? (This is 60% of your answer)
- **R**esult: What happened? Use numbers if possible.

### 10 Common SDET Behavioral Questions with Answer Outlines

**1. "Tell me about a time you found a critical bug."**

- **S:** During regression testing for a payment feature, automated API tests were passing but I noticed the booking amount in the database didn't match the API response.
- **T:** I needed to investigate whether this was a test issue or an actual production-impacting bug.
- **A:** I added a database validation step to the test, traced the code to the dynamic pricing service, found that the occupancy multiplier was using stale cached data. I wrote a reproducible test case and filed the bug with full evidence.
- **R:** The bug was fixed before release. I added permanent DB validation tests that caught 3 similar pricing issues in subsequent sprints.

**2. "Tell me about a time you improved test execution time."**

- **S:** Our regression suite took 45 minutes to run, blocking CI deployments.
- **T:** Reduce execution time to under 15 minutes without reducing coverage.
- **A:** I profiled the suite and found 3 issues: (1) sequential browser execution, (2) UI-based test data setup, (3) redundant login flows. I switched to parallel execution with TestNG (3 threads), replaced UI data setup with API calls, and implemented a shared auth token per test class.
- **R:** Suite dropped from 45 minutes to 12 minutes. Deployment frequency increased from 2/day to 5/day.

**3. "Tell me about a time you disagreed with a developer."**

- **S:** A developer insisted that a 500 error on duplicate email signup was "working as designed."
- **T:** I needed to advocate for proper error handling without damaging the working relationship.
- **A:** I showed the API contract (which specified 409 for conflicts), demonstrated that the 500 status exposed internal stack traces to the client (security risk), and proposed a specific fix. I framed it as "improving the API" not "your code is wrong."
- **R:** The developer agreed, changed it to 409 with a clean error message. We added a shared API contract review to the sprint process.

**4. "Tell me about a time you dealt with flaky tests."**

- **S:** 15% of our CI runs were failing due to flaky web UI tests, and the team was starting to ignore test failures.
- **T:** Identify and fix the root causes to restore trust in the test suite.
- **A:** I added a flaky test dashboard that tracked pass rates per test over 30 days. The top 5 offenders were all due to implicit waits and shared test data. I replaced implicit waits with explicit waits in the page objects, isolated test data per test, and added retry (max 1) for UI tests only with logging to track when retries triggered.
- **R:** Flaky rate dropped from 15% to 2%. The team started treating test failures as real bugs again.

**5. "Tell me about a time you had to learn a new tool quickly."**

- **S:** Our team decided to adopt Playwright, and I was the Selenium expert being asked to lead the migration.
- **T:** Learn Playwright well enough to design the new framework architecture within 2 weeks.
- **A:** I spent 3 days on Playwright's documentation and wrote the same 10 tests in both Selenium and Playwright. I documented the differences (auto-waits, fixtures, trace viewer) and created a migration guide for the team. I designed the new framework leveraging Playwright-specific features (fixtures for DI, built-in API testing).
- **R:** Migration completed in 4 weeks. Test execution time dropped 30% due to Playwright's parallel workers. The team had zero ramp-up issues because of the migration guide.

**6. "How do you prioritize what to automate?"**

- **S:** Joined a team with 500 manual test cases and no automation.
- **T:** Build automation coverage strategically — couldn't automate everything at once.
- **A:** I categorized tests by risk (business impact) and frequency (how often they run). P0 smoke tests (login, core flows) came first — these ran on every commit. P1 regression tests came next. I deprioritized edge cases that were unlikely to regress and visual tests that were hard to automate reliably.
- **R:** Within 8 weeks, 60% of P0/P1 scenarios were automated. Manual regression time dropped from 2 days to 4 hours.

**7. "Tell me about a time you mentored someone."**

- **S:** A junior SDET joined and was struggling with Page Object pattern — their tests had locators scattered everywhere.
- **T:** Help them understand the pattern and refactor their code without doing it for them.
- **A:** I pair-programmed for 2 hours, explaining the "why" not just the "how." I showed them a test that broke when a CSS class changed, then refactored it live to use a page object. I set up a code review process where I reviewed their PRs with detailed comments.
- **R:** Within 3 weeks, they were writing clean page objects independently. They later mentored the next new hire.

**8. "Describe a situation where you had to work with incomplete requirements."**

- **S:** The product team wanted testing for a new dynamic pricing feature, but the requirements document only said "prices should adjust based on demand."
- **T:** I needed to write tests without clear acceptance criteria.
- **A:** I read the source code to extract the actual pricing rules (5 strategies in a chain). I documented what I found, shared it with the product team for confirmation, and wrote tests based on the code behavior. I flagged 2 cases where the code behavior seemed unintentional.
- **R:** My documentation became the official spec. The 2 flagged cases were confirmed as bugs by the product team.

**9. "Tell me about a time you improved a process."**

- **S:** Our team had no test data management strategy — tests used hardcoded data that broke after database refreshes.
- **T:** Design a test data approach that was reliable across environments.
- **A:** I implemented API-based test data setup (create users, hotels, bookings via API before each test class). Each test used unique identifiers (UUID-based emails). I created a TestDataBuilder class that the team could use without understanding the API details.
- **R:** Zero test data-related failures in the next 6 months. New test creation time dropped from 30 minutes to 10 minutes because data setup was handled.

**10. "Why do you want this role?"**

- **S:** (Tailor to the specific company)
- **T:** Connect your skills to their needs.
- **A:** "I've built automation frameworks across API, web, and mobile for a hotel booking platform with real complexity — JWT auth, multi-step workflows, dynamic pricing. Your product has similar challenges, and I'm excited to apply these skills at scale."
- **R:** "I'm looking for a role where I can own the quality engineering strategy, not just write tests. Your team's focus on [specific initiative] aligns with where I want to grow."

## Self-Recording and Review

### How to Practice Solo

1. **Record yourself** — use your phone or screen recording. Watch playback at 1.5x.
2. **Time yourself strictly** — set a 15-minute timer per segment. Stop when it rings.
3. **Grade yourself** on each dimension (see rubric below).
4. **Focus on one segment per session** — don't try to practice all three in one sitting every time.

### Self-Grading Rubric

| Dimension | 1 (Needs Work) | 3 (Adequate) | 5 (Strong) |
| --- | --- | --- | --- |
| Clarity | Rambling, hard to follow | Generally clear with some tangents | Concise, structured, easy to follow |
| Technical Depth | Surface-level answers | Correct but generic | Specific details with trade-off reasoning |
| Communication | Silent coding, monosyllables | Explains when prompted | Narrates thinking proactively |
| Time Management | Runs out of time, incomplete | Finishes but rushed | Comfortable pace, time for review |
| Problem Solving | Gets stuck, no recovery | Eventual solution with hints | Systematic approach, handles ambiguity |

### Peer Practice Strategy

If you have a study partner:

1. **Alternate roles** — one person interviews, the other answers, then switch
2. **Use the question sets below** — don't show the answer outlines to the interviewee
3. **Give honest feedback** — "You were silent for 2 minutes while coding" is more helpful than "That was fine"
4. **Record and review together** — point out specific moments, not general impressions

## Mock Interview Question Sets

### Set 1: API-Focused

**Coding (15 min):** Write a method that takes a list of API response times (integers, milliseconds) and returns the 95th percentile value. Handle edge cases (empty list, single element).

Answer outline:
- Sort the list
- Calculate index: `Math.ceil(0.95 * n) - 1`
- Handle edge cases: empty → throw or return -1, single → return that element
- Time: O(N log N) for sort
- Testing follow-up: "What test cases would you write for this method?" → empty, single, all same, already sorted, 100 elements, negative values

**Framework Design (15 min):** "Design an API test automation framework for a hotel booking system with JWT auth, multi-step booking flows, and dynamic pricing."

Answer outline:
- Layers: test → API client → models → base spec → config → utilities
- Auth: TokenManager that generates and caches tokens, refreshes on expiry
- Test data: Builder pattern for creating bookings with all prerequisites (hotel, room, user, guest)
- Schema validation: JSON Schema files for key responses
- CI: Maven + TestNG + Allure, Docker for backend

**Behavioral (15 min):** Use questions 1, 2, and 6 from the list above.

### Set 2: Web Automation-Focused

**Coding (15 min):** Write a method that validates whether a web page's navigation links are in alphabetical order. The input is a `List<String>` of link texts. Return true if sorted, false otherwise. Then: how would you collect these link texts using Selenium?

Answer outline:
- Compare each element with the next: `list.get(i).compareToIgnoreCase(list.get(i+1)) > 0` → return false
- Edge cases: empty list (true), single element (true), case sensitivity
- Selenium: `driver.findElements(By.cssSelector("nav a")).stream().map(WebElement::getText).toList()`
- Testing: test with ["About", "Contact", "Home"] (sorted) and ["Home", "About"] (not sorted)

**Framework Design (15 min):** "You're building a Selenium framework for a team of 8 SDETs. How do you design it so that everyone writes consistent, maintainable tests?"

Answer outline:
- Strict POM convention: one page class per page, locators private, methods public
- Base test class: handles driver lifecycle, screenshots, logging
- Coding standards: checkstyle rules, PR template with checklist
- Shared utilities: wait helpers, assertion helpers, test data API client
- TestNG groups: smoke, regression, each SDET owns a feature area
- Documentation: contribution guide, page object template, naming conventions

**Behavioral (15 min):** Use questions 4, 5, and 7 from the list above.

### Set 3: Full-Stack SDET

**Coding (15 min):** Write a method that takes a `Map<String, List<String>>` representing test dependencies (key: test name, value: list of tests it depends on) and returns a valid execution order. If there's a circular dependency, throw an exception.

Answer outline:
- Topological sort using Kahn's algorithm (BFS) or DFS with visited/inProgress states
- Cycle detection: if inProgress set contains current node during DFS, cycle exists
- Edge cases: empty map, single test, all independent (any order valid)
- Time: O(V + E), Space: O(V)
- Testing: no deps, chain (A→B→C), diamond (A→B, A→C, B→D, C→D), cycle (A→B→A)

**Framework Design (15 min):** "Design a CI pipeline that runs API tests, web tests, and mobile tests. Walk me through every stage."

Answer outline:
- Stages: checkout → build → start backend (Docker) → API tests → web tests (if API passed) → mobile tests (BrowserStack, optional) → report → notify → cleanup
- Docker Compose for infrastructure, health checks for readiness
- Fail-fast: skip UI tests if API tests fail
- Reporting: consolidated Allure report across all suites
- Notifications: Slack with build URL and failure stage

**Behavioral (15 min):** Use questions 3, 8, and 9 from the list above.
