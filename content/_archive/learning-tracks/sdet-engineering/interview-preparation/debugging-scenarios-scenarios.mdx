# Debugging Scenarios for SDET Interviews

> **Module:** 13 — Interview Preparation
> **Focus:** 8 real-world debugging scenarios with structured investigation approaches
> **Audience:** SDET with ~3 years experience targeting senior roles
> **Complements:** Fastenal-Prep covers automation debugging and flaky test strategies; this file provides structured scenario-based answers for the "how would you debug this?" interview format

---

## How to Use This File

Debugging scenarios are the most revealing SDET interview questions. They test whether you've actually worked in real environments or just studied theory. For each scenario: describe the scenario, provide a structured approach, list key investigation steps, identify root cause categories, and outline a strong answer.

**Answer framework for any debugging question:**
1. **Reproduce:** Can I see it happen? Is it consistent or intermittent?
2. **Isolate:** What changed? What's different between working and broken?
3. **Investigate:** Gather data — logs, screenshots, network traffic, environment state
4. **Identify root cause:** Narrow to one of the known categories
5. **Fix and prevent:** Fix the issue + add safeguards against recurrence

## Scenario 1: "Your test passes locally but fails in CI. How do you debug it?"

**Why interviewers ask this:** This is the #1 most common debugging scenario for SDETs. It tests whether you understand environmental differences and have a systematic approach.

**Structured Approach:**

### Step 1: Verify the failure is real
- Check if it's a flaky test: run the CI job 3 times. If it fails consistently, it's a real environmental issue.
- Read the exact error message and stack trace — don't guess.

### Step 2: Identify what's different between local and CI

| Dimension | Local | CI | Common Issue |
| --- | --- | --- | --- |
| **Browser mode** | Headed | Headless | Element visibility differs in headless |
| **Screen resolution** | 1920x1080 | Default (often 800x600) | Responsive layout hides elements |
| **Timing** | Fast machine | Shared CI runner | Race conditions, timeouts |
| **Environment** | Dev/QA URL | Different QA instance | Different data, different config |
| **OS** | macOS/Windows | Linux | Path separators, font rendering |
| **Network** | Direct | Docker/proxy | DNS resolution, firewall rules |
| **Browser version** | Latest | Cached/pinned | API differences between versions |
| **Test data** | Known local state | Shared CI database | Data conflicts from parallel runs |
| **Timezone** | Local timezone | UTC (usually) | Date-dependent assertions fail |

### Step 3: Investigation tactics

**Quick wins (check first):**
1. Look at the CI screenshot/video (if captured) — does the page look different?
2. Check the viewport size in CI — add `--window-size=1920,1080` to headless browser options
3. Check the URL the test is hitting — is it the right environment?
4. Check if the test data exists in the CI database

**Deeper investigation:**
5. Add more logging to the failing step — log element state, page title, URL before the action
6. Run the test locally in headless mode — reproduces many CI-specific issues
7. SSH into the CI runner and run the test manually (if possible)
8. Compare network traffic — are API calls returning different responses?

### Root Cause Categories (in order of frequency)

1. **Timing issues (40%):** CI is slower → explicit waits needed, or timeouts too short
2. **Viewport/headless differences (20%):** Element not visible at CI viewport size
3. **Test data (15%):** Different database state in CI, parallel test data conflicts
4. **Environment configuration (10%):** Wrong URL, missing env variables, expired tokens
5. **OS differences (5%):** File paths, line endings, locale
6. **Browser version mismatch (5%):** Different browser version in CI container
7. **Resource contention (5%):** CI runner under load, Docker memory limits

### Answer Outline
"I'd start by reading the exact error — is it a timeout, element not found, or assertion failure? Then I'd compare the CI environment to my local setup across four dimensions: browser configuration, viewport size, test data, and timing. The most common culprit in my experience is timing — CI runners are shared and slower, so explicit waits need to be sufficient. I'd also check if the test runs in headless mode locally to reproduce it, and look at the CI screenshot if available."

## Scenario 2: "Tests are taking 45 minutes to run. How do you optimize?"

**Why interviewers ask this:** Tests strategic thinking and profiling skills. Junior SDETs guess; senior SDETs measure first.

**Structured Approach:**

### Step 1: Profile before optimizing

**Never guess where time is spent.** Measure:

```
Category breakdown:
├── Browser startup: 3 min (30 tests × 6 sec each)
├── Login flows: 8 min (30 tests × 15 sec each login through UI)
├── Test data setup (UI): 12 min (navigating to create test prerequisites)
├── Actual test execution: 15 min
├── Teardown/cleanup: 2 min
└── Thread.sleep() calls: 5 min total scattered throughout
```

### Step 2: Apply optimizations by impact

| Optimization | Effort | Time Saved | Priority |
| --- | --- | --- | --- |
| **Parallelize** (3-5 threads) | Medium | 60-70% | Do first |
| **API-based test data setup** instead of UI | Medium | 10-15 min | Do second |
| **Shared auth token** instead of login per test | Low | 5-8 min | Do second |
| **Replace Thread.sleep with explicit waits** | Low | 3-5 min | Do third |
| **Headless mode in CI** | Low | 20-30% faster | Do third |
| **Remove redundant tests** | Low | Varies | Ongoing |
| **Push tests down the pyramid** (API vs UI) | High | 50%+ long-term | Strategic |

### Step 3: Measure results after each change

Track: total suite time, average test time, slowest 10 tests, time per category.

### Answer Outline
"I wouldn't start optimizing blindly. First, I'd profile: add timing to each test, categorize time into browser startup, data setup, execution, and teardown. In my experience, the biggest wins come from three things: (1) parallelizing — if tests run sequentially, adding 3-5 threads cuts time by 60-70%, (2) replacing UI-based test data setup with API calls — creating a user through the UI takes 15 seconds, through the API takes 200ms, and (3) eliminating Thread.sleep calls in favor of explicit waits. I'd measure the impact of each change before moving to the next one."

## Scenario 3: "A test was passing yesterday, no code changes, now it fails. What do you check?"

**Why interviewers ask this:** Tests systematic thinking when the obvious cause (code change) is eliminated.

**Structured Approach:**

### Step 1: Verify "no code changes" is actually true
- Check git log for the test repo AND the application repo
- Check if deployment happened (new app version, even if test code didn't change)
- Check if a configuration change was made (environment variables, feature flags)

### Step 2: Investigation checklist (in order)

| Check | What to Look For | How |
| --- | --- | --- |
| **Test data** | Was shared test data modified or deleted? | Query the database, check API |
| **Environment** | Is the QA environment healthy? | Hit health endpoint, check status page |
| **Dependencies** | Is a third-party service down? | Check external service status pages |
| **Certificate/token expiry** | SSL cert, API token, OAuth client secret | Check cert dates, try new token |
| **Data migrations** | Did the database schema change? | Check migration logs, table schemas |
| **Infrastructure** | CI runner out of disk/memory? | Check CI machine metrics |
| **Browser/driver** | Auto-updated browser broke compatibility? | Check browser and driver versions |
| **Time-dependent logic** | Is the test sensitive to date/time? | Check if test uses dates, month boundaries |
| **Feature flags** | Was a flag toggled? | Check feature flag dashboard |
| **DNS/network** | DNS resolution changed? Firewall rule updated? | nslookup, curl the endpoints |

### Step 3: Most common root causes (when code didn't change)

1. **Test data changed** (35%) — Someone modified shared data, or a cleanup job ran
2. **Environment issue** (25%) — Service restarted, deployment happened, resource exhaustion
3. **Token/certificate expiry** (15%) — Tokens expire, SSL certs expire, API keys rotate
4. **Time-dependent test** (10%) — Month boundary, year boundary, daylight saving time
5. **Browser auto-update** (10%) — Chrome auto-updated, driver version mismatch
6. **Flakiness revealed** (5%) — Test was always flaky, you just got unlucky today

### Answer Outline
"First, I'd verify 'no code changes' — check both the test and application repos, and whether a deployment happened. Then I'd systematically check: is the environment healthy? Has test data changed? Have any tokens or certificates expired? If it's a UI test, I'd check if the browser version was auto-updated. In my experience, test data changes and token expirations are the most common causes of tests breaking without code changes."

## Scenario 4: "You see StaleElementReferenceException. What causes it and how do you fix it?"

**Why interviewers ask this:** Selenium-specific, but tests deep understanding of how the DOM works.

**Structured Approach:**

### Root cause
The WebElement reference you're holding points to a DOM node that no longer exists. The DOM was modified between your `findElement` call and your subsequent action on that element.

### Three situations that cause it

**Situation 1: Page refresh or navigation**
```
findElement() → page refreshes → click() → STALE
Fix: Re-find the element after any navigation/refresh
```

**Situation 2: AJAX update replaces the element**
```
findElement(priceLabel) → quantity changes → AJAX updates price → getText() → STALE
Fix: Wait for AJAX to complete, then find fresh element
```

**Situation 3: SPA framework re-renders the component**
```
findElement(listItem) → state changes → React re-renders → click() → STALE
Fix: Never cache WebElement references for dynamic content
```

### Fixes by approach

| Approach | When to Use |
| --- | --- |
| **Re-find every time** | Always — safest default for dynamic pages |
| **Wait for staleness, then re-find** | When you know the element will be replaced |
| **Ignore StaleElement in wait** | When timing is unpredictable |
| **Use Playwright** | Its locators are lazy by design — never stale |

### Code pattern

```java
<!-- unverified -->
// Best practice: fluent wait that ignores StaleElementReferenceException
public String getTextSafely(By locator) {
    return new WebDriverWait(driver, Duration.ofSeconds(10))
        .ignoring(StaleElementReferenceException.class)
        .until(d -> d.findElement(locator).getText());
}
```

### Answer Outline
"StaleElementReferenceException means the DOM node I'm referencing was destroyed and recreated — usually because the page refreshed, AJAX updated the element, or a SPA framework re-rendered the component. The key fix is to never cache WebElement references for dynamic content. I either re-find the element immediately before using it, or use a WebDriverWait that ignores StaleElementReferenceException and retries the find+action in a single expression."

## Scenario 5: "Your parallel tests are interfering with each other. How do you investigate?"

**Why interviewers ask this:** Tests understanding of test isolation, thread safety, and shared state.

**Structured Approach:**

### Step 1: Confirm it's a parallelism issue
- Run the failing test in isolation — does it pass? If yes, interference confirmed.
- Run the specific pair of tests together — which combination causes the failure?
- Check if the failure is timing-dependent (race condition) or data-dependent.

### Step 2: Common interference patterns

| Pattern | Symptoms | Example |
| --- | --- | --- |
| **Shared test data** | Test B fails because Test A modified the data | Both tests update the same user account |
| **Shared WebDriver** | Random elements clicked, wrong pages | Singleton driver instead of ThreadLocal |
| **Database conflicts** | Unique constraint violations, wrong counts | Both tests insert user with same email |
| **Port conflicts** | Connection refused, bind errors | Both tests start a local service on port 8080 |
| **File system conflicts** | File not found, corrupted data | Both tests write to the same file |
| **Static state** | Unexpected values in shared variables | Static field modified by both threads |

### Step 3: Investigation steps

1. **Check for shared WebDriver:** Is `ThreadLocal` used? Or is there a singleton driver?
2. **Check for shared test data:** Are both tests using the same user/booking/resource?
3. **Check for static variables:** Grep for `static` fields in test classes and page objects
4. **Check database operations:** Are tests inserting/updating the same rows?
5. **Run with `parallel="none"` to confirm:** Tests pass sequentially → it's a parallelism issue

### Step 4: Fixes

```java
<!-- unverified -->
// Fix 1: ThreadLocal for driver (not singleton)
private static final ThreadLocal<WebDriver> driver = new ThreadLocal<>();

// Fix 2: Unique test data per test
String uniqueEmail = "test-" + UUID.randomUUID() + "@test.com";

// Fix 3: Remove static mutable state
// BAD: static String currentUser = "admin";
// GOOD: each test creates its own user

// Fix 4: Database isolation
@BeforeMethod
public void setup() {
    testUser = apiClient.createUser(uniqueUser()); // Each test gets its own
}

@AfterMethod
public void cleanup() {
    apiClient.deleteUser(testUser.getId()); // Clean up after
}
```

### Answer Outline
"First, I'd confirm it's a parallelism issue by running the failing test in isolation — if it passes alone, interference is confirmed. Then I'd systematically check for shared state: shared WebDriver instance instead of ThreadLocal, shared test data in the database, static mutable variables, and file system conflicts. The most common cause in my experience is shared test data — two tests modifying the same user or resource. The fix is to ensure each test creates its own isolated data with unique identifiers."

## Scenario 6: "An API test returns 200 but the feature is broken. What went wrong?"

**Why interviewers ask this:** Tests whether you understand the gap between "test passes" and "feature works."

**Structured Approach:**

### Step 1: Identify what the test is actually verifying
Read the test code carefully:

```java
<!-- unverified -->
// This test is WEAK — it only checks status code
@Test
public void testCreateBooking() {
    given().body(request).post("/bookings").then().statusCode(200);
}
// A 200 status with an empty body, wrong data, or even an error message
// in the response body would pass this test!
```

### Step 2: Categories of "200 but broken"

| Category | What Went Wrong | What Was Missing |
| --- | --- | --- |
| **Shallow assertion** | Only checked status code, not response body | Body field assertions |
| **API lies** | API returns 200 with error in body | Error field validation |
| **Database not updated** | API returns 200 but didn't persist data | DB validation |
| **Wrong data returned** | API returns 200 with incorrect values | Business logic assertions |
| **Side effects missing** | API returns 200 but email not sent, event not published | Integration verification |
| **Stale cached response** | API returns cached (correct) data, but source data is wrong | Cache-busting in tests |

### Step 3: How to fix the test

```java
<!-- unverified -->
// STRONG test — multiple layers of validation
@Test
public void testCreateBooking() {
    BookingResponse response = given()
        .body(request)
        .post("/bookings")
    .then()
        .statusCode(201)  // Correct code for creation (not 200)
        .extract().as(BookingResponse.class);
    
    // Verify response body matches request
    assertThat(response.getGuestName()).isEqualTo(request.getGuestName());
    assertThat(response.getCheckIn()).isEqualTo(request.getCheckIn());
    assertThat(response.getStatus()).isEqualTo("CONFIRMED");
    
    // Verify database was updated
    Map<String, Object> dbRow = DbHelper.getBooking(response.getId());
    assertThat(dbRow.get("guest_name")).isEqualTo(request.getGuestName());
    
    // Verify the booking is retrievable via GET
    BookingResponse retrieved = given()
        .get("/bookings/" + response.getId())
    .then()
        .statusCode(200)
        .extract().as(BookingResponse.class);
    
    assertThat(retrieved).isEqualTo(response);
}
```

### Answer Outline
"A 200 status code only means the server processed the request — it doesn't mean the feature works correctly. I'd check: (1) Is the test only asserting the status code? It should also validate response body fields. (2) Does the API return 200 with an error message in the body? Some poorly designed APIs do this. (3) Was the data actually persisted? I'd add a database validation step. (4) Can the created resource be retrieved? A follow-up GET request confirms end-to-end functionality. The root cause is usually shallow assertions — the test proves the API responded, not that the feature works."

## Scenario 7: "Your test suite has 15% flaky tests. How do you tackle this?"

**Why interviewers ask this:** Tests strategic thinking and prioritization for a real-world problem.

**Structured Approach:**

### Step 1: Quantify and categorize (Week 1)

Build a flaky test dashboard:
- Track pass rate per test over the last 30 runs
- Define flaky: any test with &lt; 95% pass rate
- Sort by frequency of flakiness (most flaky first)

```
Top 10 Flaky Tests:
1. testCheckoutFlow          — 60% pass rate — UI timing issue
2. testSearchResults         — 70% pass rate — Dynamic content loading
3. testPaymentProcessing     — 75% pass rate — External service dependency
4. testUserRegistration      — 80% pass rate — Database race condition
5. testSortingByPrice        — 85% pass rate — Sort animation timing
...
```

### Step 2: Quarantine and fix (Week 2-4)

**Quarantine:** Move flaky tests to a separate suite that runs but doesn't block the pipeline. This restores trust in the main suite immediately.

**Fix by category:**

| Category | Tests Affected | Fix | Effort |
| --- | --- | --- | --- |
| Timing/waits | 5 tests | Replace implicit with explicit waits | Low |
| Shared test data | 3 tests | Unique data per test (UUID) | Medium |
| External dependency | 2 tests | WireMock for external calls | Medium |
| Database race condition | 2 tests | Add DB-level wait or retry | Medium |
| Dynamic content | 3 tests | Wait for specific content, not just element | Low |

### Step 3: Prevent recurrence (Ongoing)

- **PR rule:** New tests must pass 5 consecutive runs before merge
- **Monitoring:** Weekly flaky rate report to the team
- **Retry policy:** Max 1 retry for UI tests, log every retry
- **Root cause analysis:** Every fixed flaky test gets a documented root cause for team learning
- **Target:** &lt; 2% flaky rate within 6 weeks

### Step 4: Track progress

```
Week 0: 15% flaky rate (baseline)
Week 2: 10% (quarantined worst offenders, fixed 5 timing issues)
Week 4:  5% (fixed data isolation for 3 tests, mocked external services)
Week 6:  2% (fixed remaining, prevention policies in place)
```

### Answer Outline
"15% flakiness is a crisis — the team stops trusting test results. I'd attack it in three phases: (1) Immediately quarantine the flaky tests so the main suite is trustworthy again. (2) Categorize the flaky tests — in my experience, 40% are timing issues, 25% are shared test data, and the rest are environment or external dependencies. Fix the highest-frequency ones first. (3) Prevent recurrence by requiring new tests to pass 5 consecutive runs before merge, and tracking a weekly flaky rate metric. My target would be under 2% within 6 weeks."

## Scenario 8: "A new hire can't understand your test framework. What would you change?"

**Why interviewers ask this:** Tests self-awareness, documentation skills, and framework design maturity. This is a senior-level question about leading a team, not just writing code.

**Structured Approach:**

### Step 1: Diagnose where they're struggling

| Symptom | Root Cause | Fix |
| --- | --- | --- |
| Can't run tests locally | Complex setup with undocumented steps | README with 5-minute quickstart |
| Doesn't know where to add new tests | Unclear project structure | Document naming conventions and directory layout |
| Writes tests that bypass framework patterns | Doesn't understand POM/builder patterns | Template files + pair programming |
| Copy-pastes code instead of using utilities | Doesn't know utility classes exist | Internal documentation + IDE templates |
| Tests are fragile and fail randomly | Doesn't understand wait strategies | Coded wait helpers + explicit guidance |

### Step 2: Improvements to the framework

**1. README with quickstart (most impactful):**

```markdown
## Quick Start (5 minutes)

1. Clone: `git clone repo-url`
2. Configure: Copy `config/local.properties.example` to `config/local.properties`, update base URL
3. Run smoke test: `mvn test -Dsuite=smoke -Denv=local`
4. View report: `allure serve allure-results`
```

**2. Contribution guide:**
- Naming conventions: test methods, page objects, packages
- Where to put new tests (which package, which suite)
- How to create a page object (template provided)
- PR checklist: assertions present, no hardcoded data, cleanup in @AfterMethod

**3. Template files:**

```java
<!-- unverified -->
// templates/NewPageObject.java
public class ExamplePage extends BasePage {
    // Define locators as private final
    private final By pageTitle = By.cssSelector("[data-testid='page-title']");
    
    public ExamplePage(WebDriver driver) {
        super(driver);
    }
    
    // Return types: return this for same page, return new XPage for navigation
    public ExamplePage doAction() {
        click(someButton);
        return this;
    }
    
    public String getTitle() {
        return getText(pageTitle);
    }
}
```

**4. Onboarding process:**
- Day 1: Clone repo, run smoke test, read README
- Day 2: Pair program with a senior SDET — write one test together
- Day 3-5: Write first solo test with detailed code review
- Week 2: Own a small feature area for test coverage

### Step 3: Framework design principles for understandability

- **Convention over configuration:** Follow Java/Maven standard project layout
- **Consistency:** Every page object follows the same pattern. Every test follows the same structure.
- **Minimal magic:** Avoid excessive abstraction. If understanding requires tracing through 5 layers of inheritance, simplify.
- **Self-documenting code:** Method names like `loginAsAdmin()` and `createBookingViaApi()` don't need comments.
- **Fail loudly with clear messages:** `"Expected 201 Created but got 500. Response: {error: 'DB connection failed'}"` is better than `AssertionError: expected 201 but was 500`.

### Answer Outline
"If a new hire can't understand the framework, the framework has a documentation and design problem, not a people problem. I'd start with three things: (1) A README that gets someone from clone to running their first test in 5 minutes. (2) Template files for page objects and tests — new SDETs copy the template and fill in the blanks. (3) A structured onboarding: pair programming on Day 2, detailed code review on their first solo PR. Longer term, I'd simplify any over-engineered abstractions — if understanding the framework requires reading 5 layers of inheritance, that's a design smell, not a learning curve."

## Quick-Reference: Debugging Approach for Any Scenario

```
1. READ THE ERROR — what does it actually say? (Don't guess)
2. REPRODUCE — can you see it happen again? (Consistent or intermittent?)
3. ISOLATE — what changed? What's different between working and broken?
4. GATHER DATA — logs, screenshots, network traffic, database state
5. HYPOTHESIZE — based on data, what are the top 3 possible causes?
6. TEST HYPOTHESES — one at a time, starting with most likely
7. FIX — address root cause, not symptoms
8. PREVENT — add monitoring, tests, or documentation to prevent recurrence
```

**The meta-answer for any debugging question:** "I'd follow a systematic approach: first understand the error, then reproduce it, isolate what's different, gather data, form hypotheses, and test them one at a time. I'd fix the root cause and add prevention so it doesn't happen again."
