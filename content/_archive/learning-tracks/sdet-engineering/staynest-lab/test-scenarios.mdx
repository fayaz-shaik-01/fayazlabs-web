# StayNest - Test Scenarios

A prioritized scenario matrix organized by automation layer. Each scenario maps to a specific business rule from `requirements-and-business-rules.md` so you always know *what* you are testing and *why*.

---

## API Test Scenarios

API tests are the highest priority. They validate business logic without UI complexity, run fast, and catch the majority of regressions.

### Authentication

| ID | Scenario | Business Rule | Priority | Steps |
| -- | -------- | ------------- | -------- | ----- |
| API-AUTH-01 | Signup with valid data | AUTH-01 | P0 | POST /auth/signup with valid email, password (6+ chars), name. Assert 201, response has `id`, `email`, `name`, no `password` field. |
| API-AUTH-02 | Login with valid credentials | AUTH-05 | P0 | Signup a user, then POST /auth/login. Assert 200, response has `accessToken` that is a valid JWT. |
| API-AUTH-03 | Login with wrong password | AUTH-07 | P0 | Signup a user, then login with wrong password. Assert 401. |
| API-AUTH-04 | Login with non-existent email | AUTH-07 | P0 | POST /auth/login with unregistered email. Assert 401. |
| API-AUTH-05 | Signup with duplicate email | AUTH-02 | P0 | Signup a user, then signup again with the same email. Assert 500 with "already present" message. |
| API-AUTH-06 | Signup without email | VAL-01 | P0 | POST /auth/signup without email field. Assert 400 with "Email is required" in subErrors. |
| API-AUTH-07 | Signup with invalid email format | VAL-02 | P0 | POST /auth/signup with `email: "notanemail"`. Assert 400 with "Invalid email format". |
| API-AUTH-08 | Signup with short password | VAL-04 | P1 | POST /auth/signup with 5-char password. Assert 400 with "Password must be at least 6 characters". |
| API-AUTH-09 | Signup without name | VAL-05 | P0 | POST /auth/signup without name. Assert 400 with "Name is required". |
| API-AUTH-10 | Signup defaults to GUEST role | AUTH-03 | P1 | POST /auth/signup without `roles` field. Login and decode JWT -- roles should contain `GUEST`. |
| API-AUTH-11 | Signup with HOTEL_MANAGER role | AUTH-04 | P1 | POST /auth/signup with `roles: ["HOTEL_MANAGER"]`. Login and decode JWT -- roles should contain `HOTEL_MANAGER`. |
| API-AUTH-12 | Access token contains correct claims | AUTH-05 | P1 | Login, decode JWT. Assert `sub` is user ID, `email` matches, `roles` is present, `exp` is ~10 min after `iat`. |
| API-AUTH-13 | Refresh token generates new access token | AUTH-09 | P2 | Login (capture cookie), POST /auth/refresh with cookie. Assert new access token returned. |

## Test Data Requirements

For API tests, you will need helper functions to:

1. **Create a test user** -- unique email per test run (e.g., `test-{uuid}@example.com`)
2. **Get a valid token** -- signup + login, extract access token
3. **Create a hotel with rooms** -- signup as HOTEL_MANAGER, create hotel, create room, activate hotel
4. **Create a complete booking** -- init booking, add guests, initiate payment (mock mode auto-confirms)

These helpers form a reusable test infrastructure that all scenarios build upon.
