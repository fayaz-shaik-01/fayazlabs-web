# Complexity Analysis (Big-O Notation)

> **Module:** 01-programming-foundations / dsa
> **Prerequisites:** Syntax And Control Flow, Methods And Parameters
> **Mastery Target:** L3

---

## Quick Overview (2-minute read)

**What:** Complexity analysis measures how an algorithm's resource consumption (time or space) grows as the input size increases.

**Why:** Every coding interview expects you to state the time and space complexity. More importantly, choosing the wrong data structure or algorithm in a test framework can make your test suite unusably slow — imagine a test data lookup that takes O(n^2) when it could be O(1) with a HashMap.

**Where:** Test data filtering, result aggregation, duplicate detection, configuration parsing, log analysis, and every coding exercise.

<MentalModel>

Think of complexity as answering: *"If I double the input, how much longer does it take?"*

</MentalModel>


- O(1): Same time regardless of input size — like looking up a key in a HashMap.
- O(log n): Time grows slowly — like binary search (halving the search space each step).
- O(n): Time doubles when input doubles — like scanning every element in a list.
- O(n log n): Slightly worse than linear — like sorting with a good algorithm.
- O(n^2): Time quadruples when input doubles — like nested loops over the same data.

<KeyTakeaways>

1. Big-O describes the **growth rate**, not the exact time. O(n) with a large constant can be slower than O(n^2) for small inputs.
2. Drop constants and lower-order terms: O(2n + 5) → O(n). O(n^2 + n) → O(n^2).
3. Nested loops multiply: a loop inside a loop over the same data is O(n^2).
4. HashMap lookup is O(1) average — this is why HashMaps solve so many problems.
5. Sorting is O(n log n) — you can't sort faster than this with comparison-based algorithms.

</KeyTakeaways>

## First-Principles Explanation

### The Problem This Solves

Without complexity analysis, you can't predict whether your code will handle real-world input sizes. A test suite with 10 tests might work fine, but the same logic applied to 10,000 tests might take minutes instead of milliseconds.

### How Big-O Works

Big-O measures the **upper bound** of growth rate as n → infinity.

**Rules:**
1. **Count the dominant operation** — usually the innermost loop body or the most frequently called operation.
2. **Drop constants** — O(3n) = O(n). Constants depend on hardware and don't affect the growth shape.
3. **Drop non-dominant terms** — O(n^2 + n) = O(n^2). The largest term dominates for large n.
4. **Different inputs = different variables** — if you iterate over array A (length m) and array B (length n), it's O(m + n), not O(n^2).

### Common Complexities (Sorted Best to Worst)


| Big-O | Name | Example | n=10 | n=100 | n=10,000 |
|---|---|---|---|---|---|
| O(1) | Constant | HashMap.get(), array index | 1 | 1 | 1 |
| O(log n) | Logarithmic | Binary search | 3 | 7 | 13 |
| O(n) | Linear | Single loop, list scan | 10 | 100 | 10,000 |
| O(n log n) | Linearithmic | Merge sort, Arrays.sort() | 33 | 664 | 132,877 |
| O(n^2) | Quadratic | Nested loops, bubble sort | 100 | 10,000 | 100,000,000 |
| O(2^n) | Exponential | All subsets, naive recursion | 1,024 | 1.27×10^30 | Forget it |

### Space Complexity

Space complexity measures additional memory used (not counting the input itself).

- Creating a new array of size n → O(n) space
- Using a HashMap that might hold n entries → O(n) space
- Using a fixed number of variables → O(1) space
- Recursive calls: each call adds to the stack → O(depth) space

### Analyzing Loops


```java
// O(n) — single loop
for (int i = 0; i < n; i++) {
    doSomething();  // O(1) operation
}

// O(n^2) — nested loops over same data
for (int i = 0; i < n; i++) {
    for (int j = 0; j < n; j++) {
        doSomething();
    }
}

// O(n*m) — nested loops over DIFFERENT data
for (int i = 0; i < n; i++) {       // n iterations
    for (int j = 0; j < m; j++) {   // m iterations each
        doSomething();
    }
}

// O(n) — loop with early exit (worst case still n)
for (int i = 0; i < n; i++) {
    if (found) break;  // might break early, but worst case is n
}

// O(log n) — halving each iteration
int i = n;
while (i > 0) {
    doSomething();
    i = i / 2;
}

// O(n log n) — linear loop with log-n inner work
for (int i = 0; i < n; i++) {    // n iterations
    binarySearch(array, target);   // O(log n) each
}
```

### Amortized Complexity

Some operations are usually fast but occasionally slow:
- **ArrayList.add()**: Usually O(1), but when the internal array is full, it resizes (copies all elements) → O(n). However, this happens rarely enough that the *amortized* cost per add is O(1).
- **HashMap.put()**: Usually O(1), but worst case (hash collisions) is O(n). With a good hash function, amortized O(1).

### Analyzing Common Collection Operations

| Operation | ArrayList | LinkedList | HashMap | TreeMap | HashSet |
|---|---|---|---|---|---|
| Get by index | O(1) | O(n) | — | — | — |
| Get by key | — | — | O(1) avg | O(log n) | — |
| Contains | O(n) | O(n) | O(1) avg | O(log n) | O(1) avg |
| Add (end) | O(1) amortized | O(1) | O(1) avg | O(log n) | O(1) avg |
| Add (middle) | O(n) | O(1)* | — | — | — |
| Remove | O(n) | O(1)* | O(1) avg | O(log n) | O(1) avg |
| Sort | O(n log n) | O(n log n) | — | Already sorted | — |

*LinkedList insert/remove is O(1) only if you already have a reference to the node. Finding the node is O(n).

## Practical Implementation

### Example 1: Finding Duplicates — O(n^2) vs O(n)


```java
// BAD: O(n^2) — nested loops
public static List<String> findDuplicatesSlow(List<String> testNames) {
    List<String> duplicates = new ArrayList<>();
    for (int i = 0; i < testNames.size(); i++) {
        for (int j = i + 1; j < testNames.size(); j++) {
            if (testNames.get(i).equals(testNames.get(j)) 
                    && !duplicates.contains(testNames.get(i))) {
                duplicates.add(testNames.get(i));
            }
        }
    }
    return duplicates;
}
// With 10,000 test names: ~50,000,000 comparisons

// GOOD: O(n) — single pass with HashSet
public static List<String> findDuplicatesFast(List<String> testNames) {
    Set<String> seen = new HashSet<>();
    Set<String> duplicates = new LinkedHashSet<>();
    for (String name : testNames) {
        if (!seen.add(name)) {  // add() returns false if already present
            duplicates.add(name);
        }
    }
    return new ArrayList<>(duplicates);
}
// With 10,000 test names: ~10,000 operations
```

**Why the fast version works:** `HashSet.add()` is O(1) average, so the single loop gives O(n) total. The slow version does O(n) comparisons inside an O(n) loop → O(n^2).

### Example 2: Frequency Counting for Test Results — O(n)


```java
public static Map<String, Long> countByStatus(List<TestResult> results) {
    // Using streams — still O(n), just more readable
    return results.stream()
        .collect(Collectors.groupingBy(TestResult::getStatus, Collectors.counting()));
}

// Equivalent manual approach — also O(n)
public static Map<String, Integer> countByStatusManual(List<TestResult> results) {
    Map<String, Integer> counts = new HashMap<>();
    for (TestResult result : results) {
        counts.merge(result.getStatus(), 1, Integer::sum);
    }
    return counts;
}
```

**Time:** O(n) — one pass through the list, O(1) HashMap operations.
**Space:** O(k) where k is the number of distinct statuses (typically 3-5, so effectively O(1)).

### Example 3: Checking Test Name Patterns — O(n*m) Trap


```java
// TRAP: This looks O(n) but is actually O(n * m)
public static List<String> findTestsContaining(List<String> testNames, String pattern) {
    List<String> matches = new ArrayList<>();
    for (String name : testNames) {           // O(n) iterations
        if (name.contains(pattern)) {          // O(m) per call, where m = name.length()
            matches.add(name);
        }
    }
    return matches;
}
// For most automation use cases, m is small (< 200 chars), so this is effectively O(n).
// But be aware of the hidden cost if strings are very long.
```

## Failure and Debugging

### Mistake 1: Not Recognizing Hidden O(n) Operations


```java
// This LOOKS like O(n) but is actually O(n^2)
List<String> result = new ArrayList<>();
for (String item : items) {               // O(n) iterations
    if (!result.contains(item)) {          // O(n) — ArrayList.contains scans entire list!
        result.add(item);
    }
}
// FIX: Use a HashSet for the seen-check
Set<String> seen = new HashSet<>();
List<String> result = new ArrayList<>();
for (String item : items) {
    if (seen.add(item)) {                  // O(1) — HashSet.add
        result.add(item);
    }
}
```

<BestPractice>

**Prevention:** Always check the complexity of collection operations you call inside loops.

</BestPractice>


### Mistake 2: Sorting When You Don't Need To


```java
// WASTE: Sorting just to find the maximum — O(n log n)
List<Integer> durations = getTestDurations();
Collections.sort(durations);
int maxDuration = durations.get(durations.size() - 1);

// BETTER: Single scan — O(n)
int maxDuration = durations.stream().mapToInt(Integer::intValue).max().orElse(0);
// Or manually:
int maxDuration = Integer.MIN_VALUE;
for (int d : durations) {
    maxDuration = Math.max(maxDuration, d);
}
```

### Mistake 3: Premature Optimization

Not every O(n^2) algorithm needs to be optimized. If n is always small (&lt; 100), the simpler code is better.

**Rule of thumb:** Optimize when n could be > 1,000 or when the operation runs frequently (inside a loop or called per test).

## Engineering Judgment

### When Complexity Matters in Automation

| Scenario | Typical n | Worry About Complexity? |
|---|---|---|
| Filtering 20 test cases by tags | 20 | No — any algorithm is fine |
| Processing 5,000 test results from CI | 5,000 | Mildly — avoid O(n^2), prefer O(n) |
| Parsing 100,000-line log files | 100,000 | Yes — O(n^2) will be noticeably slow |
| Comparing two large JSON responses field-by-field | Varies | Yes — be aware of nested iteration |
| Validating test data in a HashMap | Per lookup | No — HashMap is already O(1) |

### The Practical Decision

1. **Write the simple solution first.**
2. **Analyze its complexity.**
3. **If n is small (&lt; 100) and it's not in a hot loop, you're done.**
4. **If n could be large or the code runs frequently, optimize.**
5. **Measure before optimizing — profiling beats guessing.**

## Interview and Revision

### Fundamental Questions

**Q1: What is the time complexity of searching for a value in an unsorted array?**
A: O(n) — you must check each element in the worst case.

**Q2: Why is HashMap.get() O(1) average but O(n) worst case?**
A: Average case: the hash function distributes keys evenly, so each bucket has ~1 entry → direct access. Worst case: all keys hash to the same bucket, forming a linked list (or balanced tree in Java 8+ for > 8 entries) that must be traversed.

**Q3: What is the complexity of `Collections.sort()`?**
A: O(n log n) — it uses TimSort (a hybrid merge sort / insertion sort). This is optimal for comparison-based sorting.

**Q4: If you have a nested loop where the outer runs n times and the inner runs n times, but the inner loop breaks after finding the first match — what's the complexity?**
A: Still O(n^2) in the worst case (if the match is always the last element or doesn't exist). Average case might be better, but Big-O measures worst case unless stated otherwise.

**Q5: What's the space complexity of a recursive function with depth d?**
A: O(d) — each recursive call adds a frame to the call stack.

### Coding Questions

1. **Given a list of integers, find two numbers that add up to a target.** State the brute force complexity and the optimal complexity. (See Coding Exercises for full solution)
2. **Given a list of test results, find the test with the longest execution time without sorting.** State the complexity.
3. **Analyze the complexity of this code:**
   ```java
   for (int i = 0; i < n; i++) {
       for (int j = i; j < n; j++) {
           // O(1) work
       }
   }
   ```
   Answer: O(n^2). The inner loop runs n + (n-1) + (n-2) + ... + 1 = n(n+1)/2 ≈ n^2/2 → O(n^2).




**Q:** What does O(1) mean?
**A:** Constant time — the operation takes the same amount of time regardless of input size. Example: HashMap.get(), array access by index.

**Q:** How do you turn an O(n^2) duplicate check into O(n)?
**A:** Use a HashSet instead of checking `list.contains()` inside a loop. HashSet.contains() is O(1) vs ArrayList.contains() which is O(n).

**Q:** What's the complexity of `Arrays.sort()`?
**A:** O(n log n) for object arrays (TimSort), O(n log n) average for primitive arrays (dual-pivot quicksort).

**Q:** What does "amortized O(1)" mean?
**A:** Most operations are O(1), but occasionally one is O(n) (e.g., ArrayList resizing). Averaged over many operations, the cost per operation is O(1).

**Q:** When should you NOT optimize for better Big-O complexity?
**A:** When n is small (&lt; 100) and the code is not in a hot loop. Simpler, readable code is more maintainable. Optimize only when you have evidence of a performance problem.
