# Screen Object Implementation — Appium Java

> **Module:** 06 — Mobile Automation > Appium Java > Screen Object Implementation  
> **Prerequisites:** Setup And First Tests, Page And Screen Objects, Gestures And Touch Actions  
> **Mastery Target:** L3 (Independent) → L4 (Engineering Judgment)

## Quick Overview (Layer 1)

**What:** The Screen Object Model is the mobile equivalent of the Page Object Model. Each screen in the mobile app becomes a Java class that encapsulates element locators and interaction methods. The key difference from web POM: mobile screen objects need platform-aware locators (Android and iOS use different strategies), gesture methods (swipe, scroll, long-press), and helpers for mobile-specific actions like hiding the keyboard and handling permission dialogs.

**Why:** You already know POM from Selenium. Screen objects apply the same principles — encapsulation, single responsibility, method chaining — but adapt them for mobile. The new challenges: locators differ between Android and iOS (`resource-id` vs `accessibilityIdentifier`), interactions include gestures that web doesn't have, and screen transitions involve native animations. This file shows how to build a BaseScreen with mobile utilities and a full screen object hierarchy for StayNest's mobile app.

**Where:** Every Appium test suite that grows beyond a handful of tests. Screen objects are the structural backbone — they make tests readable, locators maintainable, and cross-platform testing feasible.

<MentalModel>

Think of screen objects as **bilingual tour guides** for your app. Each guide (screen object) knows their specific area (LoginScreen knows the login UI), speaks the local language (Android locators on Android, iOS locators on iOS), and can perform local actions (gestures, keyboard handling). The `BaseScreen` is the tour guide training program — it teaches every guide the basics (wait, tap, type, swipe) so they can focus on their area's specifics.

</MentalModel>


<KeyTakeaways>

1. **BaseScreen provides mobile-specific utilities** — swipe, scroll, hide keyboard, and wait helpers that every screen needs.
2. **Locators use `AppiumBy.accessibilityId` for cross-platform parity** — the same test code can run on Android and iOS if locators use accessibility IDs consistently.
3. **Screen methods return screen objects** — `loginScreen.login()` returns `HomeScreen`, modeling navigation just like web POM.
4. **Cross-platform abstraction uses interfaces** — define `LoginScreen` as an interface, implement `AndroidLoginScreen` and `IOSLoginScreen` for platform-specific locators.
5. **Gesture methods belong in BaseScreen** — swipe, scroll, pull-to-refresh are used across screens and should be abstracted into reusable helpers.

</KeyTakeaways>

## First-Principles Explanation (Layer 2)

### BaseScreen: Mobile-Specific Foundation


```java
import io.appium.java_client.AppiumBy;
import io.appium.java_client.AppiumDriver;
import org.openqa.selenium.*;
import org.openqa.selenium.interactions.Pause;
import org.openqa.selenium.interactions.PointerInput;
import org.openqa.selenium.interactions.Sequence;
import org.openqa.selenium.support.ui.ExpectedConditions;
import org.openqa.selenium.support.ui.WebDriverWait;

import java.time.Duration;
import java.util.Collections;

public abstract class BaseScreen {

    protected final AppiumDriver driver;
    protected final WebDriverWait wait;

    private static final Duration DEFAULT_TIMEOUT = Duration.ofSeconds(15);

    protected BaseScreen(AppiumDriver driver) {
        this.driver = driver;
        this.wait = new WebDriverWait(driver, DEFAULT_TIMEOUT);
    }

    // --- Core interaction methods ---

    protected WebElement waitForVisible(By locator) {
        return wait.until(ExpectedConditions.visibilityOfElementLocated(locator));
    }

    protected WebElement waitForClickable(By locator) {
        return wait.until(ExpectedConditions.elementToBeClickable(locator));
    }

    protected void tap(By locator) {
        waitForClickable(locator).click();
    }

    protected void type(By locator, String text) {
        WebElement element = waitForVisible(locator);
        element.clear();
        element.sendKeys(text);
    }

    protected String getText(By locator) {
        return waitForVisible(locator).getText();
    }

    protected boolean isDisplayed(By locator) {
        try {
            return driver.findElement(locator).isDisplayed();
        } catch (NoSuchElementException e) {
            return false;
        }
    }

    // --- Mobile-specific helpers ---

    protected void hideKeyboard() {
        try {
            driver.hideKeyboard();
        } catch (Exception e) {
            // Keyboard might not be visible — safe to ignore
        }
    }

    protected void swipe(Direction direction) {
        Dimension size = driver.manage().window().getSize();
        int startX, startY, endX, endY;

        switch (direction) {
            case UP:
                startX = size.width / 2;
                startY = (int) (size.height * 0.8);
                endX = size.width / 2;
                endY = (int) (size.height * 0.2);
                break;
            case DOWN:
                startX = size.width / 2;
                startY = (int) (size.height * 0.2);
                endX = size.width / 2;
                endY = (int) (size.height * 0.8);
                break;
            case LEFT:
                startX = (int) (size.width * 0.8);
                startY = size.height / 2;
                endX = (int) (size.width * 0.2);
                endY = size.height / 2;
                break;
            case RIGHT:
                startX = (int) (size.width * 0.2);
                startY = size.height / 2;
                endX = (int) (size.width * 0.8);
                endY = size.height / 2;
                break;
            default:
                throw new IllegalArgumentException("Invalid direction: " + direction);
        }

        performSwipe(startX, startY, endX, endY, Duration.ofMillis(500));
    }

    protected void performSwipe(int startX, int startY, int endX, int endY, Duration duration) {
        PointerInput finger = new PointerInput(PointerInput.Kind.TOUCH, "finger");
        Sequence swipeSequence = new Sequence(finger, 1)
            .addAction(finger.createPointerMove(Duration.ZERO, PointerInput.Origin.viewport(), startX, startY))
            .addAction(finger.createPointerDown(PointerInput.MouseButton.LEFT.asArg()))
            .addAction(new Pause(finger, Duration.ofMillis(100)))
            .addAction(finger.createPointerMove(duration, PointerInput.Origin.viewport(), endX, endY))
            .addAction(finger.createPointerUp(PointerInput.MouseButton.LEFT.asArg()));

        driver.perform(Collections.singletonList(swipeSequence));
    }

    protected void scrollToElement(By locator, int maxSwipes) {
        for (int i = 0; i < maxSwipes; i++) {
            if (isDisplayed(locator)) {
                return;
            }
            swipe(Direction.UP);
            try { Thread.sleep(500); } catch (InterruptedException ignored) {}
        }
        throw new RuntimeException("Element not found after " + maxSwipes + " swipes: " + locator);
    }

    public enum Direction { UP, DOWN, LEFT, RIGHT }
}
```

**Design decisions:**
- `AppiumDriver` instead of `AndroidDriver`/`IOSDriver` — BaseScreen works with both platforms
- `hideKeyboard()` wrapped in try-catch — it throws if the keyboard isn't visible; safer to ignore
- `swipe()` uses W3C Actions API — the new standard for Appium 2.x (TouchAction is deprecated)
- `scrollToElement()` combines swipe with element detection — essential for mobile testing where elements are off-screen

### Platform-Specific Locators

The core challenge: Android and iOS use different attributes for elements. The solution is to use `accessibilityId` wherever possible, or platform-specific strategies when needed.


```java
// Cross-platform: accessibilityId (same on both platforms)
AppiumBy.accessibilityId("loginButton")

// Android-only: UIAutomator (powerful, Android-specific)
AppiumBy.androidUIAutomator("new UiSelector().text(\"Login\")")
AppiumBy.androidUIAutomator("new UiSelector().resourceId(\"com.staynest.app:id/email\")")

// iOS-only: Class chain (iOS-specific, more readable than XPath)
AppiumBy.iOSClassChain("**/XCUIElementTypeButton[`label == 'Login'`]")

// iOS-only: NS predicate string
AppiumBy.iOSNsPredicateString("type == 'XCUIElementTypeButton' AND label == 'Login'")
```

### Screen Transitions: Return Type Models Navigation


```java
public class LoginScreen extends BaseScreen {

    // Successful login → navigates to HomeScreen
    public HomeScreen login(String email, String password) {
        type(EMAIL_INPUT, email);
        type(PASSWORD_INPUT, password);
        hideKeyboard();
        tap(LOGIN_BUTTON);
        // Wait for home screen to load
        waitForVisible(AppiumBy.accessibilityId("homeScreenTitle"));
        return new HomeScreen(driver);
    }

    // Failed login → stays on LoginScreen
    public LoginScreen loginExpectingError(String email, String password) {
        type(EMAIL_INPUT, email);
        type(PASSWORD_INPUT, password);
        hideKeyboard();
        tap(LOGIN_BUTTON);
        waitForVisible(ERROR_MESSAGE);
        return this;
    }
}
```

### Cross-Platform Abstraction

For teams testing both Android and iOS, define screen interfaces and platform implementations:


```java
// Interface — defines the contract
public interface ILoginScreen {
    IHomeScreen login(String email, String password);
    ILoginScreen loginExpectingError(String email, String password);
    String getErrorMessage();
    boolean isLoginButtonEnabled();
}

// Android implementation
public class AndroidLoginScreen extends BaseScreen implements ILoginScreen {
    private static final By EMAIL_INPUT = AppiumBy.accessibilityId("emailInput");
    private static final By PASSWORD_INPUT = AppiumBy.accessibilityId("passwordInput");
    private static final By LOGIN_BUTTON = AppiumBy.androidUIAutomator(
        "new UiSelector().resourceId(\"com.staynest.app:id/loginBtn\")"
    );
    private static final By ERROR_MESSAGE = AppiumBy.accessibilityId("errorMessage");

    public AndroidLoginScreen(AppiumDriver driver) { super(driver); }

    @Override
    public IHomeScreen login(String email, String password) {
        type(EMAIL_INPUT, email);
        type(PASSWORD_INPUT, password);
        hideKeyboard();
        tap(LOGIN_BUTTON);
        return new AndroidHomeScreen(driver);
    }

    @Override
    public ILoginScreen loginExpectingError(String email, String password) {
        type(EMAIL_INPUT, email);
        type(PASSWORD_INPUT, password);
        hideKeyboard();
        tap(LOGIN_BUTTON);
        waitForVisible(ERROR_MESSAGE);
        return this;
    }

    @Override
    public String getErrorMessage() { return getText(ERROR_MESSAGE); }

    @Override
    public boolean isLoginButtonEnabled() {
        return waitForVisible(LOGIN_BUTTON).isEnabled();
    }
}

// iOS implementation — same interface, different locators
public class IOSLoginScreen extends BaseScreen implements ILoginScreen {
    private static final By EMAIL_INPUT = AppiumBy.accessibilityId("emailInput");
    private static final By PASSWORD_INPUT = AppiumBy.accessibilityId("passwordInput");
    private static final By LOGIN_BUTTON = AppiumBy.iOSClassChain(
        "**/XCUIElementTypeButton[`label == 'Login'`]"
    );
    private static final By ERROR_MESSAGE = AppiumBy.accessibilityId("errorMessage");

    // ... same methods, different locators where needed ...
}
```

**Factory for creating platform-specific screens:**


```java
public class ScreenFactory {

    private final AppiumDriver driver;
    private final String platform;

    public ScreenFactory(AppiumDriver driver) {
        this.driver = driver;
        this.platform = driver.getCapabilities()
            .getPlatformName().toString().toLowerCase();
    }

    public ILoginScreen loginScreen() {
        return platform.equals("android")
            ? new AndroidLoginScreen(driver)
            : new IOSLoginScreen(driver);
    }

    public IHomeScreen homeScreen() {
        return platform.equals("android")
            ? new AndroidHomeScreen(driver)
            : new IOSHomeScreen(driver);
    }
}
```

```java
// ── SearchScreen.java ──

public class SearchScreen extends BaseScreen {

    private static final By LOCATION_INPUT = AppiumBy.accessibilityId("locationInput");
    private static final By CHECK_IN_DATE = AppiumBy.accessibilityId("checkInDate");
    private static final By CHECK_OUT_DATE = AppiumBy.accessibilityId("checkOutDate");
    private static final By GUESTS_STEPPER = AppiumBy.accessibilityId("guestsStepper");
    private static final By GUESTS_INCREMENT = AppiumBy.accessibilityId("guestsIncrement");
    private static final By SEARCH_BUTTON = AppiumBy.accessibilityId("searchButton");
    private static final By SEARCH_RESULTS = AppiumBy.accessibilityId("searchResults");
    private static final By RESULT_CARD = AppiumBy.accessibilityId("resultCard");
    private static final By NO_RESULTS = AppiumBy.accessibilityId("noResults");

    public SearchScreen(AppiumDriver driver) {
        super(driver);
    }

    public SearchScreen enterLocation(String location) {
        type(LOCATION_INPUT, location);
        hideKeyboard();
        // Tap the first autocomplete suggestion
        tap(AppiumBy.accessibilityId("suggestion_0"));
        return this;
    }

    public SearchScreen selectCheckInDate(String date) {
        tap(CHECK_IN_DATE);
        // Date picker interaction — tap the date in the calendar
        tap(AppiumBy.accessibilityId("date_" + date));
        return this;
    }

    public SearchScreen selectCheckOutDate(String date) {
        tap(CHECK_OUT_DATE);
        tap(AppiumBy.accessibilityId("date_" + date));
        return this;
    }

    public SearchScreen setGuests(int count) {
        for (int i = 0; i < count - 1; i++) {  // default is 1 guest
            tap(GUESTS_INCREMENT);
        }
        return this;
    }

    public SearchScreen tapSearch() {
        tap(SEARCH_BUTTON);
        // Wait for results or no-results message
        wait.until(d -> isDisplayed(RESULT_CARD) || isDisplayed(NO_RESULTS));
        return this;
    }

    public int getResultCount() {
        return driver.findElements(RESULT_CARD).size();
    }

    public PropertyDetailScreen selectResult(int index) {
        driver.findElements(RESULT_CARD).get(index).click();
        return new PropertyDetailScreen(driver);
    }
}
```

## Failure and Debugging (Layer 4)

### Failure: Scroll Doesn't Find the Element

**Symptom:** `scrollToElement()` swipes the maximum number of times but never finds the element.

**Root Cause:** The element might be in a horizontally scrollable container, but `scrollToElement` only swipes vertically. Or the element's accessibility ID is wrong.


```java
// BROKEN: swipes UP but element is in a horizontal list
scrollToElement(AppiumBy.accessibilityId("amenityPool"), 5);

// FIXED: use Android UIAutomator's scrollIntoView for vertical scrolling
driver.findElement(AppiumBy.androidUIAutomator(
    "new UiScrollable(new UiSelector().scrollable(true))" +
    ".scrollIntoView(new UiSelector().description(\"amenityPool\"))"
));

// For horizontal scrolling:
driver.findElement(AppiumBy.androidUIAutomator(
    "new UiScrollable(new UiSelector().scrollable(true))" +
    ".setAsHorizontalList()" +
    ".scrollIntoView(new UiSelector().description(\"amenityPool\"))"
));
```

### Failure: Cross-Platform Test Uses Wrong Locator

**Symptom:** Test passes on Android but throws `NoSuchElementException` on iOS.

**Root Cause:** A platform-specific locator (like `AppiumBy.androidUIAutomator`) was used directly in the screen object instead of `accessibilityId`. iOS doesn't understand Android's `UiSelector`.

<BestPractice>

**Prevention:** Always prefer `accessibilityId` for cross-platform. Use the interface + implementation pattern from Layer 2 when platform-specific locators are unavoidable.

</BestPractice>

## Engineering Judgment (Layer 5)

### Cross-Platform Abstraction: When It's Worth It

| Team Situation | Recommendation |
|---|---|
| Testing one platform (Android only) | No abstraction needed — use concrete screen objects |
| Testing both platforms, same team | Interface + implementation pattern |
| Testing both platforms, separate teams | Separate screen objects per platform (shared test logic only) |
| Shared screens with identical accessibility IDs | One screen object with `accessibilityId` locators (no interface needed) |

**Rule of thumb:** Start without abstraction. Add the interface layer only when you actually have two platforms to support. Premature abstraction adds complexity without value.

### BaseScreen: How Much to Include

| Include in BaseScreen | Don't Include |
|---|---|
| waitForVisible, tap, type, getText | Screen-specific business logic |
| swipe, scroll, scrollToElement | Complex gestures (pinch, multi-touch) — use a GestureHelper |
| hideKeyboard | App-specific navigation (back, home) |
| isDisplayed, waitForInvisibility | Assertion methods |
| takeScreenshot | Test data creation |

## Interview and Revision (Layer 6)

### Fundamental Questions

**Q1: How does the Screen Object Model differ from POM in web testing?**

**A:** Same core principles — encapsulate locators, expose readable methods, return screen objects for navigation. Three key differences. First, **gestures** — BaseScreen needs swipe, scroll, and long-press helpers that web POM doesn't. Second, **keyboard management** — mobile tests must dismiss the soft keyboard (`hideKeyboard()`) between field interactions. Third, **platform-specific locators** — Android and iOS use different locator strategies, so cross-platform testing requires abstraction (interfaces or factory pattern).

**Q2: How do you handle cross-platform mobile testing with screen objects?**

**A:** Define screen interfaces (`ILoginScreen`) with action methods. Implement them per platform (`AndroidLoginScreen`, `IOSLoginScreen`) with platform-specific locators. Use a `ScreenFactory` that reads the platform from driver capabilities and returns the correct implementation. Tests only reference interfaces, making them platform-agnostic. Where possible, use `accessibilityId` locators which work on both platforms without needing separate implementations.




| # | Front (Question) | Back (Answer) |
|---|---|---|
| 1 | What belongs in a mobile BaseScreen that web BasePage doesn't need? | `swipe()`, `scrollToElement()`, `hideKeyboard()` — mobile-specific interactions. Also `performSwipe()` using W3C PointerInput actions (deprecated TouchAction replaced). |
| 2 | Why is `accessibilityId` preferred for cross-platform screen objects? | It maps to `content-description` on Android and `accessibilityIdentifier` on iOS. One locator strategy works on both platforms, reducing duplication. |
| 3 | How does ScreenFactory enable cross-platform tests? | It reads platform from driver capabilities and returns the correct platform implementation (AndroidLoginScreen or IOSLoginScreen). Tests reference the interface, not the implementation. |
| 4 | When should screen object methods call `hideKeyboard()`? | After any `type()` / `sendKeys()` call, before tapping elements that might be obscured by the keyboard. Wrap in try-catch since it throws if the keyboard isn't visible. |
| 5 | What's the difference between swipe and scroll in mobile screen objects? | Swipe is a gesture (finger drag from point A to B). Scroll uses platform-specific APIs (UiScrollable on Android) to navigate scrollable containers. Scroll is more reliable for finding elements; swipe is for gestures like dismissing cards. |
