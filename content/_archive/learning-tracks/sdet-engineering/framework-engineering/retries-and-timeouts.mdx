# Retries and Timeouts

> **Module:** 03 — Framework Engineering > Retries and Timeouts  
> **Prerequisites:** Framework Architecture, Exception Handling, Concurrency And Threadlocal  
> **Mastery Target:** L3 (Independent) → L4 (Engineering Judgment)

---

## Quick Overview (Layer 1)

**What:** Retries and timeouts are the mechanisms that govern how long your tests wait for things to happen and what happens when they don't. Timeouts set an upper bound on waiting — "give up after 10 seconds." Retries give failed operations another chance — "try again up to 3 times." Together, they determine whether your test suite is reliably fast or unpredictably slow.

**Why it matters:** Web applications are asynchronous. Elements appear after AJAX calls, pages load over networks with variable latency, APIs respond at different speeds under different loads. Without proper waits, tests fail because they check for elements before they exist. Without proper timeouts, tests hang forever waiting for something that will never appear. Without disciplined retry logic, teams either mask real bugs (retrying until a flaky test passes) or waste CI time on transient failures that a single retry would resolve.

**Where you encounter it:** Element waits in Selenium/Playwright, page load timeouts, API call retries with exponential backoff, TestNG retry analyzers for flaky test re-runs, suite-level timeouts in CI pipelines, implicit vs explicit waits, and the ever-present temptation of `Thread.sleep`.

<MentalModel>

Think of timeouts as a **kitchen timer** and retries as **attempts at a recipe**. When you put bread in the oven, you set a timer (timeout) — if it's not done when the timer rings, you don't wait forever, you check and decide. A retry is trying the recipe again: if the souffl collapsed, you might attempt it once more. But if you keep retrying a broken recipe without understanding why it fails, you just burn through ingredients (CI time) without learning anything.

</MentalModel>


<KeyTakeaways>

1. **Explicit waits are the only correct wait mechanism in Selenium** — they wait for a specific condition up to a maximum time, polling at intervals.
2. **Implicit waits and explicit waits should never be mixed** — combining them causes unpredictable timeout behavior where the actual wait duration is neither the implicit nor the explicit value.
3. **Retries are a treatment, not a cure** — they handle transient failures (network blips, momentary server load) but should never become a permanent fix for a test that's fundamentally flaky.
4. **The timeout hierarchy matters** — element wait &lt; page load &lt; test timeout &lt; suite timeout. If a lower-level timeout exceeds a higher-level one, tests fail with confusing timeout errors instead of actionable element-not-found errors.
5. **`Thread.sleep` is never the answer** — it either waits too long (slowing the suite) or not long enough (causing flakiness). Use condition-based waits instead.

</KeyTakeaways>

## First-Principles Explanation (Layer 2)

### The Asynchronous Problem

Modern web applications do not render instantly. When a test clicks a button, the resulting page might take 200ms or 5 seconds to load, depending on network speed, server load, and JavaScript complexity. A test that immediately checks for a result element will fail because the element doesn't exist yet.

```
Test clicks "Submit"
  → Browser sends HTTP request
    → Server processes (200ms – 5s)
      → Browser receives response
        → JavaScript renders DOM elements
          → Element is now findable by Selenium
```

The test must wait somewhere in this chain. The question is: *how* does it wait?

### Wait Mechanisms in Selenium

**Implicit Wait:** A global setting that tells WebDriver to poll the DOM for a specified duration when an element is not immediately found. Set once, applies to every `findElement` call.


```java
driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));
// Now EVERY findElement call waits up to 10 seconds before throwing NoSuchElementException
```

**The problem with implicit waits:** They apply to *all* element lookups — including assertions that an element should NOT exist. If you want to verify a "success message" is gone, the implicit wait forces a 10-second pause before confirming absence. They also cannot wait for conditions beyond element presence (e.g., element is visible, element text contains "Success", element is clickable).

**Explicit Wait:** A targeted wait for a specific condition on a specific element, with a defined timeout. Uses `WebDriverWait` with `ExpectedConditions`.


```java
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));

// Wait until the element is visible — not just present in DOM, but actually rendered and visible
WebElement successMessage = wait.until(
    ExpectedConditions.visibilityOfElementLocated(By.id("success-msg"))
);

// Wait until element text matches
wait.until(ExpectedConditions.textToBePresentInElementLocated(
    By.id("status"), "Confirmed"
));

// Wait until element is clickable — visible AND enabled
WebElement submitButton = wait.until(
    ExpectedConditions.elementToBeClickable(By.id("submit-btn"))
);
```

**Why explicit waits are superior:** They wait for exactly the condition you need, on exactly the element you care about, for exactly the duration you specify. When they time out, the error message tells you which condition wasn't met on which element.

**Auto-Waiting in Playwright:** Playwright eliminates the implicit/explicit distinction entirely. Every action (`click`, `fill`, `textContent`) automatically waits for the element to be actionable — visible, stable, enabled, and receiving events. You don't write waits; the framework handles it.

```
Selenium: findElement → wait → click (three separate concerns)
Playwright: click (one action, waiting is built in)
```

### Why Never Mix Implicit and Explicit Waits

When both are active, the actual wait behavior is unpredictable. Consider:

```
Implicit wait: 10 seconds
Explicit wait: 5 seconds, waiting for element to be clickable
```

You might expect a 5-second maximum. But `WebDriverWait` internally calls `findElement`, which triggers the 10-second implicit wait. The actual timeout could be anywhere from 5 to 15 seconds, depending on polling intervals and how the waits interact internally. The Selenium documentation explicitly warns against mixing them.

**The rule:** Set implicit wait to 0 (or don't set it at all). Use explicit waits everywhere. This gives you complete, predictable control.

### Timeout Hierarchy

Timeouts should form a hierarchy where lower-level timeouts are shorter than higher-level ones:

```
Element wait (5-10s)     → waiting for a specific element to appear or become clickable
  < Page load (30s)      → waiting for the entire page to finish loading
    < Test timeout (2m)  → maximum time for a single test method to complete
      < Suite timeout     → maximum time for the entire test suite in CI
```

**Why the hierarchy matters:** If your element wait (30s) exceeds your test timeout (20s), the test framework kills the test before the wait finishes, producing a generic "test timed out" error instead of a specific "element #submit-btn not found after 30 seconds" error. The more specific error is far easier to debug.

### Retry Strategies

**TestNG IRetryAnalyzer:** Re-runs a failed test method automatically. TestNG invokes the `retry()` method after a test failure. If it returns `true`, the test is re-run.

**Exponential Backoff for API retries:** Instead of retrying immediately (which hammers the server), each retry waits longer: 1s → 2s → 4s → 8s. This gives transient issues time to resolve and avoids overwhelming a struggling server.

```
Attempt 1: immediate
Attempt 2: wait 1 second
Attempt 3: wait 2 seconds
Attempt 4: wait 4 seconds
(give up after max attempts)
```

### When Retries Mask Bugs

A retry that makes a flaky test "pass" is not a fix — it's a painkiller. The pain is still there; you just stopped feeling it. Common scenarios where retries hide real problems:

- **Stale element references:** The DOM changed between finding and clicking an element. A retry re-finds and clicks, but the root cause is a race condition in the test design.
- **Timing-dependent tests:** A test that sometimes fails because it checks too early. A retry sometimes passes because it checks later. The fix is a proper explicit wait, not a retry.
- **Shared test data:** Two parallel tests modify the same database record. Sometimes they collide, sometimes they don't. A retry doesn't fix the data isolation problem.

**The discipline:** When a retry saves a test, log it. Review retry logs weekly. If the same test is retried repeatedly, investigate the root cause instead of accepting the retry as a solution.

## Practical Implementation (Layer 3)

### Example 1: TestNG IRetryAnalyzer Implementation

A retry analyzer that re-runs failed tests up to a configurable number of times, with logging to track which tests needed retries.


```java
import org.testng.IRetryAnalyzer;
import org.testng.ITestResult;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

/**
 * Retries failed tests up to MAX_RETRIES times.
 *
 * Usage: Apply to individual tests with @Test(retryAnalyzer = RetryAnalyzer.class)
 *        or globally via a test listener (see RetryTransformer below).
 *
 * Why per-method retry count: Each test instance gets its own RetryAnalyzer instance,
 * so the counter is naturally isolated — no thread-safety concern here.
 */
public class RetryAnalyzer implements IRetryAnalyzer {

    private static final Logger log = LoggerFactory.getLogger(RetryAnalyzer.class);
    private static final int MAX_RETRIES = 2;  // original run + 2 retries = 3 total attempts
    private int retryCount = 0;

    @Override
    public boolean retry(ITestResult result) {
        if (retryCount < MAX_RETRIES) {
            retryCount++;
            String testName = result.getMethod().getMethodName();
            String errorMessage = result.getThrowable() != null
                ? result.getThrowable().getMessage()
                : "unknown error";

            log.warn("RETRY [{}/{}] Test '{}' failed with: {}",
                retryCount, MAX_RETRIES, testName, errorMessage);

            return true;  // returning true tells TestNG to re-run this test
        }
        return false;  // all retries exhausted — mark test as failed
    }
}
```

**Applying the retry analyzer globally (without annotating every test):**


```java
import org.testng.IAnnotationTransformer;
import org.testng.annotations.ITestAnnotation;

import java.lang.reflect.Constructor;
import java.lang.reflect.Method;

/**
 * Applies RetryAnalyzer to ALL test methods automatically.
 * Register this in testng.xml as a listener — no @Test annotation changes needed.
 */
public class RetryTransformer implements IAnnotationTransformer {

    @Override
    public void transform(ITestAnnotation annotation, Class testClass,
                          Constructor testConstructor, Method testMethod) {
        annotation.setRetryAnalyzer(RetryAnalyzer.class);
    }
}
```

```xml
<!-- testng.xml — register the transformer -->
<suite name="Test Suite">
    <listeners>
        <listener class-name="com.company.automation.listeners.RetryTransformer"/>
    </listeners>
    <!-- ... -->
</suite>
```

### Example 2: Custom Explicit Wait Utility

A utility that wraps `WebDriverWait` with common conditions and clear error messages, so tests don't need to construct `WebDriverWait` and `ExpectedConditions` manually every time.


```java
import org.openqa.selenium.By;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.WebElement;
import org.openqa.selenium.support.ui.ExpectedConditions;
import org.openqa.selenium.support.ui.WebDriverWait;

import java.time.Duration;

/**
 * Reusable wait utilities that wrap Selenium's explicit waits.
 * Every method waits for a specific condition and returns the element
 * or throws a TimeoutException with a clear message.
 *
 * Default timeout: 10 seconds. Override per-call when needed.
 */
public class WaitUtils {

    private static final Duration DEFAULT_TIMEOUT = Duration.ofSeconds(10);
    private static final Duration POLLING_INTERVAL = Duration.ofMillis(500);

    private final WebDriver driver;
    private final Duration timeout;

    public WaitUtils(WebDriver driver) {
        this(driver, DEFAULT_TIMEOUT);
    }

    public WaitUtils(WebDriver driver, Duration timeout) {
        this.driver = driver;
        this.timeout = timeout;
    }

    /** Wait until the element is visible on the page (present + displayed). */
    public WebElement waitForVisible(By locator) {
        return createWait().until(ExpectedConditions.visibilityOfElementLocated(locator));
    }

    /** Wait until the element is clickable (visible + enabled). */
    public WebElement waitForClickable(By locator) {
        return createWait().until(ExpectedConditions.elementToBeClickable(locator));
    }

    /** Wait until the element's text contains the expected substring. */
    public boolean waitForTextContains(By locator, String expectedText) {
        return createWait().until(
            ExpectedConditions.textToBePresentInElementLocated(locator, expectedText)
        );
    }

    /** Wait until the element disappears from the DOM or becomes invisible. */
    public boolean waitForInvisible(By locator) {
        return createWait().until(ExpectedConditions.invisibilityOfElementLocated(locator));
    }

    /** Wait with a custom timeout (for one-off longer waits like file downloads). */
    public WebElement waitForVisible(By locator, Duration customTimeout) {
        return new WebDriverWait(driver, customTimeout)
            .pollingEvery(POLLING_INTERVAL)
            .until(ExpectedConditions.visibilityOfElementLocated(locator));
    }

    private WebDriverWait createWait() {
        return new WebDriverWait(driver, timeout).pollingEvery(POLLING_INTERVAL);
    }
}
```

### Example 3: Exponential Backoff for API Retries

A utility for retrying API calls with exponential backoff — useful for integration tests where transient server errors (503, 429) are expected.


```java
import io.restassured.response.Response;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.util.Set;
import java.util.function.Supplier;

/**
 * Retries an API call with exponential backoff.
 * Only retries on specific HTTP status codes (e.g., 429, 500, 502, 503).
 * Non-retryable statuses (e.g., 400, 401, 404) fail immediately.
 */
public class ApiRetry {

    private static final Logger log = LoggerFactory.getLogger(ApiRetry.class);
    private static final Set<Integer> RETRYABLE_STATUSES = Set.of(429, 500, 502, 503);

    /**
     * Execute an API call with retry logic.
     *
     * @param apiCall    the API call to execute (as a Supplier)
     * @param maxRetries maximum number of retries (not counting the initial attempt)
     * @param baseDelayMs  base delay in milliseconds (doubles each retry)
     * @return the Response from a successful call
     * @throws RuntimeException if all retries are exhausted
     */
    public static Response withRetry(Supplier<Response> apiCall,
                                     int maxRetries, long baseDelayMs) {
        Response response = null;

        for (int attempt = 0; attempt <= maxRetries; attempt++) {
            response = apiCall.get();
            int statusCode = response.getStatusCode();

            if (!RETRYABLE_STATUSES.contains(statusCode)) {
                return response;  // success or non-retryable error — return immediately
            }

            if (attempt < maxRetries) {
                long delay = baseDelayMs * (long) Math.pow(2, attempt);  // 1s, 2s, 4s, 8s...
                log.warn("API returned {}. Retry {}/{} after {}ms",
                    statusCode, attempt + 1, maxRetries, delay);
                sleep(delay);
            }
        }

        log.error("API call failed after {} retries. Last status: {}",
            maxRetries, response != null ? response.getStatusCode() : "null");
        return response;  // return the last response — let the test assert on it
    }

    private static void sleep(long ms) {
        try {
            Thread.sleep(ms);  // Thread.sleep is acceptable HERE — inside a controlled retry
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException("Retry interrupted", e);
        }
    }
}
```

**Usage:**


```java
@Test
void shouldCreateBookingWithRetryOnServerError() {
    Response response = ApiRetry.withRetry(
        () -> given().spec(authSpec).body(bookingRequest).post("/api/bookings"),
        3,      // max 3 retries
        1000    // 1 second base delay → 1s, 2s, 4s
    );

    assertThat(response.getStatusCode()).isEqualTo(201);
}
```

## Failure and Debugging (Layer 4)

### Failure 1: Mixing Implicit and Explicit Waits

**The Problem:**


```java
public class BaseTest {
    @BeforeMethod
    public void setUp() {
        driver = new ChromeDriver();
        driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(15));  // 15-second implicit
    }
}

public class LoginTest extends BaseTest {
    @Test
    public void shouldShowErrorOnInvalidLogin() {
        loginPage.enterCredentials("bad@email.com", "wrongpass");
        loginPage.clickSubmit();

        // Explicit wait: 5 seconds for error message
        WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(5));
        WebElement error = wait.until(
            ExpectedConditions.visibilityOfElementLocated(By.id("error-msg"))
        );

        assertThat(error.getText()).contains("Invalid credentials");
    }
}
```

**Expected:** The explicit wait times out after 5 seconds if the error message doesn't appear.

**Actual:** The wait can take up to 15 seconds (or more) because `WebDriverWait` internally calls `findElement`, which triggers the 15-second implicit wait. The 5-second explicit timeout and the 15-second implicit timeout interact unpredictably. Sometimes the test waits 5 seconds, sometimes 15, sometimes 20.

**The fix — remove implicit waits entirely:**


```java
@BeforeMethod
public void setUp() {
    driver = new ChromeDriver();
    // Do NOT set implicitlyWait. Default is 0 — that's correct.
    // Use explicit waits (via WaitUtils) for every element interaction.
}
```

### Failure 2: Thread.sleep Causing Slow and Flaky Tests

**The Problem:**


```java
@Test
public void shouldDisplayConfirmationAfterBooking() {
    bookingPage.fillBookingDetails(testData);
    bookingPage.clickSubmit();

    Thread.sleep(5000);  // "wait for the page to load"

    String status = driver.findElement(By.id("confirmation-status")).getText();
    assertThat(status).isEqualTo("Confirmed");
}
```

**What goes wrong:**
- If the page loads in 500ms, you waste 4.5 seconds per test. Across 200 tests, that's 15 minutes of wasted CI time.
- If the page takes 6 seconds (server under load), the test fails — not because the feature is broken, but because the sleep wasn't long enough.
- Developers increase the sleep to 10 seconds "to be safe." The suite gets slower. Nobody dares reduce it because "it might break."

**The fix — condition-based wait:**


```java
@Test
public void shouldDisplayConfirmationAfterBooking() {
    bookingPage.fillBookingDetails(testData);
    bookingPage.clickSubmit();

    // Waits UP TO 10 seconds, but returns immediately when the condition is met
    WebElement status = waitUtils.waitForVisible(By.id("confirmation-status"));
    assertThat(status.getText()).isEqualTo("Confirmed");
}
```

### Failure 3: Blanket Retries Hiding a Real Bug

**The Problem:**


```java
// RetryAnalyzer applied globally — every test gets 3 retries
// The team sees "95% pass rate" in CI and feels good

// This test "passes" on retry but has a real bug:
@Test
public void shouldDisplayUserDashboard() {
    loginPage.loginAs("admin", "password");
    // Race condition: dashboard loads async, test sometimes checks before data loads
    assertThat(dashboardPage.getWelcomeMessage()).contains("Welcome, Admin");
    // Fails 30% of the time on first attempt, passes on retry because data loaded by then
}
```

**What goes wrong:** The team's CI report shows "All tests passed" because retries mask the 30% failure rate. The root cause — a missing explicit wait for the welcome message to load — is never investigated. When the retry limit is eventually reached (under heavy CI load where retries also fail), the team is surprised and wastes hours debugging a problem that's been there for months.

**The fix — add proper waits, track retry frequency:**


```java
@Test
public void shouldDisplayUserDashboard() {
    loginPage.loginAs("admin", "password");
    // Proper wait — waits for the actual content to appear
    waitUtils.waitForTextContains(By.id("welcome-msg"), "Welcome, Admin");
    assertThat(dashboardPage.getWelcomeMessage()).contains("Welcome, Admin");
}
```

## Engineering Judgment (Layer 5)

### Choosing the Right Wait Strategy

| Scenario | Wait Strategy | Why |
|----------|--------------|-----|
| Element needs to appear after an action | `WebDriverWait` + `visibilityOfElementLocated` | Waits for the specific condition, returns immediately when met |
| Element needs to disappear (loading spinner) | `WebDriverWait` + `invisibilityOfElementLocated` | Negative condition — waiting for absence |
| Page fully loaded after navigation | `WebDriverWait` + custom condition (check a key element) | Page load timeout alone doesn't guarantee JS rendering is complete |
| API response during integration test | Exponential backoff retry | Transient server errors resolve themselves; hammering the server makes it worse |
| File download completion | `WebDriverWait` + custom condition (file exists and size stable) | File writes are not atomic; check that size stops changing |
| **Never** | `Thread.sleep(n)` | Fixed delay — either too long (slow) or too short (flaky) |

### When Retries Are Justified vs When They're a Crutch

| Situation | Retry? | Why |
|-----------|--------|-----|
| API returns 503 during CI (transient server issue) | **Yes** | Server load is a transient infrastructure issue outside your control |
| Element not found due to missing explicit wait | **No** | Fix the wait logic — the test design is wrong |
| Test fails because another parallel test modified shared data | **No** | Fix data isolation — this is a thread-safety bug |
| Selenium Grid node crashed mid-test | **Yes** | Infrastructure failure; retrying on a different node is reasonable |
| StaleElementReferenceException after a page refresh | **Maybe** | If the page legitimately refreshes, a re-find is correct. If it's a test design issue, fix the design. |
| Test fails only on Monday mornings (CI environment not fully warmed) | **Yes** (short-term) | Retry handles it now, but investigate the cold-start issue for a permanent fix |

### Timeout Tuning Guidelines

| Level | Recommended Range | Why |
|-------|------------------|-----|
| Element explicit wait | 5–10 seconds | Most elements appear within 2 seconds; 10s handles slow renders |
| Page load timeout | 30 seconds | Full page loads on slow connections can take 10–15 seconds |
| Test method timeout | 2 minutes | Any single test taking longer than 2 minutes is either testing too much or has a performance problem |
| Suite timeout (CI) | Proportional to suite size | 200 tests × ~10s average = ~33 minutes; add 50% buffer = ~50 minutes |

## Interview and Revision (Layer 6)

### Fundamental Questions

**Q1: What's the difference between implicit and explicit waits in Selenium?**

**A:** Implicit waits are a global setting applied to every `findElement` call — if an element isn't found immediately, WebDriver polls the DOM for the specified duration before throwing `NoSuchElementException`. Explicit waits target a specific condition on a specific element with a specific timeout, using `WebDriverWait` and `ExpectedConditions`. I use explicit waits exclusively because they're precise, condition-based, and produce clear timeout messages. Implicit waits cause problems: they slow down negative assertions (checking an element is absent), they interact unpredictably when mixed with explicit waits, and they apply the same timeout to every element regardless of context.

**Q2: How do you handle flaky tests that fail intermittently?**

**A:** First, I investigate the root cause rather than immediately adding retries. The most common causes of flakiness are: (1) missing or insufficient explicit waits — the test checks before the page finishes rendering, (2) shared mutable state between parallel tests — one test's data interferes with another, (3) environment instability — CI infrastructure is inconsistent. For cause (1), I add proper condition-based waits. For (2), I isolate test data using unique identifiers and `ThreadLocal`. For (3), I may add a retry as a temporary measure while fixing the infrastructure, but I track retry frequency so it doesn't become a permanent band-aid.

**Q3: Explain exponential backoff and when you'd use it.**

**A:** Exponential backoff is a retry strategy where each successive retry waits longer than the previous one — typically doubling: 1s, 2s, 4s, 8s. I use it for API test retries when the server might return transient errors (503 Service Unavailable, 429 Too Many Requests). The increasing delay gives the server time to recover instead of hammering it with rapid retries, which would make congestion worse. I cap the maximum number of retries (usually 3–4) and only retry on specific status codes — a 400 Bad Request is a test bug, not a transient issue, so it should fail immediately.

### Scenario-Based Questions

**S1: "Your CI pipeline shows that 15 tests are consistently retried 2-3 times before passing. The overall pass rate is 100%. Should you be concerned?"**

**A:** Absolutely. A 100% pass rate with 15 retried tests means the team is masking a 15-test flakiness problem. I'd pull the retry logs, group the retried tests by failure reason, and address the top causes. Likely culprits: missing explicit waits (fix with `WebDriverWait`), shared test data in parallel runs (fix with data isolation), or environment timing issues (fix with proper API readiness checks). The goal is zero retries in a clean run — retries should catch genuinely transient infrastructure blips, not compensate for test design problems.

**S2: "A developer added `Thread.sleep(3000)` before every assertion because 'it fixes the timing issues.' The suite now takes 40 minutes. How do you address this?"**

**A:** I'd explain the cost: with 200 assertions and 3 seconds each, that's 10 minutes of pure sleep. I'd replace each `Thread.sleep` with an explicit wait for the specific condition the assertion depends on. For example, replace `Thread.sleep(3000); assertText(el, "Success")` with `waitForTextContains(el, "Success"); assertText(el, "Success")`. The explicit wait returns immediately when the condition is met (often in 200ms), not after a fixed 3 seconds. I'd do this incrementally — replace the sleeps in the slowest tests first, measure the time savings, and use that data to justify converting the rest.
