# Framework Architecture

> **Module:** 03 — Framework Engineering > Framework Architecture

> **Mastery Target:** L3 (Independent) → L4 (Engineering Judgment)

## Quick Overview (Layer 1)

**What:** Framework architecture is how you organize automation code into layers, patterns, and conventions so that tests are maintainable, reusable, and scalable. It's the structural blueprint that determines how test code, page interactions, driver management, configuration, and utilities relate to each other — regardless of whether you're using Selenium, Playwright, Appium, or REST Assured.

**Why it matters:** Without architecture, you have a collection of scripts. With architecture, you have an engineering system. The difference shows up when the team grows from 1 to 10, when you need to support a second environment, when tests start running in parallel, or when a UI redesign forces locator changes across 200 tests. Architecture is the difference between "change one file" and "change 200 files."

**Where you encounter it:** Every structural decision you make — where to put config, how to manage drivers, how tests get data, how page objects are organized, how setup and teardown flow — is an architecture decision.

<MentalModel>

Think of a framework as a **layered cake**. Each layer has one job and depends only on the layer directly below it. The top layer (tests) doesn't know how the bottom layer (utilities) works, just as a chef tasting the cake doesn't care about the oven temperature — they care about the flavor.

</MentalModel>


```
Tests call page objects → page objects use drivers → drivers read config → config uses utilities
```

When a layer reaches *down* through multiple levels (a test directly creates a `ChromeDriver`), or reaches *up* (a utility calls a test method), the architecture is broken. Clean layers mean changes stay local: swapping Chrome for Firefox is a config change, not a 200-file refactor.

<KeyTakeaways>

1. **Layers enforce separation of concerns** — each layer has one responsibility and depends only on the layer below it, so changes stay contained.
2. **Design patterns are tools, not rules** — Page Object, Factory, Builder, Strategy each solve a specific problem; apply them when the problem exists, not preemptively.
3. **Composition over inheritance applies to framework structure** — assemble capabilities from independent components rather than building deep base class hierarchies.
4. **Configuration should be external and environment-aware** — never hardcode URLs, credentials, or environment-specific values in test code.
5. **The framework's job is to make writing the next test trivial** — if adding a new test requires understanding the entire framework, the architecture has failed.

</KeyTakeaways>

## First-Principles Explanation (Layer 2)

### Framework Layers

Every well-designed test automation framework, regardless of tooling, follows a layered architecture. Each layer has a single responsibility and communicates only with its immediate neighbors.

```
┌─────────────────────────────────┐
│     Test Layer                  │  ← test methods, assertions, test data
├─────────────────────────────────┤
│     Page/Screen/API Layer       │  ← page objects, screen objects, API clients
├─────────────────────────────────┤
│     Driver/Client Layer         │  ← WebDriver, HttpClient, AppiumDriver management
├─────────────────────────────────┤
│     Configuration Layer         │  ← environment config, test data sources
├─────────────────────────────────┤
│     Utility Layer               │  ← logging, waits, file I/O, data generation
└─────────────────────────────────┘
```

**Test Layer** — The highest layer. Contains test classes, assertions, and test data setup. Tests should read like specifications: `loginAs("admin")`, not `driver.findElement(By.id("user")).sendKeys("admin")`. This layer knows *what* to test but not *how* elements are located or drivers are created.

**Page/Screen/API Layer** — Encapsulates all interactions with the system under test. A `LoginPage` knows its locators and how to perform login. An `AuthApiClient` knows how to call `/auth/token`. This layer translates high-level actions ("log in") into tool-specific operations ("find element, type, click").

**Driver/Client Layer** — Manages the lifecycle of browser drivers, HTTP clients, or mobile drivers. Handles creation, configuration, thread safety, and cleanup. Tests never create drivers directly — they receive them from this layer.

**Configuration Layer** — Provides environment-specific values: base URLs, timeouts, browser types, credentials references. Reads from properties files, YAML, or environment variables. Enables the same tests to run against dev, staging, or production without code changes.

**Utility Layer** — Cross-cutting helpers that any layer can use: logging, custom waits, file I/O, data generation, date formatting. These are stateless functions — they take input, produce output, and hold no state.

**Why layering matters:** When a UI element's locator changes, you fix one page object — tests don't change. When you switch from Chrome to Firefox, you change config — page objects don't change. When you move from local execution to Selenium Grid, you update the driver layer — nothing above it notices. Each change is isolated to its layer.

### Design Patterns Every Framework Uses

Patterns are recurring solutions to common design problems. In test automation, six patterns appear in virtually every well-structured framework.

**1. Page Object Model / Screen Object** — Encapsulates UI element locators and interactions behind a class boundary. Each page (or screen, for mobile) gets its own class. Tests call `loginPage.loginAs("admin", "pass")`, never `driver.findElement(...)`. This centralizes locator changes: when the login button's ID changes, you fix `LoginPage.java`, not 40 test files.

**2. Factory Pattern** — Creates the right object based on runtime conditions. A `DriverFactory` reads the browser name from config and returns a `ChromeDriver`, `FirefoxDriver`, or `RemoteWebDriver`. The caller receives a `WebDriver` interface — it doesn't know or care which implementation it got. Adding a new browser means adding a new factory case, not modifying existing tests.

**3. Builder Pattern** — Constructs complex objects step by step with a fluent API. In test automation, this is used for test data: `new UserBuilder().withName("John").withEmail("john@test.com").withRole("admin").build()`. Builders make test data readable, prevent constructor parameter explosion, and let you set only the fields you care about (defaulting the rest).

**4. Strategy Pattern** — Swaps algorithms at runtime by injecting different implementations of the same interface. Used for wait strategies (fixed delay vs exponential backoff), config loaders (properties file vs YAML vs environment variables), and retry policies. The consuming code doesn't change when the strategy changes.

**5. Singleton Pattern (use with caution)** — Ensures exactly one instance of a class exists. Justified for immutable configuration loaded once at startup. Dangerous for mutable state like WebDriver — a singleton driver means only one browser for the entire JVM, which makes parallel execution impossible. Prefer `ThreadLocal` or dependency injection over singletons for any mutable resource.

**6. Decorator Pattern** — Adds behavior to an object without modifying it by wrapping it. A `LoggingApiClient` wraps an `HttpApiClient`, logging every request and response while delegating the actual HTTP call. A `ScreenshotOnFailureDriver` wraps a `WebDriver`, capturing screenshots when interactions fail. Decorators are stackable: `new LoggingApiClient(new RetryApiClient(new HttpApiClient()))`.

### Framework Composition Principles

**Prefer composition over inheritance (has-a vs is-a):** A test *has* a driver, *has* config, *has* test data. It doesn't *become* a base class. Build a `TestContext` that holds these components rather than creating `BaseTest → BaseUITest → BaseAuthTest` hierarchies. Composition lets you assemble different contexts for different test types — UI tests get a driver, API tests don't.

**Keep layers independent:** The test layer should never import `ChromeDriver` or `ChromeOptions`. It should use `WebDriver` (the interface) received from the driver layer. If a test directly creates a `ChromeDriver`, it's reached through two layers and is now coupled to Chrome.

**Dependency injection — pass dependencies through constructors, don't create them inside:** When `LoginPage` receives a `WebDriver` through its constructor, you can give it Chrome, Firefox, or a mock. When it internally creates `new ChromeDriver()`, it's locked to Chrome forever and untestable in isolation.

**Interface-based design — program to interfaces, not implementations:** Declare variables as `WebDriver`, not `ChromeDriver`. Accept `ConfigLoader` in constructors, not `PropertiesFileConfigLoader`. This lets you swap implementations without touching the consuming code.

### Test Lifecycle

Test frameworks provide hooks that execute at specific points in the test lifecycle. Understanding the hierarchy is critical for correct setup and teardown.

**Setup hierarchy (TestNG):**

```
@BeforeSuite     → runs once before ALL tests in the suite (e.g., start Selenium Grid)
  @BeforeTest    → runs before each <test> tag in testng.xml (e.g., configure environment)
    @BeforeClass → runs once before the first method in a test class (e.g., load test data)
      @BeforeMethod → runs before EACH test method (e.g., create driver, navigate to page)
        @Test        → the actual test
      @AfterMethod  → runs after EACH test method (e.g., quit driver, capture screenshot)
    @AfterClass  → runs once after the last method in a test class (e.g., cleanup data)
  @AfterTest     → runs after each <test> tag completes
@AfterSuite      → runs once after ALL tests complete (e.g., shut down Grid, flush reports)
```

**Teardown is non-negotiable:** `@AfterMethod` runs even when a test fails. This is where you quit the browser, close connections, and delete test data. Without guaranteed teardown, failing tests leak browser sessions (filling up CI memory), leave dirty database state (causing cascading failures in subsequent tests), and exhaust connection pools.

**The importance of teardown:** A leaked browser session consumes ~300MB of RAM. Run 50 tests without cleanup, and your CI agent is using 15GB just for zombie browsers. This is the #1 cause of "tests pass locally but fail in CI" — the CI machine runs out of resources because previous test runs didn't clean up.

### Configuration Management

**External config — never embed environment-specific values in code:**

Configuration belongs in external files — properties, YAML, or environment variables — not in Java source code. This enables the same compiled test code to run against any environment.

**Environment switching:**

A config hierarchy lets you override values per environment without duplicating the entire config:

```
defaults (config.properties)           → base.url=http://localhost:8080, timeout=10
  ↓ overridden by
environment-specific (staging.properties)  → base.url=https://staging.app.com
  ↓ overridden by
CLI / environment variables                → BASE_URL=https://hotfix.app.com
```

Each level overrides only the values it needs. Staging inherits the default timeout of 10 but overrides the URL. A one-off CLI override can change the URL without modifying any file.

**Secrets management:** Never hardcode credentials. Use environment variables (`System.getenv("DB_PASSWORD")`), a secrets vault, or at minimum a `.env` file that's in `.gitignore`. If credentials appear in a Git commit, they're compromised — even if you delete the commit, it's in the reflog.

### Test Data Management

**Test data builder pattern with fluent API:** Instead of constructors with 8 parameters, use a builder that sets sensible defaults and lets you override only what matters for each test.

**Unique data generation:** Use UUIDs, timestamps, or atomic counters to ensure test data doesn't collide across parallel runs. `"user-" + UUID.randomUUID()` guarantees uniqueness. Never use hardcoded values like `"testuser1"` — two parallel tests will fight over it.

**Data cleanup strategies:**
- **Create-use-delete:** Each test creates its data, uses it, and deletes it in teardown. Self-contained but slower.
- **Database reset:** Reset the database to a known state before each test suite. Fast but requires database access.
- **API cleanup:** Use API calls to delete created resources. Works when you don't have direct DB access.

**External data sources for data-driven tests:** CSV, JSON, or Excel files supply test data through TestNG's `@DataProvider`. The test method runs once per data row, keeping test logic separate from test data.

## Practical Implementation (Layer 3)

### Example 1: Framework Skeleton — Project Structure

A realistic project structure for a Java + TestNG + Maven framework. Every directory has a clear purpose — a new team member should be able to find any file by understanding the layer it belongs to.

```
src/
  main/java/com/company/automation/
    config/                          ← Configuration Layer
      ConfigManager.java             → loads and merges config from multiple sources
      Environment.java               → enum: LOCAL, STAGING, PRODUCTION
    driver/                          ← Driver/Client Layer
      DriverFactory.java             → creates the right browser based on config
      DriverManager.java             → ThreadLocal driver storage for parallel safety
    pages/                           ← Page/Screen Layer
      BasePage.java                  → shared waits, click, type methods
      LoginPage.java                 → login-specific locators and actions
      DashboardPage.java             → dashboard-specific locators and actions
    api/                             ← API Client Layer
      BaseApiClient.java             → shared HTTP methods (GET, POST), auth headers
      AuthApiClient.java             → login/token-specific API calls
      BookingApiClient.java          → booking CRUD via API
    utils/                           ← Utility Layer
      WaitUtils.java                 → custom wait conditions
      DataGenerator.java             → random names, emails, UUIDs
      FileUtils.java                 → read JSON/CSV files
    models/                          ← Data Models
      User.java                      → POJO/Record for user data
      Booking.java                   → POJO/Record for booking data

  test/java/com/company/automation/
    base/                            ← Test Infrastructure
      BaseTest.java                  → @Before/@After lifecycle, driver setup/teardown
    tests/                           ← Test Layer
      LoginTest.java                 → login scenarios
      BookingTest.java               → booking scenarios
      SearchTest.java                → search scenarios
    data/                            ← Test Data Providers
      TestDataProvider.java          → @DataProvider methods for data-driven tests

  test/resources/
    config/                          ← Config Files
      config.properties              → default config (base URL, timeout, browser)
      staging.properties             → staging overrides
      production.properties          → production overrides
    testdata/                        ← External Test Data
      users.json                     → user test data
      bookings.csv                   → booking test data

pom.xml                             ← Maven build config, dependencies
testng.xml                          ← TestNG suite definition, parallel config
```

**Key decisions in this structure:**
- **`main/java` vs `test/java`:** Framework infrastructure (`config/`, `driver/`, `pages/`, `utils/`) goes in `main/java` because it's reusable library code. Test classes go in `test/java` because they're consumers of the framework.
- **One package per layer:** Anyone can find the config loader (`config/`), driver factory (`driver/`), or page objects (`pages/`) by knowing which layer they belong to.
- **Models are separate from pages:** `User.java` is a data holder used by tests, API clients, and data providers. It doesn't belong inside `pages/` or `tests/`.
- **Test data is in resources, not hardcoded:** External files (`users.json`, `bookings.csv`) keep test data separate from test logic, enabling data-driven tests and easy updates.

### Example 2: Base Test Class with Lifecycle Management

The `BaseTest` class is the thin orchestration layer that wires together driver management, configuration, and teardown. It should be small — if it's more than 50 lines, it's doing too much.


```java
import org.testng.annotations.AfterMethod;
import org.testng.annotations.BeforeMethod;
import org.testng.annotations.BeforeSuite;
import org.testng.annotations.Optional;
import org.testng.annotations.Parameters;
import org.testng.ITestResult;

import org.openqa.selenium.WebDriver;

/**
 * Base class for all UI tests.
 *
 * Responsibilities (and ONLY these):
 * 1. Load configuration once per suite
 * 2. Create a driver before each test method
 * 3. Guarantee driver cleanup after each test method
 * 4. Provide access to the driver and config for subclasses
 *
 * This class does NOT handle:
 * - Page object creation (tests do that)
 * - Test data setup (data providers do that)
 * - Reporting (listeners do that)
 * - Login/navigation (test methods or helper methods do that)
 */
public class BaseTest {

    // ThreadLocal ensures each parallel thread gets its own driver instance.
    // Without this, parallel tests would share a single driver and corrupt each other.
    private static final ThreadLocal<WebDriver> driverThreadLocal = new ThreadLocal<>();

    protected ConfigManager config;

    // --- Suite-level setup: runs ONCE before all tests ---

    @BeforeSuite
    public void loadConfiguration() {
        // Load config once — it's immutable after this point
        String env = System.getProperty("env", "local");
        config = ConfigManager.load(env);
    }

    // --- Method-level setup: runs before EACH test method ---

    @BeforeMethod
    @Parameters({"browser"})
    public void setUp(@Optional("chrome") String browser) {
        // Create a fresh driver for each test — complete isolation
        WebDriver driver = DriverFactory.createDriver(browser, config);
        driverThreadLocal.set(driver);

        // Navigate to the base URL so every test starts at a known location
        driver.get(config.getBaseUrl());
    }

    // --- Method-level teardown: runs after EACH test, even on failure ---

    @AfterMethod(alwaysRun = true)  // alwaysRun = true ensures this runs even if setUp fails
    public void tearDown(ITestResult result) {
        WebDriver driver = driverThreadLocal.get();
        if (driver != null) {
            try {
                // Capture screenshot on failure — before quitting the driver
                if (result.getStatus() == ITestResult.FAILURE) {
                    ScreenshotUtils.capture(driver, result.getName());
                }
            } finally {
                // ALWAYS quit the driver — no leaked sessions
                driver.quit();
                driverThreadLocal.remove();  // prevent memory leak in thread pool
            }
        }
    }

    // --- Protected accessor for subclasses ---

    protected WebDriver getDriver() {
        return driverThreadLocal.get();
    }
}
```

**Why `ThreadLocal`?** When TestNG runs tests in parallel (e.g., 5 threads), each thread needs its own `WebDriver`. A regular field (`private WebDriver driver`) would be shared across threads via the same test class instance, causing tests to interfere. `ThreadLocal` gives each thread its own isolated storage. The `driverThreadLocal.remove()` in teardown prevents memory leaks when threads are reused from a pool.

**Why `alwaysRun = true`?** Without it, if `setUp()` throws an exception, `tearDown()` is skipped. That means a partially-created driver isn't cleaned up, leaking a browser process.

### Example 3: Configuration Loader

A configuration loader that supports environment switching and a clear override hierarchy: defaults → environment-specific → system properties.


```java
import java.io.IOException;
import java.io.InputStream;
import java.util.Properties;

/**
 * Loads configuration from properties files with environment-based overrides.
 *
 * Override hierarchy (later wins):
 * 1. config.properties          → base defaults
 * 2. {env}.properties           → environment-specific overrides (staging, production)
 * 3. System properties (-D)     → CLI overrides for one-off runs
 *
 * Usage:
 *   ConfigManager config = ConfigManager.load("staging");
 *   String url = config.getBaseUrl();    // reads from staging.properties, falls back to config.properties
 *   int timeout = config.getTimeout();   // reads from config.properties if staging doesn't override
 */
public class ConfigManager {

    private final Properties properties;

    private ConfigManager(Properties properties) {
        this.properties = properties;
    }

    /**
     * Load config for the given environment.
     * Merges defaults with environment-specific overrides and system properties.
     */
    public static ConfigManager load(String environment) {
        Properties merged = new Properties();

        // Layer 1: Load defaults
        loadInto(merged, "config/config.properties");

        // Layer 2: Load environment-specific overrides (if they exist)
        if (environment != null && !environment.isBlank()) {
            loadInto(merged, "config/" + environment + ".properties");
        }

        // Layer 3: System properties override everything
        // This allows: mvn test -Dbase.url=https://hotfix.app.com
        for (String key : merged.stringPropertyNames()) {
            String systemValue = System.getProperty(key);
            if (systemValue != null) {
                merged.setProperty(key, systemValue);
            }
        }

        return new ConfigManager(merged);
    }

    // --- Typed getters with sensible defaults ---

    public String getBaseUrl() {
        return getRequired("base.url");
    }

    public int getTimeout() {
        return Integer.parseInt(getOrDefault("timeout.seconds", "10"));
    }

    public String getBrowser() {
        return getOrDefault("browser", "chrome");
    }

    public boolean isHeadless() {
        return Boolean.parseBoolean(getOrDefault("headless", "false"));
    }

    // --- Internal helpers ---

    private String getRequired(String key) {
        String value = properties.getProperty(key);
        if (value == null || value.isBlank()) {
            throw new IllegalStateException(
                "Required config property '" + key + "' is missing. "
                + "Check config.properties or set -D" + key + "=value"
            );
        }
        return value;
    }

    private String getOrDefault(String key, String defaultValue) {
        return properties.getProperty(key, defaultValue);
    }

    private static void loadInto(Properties target, String resourcePath) {
        try (InputStream stream = ConfigManager.class.getClassLoader()
                .getResourceAsStream(resourcePath)) {
            if (stream != null) {
                Properties source = new Properties();
                source.load(stream);
                target.putAll(source);  // later values overwrite earlier ones
            }
            // If file doesn't exist, silently skip — env-specific files are optional
        } catch (IOException e) {
            throw new RuntimeException("Failed to load config: " + resourcePath, e);
        }
    }
}
```

**Design decisions:**
- **Immutable after construction:** `ConfigManager` takes `Properties` in its constructor and only exposes getters. No setter exists. This makes it safe for parallel execution — 50 tests can read the same config without synchronization.
- **Layered override:** Defaults → environment → CLI. You can run `mvn test -Dbase.url=https://hotfix.app.com` to override the URL for one run without changing any file.
- **Typed getters:** `getTimeout()` returns `int`, not `String`. Callers don't need to parse. `getRequired()` fails fast with a helpful error message if a critical property is missing — better than a `NullPointerException` 10 lines later.
- **Silent skip for optional files:** If `staging.properties` doesn't exist, the loader continues with defaults. This means you only need to create an environment file when that environment differs from defaults.

## Failure and Debugging (Layer 4)

### Failure 1: Shared State Between Parallel Tests

**The Problem:**


```java
// A DriverManager with a static field — one driver for the entire JVM
public class DriverManager {
    private static WebDriver driver;  // STATIC = shared across all threads

    public static WebDriver getDriver() {
        if (driver == null) {
            driver = new ChromeDriver();
        }
        return driver;
    }

    public static void quitDriver() {
        if (driver != null) {
            driver.quit();
            driver = null;
        }
    }
}
```

**What happens with 3 parallel tests:**

```
Thread-1: getDriver() → driver is null → creates ChromeDriver-A → static driver = ChromeDriver-A
Thread-2: getDriver() → driver is NOT null → returns ChromeDriver-A (WRONG — shares Thread-1's browser!)
Thread-1: test navigates to /login
Thread-2: test navigates to /dashboard → Thread-1's browser is now on /dashboard too (SAME browser!)
Thread-1: assertion fails — expected /login but page shows /dashboard
Thread-3: getDriver() → returns the same ChromeDriver-A → three tests fighting over one browser
```

**Root cause:** `static WebDriver` means one browser session for the entire JVM. Parallel tests share it, stepping on each other's navigation, cookies, and state.

**The fix — ThreadLocal driver storage:**


```java
public class DriverManager {
    // ThreadLocal gives each thread its own independent driver instance
    private static final ThreadLocal<WebDriver> driverThreadLocal = new ThreadLocal<>();

    public static WebDriver getDriver() {
        return driverThreadLocal.get();
    }

    public static void setDriver(WebDriver driver) {
        driverThreadLocal.set(driver);
    }

    public static void quitDriver() {
        WebDriver driver = driverThreadLocal.get();
        if (driver != null) {
            driver.quit();
            driverThreadLocal.remove();  // CRITICAL: prevents memory leak in thread pools
        }
    }
}
```

**Prevention rule:** Never use `static` for mutable state that differs per test. Use `ThreadLocal` or, better yet, pass the driver through constructors (dependency injection) so there's no global state at all.

### Failure 2: Missing Teardown Causes Resource Leak

**The Problem:**


```java
public class BookingTest extends BaseTest {

    @BeforeMethod
    public void setUp() {
        WebDriver driver = new ChromeDriver();
        // ... BUT: if this next line throws, the driver is never stored
        // and tearDown() has no reference to quit it
        driver.get("https://invalid-url-that-throws.com");
    }

    @Test
    public void testBooking() {
        // test logic
    }

    @AfterMethod
    public void tearDown() {
        getDriver().quit();  // getDriver() returns null → NullPointerException
        // Original driver from setUp() is a zombie — process still running, no reference to it
    }
}
```

**What happens:** The `driver.get()` call in `setUp()` throws an exception. The driver was created but never stored in `ThreadLocal` or a field. `tearDown()` can't find it. The Chrome process stays alive, consuming ~300MB. After 50 failing tests, your CI machine has 15GB of zombie browsers.

**The fix — store the driver BEFORE any operation that might fail:**


```java
@BeforeMethod
public void setUp() {
    WebDriver driver = DriverFactory.createDriver(config.getBrowser(), config);
    driverThreadLocal.set(driver);  // store IMMEDIATELY — before any navigation

    // Now if get() throws, tearDown() can still find and quit the driver
    driver.get(config.getBaseUrl());
}

@AfterMethod(alwaysRun = true)  // alwaysRun ensures this executes even if setUp fails
public void tearDown() {
    WebDriver driver = driverThreadLocal.get();
    if (driver != null) {  // null check — setUp might not have created a driver at all
        driver.quit();
        driverThreadLocal.remove();
    }
}
```

**Prevention rule:** Store the driver reference *immediately* after creation, before any other operation. Use `alwaysRun = true` on teardown. Always null-check in teardown.

### Failure 3: Hard-Coded Config Breaks Different Environments

**The Problem:**


```java
public class LoginTest extends BaseTest {

    @Test
    public void testLogin() {
        getDriver().get("https://staging.myapp.com/login");  // hardcoded staging URL
        LoginPage loginPage = new LoginPage(getDriver());
        loginPage.loginAs("admin", "Admin@123");             // hardcoded credentials
        // ...
    }
}
```

**What happens:** This test only works against staging. Run it against dev? Wrong URL. Run it against production? Wrong credentials. Move to a new staging domain? Find and replace across every test file. A developer who needs to test locally can't — the URL points to staging.

**The fix — externalize everything environment-specific:**


```java
public class LoginTest extends BaseTest {

    @Test
    public void testLogin() {
        // URL comes from config — changes per environment without touching code
        getDriver().get(config.getBaseUrl() + "/login");

        LoginPage loginPage = new LoginPage(getDriver());

        // Credentials come from test data, which can differ per environment
        User adminUser = TestDataProvider.getUser("admin", config.getEnvironment());
        loginPage.loginAs(adminUser.getUsername(), adminUser.getPassword());
        // ...
    }
}
```

**Prevention rule:** If a value changes between environments (URLs, credentials, API keys, timeouts), it must come from configuration, never from source code. Search your codebase for hardcoded `https://` — each occurrence is a potential environment-coupling bug.

## Engineering Judgment (Layer 5)

### When to Add Abstraction vs When YAGNI Applies

**YAGNI (You Aren't Gonna Need It)** is the principle that you should not build something until you actually need it. In framework design, this creates a tension: too little abstraction leads to duplication and rigidity; too much leads to unnecessary complexity.

**Add abstraction when:**
- You have 2+ concrete implementations today (Chrome and Firefox → `BrowserProvider` interface)
- You're duplicating the same code in 3+ places (extract a method, then a class)
- A change in one area forces changes in unrelated areas (the layers are coupled)
- You need testability — you want to mock a dependency in unit tests

**Don't add abstraction when:**
- You have only one implementation and no foreseeable second one (skip the interface — you can always extract one later)
- The abstraction would have more boilerplate than the code it replaces
- You're guessing at future requirements ("we might need to support Safari someday" — wait until you actually do)

**Practical example:** If your framework only runs on Chrome, don't build a `BrowserProvider` interface, `ChromeProvider`, `FirefoxProvider`, `DriverFactory`, and a registry — just create a `ChromeDriver` in your setup. When the day comes that you need Firefox, *then* extract the interface. The cost of extracting it later is low; the cost of maintaining unused abstraction now is ongoing.

### Framework for a Team of 1 vs a Team of 10

**Team of 1:** You know every line of code. Convention lives in your head. You can get away with simpler structure — fewer abstractions, less formality, direct instantiation instead of factories. The priority is speed of writing tests, not onboarding documentation.

**Team of 10:** Convention must be encoded in structure, not memory. New team members need to find things by following the project layout, not by asking you. The priority shifts to consistency, discoverability, and guard rails:
- Clear package structure (so people know where to put things)
- Base classes or context factories (so setup is consistent)
- Interfaces for extension points (so people add features without breaking existing code)
- Documentation in the README and code comments

**The inflection point** is around 3–4 people. When you start seeing different patterns for the same problem (one person creates drivers in `setUp()`, another uses a factory, a third uses a static singleton), it's time to formalize the architecture.

### When to Use Inheritance vs Composition for Page Objects

**Use inheritance for page objects** when:
- All pages genuinely share common behavior: `click(By)`, `type(By, String)`, `waitForElement(By)`
- The hierarchy is flat: `BasePage` → `LoginPage` (one level only)
- You need to share state: the `WebDriver` and `WebDriverWait` instances

**Switch to composition when:**
- Pages share partial behavior: a `NavigationBar` component appears on some pages but not all — extract it as a composed component, don't force it into `BasePage`
- You need more than one level of inheritance: `BasePage → BaseAuthenticatedPage → AdminPage` — stop and compose
- Different page types have different needs: web pages need a `WebDriver`, API "pages" need an `HttpClient` — they can't share a base class

**Recommended hybrid:** Use `BasePage` (one-level inheritance) for shared driver access and basic wait methods. Use composition for reusable components like navigation bars, date pickers, and modals.

### Signs Your Framework Needs Refactoring

| Symptom | Diagnosis | Action |
|---------|-----------|--------|
| Adding a test takes more than 10 minutes of boilerplate | Framework isn't doing its job — making tests easy to write | Extract setup into factories/builders |
| A locator change requires editing 5+ files | Locators aren't encapsulated in page objects | Introduce or fix the page object layer |
| Tests fail in CI but pass locally | Environment-specific values are hardcoded | Externalize config, use environment switching |
| Parallel execution causes random failures | Shared mutable state (static fields) | Audit for `static` mutable state, switch to ThreadLocal or DI |
| `BaseTest` is 300+ lines | God class with too many responsibilities | Split into focused components: driver management, config, reporting |
| New team member can't write a test without asking where everything is | Poor discoverability | Clarify package structure, add README, follow conventions |

## Interview and Revision (Layer 6)

### Fundamental Questions

**Q1: Walk me through your framework architecture.**

**A:** Our framework follows a layered architecture. At the top is the **test layer** — test classes with TestNG annotations that read like specifications. They call into the **page object layer**, where each page encapsulates its locators and interactions behind a clean API. Page objects receive a `WebDriver` from the **driver layer**, which uses a factory pattern to create the appropriate browser based on configuration. The **configuration layer** loads environment-specific properties files with an override hierarchy: defaults → environment-specific → system properties. At the base, the **utility layer** provides stateless helpers for waits, data generation, and file I/O. Each layer depends only on the layer below it, so a locator change touches one page object, a browser switch touches config, and test logic stays clean.

**Q2: How do you handle parallel test execution in your framework?**

**A:** The critical requirement is that no mutable state is shared between threads. We use `ThreadLocal<WebDriver>` in our driver management so each parallel test gets its own isolated browser instance. Page objects are instantiated per-test-method — they receive the thread's driver through constructor injection. Configuration is loaded once and is immutable after that, so it's safe to share across threads without synchronization. Test data uses unique identifiers (UUIDs) to prevent collisions. In teardown, we call `driverThreadLocal.remove()` to prevent memory leaks when threads are reused from a pool.

**Q3: What design patterns do you use in your framework and why?**

**A:** We use **Page Object** to encapsulate UI interactions — this centralizes locator changes. **Factory pattern** for driver creation — a `DriverFactory` reads the browser from config and returns the right `WebDriver` implementation, so tests don't know or care which browser they're running on. **Builder pattern** for test data — `UserBuilder` creates complex test data with fluent syntax and sensible defaults. **Strategy pattern** for swappable behaviors like retry policies and wait strategies — inject the interface, swap the implementation via config. We avoid **Singleton** for anything mutable; the only singleton is the immutable config loaded once at suite startup.

**Q4: How do you manage configuration across different environments?**

**A:** We use a layered override approach. A `config.properties` file has sensible defaults (timeout, browser, etc.). Environment-specific files like `staging.properties` override only what's different (base URL, API endpoints). System properties (`-Dbase.url=...`) override everything, enabling one-off CI runs against a hotfix environment. The `ConfigManager` merges these layers at startup, exposes typed getters (`getTimeout()` returns `int`), and is immutable after construction. Credentials never go in properties files — they come from environment variables or a secrets manager.

**Q5: Why do you prefer composition over inheritance for test infrastructure?**

**A:** Three reasons. First, **flexibility**: a UI test needs a driver + config, an API test needs only config + an HTTP client. With inheritance, an API test extending `BaseUITest` gets a browser it never uses. With composition, each test assembles exactly the components it needs. Second, **stability**: changing a composed component only affects code that uses it, while changing a `BaseTest` affects every test in the suite. Third, **clarity**: with composition, I read one `setUp()` method and see everything the test depends on. With inheritance, I trace through 3–4 parent classes to understand what `@BeforeMethod` hooks are running and in what order.

**Q6: How do you decide where to put a new piece of framework code?**

**A:** I ask which layer it belongs to. If it interacts with UI elements or API endpoints, it's the page/client layer. If it manages a browser or HTTP connection lifecycle, it's the driver layer. If it provides environment-specific values, it's the config layer. If it's a stateless helper (date formatting, random data, file reading), it's the utility layer. If none of these fit, I ask whether it's a new cross-cutting concern that deserves its own component — like reporting or retry logic — and give it a focused package. The rule is: each class has one reason to change, and it lives in the package for that reason.

### Scenario-Based Questions

**S1: "You join a team with 500 tests. There's no page object layer — tests directly call `driver.findElement(...)` everywhere. A UI redesign changes 30 element IDs. How do you handle this?"**

**A:** Immediate fix: find-and-replace the 30 changed locators across all test files. But this is treating the symptom. The real fix is introducing the page object layer incrementally. I wouldn't stop all work to refactor 500 tests — that's months of effort with no new test coverage. Instead, I'd (1) create page objects for the pages involved in the redesign, moving their locators from tests into page classes, (2) update new tests to use page objects, (3) refactor existing tests to use page objects when they're touched for any reason (bug fix, feature change). Over 2–3 months, the most-active pages get page objects naturally, and the next UI redesign is a locator change in one file.

**S2: "Your framework takes 45 seconds to initialize before the first test runs. Developers avoid running tests locally. How do you diagnose and fix this?"**

**A:** I'd profile the startup. Common culprits: (1) loading all config files eagerly instead of lazily, (2) pre-initializing drivers for all browser types instead of just the one needed, (3) scanning for test data files at startup instead of on demand, (4) an expensive `@BeforeSuite` that starts external services. The fix depends on the cause. If driver creation is slow, ensure we create drivers lazily (in `@BeforeMethod`, not `@BeforeSuite`). If config loading is slow, cache the parsed config as an immutable singleton loaded once. If external service startup is slow, consider using mocks for local runs. The goal: first-test-starts-in-under-5-seconds for local development.

**S3: "A colleague proposes using inheritance for everything: `BaseTest → BaseUITest → BaseAuthTest → BaseAdminTest`. Each level adds one `@BeforeMethod`. Tests are 4 levels deep. What's your feedback?"**

**A:** I'd explain the fragile base class problem concretely: changing `BaseUITest`'s setup affects every test in the suite, and debugging requires reading four `@BeforeMethod` methods across four files to understand what runs before a single test. I'd propose composition instead: create a `TestContext` with optional components (driver, auth helper, admin setup) and let each test assemble what it needs. An admin test would compose all three; an API test would skip the driver. If the team is concerned about repeated setup code, a factory method like `TestContextFactory.forAdminUITest()` encapsulates the common assembly without forcing an inheritance chain.
