## What Makes an Agent \"Agentic\"?

The key distinction between a simple LLM call and an agentic system is the **loop** — an agent observes, reasons, acts, and repeats until a goal is achieved.

## Pattern 1: ReAct Loop

The most fundamental pattern. Reason → Act → Observe → Repeat.

```python
while not task.complete:
    thought = llm.reason(task, observations)
    action = llm.select_action(thought, available_tools)
    result = execute(action)
    observations.append(result)
```

## Pattern 2: Tool-Augmented Agents

Give the LLM access to real-world tools — APIs, databases, browsers, file systems.

The key insight: tool descriptions matter as much as the tools themselves. Well-documented tool schemas dramatically improve agent performance.

## Pattern 3: Multi-Agent Orchestration

For complex workflows, decompose into specialized agents:

- **Planner Agent** — breaks down tasks
- **Executor Agent** — carries out individual steps
- **Reviewer Agent** — validates outputs
- **Router Agent** — directs traffic between specialists

## Key Takeaway

Start simple. A single ReAct loop with well-chosen tools solves 80% of real-world agentic problems. Multi-agent systems add complexity — use them only when the problem genuinely requires decomposition.

## The Problem Attention Solves

Before attention, sequence-to-sequence models compressed an entire input sequence into a single fixed-size vector — the \"bottleneck.\" A 500-word paragraph and a 5-word sentence both got squeezed into the same vector size.

This meant information loss was inevitable. The model couldn't effectively handle long sequences because early tokens would fade from the compressed representation.

**Attention** lets the model look back at all input positions when generating each output token, weighting them by relevance.

## The Intuition

Think of attention as a soft lookup table. Given a query (\"what am I looking for?\"), compare it against a set of keys (\"what information is available?\") and return a weighted combination of values (\"the actual information\").

This is exactly what happens when you search — your search query is compared against document titles (keys), and the most relevant documents (values) get the highest weight.

## Attention Step by Step

Given an input sequence of embeddings `X = [x₁, x₂, ..., xₙ]`:

### Step 1: Compute Query, Key, Value

```python
import numpy as np

def attention(X, W_q, W_k, W_v):
    \"\"\"
    X: input embeddings (seq_len, d_model)
    W_q, W_k, W_v: learned projection matrices
    \"\"\"
    Q = X @ W_q  # Queries: what am I looking for?
    K = X @ W_k  # Keys: what do I contain?
    V = X @ W_v  # Values: what information do I carry?
    return Q, K, V
```

### Step 2: Compute Attention Scores

The dot product between queries and keys measures compatibility:

```python
def compute_scores(Q, K):
    d_k = K.shape[-1]
    # Scale by √d_k to prevent softmax saturation
    scores = (Q @ K.T) / np.sqrt(d_k)
    return scores
```

**Why scale by √d_k?** Without scaling, dot products grow with dimension size. Large values push softmax outputs toward 0 and 1, creating vanishing gradients. Scaling keeps the variance manageable.

### Step 3: Apply Softmax

Convert scores to probabilities — each query distributes its attention across all keys:

```python
def softmax(x, axis=-1):
    exp_x = np.exp(x - np.max(x, axis=axis, keepdims=True))
    return exp_x / np.sum(exp_x, axis=axis, keepdims=True)

# attention_weights[i][j] = how much token i attends to token j
attention_weights = softmax(scores)
```

### Step 4: Weighted Sum of Values

```python
# output[i] = weighted combination of all values,
# weighted by how much token i attends to each position
output = attention_weights @ V
```

### Complete Implementation

```python
import numpy as np

def scaled_dot_product_attention(Q, K, V, mask=None):
    \"\"\"
    Scaled dot-product attention.
    
    Q: (seq_len, d_k) — queries
    K: (seq_len, d_k) — keys
    V: (seq_len, d_v) — values
    mask: optional (seq_len, seq_len) — mask for causal attention
    \"\"\"
    d_k = Q.shape[-1]
    scores = (Q @ K.T) / np.sqrt(d_k)
    
    if mask is not None:
        scores = np.where(mask == 0, -1e9, scores)
    
    weights = softmax(scores)
    output = weights @ V
    
    return output, weights

# Example
seq_len, d_model, d_k = 4, 8, 4
X = np.random.randn(seq_len, d_model)

W_q = np.random.randn(d_model, d_k)
W_k = np.random.randn(d_model, d_k)
W_v = np.random.randn(d_model, d_k)

Q, K, V = X @ W_q, X @ W_k, X @ W_v
output, weights = scaled_dot_product_attention(Q, K, V)

print(f\"Input shape: {X.shape}\")
print(f\"Output shape: {output.shape}\")
print(f\"Attention weights:\n{weights.round(3)}\")
```

## Causal Masking

For autoregressive models (GPT-style), each position should only attend to previous positions — not future ones. This is enforced with a causal mask:

```python
def causal_mask(seq_len):
    \"\"\"Lower triangular mask — prevents attending to future tokens.\"\"\"
    mask = np.tril(np.ones((seq_len, seq_len)))
    return mask

mask = causal_mask(4)
# [[1, 0, 0, 0],
#  [1, 1, 0, 0],
#  [1, 1, 1, 0],
#  [1, 1, 1, 1]]
```

## Cross-Attention

In encoder-decoder models (translation, summarization), the decoder attends to the encoder's output. Queries come from the decoder, keys and values come from the encoder:

```python
# Encoder output
encoder_output = encode(source_sentence)  # (src_len, d_model)

# Decoder generates Q from its own state
Q = decoder_state @ W_q  # (tgt_len, d_k)

# K and V come from encoder
K = encoder_output @ W_k  # (src_len, d_k)
V = encoder_output @ W_v  # (src_len, d_v)

# Each decoder position attends to all encoder positions
output, weights = scaled_dot_product_attention(Q, K, V)
```

## Why Attention Changed Everything

| Before Attention | After Attention |
|-----------------|-----------------|
| Fixed-size bottleneck | Variable-length context |
| O(n) sequential processing | O(1) parallel across positions |
| Information loss for long sequences | Direct access to all positions |
| Implicit alignment | Explicit, interpretable alignment |

Attention weights are **interpretable** — you can visualize which input tokens each output token focused on. This was a major advantage over opaque RNN hidden states.

## From Attention to Transformers

The attention mechanism described here is the core building block of the transformer architecture. The key insight of \"Attention Is All You Need\" (Vaswani et al., 2017) was that you don't need recurrence or convolution at all — attention alone is sufficient for state-of-the-art sequence modeling.

## Why Linear Algebra Matters for AI

Every neural network is fundamentally a sequence of matrix multiplications and nonlinear transformations. Understanding linear algebra isn't optional — it's the language your models think in.

When you train a model, you're adjusting matrices of weights. When you compute attention, you're doing dot products. When you reduce dimensions with PCA, you're finding eigenvectors. Linear algebra is everywhere.

## Vectors: Direction and Magnitude

A vector is a quantity with both direction and magnitude. In AI, we use vectors to represent:

- **Data points**: Each feature is a dimension, so a data point with 768 features lives in 768-dimensional space
- **Embeddings**: Words, images, and concepts encoded as dense vectors
- **Gradients**: The direction of steepest loss increase during training

```python
import numpy as np

# A simple 3D vector
v = np.array([1, 2, 3])

# Vector magnitude (L2 norm)
magnitude = np.linalg.norm(v)  # √(1² + 2² + 3²) = √14 ≈ 3.74

# Unit vector (direction only)
unit_v = v / magnitude
```

## The Dot Product: Measuring Similarity

The dot product measures how aligned two vectors are. This is the foundation of attention mechanisms and similarity search.

```python
a = np.array([1, 0, 0])
b = np.array([0, 1, 0])
c = np.array([1, 0, 0])

# Orthogonal vectors: dot product = 0
print(np.dot(a, b))  # 0 — completely unrelated

# Identical direction: dot product = 1 (for unit vectors)
print(np.dot(a, c))  # 1 — perfectly aligned
```

**Cosine similarity** normalizes the dot product by magnitude, giving a value between -1 and 1. This is how embedding similarity is typically computed:

```python
def cosine_similarity(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))
```

## Matrices as Transformations

A matrix isn't just a grid of numbers — it's a transformation. When you multiply a vector by a matrix, you're rotating, scaling, or projecting that vector into a new space.

```python
# Rotation matrix (90 degrees counterclockwise in 2D)
R = np.array([[0, -1],
              [1,  0]])

v = np.array([1, 0])
rotated = R @ v  # [0, 1] — rotated 90 degrees
```

In neural networks, the weight matrix of a linear layer is exactly this — a learned transformation that maps inputs to a new representation space.

## Matrix Multiplication: Composing Transformations

Matrix multiplication chains transformations together. If `A` maps from space X to Y, and `B` maps from Y to Z, then `BA` maps directly from X to Z.

```python
# Two transformations
A = np.array([[2, 0],
              [0, 3]])  # Scale x by 2, y by 3

B = np.array([[0, -1],
              [1,  0]])  # Rotate 90°

# Composed: first scale, then rotate
composed = B @ A

v = np.array([1, 1])
result = composed @ v  # Scale [1,1] → [2,3], then rotate → [-3, 2]
```

This is exactly what happens in a multi-layer neural network — each layer applies a transformation, and the composition of all layers is the model's overall function.

## Eigenvalues and Eigenvectors: The DNA of a Matrix

An eigenvector of a matrix `A` is a vector that, when transformed by `A`, only changes in magnitude — not direction. The scaling factor is the eigenvalue.

```python
A = np.array([[3, 1],
              [0, 2]])

eigenvalues, eigenvectors = np.linalg.eig(A)
# eigenvalues: [3, 2]
# The matrix stretches space by 3x along one axis and 2x along another
```

Eigendecomposition is the foundation of:
- **PCA**: Finding the directions of maximum variance
- **Spectral clustering**: Graph-based grouping
- **Understanding training dynamics**: How gradients flow through layers

## Building Intuition: What to Remember

1. **Vectors** represent points, directions, or features in high-dimensional space
2. **Dot products** measure similarity — this is the core of attention
3. **Matrices** are transformations — neural network layers are learned transformations
4. **Matrix multiplication** composes transformations — depth in networks means composed transformations
5. **Eigenvalues** reveal the intrinsic structure of a transformation

These aren't abstract concepts — they're the actual computations happening inside every model you'll build.

## What Is RAG?

Retrieval-Augmented Generation (RAG) grounds language model responses in external knowledge. Instead of relying solely on what the model memorized during training, RAG retrieves relevant documents at query time and includes them in the prompt.

This solves several critical problems:
- **Hallucination**: The model can cite actual sources instead of fabricating answers
- **Stale knowledge**: Retrieve from up-to-date documents without retraining
- **Domain specificity**: Ground answers in your proprietary data
- **Transparency**: Users can verify the sources behind each response

## The RAG Pipeline

A standard RAG pipeline has two phases:

### Ingestion (Offline)

```
Documents → Chunking → Embedding → Vector Store
```

### Query (Online)

```
User Query → Embed Query → Vector Search → Top-K Chunks → Augmented Prompt → LLM → Response
```

## Step 1: Document Chunking

Raw documents are too large to fit in a prompt. Split them into semantically meaningful chunks:

```python
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,
    chunk_overlap=50,
    separators=[\"\n\n\", \"\n\", \". \", \" \", \"\"]
)

documents = load_documents(\"./docs\")
chunks = splitter.split_documents(documents)
```

**Chunk size matters**: Too small loses context. Too large wastes context window space and dilutes relevance. 256-1024 tokens is a common range.

## Step 2: Embedding

Convert each chunk into a dense vector that captures semantic meaning:

```python
from openai import OpenAI

client = OpenAI()

def embed_texts(texts: list[str]) -> list[list[float]]:
    response = client.embeddings.create(
        model=\"text-embedding-3-small\",
        input=texts
    )
    return [item.embedding for item in response.data]

chunk_texts = [chunk.page_content for chunk in chunks]
embeddings = embed_texts(chunk_texts)
```

## Step 3: Vector Storage

Store embeddings in a vector database for efficient similarity search:

```python
import psycopg2
from pgvector.psycopg2 import register_vector

conn = psycopg2.connect(\"postgresql://localhost/ragdb\")
register_vector(conn)
cur = conn.cursor()

# Create table with vector column
cur.execute(\"\"\"
    CREATE TABLE IF NOT EXISTS documents (
        id SERIAL PRIMARY KEY,
        content TEXT,
        metadata JSONB,
        embedding vector(1536)
    )
\"\"\")

# Insert chunks with embeddings
for chunk, embedding in zip(chunks, embeddings):
    cur.execute(
        \"INSERT INTO documents (content, metadata, embedding) VALUES (%s, %s, %s)\",
        (chunk.page_content, json.dumps(chunk.metadata), embedding)
    )

# Create an index for fast approximate nearest neighbor search
cur.execute(\"\"\"
    CREATE INDEX ON documents
    USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 100)
\"\"\")
conn.commit()
```

## Step 4: Retrieval

Given a user query, find the most relevant chunks:

```python
def retrieve(query: str, top_k: int = 5) -> list[dict]:
    query_embedding = embed_texts([query])[0]
    
    cur.execute(\"\"\"
        SELECT content, metadata, 
               1 - (embedding <=> %s::vector) as similarity
        FROM documents
        ORDER BY embedding <=> %s::vector
        LIMIT %s
    \"\"\", (query_embedding, query_embedding, top_k))
    
    results = []
    for content, metadata, similarity in cur.fetchall():
        results.append({
            \"content\": content,
            \"metadata\": metadata,
            \"similarity\": similarity
        })
    return results
```

The `<=>` operator computes cosine distance. Lower distance = higher similarity.

## Step 5: Augmented Generation

Inject retrieved chunks into the prompt:

```python
def generate_response(query: str, chunks: list[dict]) -> str:
    context = \"\n\n---\n\n\".join([c[\"content\"] for c in chunks])
    
    response = client.chat.completions.create(
        model=\"gpt-4o\",
        messages=[
            {
                \"role\": \"system\",
                \"content\": f\"\"\"Answer the user's question based on the following context. 
If the context doesn't contain relevant information, say so.
Always cite which part of the context you're referencing.

Context:
{context}\"\"\"
            },
            {\"role\": \"user\", \"content\": query}
        ]
    )
    return response.choices[0].message.content

# Full RAG query
query = \"How does attention scaling work?\"
chunks = retrieve(query, top_k=5)
answer = generate_response(query, chunks)
```

## Evaluation: Is Your RAG Working?

RAG quality depends on both retrieval and generation. Key metrics:

| Metric | Measures | How |
|--------|----------|-----|
| **Retrieval Recall@K** | Are relevant docs in top K? | Check if ground truth chunks appear in results |
| **Answer Faithfulness** | Does the answer match the context? | LLM-as-judge: does the answer only use retrieved info? |
| **Answer Relevance** | Does the answer address the query? | LLM-as-judge: is this a good answer to the question? |
| **Context Precision** | Are the retrieved chunks actually relevant? | Ratio of relevant chunks in top K |

## Common Failure Modes

1. **Wrong chunks retrieved** → Improve chunking strategy, add metadata filtering
2. **Right chunks, wrong answer** → Improve prompt template, use a better model
3. **Chunks too small** → Lose context; increase chunk size or add parent-document retrieval
4. **Chunks too large** → Dilute relevance; decrease chunk size
5. **Stale index** → Implement incremental updates or scheduled re-indexing

## What Is an AI Agent?

An AI agent is a system that can perceive its environment, make decisions, and take actions to achieve goals. Unlike a simple chatbot that responds to a single prompt, an agent operates in a loop — continuously observing, reasoning, and acting until its task is complete.

The core pattern is deceptively simple:

```
while not done:
    observation = observe(environment)
    thought = think(observation, memory)
    action = act(thought)
    result = execute(action)
    memory.update(result)
```

## The Observe-Think-Act Cycle

### Observe
The agent gathers information from its environment. This could be:
- The initial user request
- Results from a previous tool call
- Error messages or feedback
- New context from the environment

### Think
The LLM reasons about what to do next given the current observations and memory. This is where the model decides whether to:
- Call a tool
- Ask for clarification
- Provide a final answer
- Try a different approach

### Act
The agent executes its decision — calling a function, searching the web, writing code, or returning a response.

## Building the Agent Loop

Here's a complete, minimal agent loop:

```python
from openai import OpenAI

client = OpenAI()

def agent_loop(
    user_message: str,
    tools: list[dict],
    tool_functions: dict,
    max_iterations: int = 10
) -> str:
    \"\"\"
    A minimal agent loop with tool calling.
    \"\"\"
    messages = [
        {
            \"role\": \"system\",
            \"content\": \"You are a helpful assistant. Use the provided tools \"
                       \"to accomplish the user's request. Think step by step.\"
        },
        {\"role\": \"user\", \"content\": user_message}
    ]
    
    for i in range(max_iterations):
        # THINK: Ask the LLM what to do
        response = client.chat.completions.create(
            model=\"gpt-4o\",
            messages=messages,
            tools=tools,
            tool_choice=\"auto\"
        )
        
        message = response.choices[0].message
        messages.append(message)
        
        # CHECK: Is the agent done?
        if not message.tool_calls:
            # No tool calls — the agent is returning a final answer
            return message.content
        
        # ACT: Execute each tool call
        for tool_call in message.tool_calls:
            function_name = tool_call.function.name
            arguments = json.loads(tool_call.function.arguments)
            
            # Execute the tool
            result = tool_functions[function_name](**arguments)
            
            # OBSERVE: Feed the result back
            messages.append({
                \"role\": \"tool\",
                \"tool_call_id\": tool_call.id,
                \"content\": str(result)
            })
    
    return \"Agent reached maximum iterations without completing.\"
```

## Error Handling and Resilience

Production agents need to handle failures gracefully:

```python
def safe_tool_execution(func, **kwargs):
    \"\"\"Execute a tool with error handling.\"\"\"
    try:
        result = func(**kwargs)
        return {\"status\": \"success\", \"result\": result}
    except Exception as e:
        return {\"status\": \"error\", \"error\": str(e)}
```

The key insight is that errors become observations — the agent can reason about what went wrong and try a different approach. This self-correcting behavior is what makes agents powerful.

## The Agent Loop vs. Chain

| Chain | Agent |
|-------|-------|
| Fixed sequence of steps | Dynamic number of steps |
| Predetermined tools | Chooses tools based on context |
| Fails if any step fails | Can recover from failures |
| Predictable execution | Flexible execution |
| Easier to debug | Harder to debug |

Use a chain when you know the exact steps. Use an agent when the path to the answer is uncertain.

## What Makes a Good Agent

1. **Clear tool descriptions** — The LLM can only use tools it understands
2. **Bounded iterations** — Always set a maximum to prevent infinite loops
3. **Error recovery** — Feed errors back as observations, not exceptions
4. **Memory management** — Long conversations need summarization or windowing

## The Tokenization Problem

Language models don't understand text — they understand numbers. Tokenization is the bridge: converting raw text into a sequence of integer IDs that a model can process.

The naive approach — splitting on spaces and assigning IDs — breaks immediately. What about punctuation? Compound words? Languages without spaces? Rare words the model has never seen?

Modern tokenizers solve this with **subword tokenization**: break text into pieces that balance vocabulary size against sequence length.

## Byte Pair Encoding (BPE)

BPE starts with individual characters and iteratively merges the most frequent adjacent pairs.

```python
# Starting vocabulary: individual characters
# Text: \"low lower newest\"

# Step 1: Most frequent pair is ('l', 'o') → merge into 'lo'
# Step 2: Most frequent pair is ('lo', 'w') → merge into 'low'
# Step 3: Most frequent pair is ('e', 's') → merge into 'es'
# ... continue until desired vocabulary size
```

Here's a minimal BPE implementation:

```python
from collections import Counter

def get_pairs(word):
    \"\"\"Get all adjacent pairs in a word.\"\"\"
    return [(word[i], word[i+1]) for i in range(len(word)-1)]

def bpe_train(corpus, num_merges):
    \"\"\"Train BPE tokenizer on a corpus.\"\"\"
    # Start with character-level tokens
    vocab = {}
    for word, freq in corpus.items():
        vocab[tuple(word) + ('</w>',)] = freq
    
    merges = []
    for _ in range(num_merges):
        # Count all adjacent pairs
        pairs = Counter()
        for word, freq in vocab.items():
            for pair in get_pairs(word):
                pairs[pair] += freq
        
        if not pairs:
            break
        
        # Find most frequent pair
        best = pairs.most_common(1)[0][0]
        merges.append(best)
        
        # Merge the best pair in all words
        new_vocab = {}
        for word, freq in vocab.items():
            new_word = []
            i = 0
            while i < len(word):
                if i < len(word) - 1 and (word[i], word[i+1]) == best:
                    new_word.append(word[i] + word[i+1])
                    i += 2
                else:
                    new_word.append(word[i])
                    i += 1
            new_vocab[tuple(new_word)] = freq
        vocab = new_vocab
    
    return merges, vocab

# Example usage
corpus = {\"low\": 5, \"lower\": 2, \"newest\": 6, \"widest\": 3}
merges, vocab = bpe_train(corpus, num_merges=10)
```

GPT-2, GPT-3, GPT-4, and LLaMA all use variants of BPE. OpenAI's `tiktoken` library provides their production tokenizer.

## WordPiece

WordPiece, used by BERT, is similar to BPE but selects merges differently. Instead of raw frequency, it maximizes the **likelihood of the training data**:

```
score(pair) = freq(pair) / (freq(first) × freq(second))
```

This favors merging rare subwords that frequently appear together, creating a more balanced vocabulary.

The key visual difference: WordPiece prefixes continuation tokens with `##`:

```python
# WordPiece tokenization of \"unbelievable\"
# → [\"un\", \"##believ\", \"##able\"]

# BPE tokenization might produce:
# → [\"un\", \"believ\", \"able\"]
```

## SentencePiece

SentencePiece treats the input as a raw byte stream — no pre-tokenization or language-specific rules needed. It works for any language, including those without word boundaries.

```python
import sentencepiece as spm

# Train a SentencePiece model
spm.SentencePieceTrainer.train(
    input='training_data.txt',
    model_prefix='tokenizer',
    vocab_size=32000,
    model_type='bpe'  # or 'unigram'
)

# Load and use
sp = spm.SentencePieceProcessor()
sp.load('tokenizer.model')

tokens = sp.encode(\"Hello world!\", out_type=str)
# → ['▁Hello', '▁world', '!']
ids = sp.encode(\"Hello world!\")
# → [8774, 296, 5]
```

The `▁` character represents a space — SentencePiece encodes whitespace as part of the token, which makes detokenization lossless.

## Practical Impact of Tokenization Choices

Tokenization directly affects model behavior:

| Factor | Impact |
|--------|--------|
| **Vocabulary size** | Larger vocab = shorter sequences but more parameters in the embedding layer |
| **Subword granularity** | Fine-grained = better handling of rare words, but longer sequences |
| **Language coverage** | Multilingual tokenizers spread capacity across many languages |
| **Byte fallback** | Ensures any input can be tokenized, even unknown characters |

```python
import tiktoken

# GPT-4's tokenizer
enc = tiktoken.encoding_for_model(\"gpt-4\")

text = \"Tokenization is fundamental to LLMs\"
tokens = enc.encode(text)
print(f\"Text: {text}\")
print(f\"Tokens: {tokens}\")
print(f\"Token count: {len(tokens)}\")
print(f\"Decoded tokens: {[enc.decode([t]) for t in tokens]}\")
```

## Key Takeaways

1. **Tokenization is not trivial** — it's a learned compression of language into a fixed vocabulary
2. **BPE** builds vocabulary bottom-up by merging frequent pairs (GPT family)
3. **WordPiece** uses likelihood-based merging (BERT family)
4. **SentencePiece** is language-agnostic and operates on raw bytes (LLaMA, T5)
5. **Token count ≠ word count** — understanding this is essential for prompt engineering and context window management

## Notes

These are my working notes on different approaches to orchestrating multiple AI agents in a system. Each pattern has trade-offs in terms of complexity, latency, and reliability.

### Supervisor Pattern

A central supervisor agent coordinates specialist agents. The supervisor decides which agent to invoke based on the current task state.

**Pros:** Clear control flow, easy to debug

**Cons:** Single point of failure, supervisor becomes bottleneck

### Hierarchical Pattern

Agents are organized in a tree structure where parent agents can delegate to child agents. Each level handles increasing specificity.

**Pros:** Scalable, modular

**Cons:** Complex routing logic, potential for deep call stacks

### Pipeline Pattern

Agents are arranged in a sequential pipeline where each agent transforms the output for the next stage.

**Pros:** Simple, predictable flow

**Cons:** Rigid, no conditional branching

## Key Insight

In practice, I've found that a **hybrid approach** works best — use a supervisor for high-level routing and pipelines for well-defined sub-workflows. This balances flexibility with predictability.
